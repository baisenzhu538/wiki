# <text color="red">Andrew Ambrosino：每个人都是 builder 是个很糟糕的主意</text>
<quote-container>
**Andrew Ambrosino，***OpenAI Codex 团队负责人*
</quote-container>


**实现不再是最贵的部分了，我斗胆说一句，最贵的是品味（taste）。 **

现在公司里有个我们急需做的功能，我确信同时有 90 个不同的、没有协调过的小团队在各自实现和尝试。在那 90 个尝试里，哪些是好的？应该把哪些部分折叠到其他方面？应该怎么定义它？它应该是另一个功能的一部分吗？开关里应该有几个选项？当 90 个人都能做出看起来能上线的产品原型，真正稀缺的不再是能不能做出来，而是该不该做。

对 PRD 已死，原型当道：我实际上完全不同意这个观点。因为实现在每个媒介上都变得便宜了，跳过思考直接做原型就变得非常诱人。

尤其是如果你不是工程师，如果你从来没写过代码，你就会忍不住说，PRD 已死，让我直接给你看我想要什么。但关键是选对媒介——模糊领域的产品清晰度该写文档，想让人上手试用、压力测试一个交互模式才做原型。

过去有一种隐含的信号，一个东西看起来像什么样子，就意味着它处于流程的什么阶段。现在这些东西脱钩了。一个本来只是探索阶段的东西，看起来已经可以上线了，视觉上它已经准备好了——但它可能根本不是正确的方向。

品味的内涵：确实有审美的部分，但也有系统思维的部分，这个东西在整个系统里怎么放；有方向性的部分，我们要去哪、这件事是哪个主题的一部分；有表达的部分，怎么呈现这个信息；还有一部分品味是交互层面的，这个动画不符合它要传达的语义，它太急促了。

<text color="red">**真正的品味问题是，如果我们什么都能做，目标是什么？怎么到达那里？**</text>

设计比软件更难评分，创建一个反馈循环来训练模型什么是好设计，比训练代码能不能编译要繁琐得多，因为人的品味是反馈机制的一部分。设计中新颖性的重要程度，远高于软件工程。软件工程你希望模型完全按已知模式来，但设计需要一定的随机性和新颖性。

招人标准：在一个拥有无限 tokens 的世界里，我们不能生产垃圾内容。你必须具备从海量内容中分辨信号与噪音的能力。每次有人问 Codex 团队有多少人，我的回答都是：大概在 10 到几千人之间。团队有两位数规模的工程师，设计师数量大约是工程师的一半，再加上几位产品经理，绝大多数人都是 IC。

**角色融合：定义一个人，不再是看设计到哪里结束、工程从哪里开始这样的职责边界，而是看他所有工作内容的平均分布。**产品经理的工作更像 区域防守，哪里存在空缺，哪里还没人覆盖。不是每个人都能做所有事，不论是从广度还是深度来说，这也是为什么管理者不会消失。

我非常确定，我们 2 月发布的那个 Codex 应用，如果在 11 月准备好了就发布，它会在市场上彻底失败。唯一的区别就是 11 月到 2 月之间模型进步了。同一个产品，完全相同的形态，结果完全不同，就差了几个月。因为一个功能最终是否足够好，前提往往不是功能本身的形态，而是模型到底够不够聪明。

不要轻易认定这个东西现在不行，所以它就是个坏功能，它可能只是还没到时候。你可能需要把同一个东西发布六次，直到它成功，形态可能完全不变。

**你不能指望同一个团队既持续产出颠覆性的创新，又始终专注于产品质量和细节打磨。**在某个阶段，你必须设计出一种机制，让这两种能力能够同时存在。就像 Codex 应用曾以某种方式颠覆 ChatGPT 一样，Codex 自己未来也可能被新的尝试所颠覆。

代码评价标准已经变了：用去年的标准来看，我们现在 100% 的代码都是 AI 写的。所以问题不再是多少是 AI 写的，而是代码是在监督下写的还是无监督写的。**但目前所有模型都有一个问题，它们总是在增加复杂度。**拜托，让模型学会删代码吧。当你尝试把开发完全交给自动驾驶的时候，这就成了一个严重的问题，不管是在人的层面还是在代码库的层面。

每个人都是 builder 是个很糟糕的主意。产品管理这个已经积累了真正最佳实践、真正踩过坑的学科，被直接抛弃了。因为有人写了几行代码，就觉得万事大吉了，那可不是个好状态。

这其实是我第一次觉得自己没在失败。我之前创业做了很多年，最后基本上是把公司拆了卖掉的。在到达现在这个位置之前，我失败了大概 10 到 15 年。

**不要和你现在的工作流程绑定终身。真正应该坚持的，是那些只有你能够独特交付的成果。**
**找到值得做的事，然后想办法去做那些事。**

# <text color="red">Ethan Mollick / OpenAI / Anthropic / Satya Nadella：AI 的基本单位从回答变成</text><text color="red">*工作流*</text><text color="red"> </text>
<quote-container>
- Ethan Mollick（宾夕法尼亚大学沃顿商学院教授，《Co-Intelligence》作者）
- OpenAI 官方《How agents are transforming work》
- Anthropic 对 40 万个 Claude Code 会话的分析
- Satya Nadella（微软 CEO） 

</quote-container>

****Ethan Mollick：工作正在转向“把工作分配给智能体，而不是继续围绕聊天机器人协作” 。****
co-intelligence 模式（人提一步、AI 返回一步、人再提下一步）不再是高价值 AI 工作的主要形态。

agent 模式下，智能体不只回答问题，还拥有工具、环境、文件、代码库、浏览器、测试系统、权限和运行时间，可以在数分钟、数小时甚至更长时间里独立推进任务。

AI 使用方式，从非专家用聊天机器人弥补知识缺口，转向专家使用智能体完成工作 。

专家的瓶颈从时间、体力、协作成本和技术实现能力，转向任务定义、上下文质量、判断标准和反馈能力。

第一阶段是人人都能问 AI，第二阶段不是人人都能管理 AI，而是懂业务、懂问题、懂标准的人能把 AI 变成执行团队。

****OpenAI：agentic AI 改变了知识工作的单位，从单次交互变成可委派的长周期任务。 ****
Codex 最初是面向编程的工具，但到 2026 年 6 月，OpenAI 内部每个部门都把它用作主要 AI 工作工具，工程部门先转移，法律、财务、招聘等非技术部门随后。到 2026 年 5 月，80.6% 抽样个人用户至少向 Codex 提交过一次相当于人类 30 分钟以上工作的请求；70.2% 提交过一小时以上任务；25.6% 提交过八小时以上任务。

到 6 月，最重度日活用户每天生成超过 60 小时的 Codex agent turns，分布在多个并行 agent 上。

Codex 已占到 OpenAI 内部每周输出 token 的 99.8%，平均员工超过 85% 的输出 token 来自 Codex 而不是 ChatGPT。

agent 时代看一个任务能被委派多久、一个人能并行管理多少 agent、agent 输出进入了多少真实流程 。

AI 的生产力不再只体现在一个回答更好，而在一个人能同时运行多少段可交付工作。 

****Anthropic 对 40 万个 Claude Code 会话的分析：人决定要建造什么，智能体决定如何建造。 ****
用户做出约 70% 的规划决策，Claude 做出约 80% 的执行决策——用户决定目标、方向、完成标准，Claude 决定修改哪些文件、运行哪些命令、怎样实现。

非程序员可以借助 coding agent 完成技术任务，法律、财务、招聘、运营等岗位开始能做自动化、数据处理、工具搭建。**但成功率不取决于用户是不是程序员，而取决于用户是否理解自己要解决的问题——软件工程师在 coding 任务上的成功率与其他主要职业接近，真正影响效果的是领域经验。AI 降低的是实现门槛，不是判断门槛。 **

<text color="red">**过去的技术鸿沟在代码能力。新的技术鸿沟在问题理解。 **</text>

****Satya Nadella：AI 不是一个技术项目，而是公司的未来形态****
公司要重新理解自己的资本结构——过去有人力资本和数字资产，现在加入第三个概念：token capital。

token capital 是公司如何把自己的知识、流程、反馈、判断和工作轨迹转化成可被模型使用、可复利、可控制的智能资产。 

公司是否知道自己的 AI 供应链是什么，是否知道哪些知识被模型吸收，是否拥有自己的工作轨迹和评估标准，是否让模型在自己控制的环境里学习。

不是所有任务都需要最强模型，重复性、确定性、流程清晰的任务可能更适合小模型、专用模型、规则系统和 agentic workflow。真正稀缺的是知道什么任务需要前沿模型，什么任务只需要稳定、便宜、可验证的执行系统。

每家公司都需要自己的 private eval——公开 benchmark 能衡量通用能力，但不能衡量一家公司的具体工作。

企业真正应该积累的，不只是数据，而是人如何下达任务、agent 如何尝试执行、专家如何纠正结果、评估如何判断成败、下一次系统如何改进。

# <text color="red">Addy Osmani：Build the loop, stay the engineer </text>
<quote-container>
**Addy Osmani，***Google Cloud AI 总监、工程师*
（文中还引用了 OpenClaw 开发者 Peter Steinberger、Anthropic Claude Code 负责人 Boris Cherny 的观点）
</quote-container>


- Loop Engineering循环工程，核心是用你设计的系统来替代你自己去 prompt agent 。
- Peter Steinberger：你不应该再去手动提示编码智能体了。你应该设计让智能体自动运行的 loop。
- Boris Cherny：我不再手动提示 Claude 了。我有 loop 在跑，它们负责提示 Claude、决定下一步做什么。我的工作是写 loop。 

<text color="red">**一个完整 loop 需要五个模块加一个记忆：**</text>
- Automations（自动触发与分类）
- Worktrees（让并行 agent 互不干扰）
- Skills
- Plugins 和 Connectors（接入真实工具）
- Sub-agents（生成者与检查者分开），外加 memory。
**智能体会忘，但代码仓库不会。**

sub-agent 为什么要拆开：让写代码的模型来评审自己的代码，它会对自己太好说话。 决定 loop 有没有完成的，应该是一个全新的模型，而不是那个做了这些工作的模型。

<text color="red">**三个重要问题：**</text>
- 验证仍是人的责任（一个无人值守运行的 loop，同时也是一个无人值守犯错的 loop ）
- 对代码库的理解会腐烂
- 最舒服的姿势最危险

一个人用它在自己深刻理解的工作上跑得更快；另一个人用它来逃避理解工作本身。
Loop 不知道这两者的区别，但你知道。 设计 loop 比提示词工程更难，不是更容易。

# <text color="red">Pete Koomen：真正的 AI-Native 是把 AI 作为组织运转的建设层</text>
<quote-container>
**Pete Koomen，***YC 合伙人、Optimizely 创始人*
</quote-container>


真正的 AI-Native 组织和把 AI 当 Copilot 用的组织有本质差异。

Copilot 是 2023–2024 年的做法，AI 辅助你完成具体任务，流程、决策、知识沉淀仍然在人的头脑里。

真正的 AI-Native 做法是把 AI 作为整个组织运转的建设层（building layer），并且系统性地记录所有 artifacts。

- **杰文斯悖论：**成本下降带来的不是需求减少，而是需求爆发。 当 SQL 查询门槛降到零，人们开始提出以前根本不敢提的问题 。
- **透明：**所有 Agent 对话对 YC 全职员工可见。
- **两个文化前提：**Trust by default（默认信任）和 Egalitarian（平等主义）。AI 能力必须向每个人开放，所有 Agent 对话默认对全员可见。这与大多数 command and control 式的企业是相反的。

- **Gmail 的 AI 写邮件功能是反例：**AI 的 prompt context 和工作逻辑被开发者锁死在后台，用户无法访问、修改、自定义。

最好的 AI 软件往往是最小的，只在模型能力之上加最少量的预写代码，让模型做最多的工作。

Gary：你基本上在活在 2028 年。现在花 100K做的事，两年后只要100*K*做的事，两年后只要10K。所以现在有一个一次性的时间跳跃窗口，你可以跳过所有现存的巨头。

# <text color="red">OpenAI 官方：把 Codex 当成需要持续配置和改进的队友</text>
<quote-container>
OpenAI 官方发布的 Codex 使用最佳实践指南（developers.openai.com/codex），这是 OpenAI 对 Codex 工程化使用方法的官方表述。
</quote-container>


**把Codex当成需要持续配置和改进的队友，而不是一次性的助手。 **

<text color="red">**提示词四要素结构：**</text>
- 目标，也就是你想改变或构建什么；
- 上下文，哪些文件、文档、示例或报错信息与当前任务相关；
- 约束条件，Codex需要遵循哪些标准、架构要求或规范；
- 完成标志，任务结束的判断依据是什么。 

即使提示词不完美，也能给出不错的结果。但如果你在大型或复杂代码库里工作，给它足够的任务上下文，是解锁更好效果的关键。 

- **复杂任务先规划再动手 ，三种方式：**Plan 模式（让 Codex 先收集上下文、提出澄清问题）、让 Codex 反向采访你（挑战你的假设，把模糊的想法变成具体的需求 ）、PLANS.md 模板。
- **AGENTS.md 是面向AI Agent的README文件 ，简洁原则：**一个简短准确的AGENTS.md，比一个充满模糊规则的长文件更有用。 反复犯同一个错误时，让它做复盘，然后更新AGENTS.md 。
- **让 Codex 自查：**为改动编写或更新测试、运行相应的测试套件、检查Lint、格式化或类型检查、确认最终行为符合需求、审查diff是否存在Bug、回归或风险模式。
- **数据点：**OpenAI内部100%的PR都经过Codex审查。 
- **技能与自动化的区分：**技能定义方法，自动化定义时间表。如果一个工作流还需要大量人工引导，先把它做成技能，等它变得可预测了，自动化才能真正发挥放大效果。 
- **会话管理：**每个连贯的工作单元保持一个线程。如果工作还是同一个问题的延续，待在同一个线程里通常更好，因为它保留了推理轨迹。只有当工作真正分叉时才fork。
- **常见错误：**把持久性规则堆进提示词里，而不是放进AGENTS.md或技能 像监工一样盯着Codex一步步执行，而不是让它并行工作 用一个线程对应一个项目而不是一个线程对应一个任务，导致上下文膨胀 。
- **把Codex用好，本质上是一套工程化的习惯养成过程：**上下文给够，规范写进文件，重复的事情变成工具，稳定的工具交给自动化。

****Jack Dorsey：从层级到智能****
两千年的组织创新都是信息路由协议，围绕一个人类局限构建：一个领导者能有效管理 3 到 8 人。 加层级就变慢，这是罗马军队、普鲁士总参谋部、铁路公司组织图、矩阵组织都在试图躲避的权衡。

<text color="red">**Block 的核心论点：**</text>
我们在质疑一个底层假设：组织必须以人为协调机制进行层级化组织。我们打算替代层级所做的事。 大多数公司给每个人一个 copilot，我们追求不同的东西：一家作为智能体（或迷你 AGI）来构建的公司——AI 就是那个技术。

第一次，一个系统能维持一个持续更新的整个业务模型，用它来协调工作，而这以前需要人通过管理层层传递信息。

- **双重世界模型：**公司世界模型（所有行为产生 artifacts——决策、讨论、代码、设计、计划）和客户世界模型。
- **人的角色翻转**：智能在系统里，人在边缘。 ——边缘是智能与现实接触的地方。
- **三种角色取代传统层级：**IC（深度专家）、DRI（直接负责人，拥有跨领域问题的完整权限）、Player-coach（既构建又培养人，替代传统管理者）。

问题从来不是你是否需要层级。问题是人类是否是这些层级所做之事的唯一选择——不再是了。

****闲庭落木：开放问题由人驱动，封闭问题由 AI 驱动****
AI 的价值不在提效，因为 AI 的边际成本不递减，提效带来的收益不递增，结合在一起不是门好生意。

AI 真正的价值应该在于变不可能为可能，只有让我做到我之前做不到的事情，我才可能付费。 

组织 AI 提效的方向：不在于给员工提供 AI 工具提升已有工作的效率，而在于重新划分工作：识别出现在工作中适合 AI 完全能搞定（至少能搞定 90%+）的子工作项，构建 Agent 来全自动化搞定。 

作者一度十分认可 Jack Dorsey 的 AI 中心主义思路（AI 驱动事 ，人作为边缘节点），但在实践中发现异常 case：AI 能把结果完成，但结果不是想要的。例如代码功能都实现了，但架构抽象不对，因为脑子里面隐隐约约有幅关于未来的画面，没有用语言描述过 。很多好的idea都是这样，电光火石间突然就出现了。产生好的idea的能力，我确信 AI 是不具备的，因为语言无法描述。

由此区分两类问题：封闭问题 （如线上 bug，解决问题本身就是全部）和开放问题 （如我想利用 AI 给组织提效 N 倍 ，无法直接回答，需要好的 idea）。

**针对封闭问题，可以由AI 驱动事，人仅作为 AI 与现实交互的工具，即智能体的边缘节点。**
**对于开放问题来说，必须由人驱动事，AI 反过来作为人的工具。 **

<text color="red">**AI-Native 组织两种形态：**</text>
- AI 控制台 ：针对开放问题，核心是保护探索者的心流（Flow） ，AI 是超级副驾，人停留在 idea 的高维空间。
- Agent 平台 ：针对封闭问题，核心是工业化 ，AI 变成调度中心，遇到物理或权限障碍时将人类作为边缘节点 呼叫进来。

不同组织开放问题与封闭问题占比不同，而且肯定不是所谓的一人公司（OPC/OPT）的样子 。
