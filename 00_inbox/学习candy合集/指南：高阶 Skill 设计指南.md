# 20. 审美：高阶 Skill 设计指南

> **导语**：本文档是基于 Anthropic 官方旗舰 Skill（如 `skill-creator`, `doc-coauthoring`, `canvas-design` 等 21-29 号前沿案例）深度拆解而成的**高级设计教程**。
>
> 当你跨越了“提示词工程”的新手期，开始思考如何为 AI 编写具备“系统级确定性”的**专业入职手册**时，本文将为你提供顶级的架构范式、模块标准与微操提示。

## 第一部分：高阶设计原则与底层原理

构建一个优秀的 Skill，本质上是在做一次“产品原型设计”，你需要平衡机器的智能与人类的控制欲。以下是驱动所有高级 Skill 的三大底层哲学：

### 核心原则一：节制的美学 (Concise is Key / Token Economy)
**原理**：上下文窗口（Context Window）是极其宝贵的公共资源。
**必知必会**：
- **拒绝系统冗余**：AI 在日常对话中已经具有很高的常识。不需要在 Skill 里解释“什么是 PPT”或“什么是 Markdown”，只需告诉它“在这个具体的公司场景下，这东西应该长什么样”。
- **坚守 500 行护栏**：主控文件 `SKILL.md` 的正文尽量控制在数百行以内。如果有长篇累牍的业务黑名单、设计理念、模板源码——大胆把它们切分出去，存放入 `references/` 里按需借调。
- **无情感输出**：全篇必须使用祈使句（命令句式）。抛弃“我认为最好是……”或“为了让你表现得更好”，直接写“Create the file...”, “Validate the output...”。

### 核心原则二：自由度匹配理论 (Degrees of Freedom)
**原理**：这是高级 Skill 开发的“阿克琉斯之踵”。你必须评估当前任务是“悬崖上的窄桥”（高度易错，必须强行护栏）还是“开阔的平原”（创意发散，可以自由探索）。
**必知必会**：
- **高自由度（文字引导）**：写文案、创设哲学、头脑风暴。你只需要提供灵感锚点和方向。
- **中自由度（模板与占位符）**：生成报告、输出表格。你需要提供 `template.md`，并严格命令其使用 `str_replace` 定点填充。
- **极低自由度（外挂脚本工具链）**：精确的旋转 PDF、打包编译 HTML。不要让 AI 猜，直接丢给 `scripts/` 下带参数的 Python 脚本。

### 核心原则三：前置认知与解耦思维 (Cognitive Grounding)
**原理**：通用 AI 对你的团队内幕一无所知，这被称为“作者诅咒（Curse of Knowledge）”。
**必知必会**：
- **不要直接动手**：任何重度协作的 Skill（例如写需求文档），绝对不要让 AI 拿到一两句话就干活。必须强制要求它先经历“信息倾倒与背景收集”阶段。



## 第二部分：架构范式大全 (Architecture Paradigms)

通过对官方 300+ 核心技能库的深度审计，我们将高阶 Skill 的行为逻辑归纳为**六种核心范式**。为了帮助你选择最合适的架构，我们将它们按**从简单到复杂**的维度进行了重新洗牌：

### 范式一：分拣路由模式 (The Navigator / Routing & Lookup)
> **复杂度**：★☆☆☆☆ | **代表案例**：`21. internal-comms`, `28. brand-guidelines`

- **核心逻辑**：AI 扮演分拣员。识别意图 → 奔向特定子文档 → 搬运规范。
- **架构特征**：
  - 拥有庞大的 `references/` 或 `examples/` 目录。
  - `SKILL.md` 极短，仅包含“意图分发规则”。
- **适用场景**：多格式报告、多品牌视觉规范、企业政策查询。

### 范式二：黑盒工具链模式 (The Operator / Toolchain Wrapper)
> **复杂度**：★★☆☆☆ | **代表案例**：`24. slack-gif-creator`, `25. pptx`, `xlsx`

- **核心逻辑**：AI 扮演操作员。将模糊语言翻译为精确参数 → 丢给底层脚本执行。
- **架构特征**：
  - 核心逻辑锁死在 `scripts/`（Python/Node）中。
  - Skill 主要负责“命令行参数映射”与“前置参数校验”。
- **适用场景**：文件格式转换、像素级图形生成、自动化打包发布。

### 范式三：协同共创模式 (The Partner / Interactive Workflow)
> **复杂度**：★★★☆☆ | **代表案例**：`22. doc-coauthoring`

- **核心逻辑**：AI 扮演合伙人。强制中断 AI 的自动生成逻辑，引入“人类确认”闭环。
- **架构特征**：
  - 无代码，纯文本指令。
  - 严格定义“阶段性退出条件（Exit Criteria）”。
  - 常用“发散-收敛”循环（先列 20 个 Ideas，再让用户选 3 个）。
- **适用场景**：深度文案创作、战略规划、复杂商业提案。

### 范式四：双步创构模式 (The Philosopher / Souls & Bodies)
> **复杂度**：★★★★☆ | **代表案例**：`27. canvas-design`, `29. algorithmic-art`

- **核心逻辑**：AI 扮演哲学家。先推导抽象哲学（Soul），再映射为具象表达（Body）。
- **架构特征**：
  - 强制分两个对话轮次或两个独立文件段落。
  - 第一步输出的美学宣言（Manifesto）是第二步渲染的唯一合法依据。
- **适用场景**：顶奢前端设计、生成艺术、高审美海报。

### 范式五：侦察与行动模式 (The Scout / Recon-Then-Act)
> **复杂度**：★★★★☆ | **代表案例**：`webapp-testing`

- **核心逻辑**：AI 扮演侦察兵。观察环境 → 获取反馈 → 动态调整计划 → 最终执行。
- **架构特征**：
  - 引入“决策树（Decision Tree）”逻辑图。
  - 包含大量“Reconnaissance（侦察）”动作，如截图、读取 DOM、探测 API 状态。
- **适用场景**：网页抓取测试、动态 UI 自动化、实时环境调试。

### 范式六：元工程化架构模式 (The Architect / Meta-Engineering)
> **复杂度**：★★★★★ | **代表案例**：`20. skill-creator`, `mcp-builder`

- **核心逻辑**：AI 扮演总建筑师。指导、构建、测试并验证另一个复杂的软件系统。
- **架构特征**：
  - **递归性**：Skill 往往配备了 `init`（自动 scaffolding）和 `validate`（自动化质检）脚本。
  - **多阶段演进**：通常包含 Phase 1 (Research) 到 Phase 4 (Evaluation) 的漫长链路。
  - **闭环验证**：内含自动化 Evaluation 机制。
- **适用场景**：开发 MCP 服务端、自动化构建 Skill、大型应用开发框架。

### 范式七：API 联动代理模式 (The Agent Orchestrator / SDK Integration)
> **复杂度**：★★★★★ | **代表案例**：`Agent SDK`, `Console Skills`

- **核心逻辑**：AI 扮演调度中枢。通过 SDK 或 API 动态挂载、卸载 Skill，并在高度受控的环境中执行。
- **架构特征**：
  - **高度程序化**：不依赖手动上传，而是通过代码逻辑（如 `container.skills` 参数）驱动。
  - **环境隔离**：运行在受保护的 Sandbox（如 Code Execution Tool）中。
  - **可观测性驱动**：所有的日志与 Trace 均接入工业级监控系统。
- **适用场景**：大规模生产级 AI 代理集群、自动化 CI/CD 流水线。

## 第四部分：执行微操极致清单 (Execution Constitution)

这是基于官方 300+ 顶级 Skill 审计出的“开发者宪法”。我们将微操分为 **To-Do** (必须做的标准动作) 与 **Not To-Do** (严禁踩坑的红线区)，并按**重要性与使用频率从高到低 (P0 -> P3)** 进行了严格排序。

### ✅ To-Do List: 顶级 Skill 的 10 条必修课

| 优先级 | 动作项 (Module/Action) | 核心逻辑与微操 | 官方实例参考 |
| :--- | :--- | :--- | :--- |
| **P0-1** | **YAML 描述 SEO 强化** | **决定了你是否被点将。** 必须包含：[工具名] + [三个触发场景短语] + [产出物属性定义]。 | `docx`, `skill-creator` |
| **P0-2** | **外科手术式编辑指令** | **保住上下文的命根子。** 强制 AI 仅使用 `str_replace` 或 `multi_replace` 进行增量修改，严禁全量重写。 | `doc-coauthoring` |
| **P0-3** | **建立“初始对话协议”** | **建立心理契约。** 在任务开始前，输出明确的流程草案描述，并强制停顿询问“是否现在开始？”。 | `mcp-builder` |
| **P1-4** | **引用库离线化 (500行)** | **保持固件清洁。** 将巨量的 API 规格、黑名单、样板模板移出主文件，存放入 `references/` 按需读取。 | `internal-comms` |
| **P1-5** | **分阶段退出条件 (Exit)** | **质量关口的哨兵。** 为每个 Phase 结尾设计具体的成功标志（如：必须获得大纲的显式授权）。 | `doc-coauthoring` |
| **P1-6** | **侦察优先 (Recon Scout)** | **拒绝盲目。** 操作前必须先 `Take Screenshot`、`Inspect DOM` 或 `Unpack`。将“所见”结果贴入 `<thought>`。 | `webapp-testing` |
| **P2-7** | **黑盒执行协议 (No Source)** | **节省认知负荷。** 告知工具用法 (`--help`) 即可，命令 AI 严禁阅读底层 Python/Node 脚本的实现源码。 | `pptx`, `xlsx` |
| **P2-8** | ** Few-shot 审美锚点** | **设定视觉/排版上限。** 在 `examples/` 中提供一个接近满分的“样板房”，让 AI 搬运其结构。 | `brand-guidelines` |
| **P2-9** | **自动化校验闭环** | **物理真实的守门人。** 在最终交付前，必须运行 `validate.py` 脚本，并根据报错递归修正。 | `docx`, `skill-creator` |
| **P2-10** | **Grep 精准提取精简** | **万字文档克星。** 对于超大 reference 文件，在主文档中提供特定 grep 搜索词典，禁止 AI 全量读取。 | `internal-comms`, `official` |
| **P3-11** | **递归“读者”验证** | **消除作者诅咒。** 模拟一个无记忆的新实例来“阅读”产出物，如果对方有疑惑，主进程自动回滚修改。 | `doc-coauthoring` |

### ❌ Not To-Do List: 严禁踩坑的 10 条红线

| 优先级 | 禁忌项 (Taboo) | 核心原因与后果 | 避坑技巧 |
| :--- | :--- | :--- | :--- |
| **P0-1** | **严禁创建 README.md** | **无效噪音。** 官方 Skill 库是给机器读的“驱动”，不需要给人类客套。 | 所有的文档必须服务于 AI 的执行逻辑。 |
| **P0-2** | **严禁对话式废话/独白** | **浪费能量。** 禁止 AI 解释“我准备怎么做”。正文只能包含：规则、指令、代码。 | 强制要求 AI 直接输出 `<thought>` 后的执行动作。 |
| **P0-3** | **严禁猜测环境状态** | **鲁棒性杀手。** 严禁猜测路径、猜测 ID、猜测网页状态。没侦察过的东西一律视为“不存在”。 | 没看到截图/没读过文件，一律禁止动手。 |
| **P1-4** | **严禁使用模糊形容词** | **审美偏差。** 严禁使用“Beautiful”, “Good”。AI 每个人的美学标准不同。 | 改用具体参数 (12pt) 或对比标杆 (Like ex01)。 |
| **P1-5** | **严禁硬编码巨量数据** | **主文件膨胀。** 禁止在 `SKILL.md` 里手写 50 个 API 接口或几百个配置项。 | 将其作为独立的资产文件 (JSON/CSV) 借调。 |
| **P1-6** | **严禁单次全量重印文档** | **回声灾难。** 在处理万字长文或代码库时，全量重印会导致严重的 Token 熔断。 | 强制使用 `str_replace` 局部补丁模式。 |
| **P2-7** | **严禁使用非标准字符** | **技术兼容性。** 在文档生成中严禁使用特殊 Bullet。 | 强制规定：`Use XML entities (&#x201C;)` 处理符号。 |
| **P2-8** | **严禁无反馈的一股脑生成** | **方向性毁灭。** 不要在未确认 Phase 1 阶段认知偏差时，就输出 Phase 3 的大段内容。 | 必须在每个关键决策点设置“人类中断器”。 |
| **P2-9** | **严禁擅自修改核心脚本** | **确定性丧失。** AI 容易弄坏原本稳健的底层工具。 | 将脚本标记为“Read-only / Execution only”。 |
| **P3-10** | **严禁单人独舞式生成** | **盲区风险。** 避免 AI 陷入单一逻辑死循环。 | 引入“第二人称审计”角色在 Prompt 中进行博弈。 |

## 第五部分：如何判断 Skill 的水准 (量化评价体系)

一个真正“高阶”的 Skill 不应只停留于“能用”，而应追求算力经济、Token 效率与极高的触发稳定性。以下是衡量一个 Skill 实战水准的四大核心量化维度：

### 1. 任务完成效率 (Tool Call Efficiency)
- **定义**：完成同一个复杂任务（如生成一份 PPT）所需的平均“工具调用/消息往返”次数。
- **水准线**：高阶 Skill 应通过清晰的工作流编排与“侦察并行”，将往返次数减少 30% 以上。
- **金标准**：无多余的澄清询问，API 调用路径最短化。

### 2. Token 节省率 (Token Economy)
- **定义**：单位产出所消耗的背景 Token 数。
- **水准线**：通过“500行原则”和“外科手术式编辑指令”，高阶 Skill 的 Token 消耗应远低于直接在对话中重复粘贴 Prompt。
- **金标准**：严禁全量重写长文档，只传输差异补丁（Diffs）。

### 3. 触发准确率 (Trigger Accuracy - 90% 原则)
- **定义**：在 10-20 个相关多元查询中，技能自动加载并激活的成功率。
- **水准线**：触发率应高于 **90%**。如果用户需要显式通过目录点击或反复提及特定词汇才能唤醒，则该 Skill 的 YAML SEO 宣告失败。
- **金标准**：改述请求（Paraphrased requests）仍能精准触发。

### 4. 无修改采纳率 (ZSAR - Zero-Shot Acceptance Rate)
- **定义**：AI 产出的结果在不做任何人工修正的情况下，直接通过审核并落地的概率。这是衡量 Skill 针对性(Specificity)的终极 KPI。
- **水准线**：高阶实战任务 ZSAR 应达到 **85%**。
- **金标准**：支持“靶向迭代”，即针对 15% 的错误进行精准的 Prompt Patch，而非整体重刷。

### 5. 自治治理等级 (C/B/A/S Autonomy Levels)
- **定义**：该 Skill 在组织内推行的深度。
- **分级维度**：
    - **C级 (Co-Pilot)**：主要提供参考，必须人类每步确认。
    - **B级 (Reviewer)**：AI 生成全稿，人类进行修正性审计。
    - **A级 (Autonomous)**：在标准环境下自动执行，人类仅做日志抽检。
    - **S级 (Supervised Self-Evolve)**：具备自回归测试与自动优化的闭环技能。

## 结语：从“写 Prompt”到“写固件”的质变

最高级的 Skill 设计不是在写文字，而是在**设计一个稳定的控制系统**。当你能够熟练运用这六大范式，并严守这四层模块架构与 20 条执行红线时，你所交付的将不再是一个简单的 AI 助手，而是一个**能够 24/7 稳健运行的数字专家**。
