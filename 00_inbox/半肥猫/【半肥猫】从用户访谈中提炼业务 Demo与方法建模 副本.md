# 半肥猫从访谈中提炼业务 Demo与方法建模

## 一个脱敏后的真实起点

**阅读到文章后面，有《Demo 五步建模法》，可参考复用。**

这次项目的起点，是半肥猫以商业策划顾问身份，对一位创业多年的创业者进行商业模式和 IP 定位的梳理访谈。访谈的目的不是简单记录经历，也不是马上设计一套宣传方案，而是先判断：这个人真正能够为客户解决什么问题，过去哪些经历已经证明了这种能力，以及它能不能被进一步做成清晰的业务 Demo。为了保护隐私，下面不出现真实姓名、行业名称、平台名称和具体金额，只保留与方法有关的部分。



他并不是一个刚开始创业、什么都没有的人。相反，他经历过多个项目，也积累了产品资源、合作资源、渠道关系和一套自己的判断方法。他能够看出很多机会：有的可以做品牌，有的可以接渠道，有的可以发展平台，有的还可以叠加数字化工具。每一个方向单独拿出来，都有成立的可能。



但问题也正是从这里开始的。方向太多，资源太散，任何一个方向都需要不同的合作方和执行团队。如果一开始就试图把所有资源整合成一个“大项目”，就会遇到三个困难：第一，客户听不懂你到底先解决什么；第二，团队不知道第一步该做什么；第三，投入很大，但很长时间都无法判断哪一个环节真正产生了价值。



这不是能力不足，而是典型的“资源过剩、模型不足”。一个人手里有很多牌，却没有先决定这一局究竟要打哪一张。访谈前，如果只问“你还能提供哪些资源”，只会让这副牌变得更厚；真正要问的是：过去哪一次已经证明你能把一个混乱项目向前推进？当时客户卡在哪里？你做了哪个关键判断？那个判断能不能被重新展示和验证？

沿着这条线追问后，原本很大的项目叙事开始收缩成一个更具体的场景：面对一个有产品、有想法、但讲不清价值和启动顺序的早期项目，帮助它完成定位梳理、核心表达和第一步行动设计。这个场景不等于完整产品，却可以在一次演示中让人看见“混乱如何变清晰”，也可以进一步验证客户是否愿意提供资料、投入时间并继续合作。

所以，这次访谈的重点不是再扩充资源清单，而是从一个真实人物的经历中，找到一个可控、可展示、可验证的业务切口。这也是我后来提炼 Demo 方法的起点。

## 一句话结论

Demo 不是把一个完整产品简单做小，也不是把所有功能做成一个漂亮的展示页面。它应该是从真实访谈中找到一个“客户确实在意、我们确实能解决、结果可以被看见”的最小业务闭环。

## 一、先问发生了什么，不要先问想做什么

很多项目一开始就讨论功能、平台和宏大愿景，最后做出来的 Demo 虽然完整，却没有人真正关心。更有效的访谈顺序是：

> 真实场景 → 具体卡点 → 已付出的代价 → 过去尝试 → 关键转折 → 最小改善
> 
> 

不要只问“你需要什么功能”，而要追问：事情发生在什么场景？谁遇到了问题？当时做了什么？哪里最费时间、最容易出错或最影响结果？如果这个问题解决，最先发生的变化是什么？

在这个案例里，访谈并没有停留在“你能提供哪些资源”，而是继续追问过去真正做成过什么、客户当时卡在哪里、哪一个判断让项目向前走了一步。这样做的目的，是把“能力介绍”转换成“问题—判断—动作—结果”的证据链。

## 二、从故事里识别 Demo 机会

一个值得做 Demo 的问题，通常同时满足四个条件：

1. 问题真实发生过，而不是访谈对象的想象；

2. 问题有明确损失，例如时间浪费、线索流失、沟通反复或决策变慢；

3. 解决过程可以被拆成几个清晰动作；

4. 结果能够在较短时间内被观察或判断。

如果一个需求需要先改变整个组织、接入大量数据、等待很长周期才能看到结果，它更像长期项目，不适合做第一版 Demo。

## 三、把复杂方案压缩成一个最小闭环

可以用下面这条链路收敛：

> 一个具体对象 \+ 一个高频问题 \+ 一条处理路径 \+ 一个可见结果
> 
> 

例如，不要展示“完整的智能经营系统”，而是展示：输入一份真实业务资料，经过一次分析、整理或生成，输出一份客户能直接使用的结果，并说明它节省了什么、改善了什么、下一步如何验证。

Demo 至少要讲清楚四件事：

- 输入是什么；

- 中间做了什么判断或处理；

- 最终输出是什么；

- 用什么标准判断它有价值。

这一步可以称为“业务建模”。它不是先画系统架构，而是先建立一张最小关系图：

> 客户对象 → 关键问题 → 解决动作 → 交付结果 → 验证指标
> 
> 

只要其中一个环节无法说明，Demo 就容易退化成概念展示。只有当这五个节点能够连起来，复杂的资源、产品和技术才有机会被压缩成一个别人看得懂的业务样板。

## 四、Demo 的展示顺序

一场有效的 Demo，不应从技术架构开始，而应按照客户的理解顺序展开：

1. 先还原客户熟悉的真实问题；

2. 展示原来的处理方式为什么慢、散或不稳定；

3. 现场演示新的处理路径；

4. 对比输出结果和节省的成本；

5. 说明它目前能解决什么、暂时不能解决什么；

6. 给出下一步小范围验证方案。

客户真正想看的不是“系统有多少功能”，而是“这件事能不能在我的业务里跑起来”。

## 五、用 Demo 验证，而不是用 Demo 证明自己

Demo 的目的不是证明方案已经完美，也不是承诺最终结果，而是验证三个假设：

- 客户是否真的在意这个问题；

- 处理路径是否比原来更有效；

- 客户是否愿意投入资料、时间或预算继续验证。

因此，第一版 Demo 应保留人工判断和质量检查，不必追求全自动。先把一个场景跑通，再根据反馈决定是否扩展到更多客户、更多数据和更多功能。

## 六、最后得到的建模方法

从这次访谈可以抽象出一个“**Demo 五步建模法**”。下面用一个脱敏示范说明：某客户拥有产品、合作资源和渠道想法，但迟迟没有形成一个可以启动的业务方案。

### 第一步：找事实

**怎么做：**不问“你未来想做多大”，先问“过去哪一次真的发生过”。追问时间、人物、场景、动作和结果。

**示范：**客户曾经帮助一个早期项目重新梳理定位，并促成对方进入一个新的合作渠道。这说明客户不是只有资源，而是具备“重新组织项目并推动落地”的能力。

**评价标准：**至少有一个真实项目、一个明确对象、一个具体动作和一个可以核对的结果。

**反例：**“我认识很多渠道，未来可以帮助更多企业增长。”这只是能力宣言，没有事实证据，不能直接拿来做 Demo。

### 第二步：找矛盾

**怎么做：**把客户说出的表面需求，继续追问到真正卡点：为什么有产品却启动不了？为什么有资源却无法成交？为什么方案讲了很多却没人行动？

**示范：**表面需求是“希望做一个大平台”，实际矛盾可能是“项目缺少清晰定位，客户不知道先买什么、先看什么、为什么现在行动”。

**评价标准：**问题必须能对应一个损失，例如线索流失、反复沟通、投入无法回收或团队无法执行；不能只是“效率不高”“体验不好”这类空话。

**反例：**把“需要更多曝光”直接当成问题。曝光只是结果愿望，还没有说明谁需要什么、哪里断了、为什么现有方式无效。

### 第三步：找切口

**怎么做：**在多个方向中，优先选一个资料容易取得、动作可以控制、结果能够快速看见的场景。

**示范：**第一版不做完整平台，也不同时展示所有资源，而是选择“把一份混乱的项目资料整理成一页清晰的定位与启动方案”，让客户先看到从混乱到清晰的变化。

**评价标准：**Demo 最好能在一次演示或一个短周期内完成；只解决一个关键问题；不依赖大量外部合作才能成立。

**反例：**一开始就承诺打通品牌、渠道、内容、交易和私域全链路。这看起来很完整，但无法快速制作，也无法判断到底是哪一环产生了价值。

### 第四步：搭闭环

**怎么做：**用“对象—问题—动作—结果—指标”五个节点写出 Demo 卡片。

**示范：**

> 对象：有产品但讲不清楚的早期项目；问题：客户不知道项目价值和启动顺序；动作：整理定位、目标人群、核心卖点和第一步行动；结果：形成一页可沟通、可演示的启动方案；指标：客户能否复述方案、是否愿意提供资料并进入下一轮验证。
> 
> 

**评价标准：**别人只看这五个节点，就能理解 Demo 服务谁、解决什么、交付什么，以及下一步如何判断有效。

**反例：**只写“接入 AI 后自动生成营销方案”。这句话没有对象、没有输入、没有具体过程，也没有验收标准，属于技术口号，不是业务闭环。

### 第五步：做验证

**怎么做：**把 Demo 给真实客户或一线使用者看，观察他们是否能理解、是否愿意提供真实资料、是否愿意为下一步验证投入时间或预算。

**示范：**演示完成后，不急着问“你觉得我们厉不厉害”，而是问：这是否对应你现在的真实问题？哪一部分最有用？如果继续做，你愿意先提供什么资料？你希望用什么结果判断值得继续？

**评价标准：**至少获得三类反馈：问题是否真实、方案是否看得懂、客户是否愿意采取下一步动作。只有口头称赞，没有资料、时间或预算投入，不算验证通过。

**反例：**内部人员觉得 Demo 很完整，就直接扩大开发范围；或者客户说“挺好的”，团队就把它当成购买意愿。这些都只是主观反馈，不是业务验证。

这个方法的核心，不是把方案讲得更大，而是把复杂能力压缩成一个可理解、可展示、可验收的最小模型。先让客户看见一件事如何跑通，再讨论如何复制、扩大和系统化。

## 最后检查

一个合格的 Demo 应该能在几分钟内回答：谁遇到了什么问题？我们具体做了什么？结果改变在哪里？下一步如何验证？如果只能讲产品愿景，却无法还原真实场景和判断标准，说明 Demo 还没有从访谈中真正长出来。
