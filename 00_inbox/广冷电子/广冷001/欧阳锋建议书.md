# 欧阳锋对电子资料归档整理及学习迭代的建议书

> 日期：2026-06-05
> 背景：基于广冷电子 HX-SMJ 红外光栅板的完整调试复盘

---

## 一、缘起：一个典型失败模式的启示

广冷红外的调试暴露了一个系统性问题：**离职工程师留下一堆没有版本的文件，新接手的人花 80% 的时间理清哪个版本是对的，而不是解决实际的技术问题。**

这不是广冷独有的问题。只要硬件项目存在以下情况，就会重复踩坑：
- 多人交接却没有交接标准
- 文件有多个版本却没有版本号的记录
- 原理图、BOM、PCB 各自独立迭代，没有锁定关系
- 调试经验存在工程师脑子里，人走了就没了

这套建议书的目的是：**从流程上杜绝"下一次还这样"。**

---

## 二、顶层架构：三层体系

电子工程的知识管理和 KDO 知识库不同——硬件的迭代成本比知识卡片高两个数量级。因此不能照搬 KDO，需要专门设计适配硬件节奏的三层体系。

```
┌─────────────────────────────────────────────────────┐
│          第三层：调试方法论（技能/playbook）             │
│  诊断版固件套路 · 三阶段诊断法 · 示波器测量checklist    │
│  ← 与具体芯片无关，跨项目可迁移                          │
├─────────────────────────────────────────────────────┤
│          第二层：失败模式库（跨项目经验）                 │
│  E-FM-001: SN74LVC2G07开漏上升沿                      │
│  E-FM-002: BOM多版本不同步                             │
│  ← 每次遇到故障修复后，沉淀一条可查询的模式                │
├─────────────────────────────────────────────────────┤
│          第一层：项目档案（单项目可复用）                 │
│  每个项目按模板归档：01_specs ~ 07_logs                │
│  核心是一张版本锁表 + 一个README                        │
│  ← 下个项目启动时直接翻同类项目档案                      │
└─────────────────────────────────────────────────────┘
```

**关键设计原则**：每一层只依赖下一层，不跨层引用。项目档案不需要引用方法论，方法论也不绑定具体的项目。

## 三、核心机制：文件三分类与版本锁

### 3.1 文件三分类

所有项目文件的三个类别，收工前过一遍：

| 类别 | 色标 | 定义 | 管理方式 | 典型文件 |
|:----|:----:|:------|:---------|:---------|
| **基准线** | 🔴 | 描述"产品是什么"的不可替代文件 | 只增不改；新版本=新文件，不覆盖旧文件 | 原理图、PCB设计、BOM、坐标文件、固件源码+hex、README |
| **佐证** | 🟡 | 有存档价值但不是产品本身 | 按项目归档，可打包压缩 | 调试日志、实物照片、示波器截图、采购清单 |
| **过程** | ⚪ | 用完即弃的中间产物 | 项目结束时删除 | 编译中间产物(.o/.crf)、重复备份、KEIL临时文件、微信传图副本 |

**收网标准**：项目结束时清理后，存储 < 清理前的一半。

### 3.2 版本锁：五文件联动

原理图、PCB、BOM、坐标、固件这五个文件不是独立迭代的。它们之间有一个依赖链：

```
原理图（设计意图）
  ↓ 决定
PCB + BOM + 坐标（物理实现）
  ↓ 决定
固件（行为）
```

**锁规则**：
- 原理图+PCB+BOM+坐标 四者锁定为同一个基线编号——动了其中任何一个，其他三者必须重新确认
- 固件可以独立迭代（不改硬件只改代码），每次迭代记录原因
- 版本锁表记录在项目 README 中

版本锁表示例：

| 基线 | 原理图 | PCB | BOM | 坐标 | 固件 | 说明 |
|:----|:------|:---:|:---:|:----|:----|:-----|
| B1.0 | V1.0 | V1.0 | V1.0 | V1.0 | V1.0 | 初始设计 |
| B2.0 | V2.0 | V2.0 | V2.0 | V2.0 | V2.0 | PCB改版 |
| B2.1 | V2.0 | V2.0 | V2.0 | V2.0 | V2.1 | 仅固件修复 |

## 四、适配硬件的 KDO 飞轮

KDO 的标准飞轮是：建造 → 使用 → 反思 → 实验。

硬件版的飞轮调整为：

```
画板/写固件（建造）
  ↓
调试验证（使用）
  ↓
写调试日志 + 沉淀失败模式（反思）     ← 这是现在最缺的一步
  ↓
下一个项目用沉淀的方法论（实验）
```

**关键改动**：增加"项目结束后写 retrospective"的强制步骤，回答三个问题：
- 这次踩了什么以前不知道的坑？
- 有没有办法下次不踩？
- 有没有可迁移的方法或套路？

广冷这次已经按这个模板写了 retrospective，路径 `_archive/07_logs/`。

## 五、一个月实施路线图

### 第一周：建立底线（不可妥协的三件事）

任何项目，做不到这三条不投产：

1. **原理图必须有版本号**——文件名带 `Vx.x_YYYY-MM-DD`，否则视为草稿
2. **BOM 和 PCB 必须互锁**——版本号一致，不一致不能下单
3. **项目必须有 README**——一句话说清用途 + 版本锁表

### 第二周：建"库"不是建"卡"

电子工程知识不适合做成孤立的概念卡。建三类参考表：
- **故障树库**：每遇到一个故障现象，更新对应的故障树
- **对照表库**：器件替代选型、电平转换方案对比
- **配置参数库**：常见 MCU 外设配置速查

### 第三~四周：广冷收网 + 模板验证

1. 完成广冷项目收网清理（已执行，从 ~3GB 清理至 667MB）
2. 归档结构 `_archive/` 已建立
3. 验证模板在实际项目中的可用性
4. 暴露出的问题立即修改模板

## 七、后续建议

1. **每完成一个硬件项目做一次"收网"**，按三分类清理文件，更新版本锁表
2. **新项目直接套用模板**，建目录、标版本号、写 README
3. **遇到新故障时先查失败模式库**，再动手；修复后更新库
4. **定期（每季度）回顾一次失败模式库**，合并重复条目，淘汰过时条目
