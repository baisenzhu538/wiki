一、到底应该怎么给 Agent 分工？先说逻辑，再说实践
1. 是按能力、岗位，还是名字？
从现在各大 Agent 框架和实践来看（OpenClaw、CrewAI、OpenAI Agents SDK 等），主流不是按“名字”分，
而是按「职责/能力 + 流程角色」分。
名字只是人类好记的标签，不是核心。
更精确一点：
底层划分依据是：
（1）任务在业务流程中的角色（决策/执行/评审/协调）
（2）所需的外部能力/工具（访问哪类数据、调用什么 API、操作什么系统）
岗位和部门名称，只是把这两点映射成人类熟悉的“岗位称谓”（比如「课程运营」「教研」「班主任/学习顾
问」）。

不是简单按“岗位名称”划分；
也不是按模型能力（写代码的一个、写文案的一个）那么粗；
而是按「在具体业务流程中承担的责任 + 能访问的工具/资源」来划。
这点在 CrewAI 的官方示例和 OpenAI Agents SDK 多 Agent 工作流示例中都很清楚：
他们通常有：
coordinator / supervisor agent（协调或路由）
specialist agents（各类具备特定工具和上下文的“专家”）
有时还有 reviewer / critic agent（做质量控制）
这些本质上都是「角色 + 能力」的组合。
2. 为什么不能只按“能力”或“岗位”来切？
如果你只按一个维度切，很容易踩坑：
按“能力”切的问题（例如：文案 Agent、代码 Agent、搜索 Agent）：
优点：工具/权限好管理，容易重用
问题：
对我们这种「围绕业务目标」的场景（比如从获客到转化到续费）不自然，
容易出现“谁负责最终结果？”的模糊 —— 每一步都有人做，但没人对业务 KPI 负责。
OpenAI Swarm 和 AutoGen 的案例里，都强调需要有「task orchestrator」来保证结果质量，否则多
Agent 只是“多人写提纲”。
按“岗位”切的问题（例如：教研 Agent、运营 Agent、销售 Agent）：
优点：
对你这个在线教育公司很符合直觉，便于和现有团队协作
问题：
岗位概念太大，Agent 的职责会被写得很宽泛，提示词不清晰，容易“万能但不精”，
工具权限容易越界（运营 Agent 去写教学脚本，教研 Agent 去搞广告投放）。
业内比较成熟的做法是：
在业务流程上划分清晰的「阶段/任务」，
每个阶段下有一个「对结果负责的角色（owner agent）」
这个角色再调用若干「能力型子 agent / 工具」，而不是随便大家互相调用。
也就是说，「岗位」更多对应的是“对某个业务结果负责的 agent（owner）”，
「能力」则更多被抽象成：

3. 什么是“业内最佳实践”？我帮你抽象成 4 个设计原则
综合 OpenClaw 生态文章（例如 CSDN 的《OpenClaw/Clawdbot 实战》）、CrewAI 官方多 Agent 指南、
OpenAI Agents SDK 的示例，可以抽象出四个共识：
1. 单一职责原则（Single Responsibility）
每个 Agent 应该有一个明确的「成功标准」：
比如“给出 3 个符合品牌调性的课程海报文案草稿”，
或者“把用户过往学习记录写成一个 5 条以内的进步反馈”。
不要让一个 Agent 负责「从市场调研到落地执行到复盘」整条链路，否则就是“大而化之的 ChatGPT”。
2. 角色清晰 + 权限边界
任何一个 Agent 都要回答三个问题：
1. 我为谁服务？（上游是谁，下游是谁/什么系统）
2. 我能做什么？（工具权限、可访问的数据域）
3. 我不做什么？（刻意写出来，避免越界）
多 Agent 框架（OpenClaw、CrewAI）里强调的「tools 限定 + scoped context」就是这个思想。
3. 有“协调者”，不是群聊
多 Agent 系统不是“群聊头脑风暴”，而是一个「有主持人的会议」。
协调者 Agent（可以叫 orchestrator / PM / lead agent）负责：
把用户需求拆解成子任务
决定什么时候叫哪个子 Agent
收集结果并做最终汇总、解释、向用户回报
这是 OpenAI Swarm、OpenAI Agents SDK、CrewAI 都反复强调的模式。
4. 持续可用 = 记忆 + 可观测 + 人类兜底
“长期可用”不是创建很多 Agent，而是：
有稳定的“长期记忆”（知识库 + 用户历史 + 项目状态）
有可观测性（日志、对话回放、关键决策的记录）
有必要的人类监督/审核位（尤其是对外内容和商业决策）
多 Agent 中常见的 reviewer/critic agent，在你的场景里可以是「品牌合规审稿 Agent」「教务质检
Agent」，或者干脆是人类。

0. 先确认你的业务链路（教育公司通用）
典型在线教育创业公司，大致有这几条主线（如果你的模式不同，后面我们可以再细化）：
1. 内容与产品线：课程设计、教案制作、练习题与测评、教辅资料
2. 获客与增长：内容种草、投放、SEO/公域内容、小红书/抖音脚本、转化页
3. 销售与转化：咨询话术、跟进脚本、话术 SOP、用户画像
4. 教学与服务：班主任运营、打卡、督学、答疑、学习路线调整
5. 运营与分析：转化数据分析、留存分析、课堂反馈、NPS、用户调研
你要搭的 Agent Team，就是把这五条主线“嵌入”到多 Agent 体系中。
1. 顶层：一个「教育业务协调者 / 总导演 Agent」
名称示例（你可以自己改）：
EduOrchestrator  / 项目总导演 Agent  / 教育产品负责人 Agent
职责：
理解人的顶层目标（比如：“帮我设计一个针对 0 基础成人的 3 个月 Python 训练营，并且给出从宣传到上课

把目标拆解成若干子任务，分派给下面的专业 Agent
决定调用顺序：先调研 → 再产品设计 → 再营销方案 → 再教学运营方案
对最终产出负责：收汇结果、做总结、向你或团队解释下一步怎么执行
输入：
你或运营同事给出的自然语言目标
现有业务的背景信息（可写在系统 Prompt 里或接入知识库）
输出：
一个结构化的「项目方案」：
产品形态
内容大纲
获客和销售策略
运营节奏
风险和执行要点
背后的最佳实践逻辑（不是我瞎想，是多 Agent 框架共同模式）：
在 OpenAI Agents SDK、CrewAI 示例和 OpenClaw 社区经验里，都强调需要「lead agent / router /
orchestrator」，否则多 Agent 没有“谁来拍板”和“谁来统筹”的角色。

2. 产品与教研线：3 个核心 Agent
2.1 教研规划 Agent（课程架构师）
**定位：**相当于「学科教研负责人」，负责课程结构与学习路径。
职责：
根据目标人群与时长，输出：
课程目标（知识 +能力）
模块化结构（阶段 1/2/3）
每阶段的关键能力与评估方式
和「学习路径个性化 Agent」协同，制定不同层级的学习路线模板
建议工具/能力：
访问你已有课程大纲、经典教材目录（作为知识库）
能调用一个“教育学/学习科学知识库”（你可以自己构建，哪怕先是文档）
为什么要单独拆？
教研工作本身的核心是“长期可维护的教学架构”，不等于内容写作。
许多实际案例（包括一些知名教育公司自研 Agent）都会把“课程大纲设计”和“内容填充”分别处理，这
样更易维护和扩展。
2.2 内容生成 Agent（课程内容写手）
**定位：**负责生成具体的教案、讲义、练习题、测验题等。
职责：
根据「课程架构师 Agent」提供的大纲，生成：
每一课的讲义草稿
板书/讲解要点
例题 + 练习题 + 解析
接受教师/人类修改后的内容，继续进行润色/扩展
工具/能力：
访问学科知识库（教材、既有课程录像转录等）
支持代码执行/公式渲染（视学科而定）
注意边界：
不直接决定课程目标和结构，只在指定框架下填充内容。
这是为了确保教研 Agent 对课程的“理论正确性”和“目标一致性”负责，而内容 Agent 偏执行和创作。

## 第 10 页

1. OpenClaw 的基本结构（基于已公开资料）
根据 CSDN《OpenClaw 详细攻略》和 GitHub：
OpenClaw 把能力拆成：
skills ：工具/能力（比如调用某个 API、读写本地文件等）
agents ：有自己 Prompt、可使用一组 skills 的实体
workspace 、channels  等：运行及接入环境
多 Agent 之间可以通过：
在一个“主 Agent”中，通过工具/脚本调用其他 Agent
或者在更高级别的 workflow 中，把多个 Agent 串起来运行
2. 设计你的「大龙虾团队」的落地步骤
步骤 A：先定义能力/工具（skills）而不是马上建很多 Agent
比如：
crm_read ：读取 CRM/线索数据
lms_read ：读取学习平台数据
kb_course ：查课程知识库
kb_brand ：查品牌规范和合规指引
data_analyze ：对上传的 CSV 做统计分析
每个 skill 明确：
输入参数
输出结构
权限范围（比如只能读，不能写）
这一步是参考多 Agent 框架的通用实践：先抽象“工具层”，再赋予 Agent。
步骤 B：建立 1 个总协调 Agent
名称：EduOrchestrator
配置要点：
system prompt 写清楚它的职责：
“你是在线教育公司的项目总导演，负责理解人类的业务目标，把任务分配给其他 Agent 和工具，并
最终输出一个清晰的方案。”
只给它必要的工具：
调用其他 Agent 的能力（通过 OpenClaw 的 agent 调用机制）
少量查询能力（如读取历史项目文档）

步骤 C：按上面几条业务线配置专业 Agent
对每个 Agent：
1. 写一个简洁但非常具体的 system prompt：
“你只负责 X，不负责 Y。你的输出必须是 Z 格式。”
2. 只给必要的 skills：
教研 Agent：kb_course 、kb_education_science

一、为什么需要分工？从人类公司和 AI 多 Agent 的“共同底层”
说起
1. 人类组织为什么会演化出分工和岗位？
从组织理论和多智能体（MAS）研究的文献来看（我查的如 MAS 概述、微软《Designing Multi-Agent
Intelligence》等），人类公司之所以发展出复杂的分工，背后有几条非常硬的物理约束：
1. 个体能力受限：认知容量 + 时间有限
人脑的工作记忆就是有限的（著名的 7±2/4±1 讨论），处理的信息越多，错误率越高；
一个人每天就那么多小时，不可能同时做教研、运营、销售、财务、客服。
→ 所以人类必须“切块”：每个人专注一小块，效率和质量更高。
2. 学习成本 & 专业化收益
成为真正的“教研专家”“流量专家”“销售高手”，都需要大量时间积累领域知识；
经济学里叫“比较优势”：不同人天赋和经验不同，把自己最擅长那块做到极致，整体产出最大。
→ 公司要赚钱，必然走专业化路径。
3. 沟通成本与协调复杂度
人类沟通很贵：开会、写文档、对齐理解都要时间和精力；
如果没有清晰分工，每个人什么都管，协调成本爆炸，组织瘫痪。
→ 分工 + 层级结构，是为了在“沟通成本有限”的前提下，让复杂协作还能运转。
4. 责任边界和激励机制
你需要知道“谁对什么结果负责”，才能做绩效、晋升、奖惩；
没有明确的职责分工，责任就会“人浮于事，锅无人背”。
→ 岗位、部门、KPI，本质是为了让责任可分配、可评估。
小结：人类分工的根本原因，是在「个体能力有限 + 沟通成本高 + 学习成本高 + 需要责任和激励」这个物理现实
下，为了追求整体效率和稳定性，不得不演化出的组织模式。

2. 到了 AI，多 Agent 分工的“相同点”和“不同点”
现在看 AI 多 Agent（大型语言模型驱动的 MAS），参考微软、CSDN 多 Agent 文章和伯克利那篇《Why Do
Multi-Agent LLM Systems Fail》，可以看到：
相同点：为什么 AI 也需要分工？
即使模型很强，也有几个类似的硬约束：
1. 上下文窗口有限 & 推理链条有限
每次调用 LLM 的 token 有上限（哪怕是 200K，也不是无限）；
任务越复杂，信息越多，如果让一个 Prompt 兜底所有上下文，容易迷糊、跑题、幻觉。
→ 把复杂任务拆成多个子任务，让不同 Agent 只处理局部上下文，反而更清晰稳定。
2. 工具/权限差异
在工程实现里，一个 Agent 通常绑一组工具和权限：
课程库、CRM、LMS、搜索、代码执行、数据库等；
安全和治理考虑：
不是每个 Agent 都应该能直接改数据库、发短信、对外发文。
→ 工程上必须有“谁能用哪些工具”的边界，这天然催生“分工”。
3. 鲁棒性和可维护性
单一超级 Agent 的 Prompt 越写越长，更新一次要改一整坨逻辑，很容易引入新 bug；
多 Agent 把逻辑拆开：
“教研规划逻辑”放一个 Agent；
“营销文案逻辑”放一个 Agent；
以后改营销，不动教研，维护成本降低。
→ 就像软件工程的“模块化”和“函数拆分”。
4. 可观测性和调试成本
一个大 Prompt 出问题，很难看出到底是“理解目标错了、数据查错了、还是文案风格崩了”；
多 Agent 时，每一步输出都可观测：
教研 Agent 的大纲是否合理？
文案 Agent 是否忠实于大纲？
审稿 Agent 是否通过了？
→ 更容易定位问题和迭代。
所以，从“为什么要分工”这个角度看，人类组织和多 Agent 系统是高度一致的：都是为了在有限认知/上下文/
工具权限/治理要求下，让复杂任务可拆解、可协作、可维护。

1. 先给一个实用的三层划分

1. Prompt 模板 / 函数（最底层）

2. Skill / 工具（中间层）
一个可被调用的能力单元，可能是：
一个函数（读数据库、发 HTTP 请求、运行 Python 代码）；
或者“一个包装好的 LLM 调用”，比如“把一段文案改成品牌语气”的子任务；

满足以下几个特征中的大部分（参考微软《Designing Multi-Agent Intelligence》与 MAS 定义）：
1. 有明确的角色/目标（goal/role），而不是一次性动作；
2. 可以自主选择用哪些 skill以及调用顺序（基于当前目标和上下文）；
3. 有一定状态/记忆（短期对话历史、长期知识）；
4. 能与其他 Agent 交互（接收任务、发送结果）；
简单说：Agent 是“带大脑的工人”，Skill 是他们手里的工具，Prompt 是他们的操作说明。

2. 很多“Agent 其实是 Skill”——怎么判断？
这点上，你的直觉完全对，很多所谓“XX Agent”，从工程视角看本质上应该是 skill，而不是独立 Agent。
判断标准（这部分是结合多框架和工程经验的归纳，不是框架强制规定）：
1. 看它是否需要“持续存在的角色和状态”
如果只是：
“给我把这段文案改成 3 种风格”
“帮我从文本里抽取邮箱地址”
“把 Markdown 转成 PPT 大纲”
它没有长期目标、也不需跨多轮对话维护状态，那这更像一个 skill（函数）。
2. 看它是否需要“自己做决策和规划”
如果它仅仅是：
接收输入 → 调用 LLM 做一次变换 → 返回结果
它没有“思考要不要调用其他工具、何时停止、下一步干嘛”，那依然更像 skill。
3. 看是否需要人与其他 Agent 多轮协作
如果这个单元从来不会是协作中的“角色”，只是被 orchestrator 调用一次就结束，那它是 skill；
如果它会被 orchestrator多次调用、会和其他 Agent 交互、需要保持自己的“内在视角”（例如教研
Agent 反复迭代课程设计），那更像 Agent。
结合你的场景举个具体例子：
“给定课程大纲，生成 10 道单选题及答案解析”：
这是典型 skill：一个内容生成工具。

这是 Agent：
它要记住前几次生成过哪些题；

自己决定下一批应该出什么题。

1. 纯程序能力

完全不需要 LLM，只是传统函数，用于读写数据、调用其他系统。

被调用才执行；

将复杂实现（包括 Prompt）封装起来，对调用者透明。
3. Prompt 是最底层的“操作说明”
单次调用的文本指令；
不带持久状态；
主要是设计“如何让模型在这一轮按我们想的方式思考”。

你完全可以用一个“非常简单的 Agent”去承载一个小 skill；

1. 并行度和复制成本完全不同

AI 组织的最佳实践，会更像“动态可重构的组织”，

3. 激励和责任模型不同
人：
有“职业生涯、利益、文化认同”，需要用 KPI、股权、晋升来驱动；
AI：
没有情绪，没有利益，完全靠“正确设计的目标函数和约束”行事；
所以：
人类组织必须考虑“政治”“文化”“心理安全感”等软因素；
AI 组织只考虑“正确性、效率、安全性、可控性”。
结果：
人类组织的最佳实践，很多是“如何让人配合、减少内耗”；
AI 组织的最佳实践，则是“如何让结构简单、调用图清晰、边界明确、错误可控”。

Skill 层：可复用的小能力 API——读数据、改写、分析、生成某种结构。
Agent 层：带角色、带目标、会挑选 skill 的“岗位影子”。
OpenClaw 层：让一群 Agent+skills 在统一世界里跑起来、协作起来、可被监管的“操作系统 & 调度中
心”。
