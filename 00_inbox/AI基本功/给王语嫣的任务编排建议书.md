# 给王语嫣的任务编排建议书

> 从 Feature 思维看 KDO，从 KDO 看编排
> 撰写：Codex Agent | 日期：2026-08-08

---

## 一、核心洞察：KDO Skills 就是 Feature 的工程化实现

Feature 思维教我们一件事：**不要把 AI 能力绑在工具上，要拆成最小实践原子。**

KDO 已经在做这件事了——只是没人用 Feature 的语言描述它。

看看这个对应关系：

| Feature 思维概念 | KDO 中的对应 |
|:--|:--|
| Feature（最小实践单位） | 每个 KDO skill 目录（如 `six-layer-cross-validation`） |
| Feature 四要素（AI范围/解题水平/实践单位/最小粒度） | 每个 skill 的 description + constraints + allowed-tools |
| Feature 库（元素周期表） | `skills-kdo/` 下的 50+ 个 skill |
| Feature 分层（模型层→Agent层） | KDO 的 stage-1 到 stage-5，从诊断到制品 |
| Feature 组合（复利效应） | Skill 之间的调用链（如 synthetic 调用 gan + iceberg + sats） |
| 刻意练习（偶遇→理解→验证→认知→沉淀） | `60_feedback/` 的反馈闭环 |

**一句话**：KDO 是你已经建好的 Feature 周期表。问题是——它被当成"技能列表"在用，没有被当成"可编排的原子 Feature"来管理。

---

## 二、独特洞察：KDO 现有设计模式中隐藏着四个"元 Feature"

不是每个 skill 都一样。有些 skill 是"普通 Feature"（做饭烧菜），有些是"元 Feature"（告诉你如何组合菜）。

从 KDO 的现有设计中，我提取出四个**可以跨域迁移的编排元 Feature**：

### 元 Feature 1：GAN 三角色（来自 `ai-collaboration-gan`）

```
生成器 → 判别器 → 合成器
```

**Feature 四要素**：
- AI范围：任何需要"产出+检验+融合"的AI任务
- 解题水平：通过角色分离消除单模型认知偏差
- 实践单位：三个角色的prompt定义 + 协作流程
- 最小粒度：三个角色不能拆成两个——这就是最小单位

**编排应用**：不仅限于"写文章/写代码"。任何 KDO 任务都可以嵌入 GAN 模式：
- 王语嫣诊断素材 → 老顽童（生成器）写卡 → 欧阳锋（判别器）攻击 → 王语嫣（合成器）定稿
- 甚至可以 GAN 嵌套 GAN：判别器自己也是一个 GAN（四路攻击 Agent）

### 元 Feature 2：OODA 闭环（来自 `ai-collaboration-ooda`）

```
Observe → Orient → Decide → Act → 回到 Observe
```

**编排应用**：整个 KDO 的 stage 流程本质上是一个大 OODA：
- Stage 1（诊断）= Observe + Orient
- Stage 2-3（骨架+工具）= Decide
- Stage 4-5（验证+制品）= Act + 回到 Observe

**关键洞察**：当前 KDO 的五个 stage 是**线性**的。但如果把每个 stage 都变成一个 OODA 微循环，质量会指数级提升——不需要等到 stage 5 才发现 stage 2 的问题。

### 元 Feature 3：合成调研（来自 `demand-analysis-synthetic`）

```
Case Retriever → Persona Agents(并行) → Verifier + Adversary(并行) → Synthesizer
```

**这是 KDO 中最成熟的编排模式**，它融合了 GAN + SATs + 冰山六层 + 多智能体架构。

**编排应用**：这个模式不仅适用于用户调研，它可以迁移到任何"需要从多视角推演+交叉验证"的场景：
- 竞品分析：Persona = 不同竞品角色，Verifier = 公开数据验证
- 策略推演：Persona = 不同利益相关方，Adversary = 反方立场

### 元 Feature 4：知识自攻击（来自 `kdo-self-attack`）

```
卡片 → 四路攻击Agent(并行) → 合并报告 → 反馈闭环
```

**编排应用**：自攻击是 GAN 模式在知识管理领域的特化。它的核心创新是——**不等人发现问题，Agent 主动找问题**。这个模式可以泛化到任何"产出物质量检验"场景。

## 三、王语嫣的编排角色定义

以 Feature 思维重新定义王语嫣：

| 维度 | 定义 |
|:--|:--|
| **身份** | Feature 周期表的活字典——知道有哪些 Feature、每个 Feature 的适用场景和边界 |
| **核心能力** | 不执行，只编排——面对任务时，从 Feature 库中"点菜"，组合出最优编排方案 |
| **输入** | 一个模糊任务（"帮我分析这个赛道"） |
| **输出** | 一个编排方案（"用 synthetic 做需求推演 → GAN 验证 → nine-layer 深挖 → 汇总"） |
| **不做什么** | 不亲自写卡片、不亲自跑验证、不亲自攻击——这些交给老顽童和欧阳锋 |
| **类比** | 天龙八部的王语嫣——通晓天下武学但不出手。她的价值不在"打"，在"知道什么时候用什么招" |

## 四、编排路径：从"技能列表"到"Feature 周期表"

### Phase 1：Feature 标注（1-2天）

给每个 KDO skill 加上 Feature 四要素标注，形成"点菜菜单"。

**格式示例**：
```markdown
## Feature 名片

| 要素 | 内容 |
|:--|:--|
| AI范围 | 知识卡片质量检验 |
| 解题水平 | 从"等用户反馈"升级为"主动发现漏洞"，提升知识库可信度 |
| 实践单位 | 四路攻击Agent并行 → 合并报告 → 写入反馈目录 |
| 最小粒度 | 单卡攻击 / 域批量攻击 / 定期自检 |

### 编排特征

| 特征 | 值 |
|:--|:--|
| 并行度 | 高（四路攻击可并行） |
| 执行者 | 欧阳锋 |
| 前置依赖 | 卡片已完成 lint |
| 输出物 | `60_feedback/adversarial/atk_*.md` |
| 典型耗时 | 2-5 min/卡 |
```

**关键**：每个 skill 不只是"做什么"，还要标注"编排特征"——并行度、执行者、前置依赖、典型耗时。这是编排的基础数据。

### Phase 2：构建编排小抄（Feature 组合菜单）（1-2天）

把常见的任务类型，预制成"编排套餐"。

**示例**：

```markdown
## 编排套餐 1：新域知识生产（完整版）

触发条件：00_inbox 有新素材入仓
执行者编排：王语嫣(诊断) → 老顽童(写卡) → 欧阳锋(攻击) → 王语嫣(合成)

Wave 0: 素材验收
  ├── stage-1-diagnose (王语嫣)
  │     ├── 盘点素材 → 置信度标记
  │     ├── 盲区识别
  │     └── 产出：诊断记录 + 任务清单
  │
Wave 1-2: 核心框架
  ├── stage-2-skeleton (老顽童)
  │     └── 产出：框架卡 + 概念卡 + 域索引入口
  ├── stage-3-tooling (老顽童)
  │     └── 产出：工具卡 + 案例卡
  │
Wave 3: 质量检验
  ├── kdo-self-attack (欧阳锋)
  │     └── 四路攻击 → 问题分级
  ├── six-layer-cross-validation (欧阳锋)
  │     └── 关键数据六层验证
  │
Wave 4: 修复+合成
  ├── 老顽童修复攻击发现的问题
  ├── kdo-self-attack (二次验证)
  └── 王语嫣最终审查 → 入库
```

```markdown
## 编排套餐 2：快速决策支持（轻量版）

触发条件：用户问"这个赛道能做吗"
执行者编排：王语嫣(诊断) → 老顽童+欧阳锋(并行) → 王语嫣(合成)

├── demand-analysis-synthetic (老顽童)
│     ├── Case Retriever 找相似案例
│     ├── 3-5 Persona Agents 推演
│     └── Verifier + Adversary 交叉验证
│
├── nine-layer-deep-dig (欧阳锋，并行)
│     └── L1-L9 逐层深挖 → 风险画像
│
└── 王语嫣整合 → 决策框架(go/no-go + 最大风险 + 最小验证路径)
```

```markdown
## 编排套餐 3：知识库健康巡检（定期）

触发条件：每周自动触发
执行者编排：王语嫣(发起) → 欧阳锋(攻击) → 老顽童(修复)

├── kdo-self-attack --random 5 (欧阳锋)
├── check-source-refs.py (自动化脚本)
├── 王语嫣审查攻击报告 → 分级处理
└── 老顽童修复致命+严重问题
```

### Phase 3：定义编排质量门禁（0.5天）

每个编排方案完成后，王语嫣必须过这几道门：

| 门禁 | 检查项 |
|:--|:--|
| Feature 覆盖率 | 该任务类型涉及的关键 Feature 是否都调用了？有没有遗漏？ |
| 并行度检查 | 可并行的 Feature 是否真的并行了？有没有不必要的串行等待？ |
| 对抗充分性 | 有没有至少一个"挑毛病"的角色？如果没有，加欧阳锋 |
| 反馈闭环 | 有没有从输出回到输入的验证环节？如果没有，加 OODA 微循环 |
| 成本预算 | 预估耗时和 token 消耗是否在可接受范围？ |

### Phase 4：建立编排反馈闭环（持续）

王语嫣也需要刻意练习：

```
每次编排任务
  ↓
记录：用了哪些 Feature → 耗时多少 → 质量如何
  ↓
复盘：哪个 Feature 选得好？哪个选错了？遗漏了什么？
  ↓
更新编排小抄：沉淀新的套餐、修正错误组合
  ↓
Feature 库越来越精准，编排越来越快
```

**具体做法**：在 `60_feedback/` 下新增 `orchestration/` 目录，每次编排任务后记录：
```markdown
# 编排复盘：<任务名>_<日期>

## 编排方案
- Feature 组合：[...]
- 并行/串行决策：[...]

## 结果评估
- 质量：[1-5]
- 耗时：[实际 vs 预估]
- 遗漏：有没有事后发现应该用但没用到的 Feature？

## 改进
- 下次类似任务应该调整什么？
```

## 五、关键路径：先做什么，后做什么

```
第1天：Feature 标注
  ├── 挑 10 个最常用的 KDO skill
  └── 给每个加 "Feature 名片"（四要素 + 编排特征）

第2天：构建编排小抄 v0.1
  ├── 定义 3 个编排套餐（新域生产 / 快速决策 / 定期巡检）
  └── 用下一个真实任务做 dogfooding

第3天：dogfooding + 调整
  ├── 用编排小抄跑一个真实新域
  ├── 记录编排复盘
  └── 修正套餐

第4-7天：扩展 + 自动化
  ├── 补齐剩余 skill 的 Feature 名片
  ├── 新增 2-3 个编排套餐
  └── 如果可能，写一个编排检查脚本（自动检测 Feature 覆盖率、并行度）
```

## 六、一句话总结

> **Feature 思维解决了"学什么"的问题，KDO 解决了"怎么存"的问题，王语嫣要解决的是"怎么编排"的问题。**
>
> 三者合一，就是：面对任何 AI 任务，王语嫣从 Feature 周期表中点菜，老顽童和欧阳锋并行执行，结果回流到 Feature 库——**"成功也好失败也好，Feature 库都变强了。"**
