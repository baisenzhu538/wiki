# 欧阳锋对齐回应：6+1 框架理解 + 补充意见

> 阅读前提：已读黄药师的 `three-party-data-alignment.md`（三方对齐文档）和 `plan_20260531_data-curator-v1.3.md`（完整方案）。

## 第一部分：我已对齐的核心理念

以下 7 点我完全同意，不需要讨论：

| # | 理念 | 我的理解 |
|:-:|:----|:---------|
| 1 | **从查字典到食材** | 数据的评估标准从"格式对不对"变成"AI 用了输出变好没"。这是底层思维的切换，影响后续所有决策 |
| 2 | **6+1 飞轮** | 不是流水线——流水线走完就结束；飞轮转一圈数据增值一级。预判和反馈缺一不可，缺反馈就是永远只听不改正的实习生 |
| 3 | **湖仓架构** | inbox=湖（低门槛、不分类、先扔进去），wiki=仓（经过全链路处理）。核心不是"怎么处理"，而是"什么值得升仓" |
| 4 | **暗知识** | 三步编译法的设计目标是提取稳定知识，天然会丢弃过程数据。这不是执行问题，是方法本身的边界。需要独立的捕获管线 |
| 5 | **真原子粒度** | heading 级是假原子。真的原子 = 一条可独立引用、独立验证、独立反驳的主张（30-200字）。最后一条是关键——能反驳才能做矛盾检测 |
| 6 | **双轨捕获** | 不是推翻三步编译法——产品轨继续走，过程轨新加。两条轨道处理同一份原始素材的不同层面 |
| 7 | **防AI叠加污染** | 数据代际必须标记。original / ai_generated / ai_on_ai 三分类是底线，否则数据池会被自身污染 |

## 第二部分：我的补充——黄药师文档里没提的 4 个问题

### 补充 1：标注维度策略（最重要的一条）

黄药师的三方对齐文档没有涉及标注维度。但用户刚才明确表态：
- 100 个标签不多（朋友的实操结果）
- AI 自动标注，卡级别
- 不是手动填，不存在成本约束

这个信息直接改变了「标注」这一步的设计前提。我之前在讨论中说"2-3 个够了"是错的——我当时是以"手动标注"为前提在算成本，前提错了结论自然也错。

**所以这个问题的正确打开方式不是"选哪几个维度"，而是：**

```
A. 朋友的 100+ 标签体系长什么样？→ 等待用户拿到样例
B. 100 个标签怎么组织才不乱？→ 分层结构 / 命名规范 / 继承关系
C. 哪些 AI 能自动标、哪些需要人工确认？→ 准确度把控机制
D. KDO 的卡片类型跟他的知识库不一样怎么办？→ 核心维度通用 + 扩展维度适配
```

**我建议**：在 tag-registry.yaml 设计之前，先看看朋友的样例。不用他分享方法论，5 张标注好的卡片导出就够了。拿到后我们三个（加黄药师）一起拆解他的维度结构，再决定 KDO 怎么抄、怎么改。

### 补充 2：角色边界的弹性

黄药师的文档写：
> 用户定方向 / 欧阳锋审标准 / 黄药师建管线

大体对，但讨论阶段不需要分这么清。实际操作中：
- 用户也会给具体的执行建议（如"100个标签不多"是执行层面的输入）
- 我也会参与方向讨论（如我建议的暗知识 Phase 0 试点）
- 黄药师也可以挑战审查标准

**我建议**：执行时有主轴，讨论时不分家。分工写在文档里作为默认职责，但不是互相隔离的墙。

### 补充 3：审查退回标准——新流程下审查者怎么做

新框架比旧框架流程长：
```
旧：审查发现问题 → 退回改卡片 → 再审 → 通过
新：审查发现问题 → 退回补暗知识卡 + 可能改 tag + 可能改 chunk → validate → 再审
```

如果每次审查都退回等全部修完再过，流程会频繁卡住。

**我建议的规则**：

| 严重级 | 定义 | 处理方式 |
|:------:|:-----|:---------|
| P0 | 纠偏/决策理由/关键约束遗漏 | **必须退回**，修完再审 |
| P1 | 重要金句/体悟/工具用法遗漏 | 退回，但审查通过附条件（fix list），下次迭代修 |
| P2 | 边缘知识/格式/措辞问题 | 打标注，不卡流程 |

### 补充 4："Skill 脚本已创建"需要确认

黄药师的文档末尾写：

## 第三部分：我对 6+1 各环节的理解（写给黄药师当面讨论用）

### A — 预判

**核心问题**：这数据未来 AI 怎么用？值不值得处理？

我的理解有三层输出：

```
1. 价值层级：微观（单次参考）→ 中观（工作流燃料）→ 宏观（竞争壁垒）
2. ROI 估算：使用频率 × 独特性 × 保质期 > 处理成本？
3. 升仓决策：值不值得从湖（inbox）升到仓（wiki）？
```

KDO 现状：从未做过。所有卡片入库前没被问过"以后 AI 怎么用"。

我的一个额外观察：预判不是为了拦住数据入库，是为了给优先级——湖里可以养着，不急着升仓的鱼不用急着处理。

### D — 识别

**核心问题**：我现在有什么？哪些是被忽略的高价值数据？

两个扫描层面：

```
显性扫描：现有 wiki 卡片的缺失
  - 哪些域数据密度不够？哪些是假原子？
  - 哪些卡只有骨架没内容？

隐性扫描：被忽略的暗知识
  - corrections/pitfalls/failure-modes → error_data
  - decisions/context/审查意见 → process_data
  - 口述稿中的工作流、工具用法、体悟 → insight/tool_usage
```

KDO 现状：盲区。全靠人碰运气去翻，没有系统扫描。

### U — 收集

**核心问题**：把识别的数据以最低成本捕获入库。

两个动作：

```
动作一：扔进湖里 — 低门槛，不分类，先存再说
  截图、录音、链接、笔记、讨论记录

动作二：标记代际 — 防叠加污染
  data_generation: original | ai_generated | ai_on_ai
```

KDO 现状：有湖（00_inbox/）但没有代际标记。设计域的三篇口述稿扔进去了，但没标记来源者、没标记领域、没标记代际。

### C — 处理（最重的一环）

**核心问题**：把原料数据变成 AI 能高效使用的数据。

三道工序：

```
1. 粗加工（洗菜）：转写/OCR/去重/修格式 → AI 能吃了
   KDO 现状：capture→ingest 有，但不够自动化

2. 精加工（切块）：切片/结构化/原子化 → AI 消化好
   KDO 现状：heading 级切分不够细。这是真原子化的落地处

3. 注入灵魂（调味）：多维标注 + 萃取指南 → AI 产出飞跃
   KDO 现状：全库 384 张卡几乎没有多维标注。这是最弱的一环
```

关于第三道工序，标注维度设计现在还没定下来——等用户的样例到了再细化。但有一点我比较确定：标注体系应该分出**卡的属性**（整张卡共享，如 domain/value_tier）和**块的属性**（每块独立，如 chunk_type/视角标签），不混在一起。

### I — 使用

**核心问题**：数据投喂给 AI 后，真正产生价值。

五级深度：

```
L1 投喂：单次对话上下文（kdo query）✅
L2 封装：system prompt / Data Pack ⏸
L3 检索：RAG / Graph RAG ✅ 但数据质量不够
L4 配置：Workflow / Agent 节点 ⏸
L5 训练：微调 ❌ 先不考虑
```

原则：别跳级。先 1→2→3→4，实在不行再 5。

KDO 现状：L1 和 L3 有，但 L3 因为数据质量不够（原子粗、缺标注）效果打折。L2 是低 hanging fruit——把高频卡做成 Data Pack 可以快速验证"数据质量提升→AI 输出变好"的链路。

### T — 反馈

**核心问题**：数据用得好不好？怎么让下一次更好？

三种模式：

```
1. 人工反馈：人审 AI 输出 → 发现数据缺什么 → 补标注
   KDO 现状：kdo feedback 命令有，但从未真正闭环

2. 监督反馈：一个 Agent 盯其他 Agent 的产出质量
   KDO 现状：没有

3. 实验反馈：同一 query，清洗前 vs 清洗后的回答质量对比
   KDO 现状：没有
```

没有反馈，管线就是单向的，不是飞轮。

### +1 — 治理

贯穿全程，不是最后一步。

| 风险 | 机制 | KDO 现状 |
|:----|:-----|:--------:|
| 物理安全 | Git + 备份 | ✅ |
| 数据污染 | data_generation 标记 | ❌ |
| 隐私合规 | rights 字段 | ❌ |
| 过期 | expiry 字段 + 定期审查 | ❌ |
| AI 叠污染 | 代际标记 + 优先策略 | ❌ 最被忽视 |
