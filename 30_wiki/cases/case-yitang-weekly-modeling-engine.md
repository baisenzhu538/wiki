# 案例：一堂的“周对周建模迭代”——把周五课程逼成公司增长引擎

## 原始表述

> 一堂的周对周的建模迭代能力是这家公司最大的增长引擎。这家公司真正的增长是什么呢？你说收入增长、利润增长、流量增长、会员增长，我觉得都不本质。这些运气好或者钱就能带来的增长，这家公司没办法拿钱买的，就是周对周的建模能力的增长。

## 问题

收入增长、流量增长、会员增长都可以靠钱买，但一堂希望建立不可用钱复制的长期竞争力。如果没有强制迭代机制，团队容易陷入“交付即结束”，模型能力难以持续进化。

## 方案

把每周五的课程交付当成强制性的建模迭代节点，用“硬截止日”把组织的自然惰性压成可执行的闭环。

### 时间线与具体机制

| 节点 | 动作 | 目的 |
|:-----|:------|:-----|
| **周一（T-7）** | 确定本周研究主题与待验证假设 | 让交付有明确的认知目标，而非为了上课而上课 |
| **周三（T-3）** | 中期检查：继续 / 取消 / 降级 | 提前暴露风险，避免周五才被动翻车 |
| **周五 18:00（T-1）** | 品控终审：内容是否达到 60 分平衡线 | 未达标即临时取消并公开说明原因 |
| **周五 21:00（T+0）** | 正式课程交付 | 把真实用户反馈作为模型验证数据 |
| **周六（T+1）** | 24 小时内写复盘日志 | 趁热捕获“当时以为对的”与“实际发生的”偏差 |
| **下周一（T+2）** | 把复盘结论注入模型 / SOP / 检查清单 | 让迭代从文字变成可复用的组织资产 |
| **每月** | 模型资产小盘点 | 识别高频复用范式与重复发明轮子 |
| **每半年** | 约 20 轮复盘驱动建模水平跨一大步 | 实现认知能力的阶梯式升级 |

### 四个关键设计

1. **每周必须交付**：周五课程是硬约束，逼团队持续输出；即使临时取消，也要向用户说明品控原因。
2. **认知-模型-复盘-迭代-反思闭环**：每次交付后必须复盘，把经验沉淀为可复用模型。
3. **半年一次大升级**：通过约 **20 轮复盘**推动建模水平跨一大步。
4. **公开承诺与反馈**：用户知道一堂在研究型内容上“无法提前排课表”，反而给予极高包容度。

## 结果

- 周对周的建模能力增长被定义为“公司真正的增长引擎”；
- 每 **半年**课程与建模水平能往前跨一大步；
- 团队形成了“交付-复盘-建模”的高速循环；
- 用户也给予极高包容度，接受研究型课程无法提前排课表。

## 可迁移

- 把“持续输出”固定成组织节律，用高频复盘倒逼模型进化；
- 真正的壁垒不是单次交付，而是“交付-复盘-建模”的循环速度；
- 用钱能买到的增长都不本质，模型能力的复利才是。

## Constraints & Boundaries

### 适用边界 / 可迁移场景

| 场景 | 说明 |
|:-----|:------|
| ✅ 知识型 / 内容型组织 | 团队的主要产出是模型、方法论、课程、SOP，而非标准化实物产品 |
| ✅ 有固定高频交付节点 | 存在周会、周报、周课等可强制对齐的组织节律 |
| ✅ 团队具备基础复盘能力 | 能区分“人没做好”和“模型没覆盖”，避免复盘变成批斗会 |
| ✅ 管理层愿为质量牺牲确定性 | 允许临时取消 / 调课，并愿意向用户解释“研究型内容无法提前排课表” |

### 常见失败模式

| 失败模式 | 真实症状 | 可执行修复 |
|:-----|:------|:------|
| **把“每周交付”当成表演，无复盘** | 课越上越多，模型能力原地踏步；同一类失误反复出现 | 强制每节课后 24 小时内填写《模型迭代日志》，必须输出“本次模型改动点” |
| **复盘只追责任，不追模型** | 复盘会气氛紧张，结论停留在“某某下次注意”，同样问题反复发生 | 复盘模板固定三栏：现象 → 当时采用的模型/假设 → 模型应如何修改 |
| **节奏太快导致质量崩盘** | 学员投诉增加、完课率下降、临时取消次数反而变多 | 设置品控红线（如 60 分平衡线），未达标即取消并公开说明原因 |
| **只学形式，不设激励机制** | 团队把建模当成额外负担，敷衍写日志、不更新资产 | 把模型定价（如 [[case-yitang-model-valuation-flywheel]]）和资产盘点与迭代成果挂钩 |

## Checklist：把周五课程变成建模引擎

在每次周五交付前后自检：

- [ ] 本周是否有 1 个明确的待验证假设？
- [ ] 是否为该假设设置了可量化的品控标准？
- [ ] 交付后 24 小时内是否完成了复盘日志？
- [ ] 复盘是否产出至少 1 个模型 / SOP / 检查清单改动点？
- [ ] 改动点是否已写入组织资产库并做了版本记录？
- [ ] 若临时取消或调整，是否向用户同步了品控原因？
