# Truman 直播 SOP 三年迭代：从 0 到 50 条的迭代递归深挖法

> **这不是方法论——这是方法论在现场长出来的过程。**

---

## 一、人话版摘要

Truman 一周讲 4-5 场直播，每场 3 小时。讲了 200+ 遍同一门课，还要保持高状态。他把过去三年怎么做到这件事的，拆成了三个阶段。

**第一阶段：太乱了，先写下来。** 前 50-100 场，50% 以上直播出意外——忘吃饭饿肚子、忘开空调、前一个会拖堂来不及准备。团队把"表现好的时候做过什么"和"出错的时候漏了什么"写成第一版 checklist，十几条。

**第二阶段：写下来了但没人执行。** 第二阶段发现：SOP 写得很具体，但不同的人执行会忘。怎么办？给 SOP 加 SOP——行政专人到点送饭、班班专人到点逼你睡觉、PM 专人到点检查配置。

**第三阶段：能执行了但不够好。** 最近两年持续加补丁——发现挑食盲区 → 固定外卖清单；被敲门惊醒 → 定制"请勿敲门"牌子；灵感闪现没地方记 → 桌边永远放本和笔；能量低撑不住 → 直播左手固定放脆脆鲨+奶茶。

---

## 二、框架化：迭代递归深挖三阶段

### 阶段一：从混沌到 checklist（被动补救）

**触发**：出了问题。
**动作**：写下来。所有参与的人在一个固定文档里加条目。
**产出**：第一版 checklist（10+ 条，基于"好状态时做了啥"+"差状态时漏了啥"）。

> "跟团队说好，所有人在这个工作环节先维护一个固定的文档。我们就把所有遇到的问题和可能的东西写了第一版本的checklist。"

**关键原则**：不是等完美再写，是出了错就加一条。

### 阶段二：从 checklist 到执行体系（强制一致性）

**触发**：SOP 存在但没人执行。
**动作**：给 SOP 加 SOP——派专人负责每个节点的检查。行政→订饭、PM→调试配置、班班→逼睡觉。
**产出**：执行清单从十几条扩展到二三十条，每条有人负责。

> "给SOP加SOP。我们开始去制定另外一个SOP是用来检查原有SOP。"

**关键原则**：SOP 的敌人不是复杂度，是"谁来做"不明确。

### 阶段三：从执行体系到微颗粒度优化（持续补丁）

**触发**：偶发意外事件。
**动作**：每次意外后立刻分析根因，加一条精准补丁。挑食→固定外卖列表。被敲门→定制牌子。能量低→固定零食位置。
**产出**：50+ 条精细规则，覆盖正常流程 + 边缘 case。

**关键原则**：不是一次做对，是每次错了就精准地加一条。

---

## 三、迭代动力：为什么能持续三年？

| 要素 | 说明 |
|:--|:--|
| **高频重复** | 一周 4-5 场，每场都是测试机会 |
| **即时反馈** | 状态好不好自己立刻知道 |
| **团队协作** | 不是一个人写 SOP，是团队共同维护 |
| **成本能感知** | 状态差→直播效果差→学员反馈差→收入影响 |
| **复盘机制** | 每次意外必然触发"加一条补丁" |

---

## 四、可迁移原则

**"迭代递归深挖"的核心不是技术——是纪律：**

1. **出错 → 加一条。** 不是开会讨论、不是立项改造，是当场加一条规则。
2. **执行不了 → 加执行者。** 不是骂人不执行，是指定专人负责这个节点。
3. **偶发意外 → 加精准补丁。** 不是"下次注意"，是改一条具体的规则。
4. **三年如一日。** 不是一次大改造，是每场直播后都可能加一条。

---

## 五、反模式（不要做的事）

| 反模式 | Truman 的替代做法 |
|:--|:--|
| 一次写完美 SOP | 出错就加一条，永远不"完成" |
| 只写不执行 | 给 SOP 加 SOP |
| 重大意外后才复盘 | 每次小意外都加补丁 |
| 一个人维护 SOP | 团队共同维护，专人负责节点 |

---

## 六、对 KDO 的启示

这条案例直接验证了 `modeling-three-stages` 框架中的 L3 流程建模——但更重要的是它展示了 L3 不是"一次建模完成"，而是"持续三年还在迭代"。

KDO 的 `60_feedback` → `30_wiki` 管线也应该有这个机制：每发现一个问题就加一条门禁规则，而不是等"大版本升级"。
