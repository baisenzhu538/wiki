# 千惠供应链复盘：6个月合作失控的70/30责任拆解

> 一句话：千惠合作6个月，交期延期超2个月、品质失控、层层转包。复盘结论：70%责任在自己——选型未做尽调、合同不严谨、过程监控不到位。换一家供应商，大多数问题还会重演。

---

## 案例速览

| 维度 | 内容 |
|:---|:---|
| 合作方 | 千惠（供应链/制造） |
| 周期 | 2026年2月-8月（6个月） |
| 总判断 | **失败**——交期+品质双重失控 |
| 根因 | 自身管理能力缺失（70%）+ 千惠执行问题（30%） |
| 结果 | 降级合作（只做钣金）+四阶段管理办法+15条踩坑案例库 |

---

## 完整过程

### 选型：把口碑当事实

袁总介绍千惠——"说有开发能力、发泡工艺稀缺、离得近"（口述）。基于这些信息选择了千惠，但**没有做任何对比验证**——没查征信（后发现20+涉诉）、没看实际生产现场、没问其他客户评价。

> 选型阶段，把"袁总说他有能力"当成了已验证的事实。

### 合同：订单合同替代正式协议

没有签正式合作协议——用订单合同替代。没有技术附件（设备参数/验收标准/交期条款均未写入合同）。4月17日打款后，缺少对千惠的法律约束。

### 过程：失控的6个月

| 时间 | 事件 | 信号 |
|:---|:---|:---|
| 3月 | 讨论硬件人员放千惠——社保/工资归属未定，后搁置 | 人员管理边界不清 |
| 4月 | 协议3次变更——通讯协议从V1.0→转换板→推翻 | 技术方案失控 |
| 5-6月 | 邓总→转接板→尚合——层层转包，甲方不知道真正干活的是谁 | 转包链 |
| 7月 | 陆工摸鱼、客户看机方案没做完——6个风险信号全部亮起 | 全面爆发 |

### 转折：7月全面爆发→复盘

原定6月1日出样机，8月7日料未到齐（延期超2个月）。7月客户来看机时方案没做完——这是最后通牒。团队复盘会（Part 0-6完整走一遍），产出70/30责任拆解+三件套。

### 结果：降级决策+体系产出

- go/no-go：**降级合作**（只做钣金单一工序）
- 四阶段供应商管理办法（选型→签约→执行→退出，27条）
- 15条踩坑案例库（每条挂对应的管理办法条款）

## 70/30 责任拆解框架

| 归属 | 占比 | 内容 |
|:---|:---|:---|
| **自身** | **70%** | |
| 选型未做尽调 | 30% | 最主要原因——未查征信/生产能力/其他客户评价 |
| 合同不严谨 | 10% | 订单合同替代协议，无技术附件 |
| 过程监控不到位 | 10% | 有跟进但未落到纸面——无工作日志/节点验收 |
| 包容过度 | ~15% | 有当时现实考量，但包容不能以项目失控为代价 |
| 内部沟通 | 5% | 被放大——提不满的人未接触一线 |
| **千惠** | **30%** | 收钱未保质保量/层层转包/隐瞒实情/人员失控 |

---

## 可迁移工具（5个）

### 1. 70/30 责任拆解框架

复盘后先做责任拆解——不是找"谁错了"，是量化"自己占多少"。把自己能控制的70%搞定，再谈对方30%。

### 2. 供应商画像共识会机制

合作前所有相关人员共同评估供应商——资质/能力/风险。不再一个人拍板。共识会产出"供应商画像"——减少后期内部"我当时就觉得不靠谱"的马后炮。

### 3. 技术疑虑举证机制

"我觉得不行"→不算数。提出技术疑虑的人必须给出具体事实——"哪个方案有问题？具体在哪里？有什么事实依据？"

### 4. 研发与生产分开原则

研发核心自己控，生产可以外包。千惠的核心问题是让供应商同时负责研发+生产——两件事的管控难度完全不同。

### 5. 风险信号六条清单

| 信号 | 说明 |
|:---|:---|
| 协议频繁变更 | >2次=技术方案未稳定 |
| 人员更换 | 干活的人在换=管理失控 |
| 追问回避 | 关键问题对方不正面回答 |
| 征信异常 | 涉诉/失信 |
| 转包链 | 不知道真正干活的是谁 |
| 节点延期 | 单次延期可原谅，连续延期=系统性失控 |

## 教训

1. **"把口碑当事实"是选型阶段最常见的错误**——供应商说"我能做"≠他真的能做。唯一的验证方式：看现场+查征信+问其他客户
2. **L5测试是复盘的转折点**——"换一家还会重演吗？"让团队从"甩锅给千惠"变成"我们需要建供应商管理能力"
3. **合同不严谨=给合作方"免费选项"**——没有技术附件和验收标准，对方可以无限延期而不承担违约成本

## 可迁移场景

| 场景 | 迁移 |
|:---|:---|
| 新供应商选型 | 用70/30框架做前置归因——"如果合作失败，可能是我哪里没做好？" |
| 合作出现裂痕 | 先用六条信号清单诊断——亮了几条？ |
| 复盘其他外包项目 | 用L5测试判断是"换人"还是"建能力" |

## 失败模式

| 失败模式 | 症状 | 修复 |
|:---|:---|:---|
| 表演识别失败 | "他说他能做"→信了，没验证 | 选型时强制：看现场+查征信+问其他客户 |
| 合同缺失 | 订单合同替代正式协议→无法律约束 | 签正式合同+技术附件（参数/验收/交期） |
| 过程失控 | 不知道干活的是谁、不知道进度 | 建工作日志+定期节点验收 |
| 信息管道断裂 | 一线人员发现问题但没传到决策层 | 建"问题升级"机制——任何红旗直接上报 |
| 资产沉睡 | 复盘出了规范但放在文件夹里没用 | 下次选供应商时强制走规范流程 |

## Critique

### 内部局限
- 复盘发生在合作基本失败后——复盘结论的"先见之明"可能有事后偏差。如果合作早期就做复盘，70/30的比例可能不同
- 供应商管理办法（轻量版 v1.1）是复盘的直接产出但尚未经过第二次实战验证——标注"待验证草案"

### 外部攻击者
**管理学家视角**："70%责任在自己"是复盘的进步，但小团队管理供应商有天然的规模边界——你不能用大公司的供应商管理体系要求3个人的团队。有些"管理缺失"不是能力问题，是规模问题。

**回应**：规模小≠可以不管理。选型时查征信（10分钟）、签合同时加技术附件（1小时）、过程中建工作日志（每周10分钟）——这些不是大公司专属，是小团队的基本功。
