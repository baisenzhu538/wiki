# 雍博具身智能工业分拣：Demo 好看产线翻车，4 个下层 Feature 缺失而非大模型不够强

> 一句话：雍博把 Feature 思维平移到具身智能行业——工业分拣「展台Demo成功率很高；部署真实工厂，连续跑1小时就大量失败」（L1767）的根因不是大模型不够强、不是硬件不够贵，而是 4 个下层原子 Feature 缺失（真实工况示教样本/动作后状态校验/多轮评测标准/物体物理属性库）；逐个补 Feature 做对照实验后产线指标达标，硬件一分没换（推演案例，L1763-L1797）。

---

## 过程（起点→尝试→失败→转折→结果）

### 起点：具身智能行业的「经验派」困局

雍博观察到的行业现状：绝大多数 Demo 团队是「传统经验派」——「换一个大模型底座试试」「换灵巧手硬件」「别人展台能跑，我们照搬方案」「调调提示词，多测几遍看运气」（L1717）。痛点是分不清到底是意图理解、案例样本、行业数据、工作流、评测标准、硬件执行哪一环出问题，**失败之后找不到根因，Demo 好看，真实产线跑不通**（L1717）。

Feature 派的替代范式：提出可证伪假设——本次工业分拣任务失败，是缺少六大类原子 Feature 中的某一个或多个（L1721）。核心逻辑：**Feature 越小，测试成本越低、迭代越快；下层 Feature 没补齐，不要过早调用上层 Agent 大能力**（L1723）。

### 尝试：六大类原子 Feature 清单（行业卡点→Feature 映射）

雍博把具身智能落地的六大卡点逐类拆成最小原子 Feature（L1725-L1753）：

| 类别 | 关键原子 Feature | 行号 |
|:--|:--|:--|
| 1 最终意图（业务层） | 客户真实业务目标结构化（不是「机器人分拣」，而是 8 小时产线、分拣成功率 ≥98%、单次故障停机 <3min）；区分「演示意图」vs「商用生产意图」（Demo 允许偶发失败，产线零容忍）；风险边界（什么情况必须停机人工介入） | L1729-L1731 |
| 2 Few-Shot/示教案例（样本层） | 同工况成功执行轨迹样本库（20-100 条真机示教）；失败案例样本库（打滑/定位偏移/形变全留存）；仿真合成样本（Sim2Real 补长尾工况） | L1733-L1735 |
| 3 专业案例&知识库（行业知识层） | 行业工艺约束库（螺丝力矩/抓取力度阈值）；物体物理属性库（材质/重量/形变/反光）；环境扰动案例（灯光变化/物料无序） | L1739-L1741 |
| 4 数据源（数据输入层） | 真机多模态数据流（视觉/力控/雷达/传感器时序）；数据清洗（过滤展台「甜点环境」数据，只留真实工厂噪声数据）；数据闭环（每次失败自动归档传感器记录） | L1743-L1745 |
| 5 工作流确定性（Workflow 层） | 原子动作库（抓取-移动-放置-复位）；状态校验节点（每步动作后强制校验物理世界状态）；异常分支（打滑/漏抓预设处理）；执行截断（Agent 每 N 步重新观测再规划，不无限推演） | L1747-L1749 |
| 6 评测标准（度量层，最易被忽略） | 多轮重复测试（同任务 ≥10 次真机重复取平均，不以单次成功为准）；双指标（完成率+过程进度分）；故障根因打标（每次失败归类到对应缺失 Feature） | L1751-L1753 |

**行业量化锚点（雍博引用，待独立核实）**：零样本 Zero-shot 在工业真实产线成功率仅 **30-65%**；叠加 **20 条真机 Few-shot 示教**可拉升至 **70-80%**——没有这个 Feature，再强 VLA 大模型也很难商用落地（L1737）。

### 失败：完整推演案例——电子产线分拣的翻车现场

业务背景：客户需求机器人完成壳体分拣上料。**展台 Demo 成功率很高；部署真实工厂，连续跑 1 小时就大量失败**（L1767）。经验派的排查方式：换更大参数 VLA 大模型、换更贵灵巧手、反复现场调试，不知道问题根源（L1771）。

罗列的失效现象（L1775）：光照波动就失败；软壳体容易打滑；失败之后机器人继续向下执行不会回退；没有统一统计失败率。

### 转折：四条可证伪假设 + 逐个补 Feature 的对照实验

Feature 派把现象转成四条假设（L1777-L1783）：

- 假设 A：缺【Few-shot 真实产线示教样本】——只用了展厅理想环境样本
- 假设 B：缺【工作流-动作后状态校验】——抓取打滑后没有检测，直接执行下一步
- 假设 C：缺【评测标准】——只用单次成功判定可用，没有多轮重复测试
- 假设 D：缺【物体物理属性知识库】——没有录入软壳体摩擦力、力度阈值

逐个增加 Feature 做对照实验，每加一个观测指标变化（L1785-L1793）：

| 补充的 Feature | 观测到的变化 |
|:--|:--|
| 25 组工厂真实工况 Few-shot 示教案例 | 成功率小幅提升 |
| 抓取后力控状态校验（打滑立刻触发重试分支） | 故障率**大幅下降** |
| 壳体材质物理属性知识库 | 进一步降低抓取失效 |
| 多轮评测（每轮跑 20 次统计平均成功率） | 排除偶然成功 |

### 结果：不是大模型不够强，是 4 个下层 Feature 缺失

复盘结论：**不需要升级硬件，补齐原子 Feature 之后产线指标达标**（L1795）。核心启示：很多具身智能项目把预算全部砸在上层 Agent 大模型，地基 Feature 大片缺失，最终只能停留在演示 Demo 阶段（L1797）。

分层重构原则（L1755-L1761）：地基层（VLA 模型/感知/运动控制）→ 工作流层（确定性约束框架，**商用落地主力层**）→ Agent 层（仅在工作流框架约束内启用，Agent 只做规划，执行交给下层确定工作流）。「生产场景害怕 Agent 无边界自主决策带来幻觉事故，用确定性工作流框定 Agent 行为边界」（L1749）。

团队切换 Feature 思维后的四象限变化（L1799-L1815）：事情×短期（失败可定位到具体 Feature，不再笼统「AI 不行硬件不行」）；事情×长期（沉淀 100 个标准化 Feature 武器库，换场景只替换行业知识库/示教样本，「借假修真」——场景是假，Feature 原子才是真价值，L1761）；人×短期（业务/产品/工程用统一 Feature 语言沟通，「业务人员看得懂缺哪一张牌」）；人×长期（从「碰运气调 Demo」进化为假设实验文化）。

## Critique

**内部局限（自指）**：全文是**行业拆解文+思想实验**，不是亲历项目复盘——电子产线分拣案例是「完整推演」（L1763 自述），对照实验的指标变化（「小幅提升」「大幅下降」）没有真实测量数据。30-65%/70-80% 两个关键量化数字是转引，雍博未注明原始出处。

**外部攻击者 1（Kahneman 式——叙事谬误）**：「不是大模型不够强，是 4 个 Feature 缺失」是一个过度整齐的归因——推演案例里作者先设计了 4 个假设，再让实验「验证」这 4 个假设，循环论证。真实产线的失败往往是多因素耦合（机械磨损/标定漂移/来料变异），归因到 4 个 Feature 可能系统性低估硬件和工艺因素——而这恰恰是「经验派」会强调的。

**外部攻击者 2（Taleb 式——领域专家反方）**：具身智能的工程现实比 Feature 清单残酷——Sim2Real 鸿沟、长尾工况分布、硬件一致性退化，都不是「补一张牌」能解决的。雍博自己也承认零样本只有 30-65%（L1737），这意味着即便 20 条示教到 70-80%，距离产线要求的 98%+（L1731 自己定的目标）仍有量级差距。Feature 清单是好的诊断语言，但补齐 Feature 就达标的结论超出证据。

**外部对标（2026-09-08 WebSearch，实证）**：学界数据方向与雍博一致但更谨慎——[VITAL（arXiv 2407.21244）](https://arxiv.org/html/2407.21244v2) 的 few-shot 模仿学习+人类在环校正，堆叠任务仿真 84% 而真实世界仅 60%，印证「仿真/Demo 到真实产线的落差」；[EmbodiSwap（arXiv 2510.03706）](https://arxiv.org/abs/2510.03706) 等 2025 年工作仍在攻关零样本迁移，说明「零样本难」是学界未解问题而非单纯工程 Feature 缺口。雍博的 30-65%/70-80% 区间与公开文献量级吻合，但精确数字应以具体任务基准为准。

## Synthesis

本卡是 Feature 思维**跨域迁移压力测试**的样本：软件侧（文本生成）的 Feature 思维迁移到物理世界（具身智能）时，概念结构完全成立（原子化/可证伪/分层叠加），但验证成本剧增——软件侧补一个 Feature 是改一行提示词，硬件侧补一个 Feature 是采 25 组真机示教。这与 Live258 族内其他案例形成对照：黄华春/jeffgirl 的 Feature 迭代以「天」计，雍博的 Feature 迭代以「产线停机小时」计。共同机制仍是 [[dk-demand-feature-stacking]] 的维度覆盖——六大类 Feature（意图/样本/知识/数据/工作流/评测）是六个正交维度，缺任何一维都会系统性失效；而 [[dk-ai-does-not-question-your-mistake]] 在物理世界的版本更残酷：软件 AI 扩散错误数字，机器人 AI 扩散的是物理动作失败——「失败之后机器人继续向下执行，不会回退」（L1775）正是「AI 不质疑」在 embodied 场景的形态，对治同样是确定性校验节点（状态校验 Feature）。

## Action Triggers

1. 具身智能/硬科技项目立项前，先用六大类 Feature 清单做缺口审计——把「买多大的模型/多贵的硬件」问题转成「缺哪几张牌」问题
2. 区分「演示意图」与「商用生产意图」并写进验收标准：≥10 次真机重复、取平均成功率、故障根因打标到具体 Feature
3. 失败案例样本库与成功案例同等建设——打滑/偏移/形变全部留存并归档对应传感器记录
4. Agent 上产线前先过工作流确定性三件套：原子动作库+状态校验节点+执行截断（每 N 步重观测）

## 失败模式

| 失败模式 | 症状 | 修复 |
|:--|:--|:--|
| Demo 成功即宣布可用 | 「跑成 1 次就对外宣传成功」（L1753） | 强制多轮重复测试（≥10 次取平均）+过程进度分双指标 |
| 失败就换模型/换硬件 | 「换大模型底座试试」「换灵巧手」（L1717），换完仍失败且不知根因 | 先列 Feature 假设清单，逐个对照实验，换硬件是最后手段 |
| 用展厅「甜点数据」训练 | 展台成功率高、工厂噪声环境立刻崩（L1745） | 数据清洗 Feature：过滤甜点环境数据，只保留真实工厂噪声数据 |
| Agent 无边界自主决策上产线 | 幻觉动作引发物理事故（L1749） | 确定性工作流框定 Agent 边界：Agent 只规划，执行交给下层工作流 |
| 把推演当实证汇报 | 思想实验的「故障率大幅下降」写成已验证结论 | 报告标注证据状态（推演/实测），关键数字补原始出处 |
