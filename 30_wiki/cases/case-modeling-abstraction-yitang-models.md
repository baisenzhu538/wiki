# 抽象建模案例：一堂内部模型武器库与跨领域商业模型地图

> 来源：Truman-高阶建模-抽象建模-案例-图-01 | 一堂建模能力培训（Truman），`src_20260614_87b29a61`、`src_20260614_8269ccdb`

## Background

一堂在多年业务实践中，各团队（增长、教研、交付、培训）分别沉淀了大量解决具体问题的工具、清单和框架。但这些模型长期散落在不同业务线：增长团队有自己的 KOL 投放分级方法，教研团队有自己的做课流程，交付团队有自己的脚本设计标准，培训团队有自己的表达模型。

问题不在于没有模型，而在于：

- 各业务线不知道彼此已经做过什么，导致重复造轮子；
- 新员工和外部合作方找不到现成模型，每次从零开始；
- 一些模型只停留在 PPT 或老员工脑中，没有边界和使用说明，容易被误用。

## What Happened

Truman 带领团队对一堂内部模型资产做了一次抽象归纳，把模型分为"内部运营模型"和"跨领域商业模型"两类，并在建模培训中展示了成果。

### 内部运营模型（5 个）

| 模型 | 来源团队 | 解决的真实问题 | 模型形态 |
|:-----|:---------|:---------------|:---------|
| SABC 分级模型 | 增长团队 | 公众号 KOL 投放体系如何分级管理 | 分级/段位图 |
| 六步做课法 | 教研团队 | "做课不回退"——课程研发反复返工 | N 步法/里程碑 |
| 5 维度案主筛选模型 | 教研团队 | "搞砸案例筛选"——案例质量不稳定 | 多维度评估 |
| 任务评价雷达图 | 交付团队 | "极限挑战"脚本设计缺乏评价标准 | 雷达图 |
| ABACC 讲香模型 | 培训团队 | 员工讲不清楚课程价值 | 结构化表达模型 |

### 跨领域商业模型（10 个）

| 模型 | 围绕的核心问题 | 模型形态 |
|:-----|:---------------|:---------|
| 一堂五步法 | 商业成败 | 流程/画布 |
| Y 模型 | 科学做事思维 | 三角/决策框架 |
| 双环图 | 时间管理工具实用性 | 双环/循环图 |
| 4 个本质要素 | 战略定义 | 本质提炼 |
| 拆解 MVP 策略集 | 低成本创业 | 武器库/清单 |
| 动力阻力触点工具箱 | 转化率背后的因果规律 | 工具箱 |
| 新人 landing 冰山图 | 新人 landing | 冰山图 |
| 科学开会的十大原则 | 科学开会 | 花瓣图/清单 |
| IPO 模型 | 学习的本质 | 底层模型 |
| 科学表达火箭图 | 科学表达 | 火箭图 |

### 抽象归纳的方法

这次归纳不是简单罗列，而是做了三步抽象：

1. **按问题域归类**：把"解决什么类型问题"作为第一分类维度，而非按部门或项目；
2. **按模型形态分层**：同一形态（如雷达图、N 步法、冰山图）的模型可以共用使用规范；
3. **区分内部运营与跨领域复用**：内部运营模型解决特定业务问题，跨领域模型可以迁移到外部客户或新课程设计。

## 结果

- 一堂把散落在各团队的模型资产显性化，形成了"内部模型武器库"的雏形；
- 模型从"部门私有"变成"组织可发现"，减少了重复建设；
- 跨领域模型成为一堂对外输出课程和产品的方法论基础；
- 这次抽象归纳与后续"AI 扫描三四百个模型资产并归集到二三十个范式"（见 [[case-yitang-model-asset-inventory]]）形成连续动作：先用人工归纳建立分类框架，再用 AI 大规模盘点验证。

## 可迁移

### 可迁移场景 / 适用边界

| 场景 | 说明 |
|:-----|:------|
| ✅ 组织已有 10+ 个散落模型，需要统一发现 | 先做模型形态分类，再建立武器库索引 |
| ✅ 新业务线需要快速复用已有方法论 | 通过问题域索引找到相关模型，避免从零开始 |
| ✅ 培训课程/咨询产品需要方法论输出 | 把内部运营模型升级为跨领域可迁移模型 |
| ✅ 引入 AI 做资产盘点前 | 先人工归纳分类框架，否则 AI 会按关键词乱聚类 |
| ❌ 组织模型数量少于 5 个 | 样本不足，抽象归纳价值有限，先鼓励一线沉淀 |
| ❌ 模型都没有经过真实场景验证 | 抽象未经验证的模型会放大错误，先验证再归纳 |

## 失败模式

| 失败模式 | 真实症状 | 可执行修复 |
|:---------|:---------|:-----------|
| **为建模型而建模型** | 模型/清单失效或无法落地，团队抱怨"又多了一个形式" | 回到源头重新界定边界与证据标准：这个模型解决什么具体问题？什么情况下不适用？ |
| **把多个场景硬塞进一个模型** | 模型边界模糊，使用者不知道何时用、何时不用 | 拆分模型或明确边界条件，给每个模型配一个"不适用场景"列表 |
| **模型只停留在 PPT，没有配套 checklist 和案例** | 新人拿到模型不会用，老员工凭感觉用 | 每个模型补全：使用步骤、检查清单、1 个正面案例、1 个反面案例 |
| **抽象层级过高，失去业务触感** | 模型看着很高级，但一线业务人员觉得"不接地气" | 每个抽象模型必须能往下推两层：L1 框架词 → L2 问题定义 → L3 检查清单/动作 |
| **把内部运营模型直接当跨领域产品卖** | 外部客户反馈"你们的方法论不适合我们" | 补充客户场景验证，把内部假设替换为外部可验证假设，必要时重命名模型 |

## 落地模板：模型资产抽象归纳 SOP

在启动组织级模型资产盘点前，按以下 SOP 执行：

### 第一步：收集（1-2 周）

- [ ] 列出各业务线已使用的模型/框架/清单/SOP 名称
- [ ] 收集每个模型的原始出处（谁创建、为什么创建、解决什么问题）
- [ ] 标记每个模型是否经过真实场景验证

### 第二步：分类（3-5 天）

- [ ] 按模型形态分类：清单/SOP、N 步法、雷达图、象限/矩阵、冰山图、三角图、火箭图、画布、武器库
- [ ] 按问题域分类：增长、教研、交付、管理、决策、学习、表达等
- [ ] 区分内部运营模型 vs 跨领域可迁移模型

### 第三步：抽象（1 周）

- [ ] 对同一形态的模型，提炼共用使用规范
- [ ] 对可迁移的模型，补全适用边界和失败模式
- [ ] 给每个模型写一句话"burns line"：这个模型解决什么问题

### 第四步：建立武器库索引

| 字段 | 填写要求 |
|:-----|:---------|
| 模型名称 | 统一命名，避免同模型多名 |
| 模型形态 | 从形态分类表中选择 |
| 适用问题 | 一句话描述解决什么问题 |
| 边界条件 | 至少 2 条不适用场景 |
| 使用 checklist | 3-5 个关键检查项 |
| 案例 | 1 个内部使用案例 |
| 相关模型 | 链接到同形态或同问题域模型 |

### 第五步：验证与迭代（持续）

- [ ] 让 3-5 个新员工或外部合作方试用武器库索引
- [ ] 收集"找不到""不会用""用了没效果"三类反馈
- [ ] 每月更新一次模型边界和案例库
