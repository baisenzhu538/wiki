# 案例：广冷电子 HX-SMJ 红外光栅项目

> 一个典型的"前人遗留硬件项目"——原理图/PCB/BOM/固件散落在多台电脑和微信聊天记录里。请外援整理后，从文件混乱到可投产基线。这个案例直接催生了 KDO 电子工程项目的八条规则和四张 dk-ef 卡。

## 场景

广冷电子 HX-SMJ 是闸机红外光栅控制系统，含四块板卡：主控板（MCU+外围）、红外主控板 A（发射端）、红外从控板 B（接收端）、继电器板（输出控制）。前工程师离职后，全套资料散落在多台电脑——文件命名混乱（"最终版""真的最终版"）、版本关系不明、原理图和 PCB 多处不一致。

## 四要素验证

### Before-After

| | Before | After |
|:---|:---|:---|
| 文件组织 | 散落多台电脑，命名混乱 | 四板卡五类归档（BOM/Gerber/坐标/原理图/固件） |
| 版本关系 | 不知道哪个版本是"对"的 | 版本锁表 + 文件名含版本号+日期 |
| 文档一致性 | 原理图和 PCM 多处不对应（MCU型号/芯片位号） | 8 项核对问题分级列出 + 核对方法 |
| 可投产性 | 不敢下单生产 | 继电器板 5 星可投产，其余板卡核对后可投产 |

### 真实锚点

真实项目。四块板卡是已经在闸机上跑过的硬件。不是"假设有一个硬件项目"——是真有 BOM、真有 Gerber、真有固件 hex。

### 受益人

- **黄药师**：从"看不懂前人资料"到"能判断哪个文件可投产"
- **下一个接手的工程师**：五分钟看懂项目（READEME 版本锁表），两小时理解设计细节，动手前烧诊断固件确认硬件状态
- **KDO**：四张 dk-ef 卡 + 八条规则全部来自这个项目的真实踩坑

### 可解性

因果链清晰——文件混乱的根源是 E-FM-002（BOM 多版本不同步）+ E-FM-003（手焊板隐性修改未记录）。解决方案不是"雇外援整理"——是项目启动时就按五类归档 + 版本锁表来管理。

## 核心设计洞察

外援的交叉验证方法可以概括为"L1→L2→L3→L4→L5"五层检查：

| 层 | 做什么 | 耗时 | 价值 |
|:--:|:---|:--:|:---|
| L1 | 文件完整性检查 | 10分钟 | 确认有没有丢文件 |
| L2 | 跨文档一致性 | 30分钟/板 | 找"哪里不一样" |
| L3 | 根因推断 | 每个不一致5分钟 | **从"哪里不一样"到"哪个是对的"** |
| L4 | 问题分级 | 全部汇总 | 告诉工程师精力该花在哪 |
| L5 | dk 卡对照 | 5分钟 | 看已知失败模式是否复现 |

**L3 是最容易被跳过的，也是最关键的。** 外援报告里 L1-L2 做得好，L3 做得不够——他只标了"不一致"，没推物理后果。工程师拿报告能知道"查什么"，但不能直接知道"问题在哪"。

## 可迁移场景

1. **任何"前人留下的硬件项目"**：直接套用五类归档 + 版本锁表 + 交叉验证检查单
2. **新启动的硬件项目**：第一天上五类归档目录结构 + 文件命名规则，不需要事后整理
3. **多人交接的任意技术项目**：版本锁表 + README 一分钟看懂——不只是硬件

## 反例

**什么时候不应该学这个案例**：
- 项目只有一块板卡、一个人维护、文件不超过 10 个——五类归档是过度工程
- 项目还在原型探索阶段，硬件设计每周大改——这时锁版本是浪费时间

## 经验教训

1. **外援能做到 L1-L2，做不到 L3。** 文档对比是手工活，可以外包。根因推断需要领域知识——这恰好是 dk-ef 卡的价值。下一个硬件项目来的时候，拿着 dk-ef-001~004 直接对照——不需要从头猜
2. **文件整理机会只有一次。** 项目刚接手时文件最全（分散但还在）。越拖越丢——微信聊天记录被清、旧电脑被格、当事人忘记细节。收网要快
3. **E-FM-002 和 E-FM-003 是同一个根因的两个表现。** BOM 版本不同步和手焊板隐性修改——本质都是"改了什么没记录"。统一的解决方案是规则七：**每次改版，版本号+日期+README 更新，三者缺一不可**
