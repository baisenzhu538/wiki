# 案例：广冷电子 HX-SMJ 红外光栅项目——从文件混乱到可投产基线

## 一句话摘要

广冷电子 HX-SMJ 红外光栅项目在前工程师离职后，原理图/PCB/BOM/固件散落、命名混乱、版本关系不清；通过四板卡五类归档、版本锁表与 L1–L5 交叉验证，最终形成可投产基线，并催生出 KDO 电子工程八条规则与四张 dk-ef 卡。

## 背景

HX-SMJ 是闸机红外光栅控制系统，包含四块板卡：主控板（MCU+外围）、红外主控板 A（发射端）、红外从控板 B（接收端）、继电器板（输出控制）。前工程师离职后，全套资料散落在多台电脑与微信聊天记录中，文件名充斥"最终版""真的最终版"等无法区分的命名；原理图、PCB、BOM 之间存在多处不一致，团队不敢下单生产。

## 关键事件/决策点

1. **资料归集与五类归档**：将四板卡资料按 BOM/Gerber/坐标/原理图/固件五类目录归档，建立统一入口。
2. **版本锁表**：建立版本锁表，文件名强制包含版本号与日期，明确"哪个版本是对的"。
3. **L1–L5 交叉验证**：引入 L1 文件完整性 → L2 跨文档一致性 → L3 根因推断 → L4 问题分级 → L5 dk 卡对照 的五层检查。
4. **问题分级与可投产判定**：8 项核对问题按影响分级，继电器板评为 5 星可投产，其余板卡核对后也可投产。
5. **规则沉淀**：将整理与验证方法固化为 KDO 电子工程规则七（五类归档目录结构）、规则八（交叉验证检查单），并产出 dk-ef-001~004。

## 结果

| 维度 | Before | After |
|:---|:---|:---|
| 文件组织 | 散落多台电脑，命名混乱 | 四板卡五类归档（BOM/Gerber/坐标/原理图/固件） |
| 版本关系 | 不知道哪个版本是"对"的 | 版本锁表 + 文件名含版本号+日期 |
| 文档一致性 | 原理图和 PCB 多处不对应（MCU 型号/芯片位号） | 8 项核对问题分级列出 + 核对方法 |
| 可投产性 | 不敢下单生产 | 继电器板 5 星可投产，其余板卡核对后可投产 |

真实锚点：四块板卡是已经在闸机上跑过的硬件，确有 BOM、Gerber 与固件 hex，不是假设项目。

## 可迁移模式

1. **任何"前人留下的硬件项目"**：直接套用五类归档 + 版本锁表 + 交叉验证检查单。
2. **新启动的硬件项目**：第一天上五类归档目录结构 + 文件命名规则，避免事后整理。
3. **多人交接的任意技术项目**：版本锁表 + README 一分钟看懂，不只适用于硬件。

## 失败模式/教训

| 失败模式 | 表现 | 避免方法 |
|:---|:---|:---|
| 外包只做 L1–L2，跳过 L3 | 报告只列出"哪里不一样"，不做根因推断 | 用 dk-ef 卡对照，由有领域知识的人完成 L3 |
| 改版不更新版本号与 README | BOM/PCB/原理图逐渐 diverge | 每次改版同步更新版本号+日期+README |
| 拖延整理 | 微信记录清空、旧电脑被格、细节遗失 | 接手后 48 小时内完成文件归集与锁表 |
| 把"前人留下"当不可解 | 直接推倒重来或不敢投产 | 先做 L1–L2 完整性+一致性检查，再分级决策 |

核心教训：
1. 文档对比可以外包，根因推断需要领域知识——这正是 dk-ef 卡的价值。
2. 文件整理的机会窗口很短，越拖越丢。
3. 可投产性不是"完美"，而是"不一致已识别、风险已分级、决策有依据"。
