# 知识库错误自暴露 — 检测半径全域覆盖，修复半径靶向

> **核心定位**：知识库的谬误不会自己消失——它们只会积累。问题不是"要不要全域检测"，而是"能不能在不触发全量重跑的前提下，让每一条错误自己暴露出来"。

---

## 一、问题定位：被动维修模型的陷阱

当前知识库的错误修复模式是**被动维修**：

```
用户/Agent 在某个知识点上发现问题 → 报告 → 定位根因 → 修复 → 结束
```

这等价于软件工程里的"用户报 bug 才修"。它的致命缺陷：

| 阶段 | 问题 |
|:----:|:----|
| **积累期** | 概念 A 的微小偏差无人发现，被后续 3-5 张卡片引用后放大 |
| **暴露期** | 用户遇到概念 Z 时发现不对，但根因在十步之前的概念 A |
| **修复期** | 修 A 不够——引用 A 的 B/C/D 需要追溯性修复，工作量大增 |
| **复发期** | 没有机制阻止同样偏差再次进入系统 |

这跟代码的技术债没有本质区别。**知识库的腐败是无声的**——不报错、不崩溃、不告诉你哪里不对。它只是让读到错误知识的人做出错误的判断。

### 为什么不能等人喊

三年前的知识库里有一个错误概念 → 它被嵌入 5 张卡片 → 被 2 篇文章引用 → 被 1 个外部交付物使用 → 一年后被发现 → 修复成本是原始写错的 20 倍。

越早暴露错误，修复成本越低。等人喊是最晚的暴露时机。

---

## 二、核心洞察：两种半径的分离

错误自暴露的核心洞察只有一句话：

> **检测半径全域覆盖，修复半径保持靶向。**

这来自软件工程中增量编译的启发：

| 类比 | 代码领域 | 知识库领域 |
|:----|:---------|:-----------|
| **不增量** | 每次改一个文件 → 强制重新链接整个项目 | 每次新输入 → 触发全库重跑 |
| **不等待** | 等人报告类型错误 | 等人发现概念矛盾 |
| **正确** | 增量类型检查 → 只重新编译受影响模块 | **矛盾检测全域扫 → 只重跑受影响引用链** |

### 两个半径的具体含义

| 半径 | 做什么 | 成本 | 频次 |
|:----:|:-------|:----:|:----:|
| **检测半径（全域）** | 每次新输入/新判断产生时，扫描全库中与之矛盾或过时的已有知识 | 一次全库语义扫描 | 每次写入后触发 |
| **修复半径（靶向）** | 只标记、只修被矛盾检测命中的那几条卡片/文章 | 极小 | 按标记数量线性 |

**关键约束**：检测不能被优化掉——它是质量门的一层。修复必须是增量的——它是效率的保障。

---

## 三、机制框架

### 三层自暴露

```
第一层：矛盾检测（新输入 → 扫描已有知识）
  每次写入一张卡/一篇文章时：
    → 提取新知识的核心断言
    → 语义匹配全库已有知识的断言
    → 输出矛盾/冲突/互补 三类关系
    → 写入卡片 frontmatter 或 独立关系记录

第二层：陈旧标记（时间衰减 → 自动降级）
  每张卡距上次更新超过阈值（如 60 天）：
    → 状态自动降级 "stable" → "needs-review"
    → 如果被其他卡引用，引用链也标记"有依赖项过时"

第三层：关联传播（一处标记 → 递归影响整个引用链）
  卡片 A 被标记为"可能过时"：
    → 所有引用了 A 的卡片 B/C/D 收到通知（不是自动改，是标记为"潜在问题"）
    → B 的作者决定是否审查
```

### 为什么不是全量重跑

全量重跑的破坏力已被证伪（见 [[dk-c8-format-complete-mind-empty]]）：规模大意味着检测频率低（不敢跑），检测频率低意味着错误积累周期长，违背了"越早暴露越好"的原则。

增量矛盾检测允许：
- **每次写入后触发** ——不是等人喊，不是等排期
- **只跑语义匹配** ——不跑全文理解，降低每次成本
- **输出是标记，不是修改** ——不擅自改任何卡，只暴露信号

### 这个框架当前缺什么

| 组件 | 状态 | 谁来建 |
|:----:|:----:|:-------|
| 矛盾检测器 | ❌ 不存在 | 黄药师（基础设施） |
| 陈旧标记规则 | ❌ 不存在 | 欧阳锋（质量标准） |
| 增量传播机制 | ❌ 不存在 | 黄药师（基础设施） |
| 标记→修复反馈闭环 | ❌ 不存在 | 老顽童+欧阳锋（流程） |

## 四、与飞轮的关系

这是对 [[kdo-flywheel]] 的补充，不是替代。

```
原飞轮：建造 → 使用 → 反思 → 实验 → 回到建造
                                        ↑
扩展后：建造 → 使用 → 自动暴露矛盾 → 反思 → 实验 → 回到建造
                            ↑
                        (新增环节)
```

**新增环节 "自动暴露矛盾" 做什么**：在使用和反思之间，加一层自动扫描。使用产生的新知识，不等人反思，先自己跟全库已有的知识撞一遍。撞出来的矛盾就是下一轮反思的燃料。

这正是你那个直觉的落地形态——**每一次新输入，全库中与它矛盾的知识都被暴露出来**。不是全库重跑，是全库扫描；不是自动修复，是自动暴露。

---

## 五、红线

1. **检测 ≠ 修改**。矛盾检测只输出标记，不修改任何卡片。擅自修改会触发 P-18 类型的批量破坏事故。
2. **不能跳过人工审查**。标记的对错需要人确认——自动检测只能降置信度，不能直接报废一张卡。
3. **全域检测不能优化成采样**。如果检测只扫 10% 的库，漏掉的 90% 里积累的错误就回到了被动维修模型。
4. **不能为性能牺牲全量**。如果检测太慢导致不敢跑，说明架构有问题——需要优化增量匹配算法，而不是缩小检测范围。
