> **核心定位**：KDO 不是静态知识库，是**每一圈产出都在提升下一圈起点的认知飞轮**。飞轮停下来的时候，KDO 就变成了一个普通的 wiki。



## 一、飞轮的结构

KDO 的每一次深度迭代都遵循同一个四拍节奏：

```
┌──────────────────────────────────────────────────────────┐
│                                                          │
│   建造（Build）          使用（Use）                      │
│  建一个工具/框架/门禁    建造者自己用它做真实产出          │
│       ↑                              ↓                   │
│   回到建造              反思（Reflect）                   │
│  用新发现驱动下一轮      在使用中发现摩擦→问为什么→挖深    │
│       ↑                              ↓                   │
│   实验（Experiment）                                      │
│   推理碰壁时跑 Pilot / A/B / Gold Standard                │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 每一拍在今天的实例

| 拍 | 实例 |
|:--:|:-----|
| **建造** | 四步编译法 + D1-D4 门禁 + 深度合成模板 |
| **使用** | 黄药师用四步编译法写"四个死刑"文章 |
| **反思** | 文章 Feedback 段留的三个问题 → 用户说"深挖" |
| **实验** | Pilot 20 张卡 → 发现 chunk_type bug + confidence 聚集 |
| **回到建造** | 飞轮基础设施提案 + Sprint 6 工单 |

## 二、飞轮转起来的条件

飞轮不是自动转的。它需要三个条件同时满足：

### 条件 1：建造者 = 使用者

建工具的人必须自己先用它做真实的事。

| 满足 | 不满足 |
|:-----|:-------|
| 黄药师建了 label 管线，自己写文章时发现四个死刑 | 建了工具→交给别人用→反馈是二手的 |
| 老顽童用深度合成产线写文章，发现写作方式和以前完全不同 | 建了产线→只用来审查别人的产出→感受不到摩擦 |

**为什么**：只有建造者本人使用时，才能感受到"设计和现实的摩擦"。二手反馈会丢失"这里我觉得不对劲"的微妙信号。

### 条件 2：反馈通道畅通

使用者的反思必须能低摩擦地变成建造者的输入。

```
Feedback 段 → 用户说"深挖" → 飞轮继续转
```

| 畅通 | 断裂 |
|:-----|:------|
| 文章末尾有 Feedback 段，问题可追溯到人 | 反馈写了没人看，或看了没人回应 |
| 用户/欧阳锋能说"不够深刻"并触发诊断 | 所有产出都是最终稿，没有迭代空间 |

**KDO 的机制**：Feedback 段、深度门禁 D1-D4、异步疑问传递机制（AGENTS.md）。

### 条件 3：摩擦力可见

每次使用都必须暴露至少一个"和预期不一样"的地方。

## 三、飞轮的停止条件

飞轮不会永远转。三个停止信号：

| # | 信号 | 示例 |
|:-:|:-----|:------|
| 1 | 下一轮需要实验数据而不是纯推理 | 推理到 Pilot 边界 → 转实验模式，实验数据回来后飞轮复活 |
| 2 | 连续两轮产出的新问题全部是"已知的未解决问题" | 边界已经摸清了 → 进入稳态 |
| 3 | ROI 递减：下一轮的深度增量 < 投入时间 | 已知的已知不需要再挖了 |

停止 ≠ 死亡。当新数据/新框架/新反馈进来时，飞轮可以重新启动。

## 四、飞轮与 KDO 其他模式的关系

| 模式 | 与飞轮的关系 |
|:-----|:-------------|
| **三步编译法** | 飞轮的"建造"产出的标准工具 |
| **四步编译法（深度合成）** | 飞轮的"建造"产出的深度工具 |
| **递归深挖法** | **飞轮在"个人脑内"的执行版本**——一个人用三反馈飞轮自我迭代 |
| **D1-D4 深度门禁** | 飞轮的"反思"环节的自动化检查点 |
| **Sprint 6 断裂点修复** | 飞轮的下一圈——把"反馈只记录不回传"这个摩擦修掉 |

## 五、可迁移性

飞轮的底层模式（建造→使用→反思→实验）不依赖 KDO 的具体实现。它可以迁移到：

| 领域 | 建造 | 使用 | 反思 | 实验 |
|:-----|:-----|:-----|:-----|:-----|
| **产品设计** | 建一个组件 | 自己用组件做页面 | 发现组件在 XX 场景不好用 | A/B 测试验证 |
| **代码审查** | 写一条 lint 规则 | 用自己的代码跑 | 发现误报/漏报 | 对比规则开关前后的 bug 率 |
| **学习方法论** | 学一个框架 | 用它分析自己的真实决策 | 发现框架的边界 | 对照别的框架做对比分析 |
| **商业策略** | 做一个市场判断 | 用这个判断做一次真实投入 | 发现前提假设错了 | 跑小规模验证实验 |

## 六、红线

1. **不能跳过"使用"**。建了不用 = 飞轮空转。没有摩擦就没有下一轮。
2. **不能跳过"反思"**。发现问题不挖 = 飞轮卡住。搬走石头不等于铺好路。
3. **不能一个人转**。需要用户（提出判断）、欧阳锋（对齐标准）、黄药师（建造工具）、老顽童（使用产出）的接力。少任何一个角色飞轮都会偏。
4. **不能用计划替代反馈**。计划告诉你做什么，反馈告诉你做错了什么、还漏了什么。飞到第三圈还按第一圈的计划走 = 方向错了。
