# 用户视角 vs 产品视角：为什么"我觉得好"不等于"用户觉得好"

> 一堂五步法：产品内核必须从用户视角定义，不是从产品视角或技术视角。

## 核心框架

| 视角 | 关注点 | 问题 | 结果 |
|:---|:---|:---|:---|
| **用户视角** | 用户的问题、痛点、体验 | "用户为什么选择我们？" | 内核清晰，转化率高 |
| **产品视角** | 功能、技术、设计 | "我们做了什么？" | 功能堆砌，内核模糊 |
| **技术视角** | 技术先进性、架构 | "我们用了什么技术？" | 技术炫但用户无感 |
| **商业视角** | 营收、成本、利润 | "我们怎么赚钱？" | 商业模式脱离用户价值 |

## 关键洞察

### 1. 用户视角的定义

用户视角不是"用户说想要什么"，而是：

- 用户现在怎么解决问题的？
- 用户现在的解决方案有什么痛点？
- 用户愿意为这个痛点付多少钱？
- 用户选择我们的真正原因是什么？

### 2. 产品视角的陷阱

| 陷阱 | 表现 | 修复 |
|:---|:---|:---|
| **功能导向** | "我们做了一个XX功能" | 用"用户的问题是..."替代 |
| **技术炫技** | "我们用了AI、大数据" | 问"技术解决了用户什么问题？" |
| **设计自嗨** | "这个设计很酷" | 问"用户觉得这个设计好用吗？" |
| **数据自欺欺人** | "我们的数据很好" | 问"用户因为数据好而选择我们吗？" |

### 3. 切换到用户视角的方法

**方法1：用户原话**
- 记录用户的原话，不加加工
- 用用户的语言描述产品价值

**方法2：用户旅程**
- 画出用户使用产品的完整旅程
- 标注每个节点的痛点和愉悦点

**方法3：用户测试**
- 观察真实用户使用产品
- 记录用户的困惑和惊喜

**方法4：用户访谈**
- 问"现在怎么解决的？"而不是"你想要什么？"
- 问"为什么选我们？"而不是"我们哪里好？"

### 4. 团队视角对齐

团队内部视角不一致时：

- **技术团队**：关注技术实现
- **设计团队**：关注用户体验
- **商业团队**：关注营收利润
- **产品团队**：需要整合为"用户视角"

对齐方法：
- 每个决策问"这个对用户有什么好处？"
- 用用户原话作为决策依据
- 定期做用户测试，让团队观察真实用户

## 失败模式

| 失败模式 | 症状 | 修复方法 |
|:---|:---|:---|
| **自我投射** | "我就是用户，我懂" | 访谈10个外部用户，寻找反例 |
| **功能导向** | "我们做了一个XX功能" | 用"用户的问题是..."开头 |
| **技术炫技** | "我们用了AI" | 问"AI解决了用户什么问题？" |
| **数据偏差** | "数据很好，所以产品好" | 区分"产品数据"和"用户价值" |
| **团队视角混乱** | 每个人对用户需求理解不同 | 建立统一的用户视角框架 |
| **忽视用户反馈** | 用户反馈不好，但认为"用户不懂" | 尊重用户反馈，寻找原因 |

## 适用边界

| 适用场景 | 不适用场景 |
|:---|:---|
| 产品内核定义 | 技术架构设计 |
| 功能优先级排序 | 内部流程优化 |
| 用户沟通 | 品牌传播策略 |
| 产品迭代决策 | 财务决策 |

## 行动触发器

- 当定义内核时 → 用用户原话描述
- 当设计功能时 → 问"用户需要这个吗？"
- 当优化体验时 → 观察真实用户
- 当团队争论时 → 回到"用户视角"
