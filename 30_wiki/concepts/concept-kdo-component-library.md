## 核心主张

KDO 工厂 41 条 pitfalls 不是孤立的错误——它们是同一类错误的重复：**依赖关系的前置节点被跳过**。每条 pitfalls 本质上记录了一个被跳过的组件。把它们反向萃取，就得到 KDO 自己的建模牌组。

每个组件是一张牌，格式：**先 X 再 Y**。五维度 × 3-4 张牌，共 17 张。

## 使用方法

面对新任务/新域，从五个维度中各抽 1-2 张最相关的牌，排列为依赖关系链：
```
[素材牌] → [边界牌] → [结构牌] → [过程牌] → [质量牌]
```
这就是你的执行方案。不是从头设计流程，是出牌拼装。

## 一、素材不确定（4 张）

> "信息还没拿全就开始下结论——这是人类最顽固的错误。" —— Truman

### 牌 1：先 OCR 再读文本

**句式**：有图 → 先跑 OCR 全部图片 → 再读文本内容
**触发信号**：新素材文件夹里有 PNG/JPG，还没跑 OCR
**跳步后果**：35 张关键框架图全部跳过→知识骨架缺失（P-7 教训）
**来源**：P-7, rules-core #10

### 牌 2：先全文扫描再选策略

**句式**：素材到达 → 先全量扫描文件数和类型分布 → 再决定消化策略（精读/粗读/VLM/OCR）
**触发信号**：发现自己在没看全文的情况下就开始判断"这个素材不重要"
**跳步后果**：250 行 Q&A 闲聊被跳过→最高价值暗知识遗漏（P-31 教训）
**来源**：P-31, wangyuyan-context.md 铁律 §2

### 牌 3：先口述稿再笔记

**句式**：有笔记也有口述稿 → 先读口述稿全文 → 再对照笔记补漏
**触发信号**：看到"笔记已经总结好了，口述稿太长先不看了"
**跳步后果**：笔记只覆盖 ~40% 内容，操作演示、暗知识、迭代细节全在口述稿里（P-31, Truman L1200-L2898 补读经历）
**来源**：P-31, wangyuyan-context.md L0 铁律 §2

### 牌 4：先扫信号词再读内容

**句式**：通读口述稿 → 先扫「我给你演示一下」「举个例子」「这是我真实的」「来我现场给你」→ 标注这些段落 → 再读全文
**触发信号**：口述稿很长，想快速跳读
**跳步后果**：Truman 摊开操作过程的段落被扫过去漏掉——那些是最值钱的东西（王语嫣 2026-07-04 教训）
**来源**：wangyuyan-context.md 硬规则

## 二、边界不确定（3 张）

> "所有的模型如果没有边界是没法建模的。" —— Truman

### 牌 5：先判归属再消化

**句式**：新素材到达 → 先判断属于哪个域/是否已有覆盖 → 再开始消化内容
**触发信号**：直接在 `00_inbox/` 里开始读文件内容
**跳步后果**：建完卡发现已有同主题卡片→重复建设→需要合并去重（C-14 教训）
**来源**：P-22, rules-core #2

### 牌 6：先查已有卡再新建

**句式**：准备建卡 → 先 `kdo cards --domain <domain>` + `kdo query "<关键词>"` → 确认没有同主题卡 → 再新建
**触发信号**：想直接写新卡，没查已有覆盖
**跳步后果**：领域外已存在类似卡片→重复→去重成本高
**来源**：laowantong-context.md 铁律 §4, rules-core #2

### 牌 7：先对标准则再建模

**句式**：发现方法论名称（如 BRM/OSCAR/FDE）→ 先 WebSearch 国际通行含义 → 确认不与已有术语冲突 → 再确定内部命名
**触发信号**：想给方法论起个缩写名字
**跳步后果**：BRM = Business Relationship Management ≠ 冉鹏的战略框架（P-28 教训：不调研就命名=浪费一个版本）
**来源**：P-28, laowantong-context.md 启动步骤 §2

## 三、结构不确定（3 张）

> "跳步是特别严重的错误。" —— Truman

### 牌 8：先定总纲再子卡

**句式**：新域建卡 → 先建 domain-digest 或总纲 framework → 再按依赖顺序建子卡
**触发信号**：在一个域里东一张西一张地建卡，没有总纲
**跳步后果**：子卡缺上游连接→后续补回链成本高（P-10 教训：不声明=不存在）
**来源**：new-domain-onboarding.md Step 6, P-10

### 牌 9：先 framework 再 concept

**句式**：域骨架 → 先建 framework 卡（呈现关系和规律）→ 再建 concept 卡（展开概念定义）→ 再建 tool/case（解压）
**触发信号**：一开始就写具体概念卡，没有框架卡定位
**跳步后果**：concept 卡孤立，看不出和其他概念的关系→松散知识而非体系
**来源**：agent-native-card-design.md 卡片三层化, C-8

### 牌 10：先骨架再填肉

**句式**：每张卡 → 先搭 section 骨架（Claims/Evidence/Critique/Synthesis/Action Triggers/Failure Modes）→ 再逐节填入具体内容
**触发信号**：卡片只有 44 行正文→半成品
**跳步后果**：「格式完整但思维空洞」卡（C-8）—— section 齐全但内容模板化
**来源**：C-8, laowantong-context.md 质量闸门 §3

## 四、过程不确定（4 张）

> "所有你埋的雷都不会消失，只会在后半段乘十倍百倍地惩罚你。" —— Truman

### 牌 11：先 dry-run 再 apply

**句式**：批量操作 → 先 dry-run 预览变更清单 → 声明影响范围 → 确认非空值不覆盖 → 再 apply
**触发信号**：想直接跑批量脚本
**跳步后果**：486 文件无从审查（P-30）/ 26 张卡 source_context 被覆盖（P-29）/ 44 张卡 frontmatter 损坏（P-29 复现）
**来源**：P-29, P-30, rules-core #3

### 牌 12：先抽样 10% 再放量

**句式**：批量修改 >50 文件 → 先改 5-10 个文件 → 全量验证（yaml.safe_load + lint + git diff）→ 再放量到全部
**触发信号**：想一次性改 100+ 文件
**跳步后果**：327+ 文件 domain/related 被批量替换为 src_unknown（P-29 复现 2026-06-28）
**来源**：P-29 复现, rules-core #3, pitfalls.md

### 牌 13：先诊断再动手

**句式**：遇到问题 → 先造诊断工具（grep/log/lint）定位根因 → 再修
**触发信号**：改了三处还不行，想继续改第四处
**跳步后果**：API 报错调参 3 小时→结果是提供商发新版（P-28）/ K2.7 发布日 Anthropic tool call 全挂（P-28）
**来源**：P-21, P-28, huangyaoshi-context.md 铁律 §1, rules-core #9

### 牌 14：先跑脚本确认再下结论

**句式**：任何报告里的数字 → 先独立跑一遍测量脚本确认 → 再写入报告
**触发信号**：想说"修复后从 X 降到 Y"
**跳步后果**：声称断链 <10→实测 359（P-15）/ 声称准确率 85%→实测 34.8%（P-17）
**来源**：P-15, P-17, huangyaoshi-context.md 铁律 §5

## 五、质量不确定（3 张）

> "我特怕把你们教错——哪怕你们学不会，也不能因为相信我被耽误。" —— Truman

### 牌 15：先自攻击再提交

**句式**：每批卡完成 → 先跑四路 Agent 自攻击（逻辑/证据/完备性/时效性）→ 修复 🔴🟡 → 再交欧阳锋
**触发信号**：pre-submit 通过就觉得可以交了
**跳步后果**：审查疲劳导致低质量卡漏过（E009/P-35）
**来源**：rules-core #4, laowantong-context.md 启动步骤 §4

### 牌 16：先 lint 再 pre-submit

**句式**：每张卡 → 先 `kdo lint` 单文件 → 修复 ERROR → 再 `kdo pre-submit` → 贴输出
**触发信号**：直接跑 pre-submit 发现一堆 ERROR
**跳步后果**：pre-submit 未跑→欧阳锋直接退回（laowantong-context.md pre-submit 门禁）
**来源**：laowantong-context.md 强制门禁, rules-core #4

### 牌 17：先逐卡清单再批量

**句式**：批量返工任务 → 先列出逐卡清单（文件名+当前缺陷+验收标准）→ 抽样复核声明"哪些被抽样、哪些未被抽样"→ 再宣布完成
**触发信号**：用"11 张 case 卡补 9 层结构"这种类型/数量描述代替逐卡清单
**跳步后果**：ROI案例01 遗漏返工→直到欧阳锋终审才发现（P-36）
**来源**：P-36, rules-core #6

## When NOT to Use

| 场景 | 原因 |
|:--|:--|
| 简单重复操作（已稳定运行 ≥10 次） | 出牌成本 > 执行成本，直接用 SOP |
| 已有成熟工作流且本次完全复用 | 不需要重新拼装，照做就行 |
| 单张卡小修（改 typo/补一个 link） | 不涉及建模决策，不需要出牌 |

## 与 Truman 18 组件对照

> 来源：口述 L2934-L3010

本卡（KDO 17 组件）是对 Truman 原 18 组件的改编。对照如下：

| Truman 维度 | KDO 维度 | 改编理由 |
|:---|:---|:---|
| 事实（客观/输入/来源优先） | 素材 | KDO 场景中"事实"= OCR/VLM/口述/笔记等原始素材 |
| 目标（出口/价值/约束优先） | 边界 | 目标+约束合并——KDO 的目标通常是"产出 N 张卡"，边界是"质量标准" |
| 方案（拆解/结构/完备/选项优先） | 结构 | 保留核心 4 张牌 |
| 过程（路径/节奏/验证/迭代优先） | 过程 | 不变 |
| 协作（角色/信息/共识/复盘优先） | 质量 | 协作的目的在 KDO 是质量保障，而非团队管理 |

KDO 新增的牌：略去；KDO 省略的牌：来源优先（信息源在 KDO 内相对单一）。

详见 `concept-truman-18-component-cards`
