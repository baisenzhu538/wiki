# Issue Tree：问题树拆解

## 核心定义

Issue Tree（问题树）是 McKinsey 将复杂商业问题逐层拆解为可独立分析的子问题的结构化工具。它的形态是一个倒立的树：树根是“核心问题”，树干是“一级子问题”，树枝是“二级子问题”，树叶是“可验证的具体假设”。

McKinsey 的标准做法：
1. **定义核心问题**：用一句话说清“我们要解决什么”，避免模糊或过度宽泛
2. **一级拆解**：将核心问题拆成 3-5 个一级子问题，每个子问题必须满足 MECE
3. **逐层下钻**：对每个需要进一步分析的子问题，继续拆成更细的二级/三级子问题
4. **叶节验证**：树的最底层叶节必须是“可以用数据或事实验证”的具体陈述，而不是更大的问题

Issue Tree 与普通“脑图”的区别在于：普通脑图只要“看起来有结构”，Issue Tree 必须**每一层都经得起 MECE 检查**，且最底层必须可验证。

## 为什么重要

大多数“分析了两周什么结论都没有”的情况，根本原因是**分析者从一开始就没有对问题做结构化拆解**。他们在同时分析“产品功能”“竞品动态”“用户反馈”“财务数据”，但这些分析之间既不独立也不完备，最后得出的是一个“拼接式的回答”——看起来什么都说了，但没有一个线性的逻辑链。

Issue Tree 解决的是三个问题：
1. **不重叠**：确保团队分工时不在做重复工作
2. **不遗漏**：确保没有重要维度被忽视
3. **可验证**：确保分析到最后一层时，每个叶节都能用数据说话

## Critique

### 外部攻击者 1：Eric Ries — “你在拆解一个假设时，已经假设了”

> **为什么应该让你睡不着**：Eric Ries（*精益创业* 作者）的核心论证是：Issue Tree 本质上是“假设驱动的”，但它隶属于“先假设再验证”，而非“先发现再理解”。当你在纸上画问题树时，你已经假设了“问题的边界在哪里”、“哪些维度是重要的”。在极度不确定的环境中（如 0→1 创业），这些假设可能 80% 都是错的。Ries 的警告：**Issue Tree 让你觉得自己在“系统性分析”，但你可能只是在系统性地编造一个错误的框架。**如果你正在用 Issue Tree 处理一个从未被定义过的市场，你的树根已经腐了。

### 外部攻击者 2：Gary Hamel — “突破性创新不能被拆解”

> **为什么应该让你睡不着**：Gary Hamel（*突破性创新* 研究者，核心竞争力理论）认为：真正的突破性创新来自于“在框架之外看到东西”——而 Issue Tree 的本质是**让你在框架之内更精致地分析**。Hamel 的论证：苹果在做 iPhone 时没有用“手机功能”的 Issue Tree 来分析——因为那会导致他们在“更好的手机”这个框架内优化，而不是发明“移动互联网设备”。**Issue Tree 是“在已知市场中做得更好”的工具，不是“发现未知市场”的工具。**如果你的目标是突破性创新，Issue Tree 可能是你最危险的敌人。

### 内部局限（Constraints）

**1. 树根假设的隐蔽性**：Issue Tree 的质量完全取决于"核心问题"的定义。如果树根问题定义错了（如"如何提高销量"而非"如何提高利润"），整个树的所有分析都是无效劳动。

**2. 深度 vs 行动力的权衡**：这是 Issue Tree 最常被误用的维度。参考以下决策矩阵：

| 树的层数 | 叶节数量(3分支/层) | 最低分析成本 | 建议场景 |
|:-------:|:-----------------:|:----------:|:---------|
| 1 层 | 3-5 个叶节 | 1-2 天 | 探索期/快速扫雷 |
| 2 层 | 9-25 个叶节 | 1 周 | 常规商业分析 |
| 3 层 | 27-125 个叶节 | 2-4 周 | 深度尽职调查 |
| ≥4 层 | 81+ 个叶节 | 2 个月+ | 学术研究/政府报告 (很少需要) |

**实战选择法则**：
- 先画 2 层树，标记每个叶节的"可验证性"
- 如果 ≥2 个红色叶节（数据不可得），不加第三层
- 任何时候不超过 3 层
- 给 CEO 汇报/0→1 创业评估：1-2 层；投资决策：2-3 层；运营问题：1-2 层

**3. 数据可得性不均衡**：树的某些叶节很容易验证（如"市场规模"有公开数据），某些几乎不可验证（如"用户心理预期"）。不对可验证性做预判，团队会把 80% 时间花在"容易分析的叶节"上。**修复方法**：画树时同步标注每个叶节的"验证难度指数"（1-5 分），优先分配时间到"对结论影响大 × 可验证"的叶节。

## 案例

### 成功案例：一堂“充分做加法”的选项池拆解

一堂的五步法中，第一步“充分做加法”本质上就是一个 Issue Tree 应用：把“如何做成这个事业”拆解为“需求层/产品层/商业模式层/增长层/壁垒层”。这个拆解的优秀之处在于：它不是随意的“我们来脑暴一下”，而是“按照创业的完整逻辑链来拆解”。每个层级的子问题都对应到一个可行动的验证动作（如“这个需求是否真实存在”“这个卖点是否被用户认可”）。

### 失败案例：咨询项目中的“假验证叶节”

某项目中，顾问把“如何提高销量”拆解为“产品优化/渠道扩展/营销推广”。在“产品优化”下面又拆出“功能增强/UI 优化/性能提升”。团队花了两周做了一个详细的产品优化方案，但最后发现——客户的核心痛点不是“产品不够好”，而是“渠道价格比竞品贵 30%”。**Issue Tree 拆解正确，但“验证优先级”判断错误**——产品优化是“好做的叶节”，但不是“最关键的叶节”。

### 边界案例：创业团队用 Issue Tree 做 0→1 产品探索

某 0→1 团队用 Issue Tree 拆解“用户为什么不付费”，拆出了一个精致的树：“价格敏感/功能不足/信任缺失/使用惯性”。但每个叶节都是假设，没有一个被验证。团队花了一周“完善树的结构”，但没有去做任何一个叶节的验证实验。结果：树越来越复杂，但真实的用户行为一点都没被触及。**这说明 Issue Tree 在“验证资源极度有限”的场景中可能是“方法论的重负”——你需要的不是更好的树，而是更快的验证。**

## Action Triggers

| 触发场景 | 第一个动作 | 成功指标 |
|---------|-----------|---------|
| 接到一个复杂问题需要分析 | 用一句话定义核心问题，然后拆成 3-5 个一级子问题 | 每个子问题都可以独立分析、不重叠、合起来覆盖核心问题 |
| 团队分工后发现有重叠 | 检查 Issue Tree 的第一层——重叠意味着分类维度错了 | 重新选择维度，确保子问题之间互不重叠 |
| 分析完成后觉得“每个都对，但整体不对” | 检查树的最底层叶节是否都已被数据验证 | ≥80% 的叶节有数据支撑，未验证的叶节明确标注为假设 |

> 核心心法：Issue Tree 的价值不在于“树有多精致”，而在于**“树叶能不能被验证”**——一个没有可验证叶节的树，只是一个精致的偶像。
