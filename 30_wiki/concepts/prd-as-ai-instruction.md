# PRD文档作为AI可执行指令

> Source: src_20260606_90b44191 (半肥猫-AI学习落地-口述，第430-448行)

## Summary

半肥猫提出的暗知识：**优质的PRD文档不仅是给人看的，更是给AI执行的**。他的实践是：写好PRD后，直接把文档作为上下文加载给AI，让AI照着做。这打破了传统PRD"只给人看"的设定。

## 进入标准

| 场景 | 信号 |
|------|------|
| 有一个反复执行的工作流程 | 每次做都要重新解释一遍，浪费token |
| 需要让团队成员执行标准流程 | 口头交代不清晰，执行结果不一致 |
| 需要AI根据标准流程自动执行 | AI每次都重新推理，结果不稳定 |

## 操作步骤

### Step 1: 写给AI的PRD结构
与传统PRD不同，写给AI的PRD需要**更多约束、更少异义**：
1. **背景**：为什么做这个事（让AI理解目的）
2. **目标**：具体要达成什么（可验证的指标）
3. **约束**：什么能做、什么不能做、什么必须遵守
4. **步骤**：1-2-3-4的执行顺序，每步的输入/输出
5. **边界**：什么时候该停止、什么时候该转交人类
6. **证据要求**：每个结论需要什么格式的支撑材料

### Step 2: 测试AI执行
1. 把PRD作为系统提示词的一部分加载给AI
2. 让AI执行一次完整流程
3. 检查结果是否符合PRD中的约束和边界
4. 如果偏离，修改PRD的约束部分，而不是用自然语言纠偏

### Step 3: 存档与复用
1. 把验证过的PRD存入知识库
2. 打上标签（业务类型、复用频率、最后使用时间）
3. 下次需要时，直接调用PRD作为上下文

## Constraints & Boundaries

### 适用边界

| 边界 | 说明 |
|:-----|:-----|
| ✅ 适合 | 有反复执行的标准化流程（每周≥2次） |
| ✅ 适合 | 流程已被人工验证过（执行过≥5次） |
| ✅ 适合 | 输出好坏可被明确判断（有量化标准） |
| ❌ 不适合 | 创意类工作（设计/文案） → 只写目标和约束，不写步骤 |
| ❌ 不适合 | 需要实时反馈的任务 → 用动态检查清单而非固定PRD |
| ❌ 不适合 | 流程本身未被验证过 → 先用人工执行3-5次验证 |
| ❌ 不适合 | 执行频率低于每月1次 → 不值得写PRD，用自然语言即可 |

### 常见失败模式

| 模式 | 症状 | 修复 |
|:-----|:-----|:-----|
| **PRD过细** | 把每个操作都写成步骤，AI变成机械执行无灵活度 | 只写约束和边界，步骤留给AI推理 |
| **PRD过松** | 只写目标不写约束，AI每次结果不同 | 增加输入格式、输出格式、禁止事项 |
| **边界缺失** | AI遇到未规定情况时自由发挥，偏离目标 | 明确写出"遇到X情况时停止并转交人类" |
| **PRD成紧身衣** | 业务变化后PRD过时，AI按旧流程执行 | 每月Review PRD，更新频率<1月则弃用 |
| **约束矛盾** | PRD中多个约束互相冲突，AI无所适从 | 用检查清单验证约束一致性，冲突时标注优先级 |
| **证据要求缺失** | AI输出无支撑材料，无法验证正确性 | 每步结论后强制要求：数据来源、置信度、备选方案 |

### 外部攻击

#### Frederick Brooks —— "没有银弹"
Brooks在《人月神话》中证明，软件工程中"没有银弹"——不存在一种技术或管理方法能让生产力提高10倍。你以为PRD可以让AI"自动执行"，但Brooks会问你：**如果一个流程真的可以被完整文档化，那它一定是一个简单到不值得用AI的流程**。复杂的、有价值的工作流程本质上就是不可完全文档化的——这正是它们有价值的原因。你用PRD给AI加紧身衣的时候，是不是在把复杂问题简化成机械流程？

#### Karl Popper —— "可证伪性的缺失"
Popper认为一个理论只有当它可以被证伪时才是科学的。PRD的问题在于：**当AI执行结果与预期不一致时，你怎么知道是PRD写得不好，还是AI理解错了？**这两者是无法区分的。你可能会不断修改PRD来适应AI的偏差，而不是发现AI本身的限制。

| 场景 | 为什么失效 | 替代方案 |
|------|--------|---------|
| 创意类工作（设计/文案） | PRD的约束会拘束创意 | 只写"目标"和"约束"，不写步骤，留给AI发挥空间 |
