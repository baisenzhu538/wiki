# 清单体故事线④：问题解决线——把混乱的诊断过程变成可追踪的思维链

## Condense

问题解决线不是"给出答案"，而是**"呈现你是怎么找到答案的"**。它的核心是把混乱的、跳跃的、直觉驱动的诊断过程，变成一条**可追踪、可验证、可复盘的思维链**。

**核心操作**：
1. **问题定义**：用一句话精确描述"现在面对的问题是什么"
2. **诊断过程**：列出你考虑过的所有可能原因（包括被否定的）
3. **排除逻辑**：每个被否定的原因，说明"为什么被排除"
4. **方案推导**：从剩余的可能中，推导出最优解
5. **验证标准**：定义"什么结果能证明这个方案是对的"

**关键原则**：
- 不隐藏死胡同：你走过但发现是死胡同的路，比正确路径更有教学价值
- 标注置信度：每个判断标注"确定/大概率/猜测"
- 暴露假设：所有方案都建立在某些假设上，假设必须被显式列出

**输出形态**：
```
- 问题：[精确描述]
- 诊断A：可能原因X → 排除原因：[证据] → 置信度：Y%
- 诊断B：可能原因Z → 验证结果：[证据] → 置信度：Y%
- 方案：[最优解]
- 假设：[方案成立的前提条件]
- 验证：[如何证明方案有效]
```

## Question

**为什么"呈现诊断过程"比"呈现答案"更有价值？** 因为答案会过时（技术变、环境变、约束条件变），但诊断过程不会过时——它训练的是"怎么思考"，而不是"想什么"。

**问题解决线和时间线的根本区别是什么？** 时间线是"发生了什么"，问题解决线是"我怎么理解发生了什么"。时间线是客观记录，问题解决线是主观认知过程的显式化。

## Critique

### 攻击者1：决策科学家——"问题解决线高估了人类的理性诊断能力"

Kahneman的《噪声》已经证明，人类专家在复杂问题上的判断充满了**系统性噪声**——同一个问题，不同时间问同一个专家，答案可能完全不同。问题解决线假设诊断过程是"理性推导"，但实际上大多数诊断是"直觉先行、理性后补"。

更危险的是：当诊断过程被显式化后，人会不自觉地"美化"自己的推理路径——把事后诸葛亮当成事前诸葛亮。问题解决线可能变成一种**"理性化包装"**，让直觉决策看起来更科学。

### 攻击者2：组织行为学家——"问题解决线在组织中会被用作甩锅工具"

当诊断过程被记录下来，它就变成了**可追溯的审计轨迹**。这意味着：如果方案失败了，"你当初为什么排除了X"会成为追责的依据。结果是，问题解决线在实际使用中可能被异化为"防御性文档"——不是为了找到最优解，而是为了"证明我已经考虑了所有可能"。

这会严重抑制创造性方案——因为越"安全"的诊断（考虑了所有已知选项）越不可能产生突破性洞察。真正有价值的方案往往来自"没被考虑到"的方向。

## Synthesis

问题解决线的本质不是"让诊断更完美"，而是**"让诊断更可学习"**。

[[yt-skill-storyline-timeline]] 中的"严格时间线"暴露的是"事件的因果链"，问题解决线暴露的是"认知的因果链"。两者结合，才能完整回答"为什么这件事发生了 + 为什么我当时这么理解"。

[[dk-note-rookie-disaster-veteran-heaven]] 的核心洞察在这里得到验证：新人和高手的差距不在"知道多少答案"，而在"诊断问题的速度和质量"。问题解决线强迫你显式化诊断路径，这本身就是训练诊断能力的最佳方式。

## Constraints & Boundaries

- **适用**：需要深度分析、多因素权衡的决策场景（产品诊断、业务复盘、技术选型、战略分析）
- **不适用**：高度标准化的决策（有明确SOP的流程）、需要快速响应的危机场景
- **警惕**：不要把"我考虑了所有可能"当成"我找到了正确答案"。考虑得全面不等于判断得准确
- **边界**：问题解决线最多处理5-7个平行假设。超过这个数量，认知负荷会压垮分析质量

## Cases

**正例：Truman的产品增长诊断**

```
- 问题：Q2用户增长率从15%降至3%
- 诊断A：竞品推出了替代功能 → 排除：竞品功能上线时间是Q1末，但增长率下降发生在Q2中 → 置信度：20%
- 诊断B：获客渠道失效 → 验证：Q2获客成本上升40%，转化率不变 → 置信度：70%
- 诊断C：产品价值主张模糊 → 验证：新用户7日留存率从45%降至28% → 置信度：60%
- 方案：优先解决B（获客），同时启动C的调研（价值主张）
- 假设：获客成本上升是短期波动，不是结构性变化
- 验证：如果Q3获客成本回落但增长仍低于8%，则假设不成立，需重新诊断C
```

这个诊断的价值不在于"答案"，而在于**假设的可验证性**——如果Q3数据不符合预期，诊断者知道该往哪个方向调整。

**反例："完美诊断"的陷阱**

某产品经理用问题解决线分析了"为什么功能A使用率下降"，列出了7个可能原因，每个都配有数据和排除逻辑。最终答案是"用户习惯变化"。但三个月后，发现真正的原因是"功能A的入口被隐藏了"——这是一个没人考虑到的第8个原因。

问题：问题解决线让团队误以为"我们已经考虑了所有可能"，从而停止了探索。7个原因的"完整性"反而成了认知盲区。

**边界案例：危机中的问题解决线**

某次生产事故，团队花了20分钟用问题解决线分析根因，结果因为"追求诊断完整性"而延误了恢复时间。后来复盘发现：前3分钟的初步判断（"数据库连接池耗尽"）就是正确答案，但团队花了17分钟"验证其他可能"。

## Action Protocol

| 阶段 | 操作 | 标准 |
|:---|:---|:---|
| **进入标准** | 问题需要"分析"而非"执行"，且涉及≥2个可能原因 | 如果只有一个可能原因，用执行流程线而非问题解决线 |
| **Step 1** | 用一句话精确描述问题 | 问题描述必须包含"现状"和"期望状态"的gap |
| **Step 2** | 列出所有可能原因（包括直觉判断） | 至少列出3个，最多不超过7个 |
| **Step 3** | 为每个原因设计验证方法 | 验证方法必须产生"可排除"或"可确认"的结果 |
| **Step 4** | 执行验证，记录结果 | 每个结果标注置信度和证据强度 |
| **Step 5** | 从剩余可能中推导方案 | 方案必须建立在明确的假设上 |
| **Step 6** | 定义验证标准 | "什么结果能证明方案有效"必须可测量 |
| **退出标准** | 方案已验证或假设被证伪 | 如果假设被证伪，返回Step 2重新诊断 |

## Attacker

### Attacker 1：行为经济学家——"问题解决线把'后见之明'包装成'先见之明'"

Dunning-Kruger效应告诉我们，人类严重高估自己的理性能力。问题解决线要求你"记录诊断过程"，但问题在于：**人类无法准确回忆自己的思维过程**。

研究表明，当人们被要求"解释你是怎么得出这个结论的"时，他们给出的解释大多是**事后建构**的——大脑自动把混乱的直觉过程，重构为一条"合理的推理链"。问题解决线没有解决这个问题，反而强化了它——它给了你一个完美的格式来"合理化"自己的直觉。

**当用这张卡的人睡不着觉时**：他们会想——"我的问题解决线看起来逻辑严密、证据充分，但这真的是我当时想的过程，还是我只是把结果往回编了一个漂亮的故事？如果再来一次，我还会走同样的路吗？"

### Attacker 2：组织社会学家——"问题解决线在组织中创造了'文档表演'文化"

Bruno Latour的"行动者网络理论"揭示了组织中的一个现象：**文档本身就是行动者**。当问题解决线成为"标准格式"，员工开始为"写出一份完美的诊断文档"而工作，而不是为"解决问题"而工作。

结果是：最擅长"写诊断"的人获得晋升，而不是最擅长"解决问题"的人。问题解决线从工具变成了**仪式**——它的存在不是为了找到答案，而是为了"证明我们已经尽力了"。

更隐蔽的是：问题解决线创造了一个**"认知精英"阶层**——那些能写出"看起来很有道理"的诊断的人，获得了对"什么是正确思考"的定义权。这不一定是好事——真正重要的洞察往往来自"不合逻辑"的直觉。

**当用这张卡的人睡不着觉时**：他们会想——"团队里最会写问题解决线的人，是不是恰恰是最不会真正解决问题的人？如果问题解决线成了晋升的硬通货，我们是不是在选拔'表演者'而非'实干家'？"
