# 产品内核的加减法：什么该加，什么该减

> 一堂五步法：产品内核需要持续做加减法——加的是强化内核的功能，减的是稀释内核的功能。

## 核心框架

| 操作 | 原则 | 判断标准 | 示例 |
|:---|:---|:---|:---|
| **加** | 强化内核 | 能提升关键转化率 | 增加核心功能的易用性 |
| **减** | 保护内核 | 不影响关键转化率 | 砍掉使用率低于5%的功能 |
| **不加** | 避免稀释 | 不能提升关键转化率 | "可能有人用"的功能 |
| **不减** | 保护核心 | 影响关键转化率 | 用户选择的核心功能 |

## 关键洞察

### 1. 加法原则

什么该加：
- 能提升关键转化率的功能
- 用户频繁请求且验证过的功能
- 强化内核差异化的功能

什么不该加：
- "可能有人用"的功能
- 竞品有但用户不用的功能
- 技术能做但用户不需要的功能

### 2. 减法原则

什么该减：
- 使用率低于5%的功能
- 维护成本高但价值低的功能
- 与内核方向不符的功能

什么不该减：
- 影响关键转化率的功能
- 用户选择的核心功能
- 差异化竞争优势功能

### 3. 加减法的决策流程

```
考虑新增/砍掉功能
    ↓
问：这个功能影响关键转化率吗？
    ↓
是 → 保留/优化
    ↓
否 → 问：这个功能使用率是多少？
    ↓
>20% → 保留，但考虑是否整合到核心
    ↓
5-20% → 评估是否值得维护
    ↓
<5% → 考虑砍掉
```

### 4. 加减法的时机

| 时机 | 加法 | 减法 |
|:---|:---|:---|
| 验证期 | 不加，聚焦核心 | 不减，保持最小功能集 |
| 增长期 | 加验证过的功能 | 减使用率低的边缘功能 |
| 成熟期 | 加提升体验的功能 | 减维护成本高的功能 |
| 转型期 | 加新方向的功能 | 减旧方向的功能 |

## 失败模式

| 失败模式 | 症状 | 修复方法 |
|:---|:---|:---|
| **只加不减** | 功能越来越多，产品臃肿 | 定期做减法，砍掉低使用率功能 |
| **减法过度** | 砍掉核心功能，用户流失 | 减法前验证是否影响关键转化率 |
| **竞品驱动加减** | 竞品加就加，竞品减就减 | 基于自己的用户数据决策 |
| **技术驱动加法** | "我们能做，所以做了" | 回到"用户需要吗？" |
| **忽视维护成本** | 功能多，维护成本高 | 评估功能的维护成本和用户价值 |
| **加法无验证** | 加了功能，但不知道是否提升转化 | 加法后验证关键转化率是否提升 |

## 适用边界

| 适用场景 | 不适用场景 |
|:---|:---|
| 产品功能优先级 | 技术架构设计 |
| 资源分配决策 | 品牌传播策略 |
| 产品迭代规划 | 运营活动规划 |
| MVP设计 | 财务预算分配 |

## 行动触发器

- 当考虑新增功能时 → 问"能提升关键转化率吗？"
- 当考虑砍掉功能时 → 问"影响关键转化率吗？"
- 当功能膨胀时 → 统计使用率，砍掉低于5%的
- 当资源有限时 → 优先保障核心功能，砍掉边缘功能
