# 挑战点设计

> 每次练习设定一个需要「跳一跳」才能够到的具体挑战点，让非舒适区从被动反应变成主动设计。

## Summary

非舒适区不是盲目追求痛苦，而是有意识地进入「拉伸区」——有点费劲、需要用脑、但仍然能完成的区域。

挑战点设计的作用：
1. 把模糊的勇气变成具体动作
2. 让每次练习都有明确的突破方向
3. 突破后可以记录、复盘、复用

好的挑战点应该满足：**具体、可验证、和当前能力相关、在一次练习周期内可完成。**

## Challenge Point Examples

| 场景 | 普通做法 | 挑战点设计 |
|:---|:---|:---|
| 学 AI 工具 | 看中文教程跟着做 | 「至少 50% 看英文官方文档」 |
| 学编程工具 | 用网页版点点 | 「必须跑通一个 API 调用」 |
| 做产品化判断 | 随便想想 | 「跑完后产出一页不少于 300 字的判断」 |
| 学设计工具 | 跑官方 demo | 「用这个工具完成一个真实业务需求」 |

## Core Claims

### claim:01 [conf=0.85] 没有挑战点的练习容易滑向舒适重复

如果只是重复已经会的内容，练再多也只是巩固现状。挑战点确保每次练习都在拉伸边界。

### claim:02 [conf=0.80] 挑战点必须具体，不能是"我要更难一点"

"更难"无法执行。"只用英文文档""必须产出判断""限时完成"才是可验证的挑战。

### claim:03 [conf=0.80] 挑战点需要被固定套路承接

勇气如果没有方法承接，就会变成蛮力。挑战点应该嵌入学习曲线的某个阶段，而不是孤立存在。

## Usage Template

```markdown
## 本次挑战点

**挑战内容：** _____________

**为什么选这个：** _____________

**完成标准：** _____________

**突破记录：** _____________
```

## Constraints & Boundaries

### 适用边界

| 边界 | 说明 |
|:-----|:---|
| ✅ 适合 | 用户已经愿意练习，但进步不明显 |
| ✅ 适合 | 用户进入非舒适区后缺少方向 |
| ✅ 适合 | 每次新练习周期开始时 |
| ❌ 不适合 | 用户还在零基础摸索（先建立套路） |
| ❌ 不适合 | 用户状态很低，需要先从最小动作恢复信心 |

### 常见失败模式

| 模式 | 症状 | 修复 |
|:---|:---|:---|
| **挑战点太泛** | "这次要更努力" | 换成具体动作 |
| **挑战点太难** | 一次设定多个高难度挑战 | 只设 1 个，和当前能力匹配 |
| **挑战点不记录** | 挑战完了就忘 | 写在文档里，学完后记录突破/卡点 |

## Action Triggers

| 触发场景 | 第一个动作 |
|:---|:---|
| 用户开始新一轮练习 | 设定 1 个挑战点 |
| 用户说"练得很舒服但没进步" | 检查挑战点是否缺失 |
| 用户完成练习 | 复盘挑战点是否达成 |
