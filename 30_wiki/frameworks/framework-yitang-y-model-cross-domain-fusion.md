# Y模型跨域融合框架

> **一句话定义**：Y模型跨域融合框架 = 把 Y模型 作为迭代发动机，将需求分析、产品内核、一堂五步法、科学销售、时间管理、AI 落地等域的「事实端 / 理论端 / 关键假设 / 验证动作 / 壁垒沉淀」统一映射到同一套认知循环中，使人和 Agent 能够判断“这个问题该进哪个域、何时跨域迁移、如何迭代复盘”的元导航层。

---

## 核心命题

**Y模型是迭代发动机，不是一次性分析图。**

多数人学完 Y模型 后的用法是：遇到问题 → 画一个 Y 字 → 填左臂理论、右臂事实 → 得出结论 → 结束。这是工具层用法。Truman 在课程中反复强调的却是引擎层：`[conf=0.92, source=30_wiki/concepts/yt-decision-y-model.md]`

> 「列出来你对这个问题的基础框架认知，列出来多条，不完整也没关系，会不断迭代的。」

跨域融合要做的，不是在一张更大的表上把各域内容平铺，而是在发动机视角下回答三个元问题：

1. 用户当前问题属于哪个域的哪一层？
2. 该域的 Y模型 映射与相邻域如何衔接？
3. 什么时候该做子域调用、跨域迁移、实事求是审查或解放思想激发？

## 12 条通用模式

这些模式从 5 份子域诊断报告的共同结构中提炼出来，是跨域迁移时可复用的元语法：`[conf=0.85, source=60_feedback/diagnosis/diag_20260708_yitang-y-model-cross-domain-fusion-deep-dive-v2.md]`

| # | 通用模式 | 跨域引用 |
|---:|---|---|
| 1 | **先事实后方案 / 方案中立** | 需求分析 L4/L5 前禁止产品形态；泛产品「做而不信」；销售先分层再卖点；时间管理先审计再排程。 |
| 2 | **关键假设先行** | Y模型引擎步骤 4；产品内核关键假设；五步法价值 / 增长假设；AI 落地五部曲「快验证」。 |
| 3 | **最小成本验证 / 验证成本阶梯** | 实事求是框架；需求分析「10% 至 1% 成本验证」；产品内核「聊问查测盘赌」；销售前三秒 A/B 测试。 |
| 4 | **不要过早放大 / 未经验证不复制** | 五步法「不要过早复制」；产品内核「不要在产品内核上过度承诺」；销售工具箱先补 60 分。 |
| 5 | **粗粝外化优于精美脑中** | Y模型引擎 V1 可以粗糙；双三角 Truman PPT 案例；产品内核「勉强可交付」。 |
| 6 | **把经验 / 直觉转写为因果模型** | Y模型避坑之经验主义；销售过程拆解 / 业绩画布；时间管理三门模型。 |
| 7 | **一次只验证 1–2 个关键变量** | [[tool-yitang-Y-model-application]]；产品内核每次实验聚焦；时间管理双周假设。 |
| 8 | **失败 = 认知资产，不清零** | Y模型迭代发动机；双三角「结果不好只是积累未到」；销售话术日会 / 周会迭代。 |
| 9 | **工具迷信 → 自己建模** | 时间管理 L2→L4 进阶；销售工具箱成熟度；Y模型蓝卡陷阱；解放思想 PPT 案例。 |
| 10 | **触点 / 场景匹配决定执行质量** | 需求分析场景推演；销售电话 / 线上 / 面谈差异 + 前三秒；时间管理「大对大、小对小、双峰」。 |
| 11 | **迁移成本 / 组织能力即壁垒** | 五步法六大护城河；科学销售工具箱 / 激励体系；时间管理个人操作系统；AI 原生组织上下文资产。 |
| 12 | **事实 / 假设 / 信念三列分离** | Y模型引擎步骤；实事求是框架；销售日报语言「完成 85%」vs「大部分完成」。 |

## 6 条张力点

跨域融合不是消除张力，而是把张力显式化、规则化，让 Coach Agent 和人类知道何时换挡：`[conf=0.85, source=60_feedback/diagnosis/diag_20260708_yitang-y-model-cross-domain-fusion-deep-dive-v2.md]`

| # | 张力点 | 涉及域 | 说明 | 跨域 Coach 处理原则 |
|---:|---|---|---|---|
| 1 | **需求分析「方案中立」 vs 销售「前三秒话术」** | 需求分析 / 销售 | 需求冰山 L4/L5 前禁止产品形态，销售把成熟话术直接输出。张力在于销售话术应被视为已验证下游动作，不能被拿到上游需求探索阶段使用。 | 判断当前处于「探索期」还是「验证期 / 复制期」，前者禁用话术，后者可调用车术 Agent。 |
| 2 | **五步法「不要过早复制」 vs 增长「规模对抗」** | 五步法 / 增长 | 前三步强调未经验证不能放大；增长阶段又强调标准化、规模化对抗。张力在于**两次跃迁的换挡条件**未工具化。 | 用关键假设状态表判定：价值假设已验证 → 可复制；增长假设已验证 → 可规模化。 |
| 3 | **产品内核「做减法 / 边界」 vs 泛产品「加法 / 减法」** | 产品内核 / 泛产品设计 | 内核要求砍掉非核心，泛产品第四步要求先充分加法再收敛。阶段不清时团队会「只加不减」或「过早收敛」。 | 明确阶段：内核未验证前做减法保焦点；泛产品第四步先做加法再收敛。 |
| 4 | **时间管理「只讲个人工作时间」 vs 五步法 / 泛产品「团队 / 组织应用」** | 时间管理 / 五步法 / 泛产品设计 | 时间管理有硬边界，但五步法 / 泛产品大量用于组织场景。跨域 Coach 必须识别问题属于个人时间配置还是组织流程设计。 | 先问「这个问题的主体是个人还是组织 / 团队？」，再决定域归属。 |
| 5 | **实事求是「定量」 vs 早期项目 / 创意「不可量化」** | 实事求是 / 产品内核 / 创意 | Y模型 承认品味型、微型决策不适合强行量化，但销售话术、品牌创意等仍大量依赖定性判断。张力在于「何时降级为定性草案」缺乏规则。 | 显式标注置信度与证据等级；不可量化时输出「定性草案 + 下一步可量化信号」。 |
| 6 | **解放思想「挑战隐含假设」 vs 销售 / 流程「标准化复制」** | 解放思想 / 销售 / 组织 | 标准化话术 / SOP 之所以有效，正因为固化了被验证的假设；过度解放思想可能破坏已被验证的惯例。边界在于区分「过时的行业惯例」与「真实的因果规律」。 | 挑战前先问：这个假设是否已被多轮事实验证？是 → 不挑战；否 → 进入解放思想激发。 |

## 跨域诊断流程

跨域 Coach 的工作流由 5 个步骤组成，每一步都有明确输入、输出和边界：`[conf=0.85, source=60_feedback/diagnosis/diag_20260708_yitang-y-model-cross-domain-fusion-deep-dive-v2.md]`

```
边界确认 → 域归属判断 → 短板识别 → 子域调用 / 跨域迁移 → 迭代复盘
```

| 步骤 | 输入 | 核心动作 | 输出 |
|:---|:---|:---|:---|
| **1. 边界确认** | 用户原始问题、约束、目标 | 声明只做路由 / 审查 / 激发，不替代域 Agent；排除一次性低风险任务；标记法律 / 医疗 / 合规边界 | 边界声明 + 是否进入完整流程 |
| **2. 域归属判断** | 问题重述、已知信息、目标指标 | 对照 6+ 域映射表，判断问题落在哪个域的哪一层；若跨域，识别主域和从域 | 域归属结论 + 置信度 |
| **3. 短板识别** | 域归属结论、当前信息充足度 | 用 12 条通用模式扫描，判断当前最大短板是事实端、理论端、假设质量还是验证动作 | 1–2 个最短板 + 证据 / 假设状态 |
| **4. 子域调用 / 跨域迁移** | 短板、用户目标 | 推荐 1–3 个子域 Agent / 框架卡；若跨域迁移，抽象源域模式、映射目标域、列差异、给验证计划 | 推荐入口 + 信息包摘要 + 验证计划 |
| **5. 迭代复盘** | 执行结果、V1 认知、实验日志 | 把结果抽象为 V1→V2 框架认知更新、更新假设状态表、写入飞轮日志 | V2 认知 + 下一轮问题 |

## When to Use / When NOT to Use

### When to Use

| 场景 | 第一个动作 |
|:---|:---|
| 问题明显跨域（如「销售话术能不能用来写内容钩子」） | 进入跨域迁移判断，列 source/target 差异 |
| 不确定该调用哪个域 Agent | 先做域归属判断，再推荐 1–3 个入口 |
| 单域循环卡壳，怀疑是相邻域短板 | 用 6 条张力点检查是否错配了阶段或边界 |
| 方案需要事实校准 | 启动实事求是审查模式，输出事实 / 假设 / 信念三列 |
| 团队陷入行业常识、多轮优化无突破 | 启动解放思想激发模式，列出隐含假设清单 |
| 项目结束，想把结果沉淀为认知资产 | 启动迭代复盘模式，写 V1→V2 变更说明 |

### When NOT to Use

| 场景 | 原因 | 替代 |
|:---|:---|:---|
| 一次性、低风险、答案已知的微型决策 | 分析成本超过决策收益 | 直接决策或调用通用工具 |
| 纯执行型任务已有成熟 SOP | 不需要升级认知 | 按 SOP 执行，事后复盘 |
| 明确单域问题 | 不需要跨域 Coach 分诊 | 直接调用该域 Agent/框架卡 |
| 法律 / 医疗 / 合规最终判断 | 超出 Agent 责任边界 | 建议人工复核 |
| 品味 / 意义型决策（品牌视觉、公司使命） | 强行结构化会扭曲不可通约价值 | 用 [[framework-taste-as-judgment-system]] 等轻量方式 |

## Critique

### 外部攻击者

1. **Daniel Kahneman（判断心理学 /《噪声》）**：结构化框架能减少偏差，但不能减少判断噪声。当团队对「域归属」「短板优先级」「假设置信度」的估计差异巨大时，跨域融合框架会把噪声包装成精确的分类，反而掩盖分歧。`[conf=0.88, source=30_wiki/concepts/yt-decision-y-model.md]`
   - **回应**：本框架的输出是草案而非终审，关键判断必须回到人。要求每个判断标注置信度、列出可能推翻它的反例，并通过迭代复盘暴露和收敛噪声。

2. **Paul Feyerabend（科学哲学，《反对方法》）**：历史上重大科学突破并非都遵循统一方法。把创业成功简化为「假设 → 验证 → 迭代」的规范化叙事，可能混淆科学的公共关系宣传与科学真实发生的方式。`[conf=0.85, source=30_wiki/concepts/yt-decision-y-model.md]`
   - **回应**：本框架不声称是唯一正确方法，而是一套诊断清单。当用户卡住时，用它定位缺了哪一步；简单问题直接知行合一即可。

3. **Gary Klein（自然决策理论）**：消防员、急救人员在高压情境下依赖模式识别（RPD）往往优于结构化分析。强制所有复杂问题先走跨域诊断，可能在高段位、时间紧迫的专家决策中成为负担。`[conf=0.85, source=30_wiki/concepts/yt-decision-y-model.md]`
   - **回应**：本框架明确把「答案已知 / 有成熟 SOP」的场景列为 When NOT to Use。跨域 Coach 只在跨域、无域归属或循环卡壳时触发。

### 内部局限

1. **域注册表不完整会降低路由精度**。如果新域 Agent 没有按规范注册，跨域 Coach 会把真实需求误判为「待注册域」，只能给出临时建议。`[conf=0.80, source=60_feedback/diagnosis/diag_20260708_yitang-y-model-cross-domain-fusion-deep-dive-v2.md]`
2. **输入质量决定诊断质量**。用户问题越模糊，域归属判断越依赖常识推断，短板识别的置信度会明显下降。
3. **跨域迁移的类比风险**。源域模式迁移到目标域时，若差异点没有被充分列出，容易把类比当成论证，导致错误复制。
4. **框架自身也可能仪式化**。团队可能把「我们已经用跨域 Coach 诊断过了」当作挡箭牌，抑制真正的质疑。必须保留人工复核和飞轮日志机制。

### 使用提醒

- 本框架不是把各域内容合并成一张更大的表，而是建立「域归属 → 短板 → 调用 / 迁移 → 复盘」的元循环。
- 概念卡 [[yt-decision-y-model]] 讲 Y模型 是什么；本框架讲 Y模型 在各域如何映射、如何跨域切换。
- 每次跨域迁移后，必须在目标域跑一轮最小验证，否则类比只是说明，不是论证。
