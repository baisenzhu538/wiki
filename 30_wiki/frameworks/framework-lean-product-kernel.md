# 产品内核：不要过早细化未经思考的内核

> 在产品开发进入细化与重投入之前，先用三个问题审视：你以为的内核，真的经得住推敲吗？

## 一句话定义

产品内核框架是一个**前置性警示工具**：它要求团队在把资源投入细节打磨之前，先回答内核三问——是否决定、是否优化、是否完备——以避免把非内核要素当内核打磨，或在产品内核尚未成立时过早细化。

## 核心模型：内核三问

| 问题 | 核心含义 | 如果回答为"否" |
|:---|:---|:---|
| **是否决定** | 你认定的内核要素，去掉之后用户还会选你吗？ | 该要素只是优化项，不是内核 |
| **是否优化** | 你忽略的非内核要素，有没有可能反而是决定性的？ | 存在被低估的关键假设 |
| **是否完备** | N 个内核要素组合在一起，能否支撑一个不错的结果？ | 内核之间无法形成闭环，需要补全或转型 |

三问的使用顺序：先确认**是否决定**，再排查**是否优化**，最后验证**是否完备**。任何一问出现"否"，都意味着当前内核尚未经过充分思考，不应进入大规模细化或重投入。

### 一个极简自查表

| 检查项 | 通过标准 |
|:---|:---|
| 每个"内核"要素都经得起"去掉测试" | 去掉后用户价值显著下降 |
| 每个"非内核"要素都有明确优先级 | 不会挤占内核验证资源 |
| 所有内核要素能串成完整价值链路 | 从获客到交付到复购不出现断点 |

## 失败模式

| 失败模式 | 症状 | 修复 |
|:---|:---|:---|
| **把优化项当内核打磨** | 在包装、UI、VI、官网等"是否优化"要素上投入过多，去掉后用户并不在意 | 先用"是否决定"砍掉非决定性要素 |
| **内核未验证就过早细化** | 产品方案已经做到 80 分，但"用户是否真正需要"仍是未知 | 回到 FALSE 模型左侧（F/A/L/S）做一轮需求验证 |
| **忽视完备性，单点优秀却无法闭环** | 每个内核要素单独看都很好，但组合后无法形成可交付的价值 | 用"是否完备"画通用户旅程，找出断点 |
| **把"三问"当一次性检查** | 只在立项时问一次，后续迭代不再回顾 | 每次重大投入前重新回答三问 |
