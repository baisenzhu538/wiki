# 王欢三层开发架构：需求拆解→AI开发→哨兵质检

> **Burn line**: 程序员不是写代码的人，是让 AI 把代码写好的人。
>
> **来源**：王欢 AI 实战分享（2026-06-18）

---

## 一、用一句话讲清楚

把人机协作的软件开发拆成三层：**需求拆解层、AI 代码执行层、审查验收层**。人负责定义和验收，AI 负责中间执行。

---

## 二、三层架构

```
原始需求文档 + 客户背景
        ↓
┌─────────────────┐
│  第一层：需求拆解  │  ← 人定义，AI 辅助
│  把模糊需求拆成   │
│  可执行的原子任务  │
└─────────────────┘
        ↓
原子任务清单 + API 文档
        ↓
┌─────────────────┐
│  第二层：AI 开发   │  ← AI 执行
│  按任务生成代码   │
│  和单元测试      │
└─────────────────┘
        ↓
生成的代码
        ↓
┌─────────────────┐
│  第三层：哨兵质检  │  ← 人验收，AI 辅助
│  代码质量/安全/   │
│  规范审查       │
└─────────────────┘
        ↓
   可交付代码
```

---

## 三、每层详解

### 3.1 第一层：需求拆解

| 项目 | 内容 |
|:---|:---|
| **核心职责** | 把客户需求分解成具体的、可执行的功能单元 |
| **关键能力** | 理解业务、识别原子任务、定义验收标准 |
| **可用工具** | requirement-decomposition.md、思维导图、BITCOE |
| **人的角色** | 主导拆解，AI 辅助补充和结构化 |

**输出物**：
- 原子任务清单
- 每个任务的输入/输出定义
- 验收标准

### 3.2 第二层：AI 开发

| 项目 | 内容 |
|:---|:---|
| **核心职责** | 按原子任务生成代码和单元测试 |
| **关键能力** | 代码生成、上下文理解、单元测试生成 |
| **可用工具** | Cursor、Copilot、code-generation.md |
| **人的角色** | 审查 AI 生成的代码，确认符合需求 |

**输出物**：
- 代码实现
- 单元测试
- 文档注释

### 3.3 第三层：哨兵质检

| 项目 | 内容 |
|:---|:---|
| **核心职责** | 代码质量、安全、规范审查 |
| **关键能力** | 静态分析、安全扫描、逻辑复核 |
| **可用工具** | ESLint、SonarQube、自定义审查模板 |
| **人的角色** | 做最终判断：能不能上线 |

**输出物**：
- 质检报告
- 问题清单
- 上线/返工决策

---

## 四、与传统开发流程的对比

| 维度 | 传统开发 | 三层人机协作开发 |
|:---|:---|:---|
| 需求处理 | 人直接理解需求 | 先拆解成原子任务 |
| 代码生产 | 人写 | AI 生成，人审查 |
| 质量保障 | 测试阶段集中进行 | 每个任务都有质检 |
| 人的角色 | 执行者 | 定义者 + 验收者 |
| 效率 | 基准 | 接近 3 倍 |

---

## 五、为什么能提升 3 倍效率

1. **需求拆解前置**：把“脑慢”的问题交给 AI，人只需要验收拆解结果。
2. **AI 批量生成代码**：人不再逐行写代码，而是批量审查。
3. **质检自动化**：用工具先做一轮静态检查，人只做逻辑复核。
4. **角色升级**：人的经验从“写代码”变成“判断代码能不能用”。

## 六、通用化：从软件开发到知识工作

| 软件开发 | 通用知识工作 |
|:---|:---|
| 需求拆解 | 任务拆解 |
| AI 生成代码 | AI 生成内容/方案/分析 |
| 哨兵质检 | 审查验收 |

### 6.1 内容生产

| 层级 | 动作 |
|:---|:---|
| 需求拆解 | 把选题拆成结构、要点、案例 |
| AI 执行 | AI 生成初稿 |
| 哨兵质检 | 事实核查、风格审查、合规审查 |

### 6.2 知识萃取

| 层级 | 动作 |
|:---|:---|
| 需求拆解 | 定义要萃取的专家和场景 |
| AI 执行 | AI 访谈整理、模式提取 |
| 哨兵质检 | 专家复核、逻辑验证 |

### 6.3 KDO 知识工厂映射

| 三层开发架构 | KDO 知识工厂 |
|:---|:---|
| 需求拆解 | 老顽童：识别值得建卡的内容，拆解结构 |
| AI 执行 | AI/老顽童：生成卡片初稿 |
| 哨兵质检 | 王语嫣/欧阳锋：质量门禁和审查 |

## 七、常见走偏模式

| 走偏模式 | 表现 | 纠偏动作 |
|:---|:---|:---|
| **拆解不清就开发** | AI 生成的代码偏离需求 | 回到需求拆解层，补全原子任务 |
| **人陷入代码细节** | 程序员忍不住自己改代码 | 明确角色：你是让 AI 写好的人 |
| **质检流于形式** | 只跑工具，不做逻辑复核 | 建立人工复核 checklist |
| **三层串行变成三层孤立** | 拆解不管开发，开发不管验收 | 每层输出必须是下一层的输入 |

---

## 八、Action Triggers

| 触发场景 | 第一个动作 |
|:---|:---|
| 开发效率遇到瓶颈 | 检查需求拆解层是否足够细 |
| AI 生成代码质量差 | 检查原子任务是否清晰 |
| 上线后 bug 多 | 检查哨兵质检层是否有效 |
| 团队成员抗拒 AI | 重新定义角色，从执行者到质量守门人 |
