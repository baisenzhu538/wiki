# ToB/ToC/硬件/内容产品的测试差异

> **Burn line**: 产品形态不同，风险结构就不同；风险结构不同，测试手段就必须分层。
>
> 来源：张磊 AMA 问答 `Q23`（src_20260616_b1e25c49），口述整理（src_20260616_59f708ea），课堂笔记（src_20260616_e66bd149）。

---

## 核心框架：风险结构决定测试手段

张磊在回答 `Q23` 时反复强调一句话：**“产品形态差别大，测试手段差别极大。”** 差异的根源不是行业标签，而是四类业务的风险结构不同：

| 业务类型 | 核心风险 | 主导测试范式 | 关键判断 |
|---------|---------|-------------|---------|
| ToC 消费品 | 用户感性冲动、转化效率 | ① 灰度测试 | 用户是否愿意真实付费/复购 |
| 内容/课程 | 产品内核是否足够好 | ①+② 灰度+组合测试 | 用户是否主动好评、优先选择 |
| 硬件 | 研发投入大、回退成本极高 | ①+②+③ 三层嵌套 | 需求/技术/商业风险能否被提前拆解 |
| ToB | 客户少、周期长、价值理性 | ③ 里程碑测试为主 | 客户是否真实感受到“问题被解决” |

---

## Constraints & Boundaries

| 边界 | 说明 |
|-----|------|
| 此框架适用于“业务形态已经明确”后的测试设计阶段 | 若业务形态仍模糊，需先用关键假设拆解（如 [[yt-entrepreneur-key-hypotheses]]）明确要验证的假设 |
| 必须与前置假设拆解配套使用 | 本框架只回答“怎么测”，不回答“测什么”；若团队对要验证的假设没有共识，需先用 [[yt-lean-assumption-verification-3means]] 拆出关键假设 |
| 不替代具体方法细节 | 灰度测试、里程碑测试、FALSE 模型等需结合具体方法论执行；本卡只解决“选哪种测试组合” |
| 不适用于已规模化增长阶段的效率优化 | 当业务已通过验证、进入放量增长期，应使用单元模型、渠道 ROI 分析等增长工具，而非本框架做测试范式选择 |
| 样本量标准随业务走 | ToB 可用 5-10 家天使用户做判断，不要用大样本标准卡小样本场景 |

## Common Failure Modes

| 模式 | 症状 | 修复 |
|-----|------|------|
| 一把尺子量所有业务 | ToB 项目照搬 ToC 的 Landing Page 测试，只看点击率不判断客户真实问题是否被解决 | 按风险结构选范式：ToB 重里程碑+客户成功故事，ToC 重灰度+真实转化 |
| ToB 项目不做里程碑拆分 | 一个陪跑项目 3-6 个月后才发现客户不买单，大量交付成本沉没 | 把长周期拆成“可交付、可验证”的里程碑节点，每个节点有明确停止条件 |
| 硬件一上来就做完整样机 | 投入数百万、十几个月后才发现技术或需求不成立 | 先做三层嵌套：项目赛马选方向 → 里程碑拆分验证 → 技术路线灰度测试 |
| 内容产品先测需求再打磨内核 | 用户都说“愿意学”，但课程上线后评价差、复购低 | 先验证产品内核：用一节课/一个模块 Demo，找 10-30 个精准用户拿高质量定性反馈 |
| 小样本业务强要大样本数据 | ToB 早期只有 5 个客户，却要求几百个样本才做判断 | 接受“小样本证伪”逻辑：少量真实付费订单的认知价值远高于大量点击数据 |

## 一、ToB vs ToC：三大特性决定 MVP 设计

### 特性一：价值理性（而非感性冲动）

ToB 解决的是企业经营管理问题，客户决策是理性的、甚至是集体决策。

- **ToC**：一个人的感性和冲动就足以支付高昂费用，一张假海报可以测出 80% 真实转化率。
- **ToB**：假页面价值远低于 ToC，客户不会为一个好看的 PPT 付费。

> **关键判断**：ToB 不是在测“用户感不感兴趣”，而是判断客户是否真实感受到“我帮你解决了什么问题”。

### 特性二：周期长

ToB 的成交、交付、回款、财务确认周期往往以月/年计。

- **ToC**：可能一周跑一轮灰度测试。
- **ToB**：一轮种子客户陪跑可能就是 3-6 个月。

> **关键判断**：ToB 更需要里程碑测试，每一轮投入大、周期长，里程碑节点必须算得准，不能像 ToC 那样“随便测测看”。

### 特性三：客户少、单个价值高

ToB 客户天然少，但一个真实付费订单的认知价值可能远超 ToC 的几百个点击数据。

> **关键判断**：判断层级跟着业务走，不要用大样本标准卡小样本场景。钉钉早期天使用户只有 5 个客户，就足以判断需求是否存在。

## 二、ToB 案例：一堂 2B 标准内训项目

### 项目背景

给中小团队做一个标准化单点内训产品，把一堂课程拆解成独立“学习单元”（五步法、专家访谈、复盘、战略会等），客户采购单个模块，拿到 2 周团队共学方案。

### All-in 方案的问题

- 做 3-5 个课题
- 打磨成完整产品服务
- 搭建产品、交付、销售小分队
- 在会员日正式销售验证
- **成本**：3-6 个月筹备，50-100 万综合成本

### 更优策略：里程碑测试 + 小范围灰度

1. **先用里程碑拆分**：把“完整产品化”拆成“单模块 Demo → 1-3 家种子公司陪跑 → 验证交付闭环 → 产品化”。
2. **每一轮可交付、可验证**：不是把产品做完整再销售，而是让每一阶段都有真实客户反馈。
3. **小样本即可判断**：ToB 客户少但需求相对统一，少量真实付费订单即可验证关键假设。

## 三、硬件：三层嵌套测试

硬件有一个致命特征：**研发投入大、回退成本极高**。

课程里导盲机器狗案例是最痛的教训：1800 万、18 个月、十几位博士，最终发现产品 300 斤重，盲人根本扶不起来。

### 硬件 MVP 的灵魂三问

1. 真的需要做硬件么？能不能只做软件？
2. 真的需要做独立 App 么？能不能做小程序？
3. 真的需要做小程序么？能不能不动开发，借用已有工具？

### 三层嵌套框架

| 层级 | 测试范式 | 负责角色 | 降低的风险 |
|-----|---------|---------|-----------|
| 整体项目方向 | ② 项目赛马 | CEO | 选项错的风险 |
| 单一项目推进 | ③ 里程碑测试 | 业务一号位 | 全盘推翻的风险 |
| 项目内部技术路线 | ① 灰度测试 | 技术 Leader | 重投入失败的风险 |

> **案例**：某医疗硬件研发公司，整体上是项目赛马，单一项目是里程碑测试，项目内部的技术路线探索又是灰度测试。任何一层跳过都会付出惨重代价。

## 四、内容产品：内核优先

内容（课程、IP 产品）的核心风险集中在**产品内核假设**——“这个课到底够不够好”。

### 一堂自身案例

2019 年一堂样本量只有几百上千，作业率、NPS 甚至样本不够做精确定量判断，但靠着三个信息源完成了内核打磨：

1. **横向课程对比**：与市场上同类课程比较
2. **用户定性评价**：用户是否主动给出积极评价
3. **主观审美信心**：团队对内容质量的判断

### 内容产品的里程碑顺序

| 顺序 | 里程碑 | 关键动作 |
|-----|--------|---------|
| 第一 | 产品内核验证 | 用一节课/一个模块 Demo，找 10-30 个精准目标用户，人工服务式交付，拿高质量定性反馈 |
| 第二 | 定价验证 | 边打磨边感知价格锚点，不是“先定价再打磨” |
| 第三 | 单元模型验证 | 内核+定价双确定后，才跑通获客到交付的完整闭环 |
| 第四 | 规模化验证 | 单元模型跑正后，再考虑渠道扩展、团队搭建、内容矩阵化 |

> **案例**：游爸做桌游教育时，先让 60 个人体验桌游，拿到“孩子喜欢 + 家长认可”的定性反馈，才决定开店。

## 五、如何快速选择测试组合

| 如果你的业务是... | 优先测试范式 | 第一问 |
|------------------|-------------|--------|
| ToC 消费品 | 灰度测试 | 用户是否愿意真实付费/复购？ |
| ToB 服务 | 里程碑测试 + 小样本 | 客户是否真实感受到问题被解决？ |
| 硬件 | 项目赛马 → 里程碑 → 灰度 | 能不能不做硬件/独立 App/开发？ |
| 内容/课程 | 产品内核灰度 | 课到底够不够好？用户会主动好评并优先选择吗？ |

## 六、B2B / ToC / 硬件测试设计速查表

| 设计维度 | ToC 消费品 | ToB 服务 | 硬件 |
|:---------|:-----------|:---------|:-----|
| **第一问（关键假设）** | 用户是否愿意真实付费/复购？ | 客户是否真实感受到问题被解决？ | 需求/技术/商业风险能否被提前拆解？ |
| **最小测试单元** | 一个 SKU、一个卖点、一个落地页 | 一个可交付里程碑、一家种子客户 | 一个软件 Demo、一条技术路线、一个最小功能 |
| **推荐测试范式** | 灰度测试（Landing Page、A/B、小批量试卖） | 里程碑测试 + 小样本深度访谈 | 项目赛马 → 里程碑测试 → 灰度测试 |
| **样本量参考** | 100-500 次曝光或 30-100 个真实付费 | 3-10 家天使用户 | 5-20 个技术验证点、10-30 个用户反馈 |
| **停止条件（红灯）** | CTR/转化率低于行业 benchmark 50% 且无法解释 | 连续 2-3 个里程碑未达客户成功标准 | 需求验证不成立，或技术路线核心指标无法达成 |
| **继续条件（绿灯）** | 真实付费订单 + 复购/推荐信号 | 客户愿意付费或续费 + 成功故事可讲述 | 三层风险都被更低成本方案排除 |
| **最容易踩的坑** | 只看点击率，不看真实付费和复购 | 只看客户兴趣，不看决策链和交付闭环 | 跳过软件/小程序模拟，直接做完整样机 |

> **使用说明**：上表是“设计起点”而非“标准答案”。实际执行时，先把业务按五步法拆到“需求→解决方案→商业模式→增长”，再落到对应格子里选最小测试单元。

## 七、测试方案设计检查清单

设计完测试方案后，用下面 7 项自检，避免“测了但没用”：

- [ ] 已用 [[yt-entrepreneur-key-hypotheses]] 或 [[yt-lean-assumption-verification-3means]] 拆出当前阶段的关键假设
- [ ] 已识别致死率最高的 1-2 条假设，资源优先投向它
- [ ] 已根据业务类型（ToC/ToB/硬件/内容）选定测试范式
- [ ] 已设计最小可交付测试单元，而不是直接做完整产品
- [ ] 已为每个里程碑设定明确的停止/继续标准
- [ ] 已确定与业务匹配的样本量，不盲目追求大样本
- [ ] 已准备降级路径：若原计划卡壳，可用更轻量的方式验证同一假设
