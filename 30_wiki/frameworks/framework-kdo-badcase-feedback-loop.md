# KDO Bad Case 回流机制：从用户纠错到知识进化的闭环

> 一句话：当自攻击没拦住、审查没发现、用户明确指出错误时，用结构化流程把每一次纠错变成知识库的永久进化，而不是修完就忘。

---

## 1. 为什么需要 Bad Case 回流

KDO 知识工厂已有三层质量防线：
```
生产自检（pre-submit）  → 自攻击（四路 Agent）    → 欧阳锋审查（三阶段）
      → 交付
```

但三层防线仍然可能漏网。当用户在使用中发现了错误——无论是事实错误、逻辑漏洞、还是 Agent 行为违反协议——这个纠错信号极其珍贵。如果不系统化记录，就会：
- **同一类错误反复出现**：老顽童在 #175 犯的前端路径错误（写到 ~ 而非 Desktop/wiki/），之前在 #134 也犯过类似问题。没有回流机制，教训只停留在口头。
- **用户纠错无法追溯**：老板说"这个数字不对"，修了。但为什么错？是 OCR 幻觉还是 VLM 误读？下次还会不会再犯？没人记录根因。
- **审查无法进化**：欧阳锋的审查标准应该从漏网的 bad case 中学习，但没有结构化输入，审查只能依赖个人经验。

Bad case 回流是**第四层防线**：它不是事前预防，而是事后学习。它的核心价值不是修复一个错误，而是**让整个系统从错误中进化**。

---

## 2. 定义

### 2.1 什么是 Bad Case

| 条件 | 说明 |
|:---|:---|
| **Agent 输出存在可验证的错误** | 不是风格争议，不是偏好差异 |
| **用户明确纠正** | 用户说"这个不对""这个数字错了""这个结论有问题" |
| **审查未拦截** | 自攻击和欧阳锋审查都没有发现 |
| **造成了实际影响** | 返工、误导、或用户信任受损 |

### 2.2 什么不是 Bad Case

| 情况 | 说明 | 处理方式 |
|:---|:---|:---|
| 用户偏好差异 | "我不喜欢这个写法""换一种表达" | 正常反馈，不记录为 bad case |
| 风格争议 | "这个方法论分类我不完全同意" | 在卡片 Critique 中讨论，不记录为 bad case |
| 未采纳建议 | Agent 给了建议但用户没用 | 不记录 |
| 自攻击已发现的问题 | 自攻击报告里已有的 🔴/🟥 项 | 已在前置流程覆盖 |
| 审查中被拦截的问题 | 欧阳锋审查时退回的 | 已在他检流程覆盖 |

> **核心标准**：用户纠错 + 三层防线均未拦截 = bad case。

## 3. 发现渠道

| 渠道 | 触发场景 | 记录人 |
|:---|:---|:---|
| **用户主动反馈** | 老板在看卡/用 Agent 时发现错误，直接指出 | 老顽童/王语嫣 |
| **欧阳锋终审时发现** | 审查中发现了前面几轮审查都漏掉的问题 | 欧阳锋 |
| **老顽童生产时自攻击发现** | 自攻击报告中的问题，但属于之前批次已通过审查的卡 | 老顽童 |
| **王语嫣方向把关时发现** | 诊断/编排时发现已有卡片与方向冲突 | 王语嫣 |
| **后续使用中发现** | 卡片发布后，在真实场景中使用时暴露的问题 | 段王爷/用户 |

## 4. 缺陷分类

| 一级分类 | 二级分类 | 典型表现 | 示例 |
|:---|:---|:---|:---|
| **事实错误** | 数据错误、来源误引、年份混淆 | 数字、引文、案例事实对不上 | "市场份额 35%" 实际为 23% |
| **逻辑漏洞** | 推导跳跃、因果倒置、以偏概全 | 结论推不出前提 | 从一个案例的成功推断整个行业规律 |
| **边界遗漏** | 未考虑例外、未标注适用条件 | 绝对化表述、忽视特殊场景 | "所有企业都适用" 忽略平台型企业例外 |
| **流程违反** | 未按角色协议执行、跳过门禁 | 该检索未检索、该自检未自检 | 回答域知识问题前未跑 `kdo query` |
| **幻觉** | 编造不存在的卡片/来源/数据 | source_refs 指向不存在文件、虚构数据 | 引用了一个不存在的 framework 卡 |
| **用户模型错误** | 误判用户偏好、决策记录、战略方向 | 给出与用户已知结论冲突的建议 | 用户已明确说"不做 X"，Agent 又建议做 X |

> 分类互斥原则：一个 bad case 只归入最匹配的一级分类。如果涉及多个缺陷，选最根因的那个。

## 7. 闭环流程

```
      发现
        │
        ▼
   ┌─ 记录 ────────────── 写入 badcase_YYYYMMDD_xxx.md
   │    │
   │    ▼
   │  分类 ────────────── 确定一级/二级分类 + 严重程度
   │    │
   │    ▼
   │  归因 ────────────── 根因分析：知识缺口？流程缺陷？模型局限？上下文缺失？
   │    │
   │    ▼
   │  决策 ────── 立即修：critical 级别，阻塞当前工作
   │         ├── 排期修：major 级别，不阻塞但必须修
   │         └── 不修：minor 级别，已知但 ROI 不够（必须写理由）
   │    │
   │    ▼
   │  修复 ────────────── 更新卡 / skill / agent-spec / context 文件
   │    │
   │    ▼
   │  验证 ────────────── 抽检确认 / 回归测试 / 门禁增强
   │    │
   │    ▼
   └─ 关闭 ────────────── status: closed，追加 resolved_at
```

| 状态 | 含义 | 谁操作 |
|:---:|:---|:---|
| `open` | 已记录，待归因 | 发现者 |
| `analyzed` | 已完成归因分析 | 老顽童/王语嫣 |
| `in_progress` | 正在修复 | 老顽童/黄药师 |
| `verified` | 修复完成，待验证 | 修复者 |
| `closed` | 验证通过，已关闭 | 欧阳锋 |

## 8. 与现有机制的关系

```
事前防线（预防）              事后防线（学习）
┌───────────────┐     ┌──────────────────────┐
│               │     │                      │
│ pre-submit    │     │                      │
│   ↓           │     │ Bad Case 回流         │
│ 自攻击        │────→│  ← 用户纠错信号        │
│   ↓           │     │  ← 审查漏网之鱼        │
│ 欧阳锋审查    │     │  ← 使用中暴露的问题    │
│   ↓           │     │                      │
│ 交付          │     │ 记录→分类→归因→修复   │
│               │     │  →验证→关闭→进化     │
└───────────────┘     └──────────────────────┘
```

- **与 `framework-kdo-self-attack` 的关系**：自攻击是事前预防（提交前主动找问题），bad case 回流是事后学习（从漏网案例中进化）。**边界**：自攻击修卡片内容层面的逻辑/证据/完整性/时效性缺陷，属于交付前质量门禁；bad case 修已交付后用户发现的任何类型缺陷（含流程违反、幻觉、用户模型错误等自攻击覆盖不到的类型），属于事后学习。二者互补：自攻击发现的常见问题应回流到自攻击规则中让下一轮更强，bad case 发现的系统性缺陷应反馈到自攻击的检查清单中。

- **与 `framework-ouyangfeng-review-methodology` 的关系**：欧阳锋审查是第二层他检防线。审查中发现的 bad case 如果属于"前几轮审查也漏掉"的类型，说明审查标准需要升级。回流机制提供升级的输入信号。

- **与 `system-kdo-quality-labels` 的关系**：bad case 的缺陷类型可以映射到 quality_labels 的检查维度，帮助完善质量标签体系。本卡的 quality_labels 选择依据 `system-kdo-quality-labels`：`insight`（提出了一种新的质量防线设计视角——第四层事后学习防线）、`principle`（定义了 bad case 识别-记录-归因-修复-验证的原则性流程）、`actionable`（提供了可直接使用的记录模板和闭环流程，任何一个 Agent 都可以立即执行）。

- **与 `kcard-issues-board` 的关系**：issues board 是 P0/P1/P2 的静态问题清单，bad case 回流是动态的学习机制。issues board 中的高频问题类型应触发 bad case 分析。

- **与 KDO 飞轮的关系**：bad case 回流是飞轮「使用→反思→实验→建造」中「反思」环节的结构化实现。

## 9. When NOT to Use

- **自攻击已发现的问题**：如果自攻击报告已经标记了 🔴/🟥，直接修，不需要走 bad case 流程。
- **审查中正常退回的问题**：欧阳锋审查时退回的修改请求，属于正常审查流程，不记录为 bad case。
- **纯偏好/风格问题**："这个标题不好""换个说法"——不是错误，不记录。
- **首次生产中的试错**：新域开荒时的素材理解偏差，如果还没通过审查，属于正常迭代，不记录。
- **已知技术债务**：已记录的 P0/P1/P2 债务项，修就是了，不需要再开 bad case。

## 10. 常见失败模式

| 失败模式 | 症状 | 修复 |
|:---|:---|:---|
| 记录了就以为修了 | bad case 文件写得很详细，但没人跟进修复 | 强制要求每个 open bad case 必须有 assignee 和 due date |
| 分类不当导致归因错误 | 把"幻觉"归为"事实错误"，修错了方向 | 归因前必须确认根因：是人类写错还是模型编造？ |
| 修复只在单点 | 修了一张卡，但同类问题在其他 10 张卡里仍然存在 | 修复时必须扫描同类问题（同域/同类型卡） |
| 回流不到位 | 卡修了，但 skill/agent-spec/context 没更新 | 回流位置检查清单强制逐项确认 |
| 用户不信任 | 老板纠正了但没走 bad case 流程，"你记住就行" | 即使不走正式流程，也要在 session 复盘里记录，下次启动时提醒自己 |
| bad case 泛滥 | 门槛太低，什么都记，索引变成垃圾堆 | 严格按 2.1 定义过滤：必须是三层防线都漏网的用户纠错 |

## 11. Critique

- **机制成本**：每条 bad case 按模板填写需要 10-15 分钟。如果 rigorous 执行，可能成为负担。建议只对 critical 和 major 级别的 bad case 走完整流程，minor 级别的在 session 复盘里一句话记录即可。
- **用户配合度**：老板可能不愿意配合走流程——"我就说一句，你记住就行"。需要设计一个轻量化的入口：老板随口说的纠正，Agent 自己归档到 bad case，不需要老板填模板。
- **分类的边界模糊**："幻觉"和"事实错误"有时难以区分——如果 Agent 引用了 OCR 文本但 OCR 本身错了，这算幻觉还是事实错误？建议：如果 Agent 有合理的源但源本身有问题，归为"事实错误"；如果 Agent 没有任何依据就编造，归为"幻觉"。
- **机制自身也需要进化**：本机制卡本身就是 v1.0，应该在使用 3 个月后根据真实 bad case 数据做一次回顾修订。如果 6 类缺陷中有某些从未出现，考虑合并；如果有新的模式反复出现，考虑新增分类。
- **过度规范化风险**：不要让 bad case 流程变成官僚主义——核心价值在于"从错误中学习"，而不是"把模板填完"。如果模板阻碍了记录，简化模板。

---

## 12. 行动触发器

当你接到用户纠错时：

1. 先确认：这是不是三层防线都漏网的问题？如果是自攻击或审查已经拦住的，直接修。
2. 如果是 bad case：即使现在没时间走完整流程，先在 `60_feedback/badcases/` 下创建一个最小文件（现象 + 正确做法），回头补完整模板。
3. 修完卡后：问自己——这个错误有没有可能在同类卡/同域卡里也出现？扫一遍再关。
4. 关 bad case 时：确认回流位置已经全部更新（卡 + skill + agent-spec + context，至少一个）。
