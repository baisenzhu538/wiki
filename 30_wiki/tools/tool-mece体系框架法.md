# 技能：MECE体系框架法

## 原始表述
> L2.体系框架 √雷达图：完整评价维度 √建框架：建mEcE体系 N步法：完整逻辑链条

## 操作步骤
1. 用雷达图建立完整评价维度
2. 构建MECE（ mutually exclusive, collectively exhaustive）体系
3. 形成N步法的完整逻辑链条

## Constraints & Boundaries

### 适用边界

| 边界 | 说明 |
|:-----|:-----|
| ✅ 适合 | 复杂问题分析，需要全面无遗漏的思考 |
| ✅ 适合 | 建立评价体系，需要多维比较 |
| ✅ 适合 | 需要全面无遗漏的决策，减少盲点 |
| ✅ 适合 | 问题结构清晰，元素之间可明确划分 |
| ❌ 不适合 | 简单直接的问题 → 无需MECE，直接解决 |
| ❌ 不适合 | 快速变化的市场 → 机会窗口可能关闭 |
| ❌ 不适合 | 追求突破性创新 → MECE限制框架外思考 |
| ❌ 不适合 | 复杂网状系统 → 元素之间模糊不可分 |



## Critique


**Clayton Christensen**（哈佛商学院教授）会质疑：现有方法论框架的有效性依赖于环境稳定性——当环境发生颠覆性变化时，旧框架不仅无效，还可能误导。

## 判断标准

**什么算一个好的 MECE 框架**：

| 标准 | 好的框架 | 坏的框架 |
|:---|:---|:---|
| 可操作 | 每个维度有明确的判断标准 | "重要性高/中/低"——"重要"的定义模糊 |
| 可复现 | 不同人/不同时间分出来的结果一致 | 同一个人不同时间分出来结果不一样 |
| 无遗漏 | 任意一个实例都能被某个类别覆盖 | 总能找到"哪个都不是"的例子 |
| 无重叠 | 任意两个类别的交集为空 | 某个实例同时属于多个类别 |
| 有目的 | 分类的目的是解决问题，不是展示分类技术 | 花了三天分类，问题还是那个问题 |

**自检问题**：
1. 这个框架用于解决什么具体问题？如果问题消失了，框架还有价值吗？
2. 任意一个实例放进来，能在 10 秒内确定它属于哪个类别吗？
3. 如果换一个不熟悉这个领域的人来分类，他能得到相似结果吗？
4. 最后一次使用这个框架是什么时候？如果超过 3 个月没用，说明它可能已经过时。

## 常见失败模式

| 失败模式 | 症状 | 修复 |
|:-----|:-----|:-----|
| **MECE强迫症** | 为追求"完全穷尽"在无关细节上反复拆分，分析成本远超问题价值 | 先写清要解决的决策问题并设定时间盒，接受"足够全面"而非绝对MECE |
| **分类维度不可操作** | 维度使用"重要/紧急/难"等模糊词，不同人分类结果不一致 | 每个维度必须有可观察、可量化的判断标准，三人独立分类一致性应>80% |
| **只分不合** | 搭完树状框架就存档，没有填充实例、验证覆盖度、推导出下一步动作 | 框架必须进入"填充实例→检查重叠/遗漏→导出行动"的闭环 |
| **框架维度过时** | 沿用去年的业务维度拆分今年问题，漏掉新渠道/新角色/新技术 | 每次使用前Review维度是否仍覆盖当前业务现实 |
| **把网状问题硬拆成树** | 面对相互耦合的系统强行做单一层级分类，丢失因果关系 | 对强耦合系统改用系统循环图等方法，MECE只用于可拆分模块 |
| **低估构建成本** | 承诺一小时搭完MECE框架，实际花费数天仍不完美 | upfront评估数据可得性和问题复杂度，复杂框架拆成多轮迭代 |
| **混淆MECE与优先级** | 把"分类"直接当成"排序"，认为互斥穷尽就等于知道先做哪个 | MECE负责不重不漏，优先级需另用决策标准（如ROI、风险、依赖） |
| **忽视框架外部盲区** | 框架本身基于旧假设，导致"框架外"的关键信息永远进不来 | 定期引入外行/外部视角，强制问"有什么重要信息不在当前分类里" |

## Critique

### 外部攻击

**攻击者1：贝佛斯风格企业家 —— “过度分析导致行动力丧失”**

> 在快速变化的市场中，花三天搭建一个完美的MECE框架，结果机会窗口已经关闭了。真正的创业者用“尝试—反馈—调整”循环快速迭代，而不是先搞一个理论上完美的分析框架。分析是为了行动，但很多人把分析当成了行动。

**攻击者2：设计思维实践者 —— “创新从来不是MECE的”**

> 真正的突破性创新往往来自于“看到了框架之外的东西”。MECE让你的思考完整但也让你的思考被框架限制。iPhone之所以是革命性的，是因为它跳出了“手机”的原有MECE分类（通话/发短信/上网）。
