# 人工替代复杂系统

> 在核心业务假设尚未被证实时，用人工流程临时顶替调度、订单、会员、客服等复杂系统，以验证「用户真的需要这些系统功能」以及「系统背后的业务逻辑是否成立」，而不是直接投入研发。

## 一句话定义

人工替代复杂系统是 FALSE/FLESAI 模型中 **S（Substitute）** 阶段的落地工具，它验证的假设是：**在用户需求被确认之前，那些看起来必须上线的系统模块，是否可以用更便宜、更快的人工流程先跑通业务闭环** [conf=0.85, source=framework-lean-false-model]。

## 操作步骤

1. **拆解系统清单**
   把产品第一版计划中的系统模块全部列出来，例如调度、订单、外呼、选品、会员、客服、支付等 [conf=0.90, source=一堂DOC-20260622212351_ocr_text.md]。

2. **按风险与复杂度排序**
   优先替代两类模块：
   - 开发周期长、技术复杂度高的模块；
   - 与最高风险假设直接相关、但尚未被验证的模块。

3. **设计最小人工流程**
   为每个待替代模块设计一个可在数小时到数天内启动的人工方案，典型映射如下：

   | 不做这个系统 | 用人工方式替代 | 验证什么 |
   |:---|:---|:---|
   | 调度系统 | 人工协调、微信群/电话分派 | 调度规则是否成立 |
   | 订单系统 | Excel/在线表格记录订单 | 订单流转是否顺畅 |
   | 外呼系统 | 人工电话逐一触达 | 话术与转化是否成立 |
   | 选品系统 | 人工调研、小样本试采 | 选品逻辑是否被用户接受 |
   | 会员系统 | 手工积分、CRM 表格 | 会员权益是否有吸引力 |
   | 客服系统 | 创始人/运营亲自回复 | 高频问题与痛点是什么 |
   | 支付系统 | 人工对账、二维码收款 | 付费意愿是否真实 |

   > 上述 7 组映射直接来自讲义清单 [conf=0.90, source=一堂DOC-20260622212351_ocr_text.md]。

4. **设定通过/不通过标准**
   在启动人工流程前，明确：
   - 多少人愿意使用这个人工方案？
   - 用户愿意为替代后的服务付费吗？
   - 哪些环节卡顿、哪些环节被用户忽略？

5. **跑真实用户并记录**
   用人工流程服务一小批种子用户，记录流程中的摩擦点、用户反馈和转化数据。

6. **决策：开发、调整或砍掉**
   验证通过后，再投入系统开发；验证不通过，则回到假设拆解阶段，避免把错误逻辑固化成代码。

## 成本/周期/样本量

| 维度 | 经验参考 | 说明 |
|:---|:---|:---|
| 成本 | 主要为人工时间，通常显著低于同类系统开发 | 具体倍数因项目差异较大，未在素材中给出精确比例 [conf=0.60, source=讲师经验判断] |
| 周期 | 1-4 周可完成一轮 | 取决于模块数量和用户触达难度 [conf=0.70, source=一堂课程常见经验值] |
| 样本量 | 6-20 个种子用户 | 与「只测试最小数量」工具一致，核心在于覆盖关键场景而非统计显著 [conf=0.70, source=一堂课程常见经验值] |

> 对于需要统计显著性的产品（如转化率优化），人工替代只能用于定性或方向性验证，后续仍需扩大样本。

## 适用边界

### 最适合的场景

- **O2O / 本地生活服务**：调度、订单、履约链路复杂，但早期可用微信群+表格替代。
- **平台型业务早期**：先人工撮合供需双方，验证双边市场是否成立。
- **SaaS 产品第一版**：用人工客服、人工配置替代自动化后台，先验证客户愿意为什么付费。
- **电商 / 零售创业**：用人工选品、人工会员运营替代算法和积分系统。

### 需要调整或避免的场景

- **强监管行业**：涉及支付清结算、医疗数据、金融交易等场景，人工对账或人工客服可能无法满足合规要求，需先咨询法务与行业监管规定 [conf=0.85, source=任务指令 L3 政策/合规边界]。
- **品牌敏感型高客单价产品**：粗糙的人工流程可能让客户质疑专业度，需在人工方案中保留足够的品牌体验 [conf=0.80, source=任务指令 L8 边界案例]。
- **B2B 长决策链**：客户采购流程长、涉及多人决策，人工替代订单/客服系统的验证价值有限，更适合用访谈、预售、POC 等方式验证 [conf=0.80, source=任务指令 L8 边界案例]。
- **高频高并发场景**：当并发量达到人工无法承载的临界点时，人工方案会失真，需提前设定替代方案的容量上限。

## 失败模式

| 失败模式 | 症状 | 修复 |
|:---|:---|:---|
| 人工流程比系统还重 | 运营团队 24 小时手工派单、对账，成本与错误率反超开发系统 | 为每个替代模块设定「人工成本上限」和「错误率上限」，超过即进入开发 |
| 把临时人工方案当作永久架构 | 业务已经验证成功，却仍用表格和微信群跑核心流程，成为规模化瓶颈 | 在启动人工方案时同步制定「系统化触发条件」 |
| 没有明确通过标准 | 跑了两个月人工客服，却说不出用户最高频的问题是什么 | 每次替代前定义 1-2 个可量化的验证目标 |
| 忽视合规与安全 | 人工处理支付对账、会员资金池，留下财务与法律风险 | 涉及资金与敏感数据的模块，优先咨询合规，必要时跳过人工替代 |
| 替代了不该替代的内核 | 用人工流程掩盖产品价值主张的模糊，例如人工撮合两边却没有验证双边需求 | 回到关键假设拆解，确认替代的是「系统实现」而非「价值主张」 |

## 案例映射

**教学推演：O2O 生鲜配送的订单与调度系统** [conf=0.60, source=基于讲义清单的教学推演]

- **背景**：团队计划开发一个生鲜配送平台，第一反应是自研订单系统 + 骑手调度系统。
- **人工替代方案**：
  - 用户通过微信群或小程序表单下单（不做订单系统）；
  - 运营人员在 Excel 中汇总订单，手动分配给兼职配送员（不做调度系统）；
  - 配送完成后人工在表格中标记状态，每晚统一对账（不做完整履约系统）。
- **验证假设**：
  - 用户是否愿意为「当日达生鲜」持续下单？
  - 配送半径、时段、客单价是否能支撑单位经济模型？
  - 哪些品类的复购率足够高，值得后续投入系统优化？
- **结果与决策**：
  - 若 2 周内无法稳定获得 20 个复购用户，说明需求或方案不成立，应停止或转型；
  - 若跑通，则优先开发订单与调度系统中最高频、最痛点的模块，而非一次性做全。

> 该案例为基于 FALSE 模型 S 阶段的教学推演，非特定公司真实运营数据，用于说明工具用法。

## Purpose

人工替代复杂系统的目的不是「省技术投入」，而是**把高复杂度系统的开发决策后置到关键假设被验证之后**。它帮助团队在早期避免两类浪费：

1. **过早细化**：在需求尚未被证明前，就把大量资源投入系统架构设计；
2. **闭门造车**：用系统代码固化未经用户检验的业务假设。

通过人工流程，团队可以在真实用户场景中快速学习系统逻辑的真实约束，而不是在会议室里推演。

## When NOT to Use

以下情况不宜或需谨慎使用本工具：

- **合规底线不可触碰**：支付清结算、医疗数据、用户隐私等场景，人工处理可能直接违反监管要求。
- **用户体验是核心竞争力**：如果产品卖点就是「丝滑的自动化体验」，过度人工的 MVP 会让用户产生错误认知。
- **团队没有人工运营能力**：创始人不愿意下场、没有运营人员兜底时，人工方案会迅速崩溃。
- **已经跨过早期的假设验证阶段**：当商业模式已被验证，系统开发就是核心能力时，应进入正式研发而非继续人工替代。

## Critique

本工具的局限性在于：

1. ** scalability 失真**：人工流程能验证「需求存在」，但无法验证「系统能否支撑规模化」。它回答的是「用户要不要」，而不是「系统能不能扛住」。
2. **体验天花板**：人工服务往往比自动化服务更「贴心」，可能掩盖产品本身体验设计的缺陷。
3. **容易被误用为长期方案**：一些团队以「低成本验证」为名，长期依赖表格和微信群，错失系统化的最佳窗口。

因此，人工替代复杂系统应被视为 **F/A/L/S/E 验证链中的一环**，而不是独立的最终方案。它的最佳退出条件是：已经通过人工流程确认了用户价值和业务逻辑，接下来用最小系统逐步替代人工流程。
