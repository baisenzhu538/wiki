## 操作步骤

1. **从业务痛点出发**：不要问"AI 能做什么"，而是问"我上周哪 3 件事最费时间且重复性高"。列出 5-10 个候选痛点，按"重复频率 × 人工耗时"排序，选 top 3。

2. **拆解为标准工作流**：将选定的业务任务拆成 5-8 个明确的子步骤。每个子步骤必须满足：(a) 输入明确 (b) 输出可判断对错 (c) 不依赖"感觉"或"经验"。

3. **为每个环节设计判断标准**：不仅写执行 Prompt，还要写"这个环节做对了没有"的检查规则。例如：摘要环节→检查是否包含 3 个关键数据点；分类环节→检查是否所有输入都被分到了预定义类别。

4. **用最小工具组合跑通**：第一个版本只用已有的工具——一个 LLM API + 一段胶水代码。不要引入新框架、新数据库、新部署方案。目标：从输入到输出全链路跑通一次。

5. **平行运行验证后替换**：新流程和旧流程同时运行至少 1 个月，每周对比：(a) 输出质量（抽样人工评分）(b) 时间节省 (c) 错误率。只有三项都优于人工，才正式替换。

## 常见失败模式

| 失败模式 | 症状 | 预防 |
|:
------|:-----|:-----|
| **先建平台再找场景** | 平台建了 3 个月，上线后发现没人在用 | 强制规则：找到至少 1 个每周使用 ≥3 次的场景后才开始建任何平台组件 |
| **跳过平行运行直接替换** | AI 在某个边缘 case 出错，造成业务事故 | 硬性规定：平行运行 ≥1 个月，且至少覆盖 1 个完整的业务周期（如月初到月末） |
| **工作流拆得太粗** | 某个子步骤依赖人的判断，AI 无法独立完成 | 拆解后自检：每个子步骤能否在"不看上下文、只根据输入输出"判断对错？ |
| **第一个场景选错** | 选了重复频率低或复杂度极高的场景，验证周期过长 | 第一个场景优先级公式：频率 × 人工耗时 × (1/复杂度)。选最高的 |

## Example

**场景**：电商团队每天需要从 200+ 条用户评论中分类出"售前咨询"和"售后投诉"，人工分类耗时 2 小时/天。

**按五步法执行**：
1. 痛点识别：评论分类是三件最费时的事之一（2h/天 × 22 天 = 44h/月）
2. 工作流拆解：抓取评论 → 预处理（去表情/统一格式）→ 分类 → 路由（售前→客服群/售后→工单系统）→ 标注紧急度
3. 判断标准：分类准确率 > 90%（抽 50 条人工验证）；紧急度标注漏报率 < 5%
4. 最小工具：OpenAI API + Python 脚本 + 飞书 Webhook。不建数据库，不写前端。
5. 平行运行：AI 分类 + 人工抽查 1 个月。第一周准确率 82%（不及格），调整 prompt 后第二周 91%（达标）。

**结果**：人工从 2h/天降到 30min/天（抽查+处理 AI 不确定的 case），节省 75%。

## 为什么有效

业务是内核，技术是手段。小团队的竞争优势不在技术架构，在对业务的理解深度和迭代速度。"手持锤子找钉子"的最大问题是：你花了 3 个月建锤子，但钉子在哪你并不知道。从钉子出发，锤子的规格自然就出来了。

### 外部攻击

**Fred Brooks**（《人月神话》作者）会指出："最小工具组合"的胶水代码最终会变成"大泥球"——脚本 A 依赖脚本 B 的输出格式，脚本 B 的 prompt 改了导致脚本 C 崩溃。没有架构约束的快速迭代，长期会导致系统熵增到不可维护。解决之道：在平行运行阶段就要开始设计模块间的接口契约。

**Marty Cagan**（硅谷产品管理教父）会补充：业务为先的 AI 落地方法是对的，但缺了一个关键步骤——**在步骤 1 之前要先确认这个"业务痛点"是不是真正的用户需求**。很多时候操作者觉得"痛苦"的事，对最终用户来说根本不重要。建议在步骤 1 之前加一个前置步骤：问"解决这个问题后，谁会受益？受益多少？"

## Action Triggers

| 触发场景 | 第一个动作 | 成功指标 |
|:---------|:----------|:---------|
| 老板说"我们要建一个 AI 中台" | 反问："目前有哪个具体业务场景急需 AI 提效？" | 如果能列出 ≥1 个有量化痛点的场景 → 从中台思维切换到场景思维 |
| 团队想引入 AI 但不知从哪开始 | 每人列出上周最费时的 3 个重复性任务，团队投票选 top 1 | 1 周内锁定第一个试点场景 |
| AI 试点项目已经跑了 1 个月 | 用"平行运行检查单"逐项对比 AI vs 人工的输出质量/耗时/错误率 | 三项都优于人工 → 正式替换；任一项不达标 → 继续调优或放弃 |
