# CI Implement 阶段工具：洞见嵌入运营节奏

## 原始表述

> "CI 的终点不是产出报告，而是改变销售行为。"
>
> "如果把竞品攻防卡（Battlecard）存在文件夹里等人主动来看，那等于没有。"

**Implement 阶段的核心认知**：CI 洞见必须嵌入**决策已经发生的场景**，而不是要求大家主动找文档看。

一堂调研武器库的终点是"产出报告"。CI Implement 阶段把终点延伸为"改变销售行为"——这是 CI 从成本中心变成收入引擎的最后一步。

---

## 使用场景

### 适合启动 Implement 阶段的条件

- Define + Gather + Analyze 三个阶段已经完成，有了可行动的结论
- 销售团队 ≥10 人（否则 Battlecard 维护成本高于收益）
- 组织有定期业务复盘节奏（forecast call / deal review / QBR）
- 管理层愿意把 CI 纳入这些节奏（否则 Implement 无处嵌入）

### 不适合的情境

- 只有 1-2 个销售（维护 Battlecard 的成本太高，先用简化版）
- 没有任何定期业务复盘节奏（CI 无处嵌入，先建立节奏再做 Implement）
- 期望"设一次就不用管了"——Battlecard 需要季度更新，否则快速过时

---

## 操作方法

### 第一步：按部门制作可使用的交付物

| 部门 | 交付物 | 使用场景 |
|:---|:---|:---|
| **销售** | Battlecard（竞品攻防卡） | 销售在准备订单时快速查阅 |
| **销售运营（RevOps）** | CRM 竞品追踪字段标准化 | 每次输单/赢单时结构化录入竞品接触信息 |
| **市场** | 定位更新、证明素材库 | 市场内容生产时引用差异化要点 |
| **产品** | 差距分析、路线图决策输入 | 产品规划会上的竞品对标输入 |

### 第二步：Battlecard 制作标准

**Battlecard 不是竞品档案**——它的唯一目的是**帮销售赢单**。

**标准 Battlecard 结构**（一页纸，不前于 5 分钟能读完）：

```
┌─────────────────────────────────────┐
│ 竞品 X Battlecard（2026-Q3 版）    │
├─────────────────────────────────────┤
│ 🔴 竞品 X 赢我们的场景（必读）      │
│    • 场景 1：...                  │
│    • 场景 2：...                  │
├─────────────────────────────────────┤
│ 🟢 我们的反击话术（按异议分类）    │
│    • 异议："竞品 X 更便宜"        │
│    • 回应："..."（附证明点）      │
├─────────────────────────────────────┤
│ 🟡 竞品 X 的弱点（我们的机会）    │
│    • ...                           │
├─────────────────────────────────────┤
│ 📊 证明素材（用什么证明我们说的话）│
│    • 客户案例：...                │
│    • 数据：...                    │
├─────────────────────────────────────┤
│ 🔵 什么时候不要打竞品 X（避坑）  │
│    • ...                           │
└─────────────────────────────────────┘
```

### 第三步：嵌入决策发生的场景

**核心原则**：CI 必须出现在这些高频业务场景中，而不是要求大家主动看文档。

| 嵌入场景 | CI 出现形式 | 频率 |
|:---|:---|:---|
| **Forecast Call（预测会）** | "本周竞品出现在多少个订单中？趋势？" | 每周 |
| **Deal Review（订单复盘）** | "输给竞品 X 的订单，根因是什么？" | 每次大额订单复盘 |
| **QBR（季度业务复盘）** | "竞品 X 的本季度动作 + 下季度应对" | 每季度 |
| **销售赋能培训** | Battlecard 角色扮演演练 | 每月或新员工入职 |
| **CRM 录入** | 竞品接触强制字段（哪個竞品、什么场景、谁赢） | 每次订单录入 |

### 第四步：轻量 Governance（避免信息过载）

**只需要 4 个规则**：

1. **1 名负责人**：CI 项目所有者，负责更新节奏和质量
2. **1 个信息录入路径**：统一用 CRM 竞品字段，不分散在多个地方
3. **1 套输出标准**：Battlecard 统一模板，不每个人自己建格式
4. **定期优先级排序会**：每季度，销售 + 产品 + 市场一起决定下季度重点追踪的竞品

---

## CI 资产度量（证明 CI 真的有用）

**为什么需要度量**：CI 项目容易被砍，如果没有证明"它真的有用"。

### 业务结果指标（最关键）

| 指标 | 定义 | 目标 |
|:---|:---|:---|
| **Tier 1 竞品赢单率** | 和 Tier 1 竞品同台竞标时的赢单比例 | 持续提升（例如 +10%） |
| **竞争类订单的销售周期** | 涉及竞品的订单的平均销售周期 | 缩短（CI 帮销售更快应对异议） |
| **定价 hold 住的比例** | 最终成交价 vs 初始报价的偏差 | 提升（CI 帮销售更好捍卫价值） |

### 运营结果指标（过程指标）

| 指标 | 定义 | 目标 |
|:---|:---|:---|
| **Battlecard 使用率** | 销售在订单准备中引用 Battlecard 的比例 | >60%（用 CRM 或 Salesforce 插件追踪） |
| **从信号到洞见的时间** | 竞品动作出现 → 销售收到可行动 Battlecard 更新的时间 | <7 天 |
| **输单原因中"未知"占比** | CRM 中"输单原因=未知竞品优势"的占比 | 降低（说明 CI 在覆盖真实竞品优势） |

---

## 适用边界

### Implement 阶段生效的前提

- **Define 阶段做得好**：如果 KIQs 没有绑定具体决策，Implement 阶段的交付物会"答非所问"
- **Gather + Analyze 阶段有产出**：没有可行动的结论，Implement 无物可嵌
- **组织有嵌入场景**：如果没有 forecast / deal review / QBR 节奏，CI 只能"存在文件夹里"

### 小团队简化版（<10 个销售）

- Battlecard 只做 Tier 1 竞品（1-2 个），不做全覆盖
- 嵌入场景只选 1 个（优先 forecast call）
- 更新频率降为每半年（而非每季度）

---

## 为什么值钱

1. **直接绑定收入**：CI 的成败标准是"竞品赢单率变化"，不是"报告质量"——可衡量，不是虚的。
2. **一堂武器库的自然延伸**：Gather 阶段完全复用三层八模块，Implement 是最后一块拼图。
3. **把"隐性竞争知识"变成"组织资产"**：销售个人的竞品应对经验，通过 Battlecard 变成所有人可用的资产。
4. **避免"分析瘫痪"**：Implement 阶段的"嵌入场景"强制 CI 产出必须是"可行动的"，不能是"供欣赏的报告"。

## 失败模式

| 失败模式 | 症状 | 根因 | 修正方法 |
|:---|:---|:---|:---|
| **"吃灰症"** | Battlecard 存在 Confluence / Notion 里，销售不知道也不使用 | CI 没有嵌入决策场景 | 选 1 个高频场景（优先 forecast call）先嵌入，验证有效再扩展 |
| **"完美 Battlecard 症"** | Battlecard 写得像竞品档案（10+ 页），销售不看 | 没有遵循"一页纸，5 分钟读完"标准 | 强制 Battlecard ≤2 页，只保留"帮销售赢单"的内容 |
| **"过时症"** | Battlecard 还是去年版的，竞品已经改了定价策略 | 没有更新节奏 | 设置 Tier 1 竞品 Battlecard 季度更新日历 |
| **"无度量症"** | CI 项目运行了一年，但没人知道它有没有用 | 没有设立 CI 资产度量指标 | 从"Tier 1 竞品赢单率"开始，至少追踪 1 个业务结果指标 |

## Action Checklist

- [ ] **选择嵌入场景**：选 1 个高频业务场景（优先 forecast call），先嵌入，验证有效再扩展
- [ ] **Battlecard**：只做 Tier 1 竞品（1-2 个），遵循"一页纸"标准
- [ ] **设立 CI 资产度量指标**：至少 1 个业务结果指标（优先"Tier 1 竞品赢单率"）
- [ ] **Governance**：1 名负责人 + 1 个信息录入路径 + 1 套输出标准
- [ ] **和销售确认**：Battlecard 的话术和证明点，是不是销售实际能用的？（不是"产品市场部认为的结论"）

## 质疑

> 待补充：这个工具的内在局限是什么？外部反对者会怎么批评？

**Michael Porter** 可能会质疑：这个工具依赖的 **执行资源、组织响应速度、情报行动假设、反馈闭环** 是否已经被充分验证？

- 情报若不转化为可执行决策，只是昂贵的信息堆砌。
- 实施阶段需要明确责任人和反馈机制，否则情报会变成一次性的报告。

- 使用前应明确本工具的 **具体假设**、适用 **边界**、潜在 **反例** 和隐含 **前提**，避免把模板输出直接当成战略结论。
