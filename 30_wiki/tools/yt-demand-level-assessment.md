# 需求分析段位自评表：从L1到L6的进阶路径

> 一堂五步法：需求分析有段位，从"能描述功能"到"能预判需求变化"。

## 核心框架

| 段位 | 名称 | 核心能力 | 标志 | 典型错误 |
|:---|:---|:---|:---|:---|
| **L1** | 初心者 | 能描述产品功能 | "我们做一个XX平台" | 把功能当需求 |
| **L2** | 探索者 | 能说出用户问题 | "用户需要高效管理" | 问题描述太泛 |
| **L3** | 分析者 | 能拆推评算 | 有框架，有分析 | 分析未验证 |
| **L4** | 验证者 | 拆推评算+用户验证 | 有访谈，有数据 | 验证范围不足 |
| **L5** | 洞察者 | 能发现用户没说出的需求 | 从行为数据中发现新需求 | 洞察未验证 |
| **L6** | 预判者 | 能预测需求变化，提前布局 | 需求趋势预判+产品路线图 | 预判过于主观 |

## 关键洞察

### 1. 段位进阶的关键跃迁

| 跃迁 | 从 | 到 | 关键动作 |
|:---|:---|:---|:---|
| L1→L2 | 功能视角 → 用户视角 | 用"用户的问题是..."替代"我们做了一个..." |
| L2→L3 | 问题描述 → 结构化分析 | 掌握拆推评算四步法 |
| L3→L4 | 分析假设 → 验证假设 | 至少访谈10个用户，收集数据 |
| L4→L5 | 验证已知 → 发现未知 | 从用户行为数据中发现新需求 |
| L5→L6 | 发现现在 → 预判未来 | 建立需求趋势监测机制 |

### 2. 段位自评的测试题

**L1测试**：
- 你能用3句话描述你的产品吗？
- 如果描述中全是功能（"我们有一个XX功能"），不是用户问题（"用户的问题是..."），则是L1。

**L2测试**：
- 你能说出用户的核心问题吗？
- 如果问题描述超过5句话，或包含多个问题，则是L2。

**L3测试**：
- 你能完成拆推评算四步吗？
- 如果每一步都有明确答案，则是L3。

**L4测试**：
- 你的拆推评算有用户验证吗？
- 如果有访谈记录、转化数据支撑，则是L4。

**L5测试**：
- 你能从用户行为数据中发现新需求吗？
- 如果曾因数据洞察而新增/砍掉功能，则是L5。

**L6测试**：
- 你能预测未来6个月的需求变化吗？
- 如果预测准确率>70%，则是L6。

### 3. 团队段位对齐

团队需求分析能力不一致时：

- **对齐方法**：一起填一张拆推评算表，对比差异
- **常见问题**：
  - 创始人L4，团队L2 → 团队执行不到位
  - 创始人L2，团队L4 → 创始人决策偏差
  - 全员L3 → 缺乏验证，需要推动L4

## 失败模式

| 失败模式 | 症状 | 修复方法 |
|:---|:---|:---|
| **段位自我高估** | "我懂用户"，但实际L1-L2 | 用测试题自评，寻找反例 |
| **段位停滞不前** | 长期L3，未验证到L4 | 强制要求每个分析必须有用户验证 |
| **团队段位断层** | 创始人L5，团队L2 | 建立统一的需求分析流程和模板 |
| **忽视段位进阶** | 满足于"能分析"，不追求"能洞察" | 建立数据洞察机制，定期复盘 |
| **段位与角色不匹配** | 产品经理L6，但CEO只有L2 | CEO必须参与需求分析，提升段位 |

## 适用边界

| 适用场景 | 不适用场景 |
|:---|:---|
| 个人能力评估 | 技术能力评估 |
| 团队能力对齐 | 运营能力评估 |
| 招聘需求分析师 | 销售能力评估 |
| 培训需求分析能力 | 设计能力评估 |

## 行动触发器

- 当你说"我懂用户"时 → 用测试题自评，寻找反例
- 当团队争论需求时 → 一起填拆推评算表，对齐段位
- 当做完分析后 → 检查是否验证了，还是停留在假设
- 当发现新需求时 → 记录数据来源，建立洞察机制
