# 技能：模型组合调用

## 原始表述
> 5.模型组合

## 操作步骤
1. 分析任务链条，识别各环节所需能力
2. 为每个环节匹配最适合的模型
3. 设计模型间的数据传递格式
4. 串联或并联执行

## 目的

解决单一AI模型无法覆盖复杂任务链路中不同环节的能力需求问题。不同AI模型在不同维度上各有优劣——有的擅长创意发散、有的擅长逻辑推理、有的擅长格式化输出。面对一条包含多环节的任务链（如需求分析→方案生成→细节验证→格式排版），试图用单一模型完成所有环节往往效果不佳。模型组合调用通过分析任务链各环节所需能力→为每个环节匹配最适模型→设计模型间数据传递格式→串联或并联执行，实现"各取所长"的模型编排。适用于复杂AI工作流设计、多步骤AI自动化、以及需要精确控制输出质量的AI应用开发场景。

## 不要用的场景

任务链路过短（单步骤即可完成），或组合调用的编排成本超过收益时不应使用。当任务本身不到3个环节时，模型切换的上下文传递损耗可能大于模型优化带来的收益。简单问答、单次生图、简短翻译等轻量任务直接调用单一模型即可。此外，在模型质量差异不大的维度上（如两个模型在某任务上表现接近），强行组合切换带来的边际收益微弱，增加的编排复杂度不值得。

## 质疑

模型组合调用增加了系统的编排复杂度和故障点，在工程实践中面临"收益被复杂度吞噬"的风险。**Chip Huyen**（ML系统设计专家）指出，在生产环境中，多模型流水线的调试难度远超单模型方案——当输出质量不达预期时，你无法快速定位是哪个模型在哪个环节出了问题。**Jack Clark**（Anthropic联合创始人、AI政策研究者）从成本角度批评，多模型调用意味着每个环节的数据传递都可能导致"上下文膨胀"和token浪费——模型A生成的输出被输入给模型B时，B需要重新处理大量已经分析过的信息。

进一步审视这一方法的四类关键术语：
- **具体假设**：任务链中每个环节的能力需求可以被清晰拆分，并且存在显著优于通用模型的专用模型或模型版本。
- **边界**：组合收益必须超过编排、调试、延迟和上下文传递所带来的额外成本；一旦任务链路短于 3 个环节或各环节能力差异不大，组合调用就失去优势。
- **反例**：许多长文本总结、代码生成或创意写作任务中，单一大型模型配合精心设计的 prompt 与后处理，效果并不亚于多模型流水线，且故障面更小。
- **前提**：前提是团队具备足够的 MLOps/提示工程能力、可观测的模型输出日志，以及允许迭代调优的预算与时间；缺乏这些前提时，盲目组合反而降低系统可靠性。

对于大多数商业应用场景，一个足够好的模型搭配好的 prompt 工程，可能比精心编排的多模型流水线更可靠、更经济。
