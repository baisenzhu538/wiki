# 技能：动手建模法

## 原始表述
> L3.动手建模 √整理框架：梳理流程方法 √提炼本质：挖掘底层原理

## 操作步骤
1. 整理框架：把学到的内容梳理为流程方法
2. 提炼本质：挖掘底层原理和核心要素

## Constraints & Boundaries

### 适用边界

| 边界 | 说明 |
|:-----|:-----|
| ✅ 适合 | 学习后需要内化时，把知识转化为自己的产出 |
| ✅ 适合 | 需要传授他人或标准化时，建立可复用的框架 |
| ✅ 适合 | 复杂问题需要结构化分析时，降低认知负荷 |
| ✅ 适合 | 团队知识沉淀，需要统一认知语言 |
| ❌ 不适合 | 仅为了解常识，无需深入应用 → 建模成本超过收益 |
| ❌ 不适合 | 问题过于简单，一句话能说清 → 过度建模 |
| ❌ 不适合 | 没有使用场景，建完即弃 → 浪费建模投入 |
| ❌ 不适合 | 信息不足，无法提炼本质 → 强行建模产出空架子 |

## 判断标准

**什么算一个好模型**：

| 标准 | 好的模型 | 坏的模型 |
|:---|:---|:---|
| 有内容 | 框架分类下面有具体的行为标准、判断依据 | "分了三类但每类都是空的"——只有框架没有洞察 |
| 可操作 | 别人照着模型的步骤能执行并得到相近结果 | 太抽象或太复杂——看懂它的人做不了，能做的人不需要它 |
| 有迭代记录 | 模型有版本号，标注了每次更新修正了什么 | 第一版用了一年没改过——模型是假设，需要持续验证 |
| 有使用证明 | 过去一个月至少用这个模型解决过一个真实问题 | 写得漂亮的模型静静躺在文件夹里，从来没用过 |

**自检问题**：
1. 这个模型最近用过了吗？如果超过 1 个月没用，它可能已经过时了。
2. 模型里的分类，是否不同人/不同时间分类结果一致？——如果不一致，说明维度不够客观。
3. 用一个真实案例跑一遍这个模型，它能覆盖所有关键因素吗？——如果总有例外，说明模型还需要修正。

## 常见失败模式

| 失败模式 | 症状 | 修复 |
|:-----|:-----|:-----|
| **建空架子** | 框架分得很细，但每个分类下只有标题，没有判断标准、行为动作或案例 | 每个分类必须补充"看到什么现象算属于这一类"和"这一类该怎么处理" |
| **本质提炼失败** | 模型只罗列流程步骤，没有回答"为什么这一步有效" | 追问三步：这个步骤依赖什么前提？在什么情况下会失效？能否迁移到其他场景？ |
| **过度建模** | 用三层框架解释一个两步就能说清的问题 | 先尝试用一句话概括规律；只有一句话说不清楚时才引入结构 |
| **建完不用** | 模型写完后存入知识库，一个月内没有用来解决真实问题 | 建模后必须绑定一个近期要处理的具体问题，并设定使用回检时间 |
| **建完不迭代** | 模型沿用超过一个月，遇到反例时靠"例外"解释而不是修正模型 | 每次使用模型后记录"覆盖住的"和"没覆盖住的"，定期合并反例升级版本 |
| **维度不客观** | 同一案例由不同人分类会得到不同结果 | 把分类标准改为可观察、可量化或可验证的描述，两人独立分类后比对一致性 |
| **框架僵化** | 面对新情况时强行套用旧模型，而不是修正模型 | 明确写出模型的三个失效条件，遇到反例立即更新或拆分出新模型 |
| **协作断层** | 只有建模者自己能用，他人看不懂或按步骤执行结果不一致 | 让一位不熟悉背景的人按模型独立操作一次，根据偏差补充中间假设和示例 |

## 质疑

- **具体假设**：该工具假设结构化方法论能提升效果，但方法论的有效性取决于执行者的判断力和场景适配——没有判断力的执行只是'走流程'，不等于'做好事'。
- **边界**：在全新领域或快速变化的环境中，已有数据和经验可能完全失效——工具的有效性高度依赖场景的稳定性。
- **前提**：该工具的前提是使用者能正确理解和执行工具的规则，但执行者的认知偏差和经验限制会影响工具的实际效果。

**Peter Drucker**（管理学大师）会质疑：工具的价值不在于"有没有"，而在于"用得好不好"。任何工具都是"能力放大器"——如果使用者的判断力不足，工具只会放大错误。真正的风险不是"缺少工具"，而是"有了工具后产生的虚假安全感"——让你以为自己已经覆盖了所有可能性，实际上只是走完了流程。
