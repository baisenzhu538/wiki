# L3圈定核心任务

> 如果L1/L2是"谁在什么情况下有什么问题"，L3就是"他们真正要完成什么"。关键：方案中立——不能用特定产品/技术的语言描述任务。

## JTBD核心任务公式

```
核心任务 = 动词 + 对象 + 语境
```

| 方案绑定（差） | 方案中立（好） |
|:---|:---|
| "用App点外卖" | "在不想做饭的晚上，快速获得一顿热饭" |
| "在淘宝上买衣服" | "为下周的面试准备一套得体的穿搭" |
| "用Zoom开会" | "和异地团队高效同步项目进度" |

## 为什么方案中立如此重要

一旦你在L3说了"用App点外卖"，你就已经把"App"这个方案锁死了。你不再会去想：也许用户真正需要的是"附近的食堂延长营业时间"或"预制菜配送"。

## 失败模式

| 失败 | 症状 | 修复 |
|:---|:---|:---|
| 方案绑定 | 核心任务里出现了产品/技术名词 | 去掉所有方案词汇，只留动词+名词+情境 |
| 太宽泛 | "高效工作"——什么任务？ | 加动词+对象，直到可被观察和测量 |

## 质疑

- **具体假设**：该工具假设"方案中立的'动词+对象+语境'能准确描述核心任务"，但方案中立是一个理想化的概念——用户对任务的理解本身就受到现有方案的影响。用户描述"我想在通勤时听新闻"时，"听"这个动词已经预设了"音频"方案，而非"阅读"或"视频"。
- **边界**：在情感型任务（如"感觉被重视"）中，"动词+对象+语境"的结构化描述几乎不可能——情感任务没有明确的"对象"和"语境"。
- **反例**：iPhone 的核心任务如果用方案中立描述是"在移动中获取信息和沟通"——但这个描述同样适用于黑莓手机。真正让 iPhone 不同的不是"任务"，而是"体验"——而体验无法被方案中立的描述捕捉。

**Bob Moesta**（JTBD 实践者，ReWired Group 创始人）会质疑：方案中立的目的是避免"以现有方案定义需求"，但实践中几乎不可能做到完全方案中立——因为我们使用的语言本身就是被现有方案塑造的。更务实的做法不是"追求方案中立"，而是"刻意描述多个不同的方案路径"——通过对比不同方案如何满足同一需求，来逼近"任务本身"的本质。
