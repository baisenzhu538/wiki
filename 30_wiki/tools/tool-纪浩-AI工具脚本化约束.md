# 技能：AI工具脚本化约束

- src_unknown

## 原始表述

AI工具脚本化约束是纪浩在AI协作方法论分享中提出的具体方法，用于AI工具脚本化约束。

## 操作步骤

1. 识别AI执行中的重复操作（如查目录、找文件、读表格、查数据库、验证结果）
2. 将这些操作写成确定性脚本，而非让AI随机执行
3. 将脚本纳入Agent工具集
4. 要求AI优先调用工具而非自主分析

## Constraints & Boundaries

### 适用边界

| 边界 | 说明 |
|:-----|:-----|
| ✅ 适合 | AI执行结果不稳定、随机性高时，需要确定性输出 |
| ✅ 适合 | 需要与外部系统（数据库、飞书等）交互时，确保调用正确 |
| ✅ 适合 | 有重复性验证步骤时，需要可复用工具 |
| ✅ 适合 | AI自主分析产生幻觉，需要基于真实数据做分析 |
| ❌ 不适合 | 完全开放性的创意任务 → 脚本化会扼杀创意发散 |
| ❌ 不适合 | 一次性探索性任务 → 脚本编写成本超过收益 |
| ❌ 不适合 | 快速变化的需求 → 脚本维护成本过高 |
| ❌ 不适合 | 无技术能力编写脚本 → 需要先有脚本开发能力 |

#| 模式 | 症状 | 修复 |
|:-----|:-----|:-----|
| **随机输出** | AI执行结果不稳定，每次输出格式不一致 | 识别重复操作，写成确定性脚本。AI不脚本化则行为随机，脚本化确保操作确定性 |
| **外部交互失败** | AI与外部系统交互时出错，如查数据库、调API失败 | 将外部交互写成脚本，纳入Agent工具集。要求AI优先调用工具而非自主分析 |
| **重复描述** | 重复性验证步骤每次都要重新描述，效率低下 | 将验证步骤脚本化，变成可复用工具。一次编写，多次调用 |
| **分析幻觉** | AI自主分析时产生幻觉，数据查询结果不准确 | 要求AI优先调用工具获取数据，再基于数据做分析。不要让AI直接'知道'数据 |
| **脚本耦合** | 脚本维护成本高，改一处坏多处 | 脚本模块化设计，每个脚本只做一件事。做好版本控制，变更前测试兼容性 |
| **过度脚本化** | 所有任务都脚本化，灵活性丧失 | 区分确定性任务（脚本化）和探索性任务（保持开放）。不是所有任务都需要脚本 |
| **工具滥用** | AI调用工具但不理解工具输出，机械拼接 | 要求AI在调用工具后解释输出含义，再基于理解做下一步决策 |
| **脚本过时** | 外部系统API变更，脚本失效 | 定期Review脚本有效性（每月），建立脚本健康检查机制 |

## 为什么有效

AI不脚本化则行为随机，脚本化可确保操作确定性和结果可验证。将重复操作固化为工具，降低认知负担，提升执行一致性。

## 质疑

- **具体假设**：该工具假设结构化方法论能提升效果，但方法论的有效性取决于执行者的判断力和场景适配——没有判断力的执行只是'走流程'，不等于'做好事'。
- **边界**：在全新领域或快速变化的环境中，已有数据和经验可能完全失效——工具的有效性高度依赖场景的稳定性。
- **前提**：该工具的前提是使用者能正确理解和执行工具的规则，但执行者的认知偏差和经验限制会影响工具的实际效果。

**Peter Drucker**（管理学大师）会质疑：工具的价值不在于"有没有"，而在于"用得好不好"。任何工具都是"能力放大器"——如果使用者的判断力不足，工具只会放大错误。真正的风险不是"缺少工具"，而是"有了工具后产生的虚假安全感"——让你以为自己已经覆盖了所有可能性，实际上只是走完了流程。
