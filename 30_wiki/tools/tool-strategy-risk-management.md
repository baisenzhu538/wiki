# 业务设计风险管理工具：ISO31000 四步闭环 × Grace LaConte 矩阵

> 业务设计六要素第 6 要素。核心问题：**业务设计有哪些关键风险？如何应对？**

---

## 一、风险管理四步闭环（ISO31000 / PMBOK）

| 步骤 | 英文 | 核心动作 | 输出物 |
|--|--|--|--|
| 1. 风险识别 | Identify | 系统找出潜在风险 | 风险清单 |
| 2. 风险评估 | Analyze | 量化可能性与影响 | 风险矩阵 |
| 3. 风险应对 | Respond | 制定应对策略 | 应对计划 |
| 4. 风险监控 | Monitor | 跟踪与调整 | 风险看板 |

---

## 二、风险识别清单

### 2.1 内部风险

| 类别 | 典型风险 | 检查问题 |
|--|--|--|
| 能力风险 | 核心能力缺失、人才短缺 | 我们的关键能力是否足够支撑新业务设计？ |
| 资源风险 | 资金、技术、数据不足 | 资源投入是否匹配战略优先级？ |
| 组织风险 | 部门墙、变革阻力 | 组织结构和流程是否能支撑新设计？ |

### 2.2 外部风险

| 类别 | 典型风险 | 检查问题 |
|--|--|--|
| 市场风险 | 需求变化、竞争加剧 | 客户是否真的会为价值主张买单？ |
| 对手风险 | 竞品模仿、价格战 | 对手最可能攻击我们的哪个弱点？ |
| 技术风险 | 技术迭代、替代品 | 技术路线是否可能突然变化？ |
| 政策风险 | 监管变化、合规要求 | 政策是否会影响我们的盈利模型？ |

---

## 三、风险评估：Grace LaConte 矩阵

PPT `_129` 采用影响程度（Severity）× 发生可能性（Likelihood）矩阵：

```
                影响程度 Severity
                Low        High
可能性    High   低风险      高风险
Likelihood       策略：接受   策略：减轻
          Low    低风险      中风险
                 策略：接受   策略：控制
```

> 注：PPT 中四象限为：接受 / 控制 / 分担 / 减轻。以下为更常用的完整版：

| 可能性 \ 影响 | 低影响 | 高影响 |
|--|--|--|
| **高可能** | 低风险：接受（Accept） | 高风险：减轻（Mitigate） |
| **低可能** | 低风险：接受（Accept） | 中风险：控制（Control） |

**补充策略：**
- **分担（Share）**：通过合作、外包、保险等方式共担风险
- **规避（Avoid）**：退出高风险活动或改变策略方向

### 3.1 风险评分模板

```markdown
| 风险 | 类别 | 可能性 (1-5) | 影响 (1-5) | 风险等级 | 应对策略 | 负责人 | 截止日期 |
|--|--|--|--|--|--|--|--|
| 供应链波动 | 外部 | 4 | 4 | 高 | 减轻：双供应商 | | |
| 竞品抄袭 | 外部 | 3 | 4 | 高 | 减轻：加速专利 | | |
| 现金流压力 | 内部 | 3 | 5 | 高 | 控制：分阶段投入 | | |
| 组织变革阻力 | 内部 | 4 | 3 | 中 | 分担：变革管理顾问 | | |
```

## 四、风险应对策略选择

| 策略 | 适用场景 | 典型动作 |
|--|--|--|
| **接受 Accept** | 影响小、可能性高，或成本高于收益 | 监控即可，不额外投入 |
| **控制 Control** | 影响大、可能性低 | 建立流程、规范、预案 |
| **减轻 Mitigate** | 影响大、可能性高 | 主动降低概率或影响 |
| **分担 Share** | 单方承担成本过高 | 保险、外包、合作、联盟 |
| **规避 Avoid** | 风险不可接受 | 退出市场、停止项目、改变模式 |

## 五、业务设计风险示例（PPT _131）

PPT `_131` 以某零食企业为例：

| 六要素 | 风险识别 | 应对策略 |
|--|--|--|
| 客户选择 | 线上获客能力弱，数据标签体系缺失 | 建设数据中台 |
| 价值主张 | 产品研发周期长，情感品牌塑造经验不足 | 小步快跑测试，引入品牌顾问 |
| 价值获取 | 会员运营系统未建，定价溢价客户接受度低 | MVP 验证会员模型 |
| 活动范围 | 供应链协调难度大，数字化能力不足 | 分阶段外包+数字化投入 |
| 战略控制 | 数据中台建设投入大，人才短缺 | 引入外部专家+内部培养 |
| 风险管理 | 依赖线下客流 | 双供应商、加速专利、分散渠道 |

## 六、Agent 执行指令

```python
def design_risk_management(business_design: dict):
    """为业务设计建立风险管理体系"""
    prompts = {
        "识别": f"""基于业务设计{business_design}，
从内部（能力/资源/组织）和外部（市场/对手/技术/政策）识别风险。""",
        "评估": "用可能性×影响矩阵评估每个风险，确定风险等级。",
        "应对": "为每个高风险选择接受/控制/减轻/分担/规避策略，制定具体动作。",
        "监控": "设计风险看板：多久review一次、触发什么升级机制、谁负责。"
    }
    return {step: ask(prompt) for step, prompt in prompts.items()}
```

## 七、失败模式

| 失败 | 症状 | 修复 |
|--|--|--|
| 风险清单流于形式 | 列了很多风险但没有评估 | 强制打分和排序，只聚焦 Top 5 |
| 只有识别没有应对 | 知道风险但无动作 | 每个高风险必须配负责人、策略、Deadline |
| 应对策略单一 | 所有风险都“加强管理” | 按矩阵选择不同策略 |
| 不更新 | 年初做一次就放下 | 建立月度/季度风险review机制 |
