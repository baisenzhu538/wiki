# 常见模型武器库：按问题难度调用模型

> **Burn line**: 建模高手不是会很多模型，而是知道什么问题用什么模型。

常见模型武器库是抽象建模阶段的**模型选型工具**。它将常用模型按问题难度分为三层：基础模型（简单）、进阶模型（更难）、深度模型（最难），帮助创作者根据问题复杂度快速选择合适的建模结构，避免「杀鸡用牛刀」或「用小刀砍大树」。

---

## 用一句话讲清楚

按问题难度把常用模型分成「基础—进阶—深度」三层，让建模者快速匹配结构、避免难度错配。

---

## 核心要点

1. **模型是结构，不是答案**。武器库提供的是表达和思考的结构，最终洞察仍需人来完成。
2. **先判难度，再选模型**。同一问题对不同团队难度可能不同，但必须先有共识，否则容易错配。
3. **三层递进，可组合使用**。复杂项目通常需要「基础模型整理信息 → 进阶模型结构化 → 深度模型提炼洞察」的叠加。
4. **图形不等于深度**。三角图、冰山图本身不带来洞察，真正深度的是思考过程。
5. **避免模型堆砌**。不是用得越多越好，而是越匹配越好；一个清晰的 SOP 往往胜过糟糕的本质公式。

## Purpose

帮助建模者根据问题难度快速选择合适的模型结构，避免模型过简或过繁，提升抽象建模的效率和质量。

---

## Protocol

### 步骤 1：判断问题难度

| 难度 | 问题特征 | 典型问法 |
|---|---|---|
| **简单** | 重复发生、信息明确、答案确定 | 「这件事的标准步骤是什么？」 |
| **更难** | 多维度、需比较、需排序 | 「如何从多个方案中选最优？」 |
| **最难** | 底层原因、创新突破、跨领域 | 「这个领域的本质是什么？」 |

### 步骤 2：选择模型类型

| 问题类型 | 推荐模型 |
|---|---|
| 信息整理 | 清单、案例包、画布 |
| 流程执行 | SOP、模板 |
| 多维度评估 | 雷达图、N 要素 |
| 分类对比 | 二分法、象限图、横纵表 |
| 优先级排序 | SABC 分级、段位图 |
| 因果关系 | 逻辑链、漏斗图、公式 |
| 洞察本质 | 三角图、冰山图、圈层图 |
| 创新突破 | 三环图、曲线图、火箭图 |
| 底层定义 | 本质、本质 N 要素 |

### 步骤 3：组合与验证

1. 先用基础模型整理信息。
2. 再用进阶模型进行结构化分析。
3. 最后用深度模型提炼洞察或本质。
4. 用「撞击实验」寻找反例，验证模型边界。

## 代表性模型使用指南

| 模型 | 适用问题 | 使用步骤 | 典型场景 | 常见错误 |
|---|---|---|---|---|
| **清单/Checklist** | 高频重复任务，怕漏步骤 | ① 列出所有关键步骤 ② 标注检查标准 ③ 设定触发条件 ④ 迭代更新 | 直播前准备、活动复盘、新人 onboarding | 把清单当万能工具，用于需要判断的复杂决策 |
| **SOP** | 需要稳定产出的流程 | ① 定义输入/输出 ② 拆分到可检查动作 ③ 加关键节点检查 ④ 写明边界和异常处理 | 客服话术、内容生产、数据录入 | 步骤太粗或太细，没有监督机制 |
| **雷达图** | 多维度评估/评选 | ① 确定 4-6 个维度 ② 定义每个维度的评分标准 ③ 打分 ④ 排序并讨论分歧 | 讲师评选、供应商评估、方案比选 | 维度之间不独立（违反 MECE），权重不明确 |
| **象限图/二分法** | 分类、优先级 | ① 选择两个关键维度 ② 定义坐标轴含义 ③ 把案例放入象限 ④ 为每个象限制定策略 | 客户分层、任务优先级、产品定位 | 维度选择不关键，导致分类无意义 |
| **逻辑链/漏斗图** | 因果分析、流程优化 | ① 写出结果 ② 逆向追问"导致它的直接因素" ③ 检查因果 vs 相关 ④ 找到杠杆变量 | 转化率提升、问题归因、增长拆解 | 把相关当因果，跳过中间变量 |
| **三角图** | 本质提炼、三要素平衡 | ① 找出三个相互支撑的要素 ② 验证缺一不可 ③ 推导出具体策略 | 商业模式、组织能力、产品内核 | 三个要素其实是同一维度，或有一个是结果而非原因 |
| **冰山图** | 从表象到本质 | ① 列出事件/行为 ② 下挖到模式、结构、信念 ③ 找到杠杆变量 | 问题反复出现、团队冲突、组织惯性 | 停在"模式"层，没有真正下到"信念/结构"层 |

## 边界

| 边界 | 说明 |
|------|------|
| **难度判断主观** | 同一问题对不同人难度不同，需结合团队共识。 |
| **模型不是答案** | 模型提供结构，最终判断仍需人来做。 |
| **避免模型堆砌** | 不是用得越多越好，而是越匹配越好。 |
| **AI 边界** | AI 可推荐模型，但需人类判断问题难度和模型适配性。 |
| **不能替代数据** | 抽象建模需要案例和样本支撑，空模型无意义。 |
| **不能替代问题定义** | 问题未澄清时，再好的模型也会输出错误结构。 |

---

## 失败模式

| 失败模式 | 典型症状 | 根因 | 修复方案 |
|---|---|---|---|
| **难度错配：杀鸡用牛刀** | 用三角图、本质公式解决简单执行问题 | 过度追求深度，忽视成本 | 降维到清单/SOP/模板 |
| **难度错配：小刀砍大树** | 用清单/SOP 解决复杂战略问题 | 害怕复杂，停留在表层 | 升维到逻辑链/象限图/本质模型 |
| **模型堆砌** | 一张图里塞了 5+ 模型，读者看不懂 | 误以为多=专业 | 选定 1 个主模型，其余作为补充 |
| **图形替代思考** | 画了冰山图但没有真洞察 | 把图形形状当深度 | 先写清楚核心观点，再选图形 |
| **数据不足就建模** | 模型很完整但缺少案例验证 | 样本太少或代表性差 | 先收集 10+ 案例，再做抽象 |
| **问题未清先建模** | 模型结构和真实问题对不上 | 跳过问题定义 | 先用 5W2H/问题澄清画布明确问题 |

## When NOT to Use

| 场景 | 为什么失效 | 替代方案 |
|---|---|---|
| **问题本身未定义清楚** | 模型是结构工具，不能替代问题定义。 | 先用 5W2H 或问题澄清画布明确问题。 |
| **数据/案例不足** | 抽象建模需要样本支撑。 | 先收集 10+ 案例再做模型。 |
| **追求创新但团队保守** | 深度模型可能引发抵触。 | 先用进阶模型建立共识，再引入深度模型。 |

### 外部攻击：Edward Tufte — "图表种类不等于分析深度"

**Edward Tufte**（信息设计先驱）会批评：把模型按难度分类容易让人误以为「用三角图就是深度分析」。真正深度的是思考过程，而不是图形形状。一个糟糕的本质公式比一个清晰的 SOP 更没有价值。

## Action Triggers

| 触发场景 | 第一个动作 | 成功指标 |
|---------|-----------|---------|
| 要为一个复杂问题建立方法论 | 用问题难度分层表判断难度层级 | 确定基础/进阶/深度中的一层 |
| 已有信息但不知如何结构化 | 从武器库中选择 1 个匹配模型 | 输出一张结构化的图或表 |
| 模型被质疑过于简单/复杂 | 回到问题难度判断，重新匹配 | 调整到相邻难度层级的模型 |
