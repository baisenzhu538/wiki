# L2粗拆场景问题

> L1确定了"谁"，L2回答"在什么情况下遇到什么问题"。场景是连接用户和需求的桥梁。

## 核心三问

| 问题 | 示例 |
|:---|:---|
| **在什么场景下？** | 出差、加班、带娃、通勤、周末宅家 |
| **遇到了什么问题？** | 时间不够、信息过载、选择困难、信任缺失 |
| **现在怎么解决的？** | 用竞品、问朋友、忍了、用土办法——暴露替代方案 |

## Agent执行指令

```python
# 引自 AI场景推演教练 Step 1（续）
prompt = """基于已确认的目标用户群（{USER_SEGMENT}），
列出该用户群最常遇到的3-5个场景和对应痛点：
1. 场景描述（什么时候/在哪）
2. 痛点（具体什么困难）
3. 现有解决方案（他们现在怎么做）
"""
```

## 失败模式

| 失败 | 症状 | 修复 |
|:---|:---|:---|
| 场景太泛 | "用户想买东西"——太泛 | 缩小到具体的购买情境 |
| 只列场景不列痛点 | "用户在通勤"——然后呢？ | 每个场景必须跟一个具体痛点 |

## 适用边界

- **适用**：L1用户标签确定后，需要"用户×场景×痛点"矩阵
- **不适用**：B2B复杂采购场景（决策链长，场景单一维度不够）

## 质疑

- **具体假设**：该工具假设"场景拆解能捕捉表层痛点和需求"，但"场景"和"痛点"之间的关系不是直接的——用户在同一个场景中可能有完全不同的痛点，取决于他们的先前经验、情绪状态和资源约束。场景拆解只是"提供了观察窗口"，但不能保证"看到了正确的痛点"。
- **边界**：在新场景（如 AI Agent 时代的新工作流）中，用户的"场景"本身还在演化——拆解一个正在变化的场景就像击中移动靶。
- **前提**：该工具的前提是"用户能准确描述自己的场景和痛点"，但用户常常只描述"症状"而非"根因"——"我觉得流程太慢"的根因可能是"我不理解为什么要这么做"。

**Don Norman**（UCSD 认知科学教授，《设计心理学》作者）会质疑：场景拆解把"用户说什么"当作需求来源，但他的核心洞察是"用户不知道自己需要什么"。真正有价值的需求洞察来自观察用户的行为——尤其是"用户的变通行为"（workaround），而非他们的口头描述。用户说"我需要更快的搜索"，但他们真正的痛点是"找不到该搜什么"——场景拆解如果不结合行为观察，只会收集到"用户自以为的需求"。
