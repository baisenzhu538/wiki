# 落地卡片：低成本测试MVP

落地卡片：低成本测试MVP是泛产品设计落地工具箱中的一项——把产品想法变成可执行动作的具体方法 [conf=0.75, source=原图/VLM描述]。

*基于 VLM 描述生产。泛产品设计系列。*

## 目的

解决"建了完整产品才发现没人要"的问题——团队花数月构建功能完整的产品，上线后发现核心假设不成立，时间和资金已耗尽。低成本测试MVP通过用最小成本构建"恰好能验证核心假设的产品形态"，在投入大量开发资源前获得真实用户反馈。适用于资源有限的创业团队和内部创新项目，核心不是"做一个简化版"，而是"做一个能回答关键问题的东西"。

## 操作步骤

1. **确定要回答的问题**：MVP 不是产品的缩小版，而是某个关键问题的验证工具。明确"这个 MVP 要回答什么问题"——比如"用户是否愿意为这个功能付费"或"用户能否完成核心操作流程"。
2. **选择最低成本的验证形态**：MVP 不一定是软件——可能是人工后台 + 前端表单（Concierge MVP）、可能是落地页 + 等待列表、可能是手动服务模拟自动化。原则是"能回答问题的最便宜形态"。
3. **设定验证标准与时间盒**：在开始前写好"什么数据意味着验证通过、什么数据意味着放弃"，并设定时间盒（通常 1-2 周）——避免 MVP 变成无止境的调整。

## 不要用的场景

- **品牌/信任敏感型产品**：医疗、金融、安全类产品的粗糙版可能永久损害用户信任——这些领域的 MVP 需要最低质量底线。
- **已有明确市场验证的方向**：如果竞品已经验证了需求存在，再做 MVP 验证是浪费时间——应该直接进入执行优化阶段。
- **网络效应型产品**：MVP 的少量用户无法展现网络效应的价值，验证结果可能误导——这类产品需要冷启动策略而非 MVP 测试。

## 质疑

低成本测试MVP的隐含前提是"用户对粗糙产品的反馈能预测对完善产品的反应"，但这个假设在很多场景下不成立。**Don Norman** 批评 MVP 方法论时指出，粗糙的原型会让用户聚焦于产品的不完善之处而非核心价值主张，导致验证结果反映的是"产品质量"而非"需求存在性"。一个具体反例：一个 UI 粗糙的 MVP 测试出用户不愿使用，团队得出"需求不存在"的结论，但实际上需求存在只是体验太差。另一个前提是 MVP 能在短期内获得有统计意义的信号，但对于需要长期使用才能体现价值的产品（如习惯养成、协作工具），短期 MVP 测试的信号几乎无用。**Eric Ries** 虽然推广了 MVP，但也承认 MVP 最大的失败模式不是"做了太粗糙的 MVP"，而是"把 MVP 当成了产品来持续迭代"。
