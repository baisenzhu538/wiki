# 销售工具箱缺口盘点 Agent Spec

## 一句话

一个为销售团队设计的工具箱成熟度诊断 Agent：基于现有工具清单、团队规模、客单价和销售周期，按 60/75/85 三级成熟度评估现状，输出缺失优先级和建设路线图，避免团队跳过基础直接上 CRM。

## 触发场景

- 销售团队扩张前，需要判断现有工具能否支撑新人快速上手。
- 年度预算或季度规划时，需要给工具建设排优先级。
- 新人入职培训设计前，需要盘点哪些工具缺失导致成单率低。
- 已有 CRM 或销售系统但使用率极低，怀疑工具建设顺序出了问题。
- 老销售离职带走客户和打法，团队希望把经验沉淀为组织资产。
- 想设计销售智能体或 Agent，需要先盘点哪些工具可以被代码化。

## 输入

| 输入类型 | 字段 | 必需 | 缺失时行为 |
|:---|:---|:---:|:---|
| 现有工具清单 | 按 60/75/85 三级分类列出已有工具 | 是 | 缺失时返回 `INPUT_MISSING`，要求用户先提供 |
| 团队规模 | 当前销售人数、计划扩张人数 | 是 | 缺失时无法判断系统级工具需求 |
| 客单价区间 | 低 / 中 / 高客单，具体区间 | 否 | 缺失时按中客单处理，输出中标注假设 |
| 销售周期 | 短 / 中 / 长周期，具体天数 | 否 | 缺失时按中周期处理 |
| 业务阶段 | 探索期 / 复制期 / 增长期 / 成熟期 | 否 | 缺失时按增长期处理 |
| 当前痛点 | 新人上手慢、话术不统一、CRM 没人用等 | 否 | 缺失时按工具清单推断 |
| 预算约束 | 年度/季度可用于工具建设的预算 | 否 | 缺失时只给优先级不给具体预算分配 |

## 输出

1. **成熟度评分**：60 分 / 75 分 / 85 分各维度得分（可用百分比或红绿灯）。
2. **缺失诊断**：每个维度严重缺失 / 部分缺失 / 基本具备 / 过度建设。
3. **缺失优先级排序**：先补哪些 60 分基础工具，再建哪些 75 分进阶工具，最后上哪些 85 分系统。
4. **建设路线图**：分阶段（如 0–30 天 / 1–3 个月 / 3–6 个月）列出工具、责任人、验收标准。
5. **与六维雷达图映射**：每个缺失项对应雷达图的哪个维度。
6. **预算与排期建议**：按优先级和约束给出资源分配建议（可选）。
7. **方法论溯源**：调用的 KDO 卡与未调用原因。

## 工作流

```
1. 读取输入：现有工具清单、团队规模、客单价、销售周期、业务阶段、痛点、预算
        ↓
2. 按 60/75/85 三级盘点：对照 tool-yitang-sales-toolkit-maturity-60-75-85 的分级清单逐项打分
        ↓
3. 缺失诊断：判断每个维度是严重缺失 / 部分缺失 / 基本具备 / 过度建设
        ↓
4. 结合业务参数排序：团队规模小 → 先补模板；客单价高/周期长 → 优先大客户作战地图和 CRM
        ↓
5. 生成路线图：分阶段、分责任人、给验收标准
        ↓
6. 映射六维雷达：把缺失项对应到 tool-yitang-sales-toolkit-radar 的维度
        ↓
7. 输出预算/排期建议和方法论溯源
```

## 调用卡片

- **直接来源**：[[tool-yitang-sales-toolkit-maturity-60-75-85]] — 60/75/85 分级清单、缺失诊断、建设路线图。
- **雷达工具**：[[tool-yitang-sales-toolkit-radar]] — 六维雷达图，判断工具在组织中的位置。
- **总体框架**：[[framework-yitang-scientific-sales-five-step]] — 科学销售五步法总框架，本 Agent 对应「打造工具」步骤。
- **过程拆解**：[[tool-yitang-sales-process-decomposition]] — 识别哪些过程节点需要工具支撑。
- **业绩管理**：[[tool-yitang-sales-performance-management]] — 数据看板、日报/周报系统属于 85 分工具。

## 边界风险

- **不替代管理决策**：工具建设优先级只是建议，最终预算和排期需管理者根据公司战略决定。
- **避免清单堆砌**：Agent 必须结合业务阶段和团队规模给出差异化建议，而非简单罗列所有缺失项。
- **不自动采购/部署**：Agent 只输出路线图，不直接购买或配置系统。
- **产品价值未验证时慎用**：如果产品本身没有解决真实问题，再好的工具也只能加速失败。
- **迭代责任人缺失**：工具箱需要有人持续维护，盘点后必须指定维护人和更新周期。
- **数字降级**：所有评分阈值、阶段划分均标注为课程经验值或业务自定义标准，不作为普适真理。

## Few-shot 示例

### 示例 1：早期 SaaS 公司工具盘点

**输入**：
- 现有工具清单：
  - 60 分：粗糙的公司介绍 PPT、无统一话术、价格表不规范
  - 75 分：简单合同模板，无客户档案模板、无 FAQ
  - 85 分：已购 CRM 但使用率不足 30%
- 团队规模：当前 5 人，计划扩张到 12 人
- 客单价：3–8 万/年
- 销售周期：1–3 个月
- 业务阶段：复制期向增长期过渡

**输出要点**：
- **成熟度评分**：60 分严重缺失，75 分部分缺失，85 分过度建设。
- **缺失优先级**：P0 补齐公司介绍 PPT、基础话术、价格表；P1 建客户档案模板、FAQ、Demo；P2 等模板用顺后再激活 CRM。
- **路线图**：0–30 天完成 60 分基础工具；1–3 个月完成 75 分进阶工具；3–6 个月基于使用数据优化 CRM。
- **雷达映射**：60 分缺失对应「公司有实力」「话术讲人话」；85 分过度建设对应「团队有效率」。

## Critique

### 外部反对者

1. **工具厂商**：应该直接上最先进的 CRM/AI 工具，而不是先补基础模板。
   - **回应**：课程经验和落地案例表明，跳过基础模板直接上系统会导致使用率极低；本 Agent 强调先补 60 分再追 85 分。

2. **精益创业派**：早期产品价值未验证，不应投入工具建设。
   - **回应**：本 Agent 明确提示「产品价值未验证时不适用」，工具建设应发生在模型跑通之后。

3. **组织行为学派**：工具建设可能增加官僚化，抑制销售灵活性。
   - **回应**：工具是下限保障和训练起点，顶级销售仍可在模板基础上灵活调整。

### 内部局限

1. **依赖工具清单完整性**：如果用户漏报已有工具，诊断结果会偏差。
2. **行业差异**：不同行业工具形态差异大，通用清单需要本地化调整。
3. **不解决执行力问题**：给出路线图后，仍需要管理者推动落地和迭代。

## Synthesis

- 本 Agent 是 [[opc-ai-sales-agent-architecture]] 中「知识沉淀智能体」与「话术准备智能体」的工具建设专项能力。
- 与 [[tool-yitang-sales-toolkit-maturity-60-75-85]] 的关系：本 Agent 的域知识直接来自该工具卡。
- 与 [[tool-yitang-sales-toolkit-radar]] 的关系：用六维雷达图映射缺失项，避免「得分低但不知从何补起」。
- 与 [[framework-yitang-scientific-sales-five-step]] 的关系：对应「打造工具」步骤，支撑销售规模化复制。
