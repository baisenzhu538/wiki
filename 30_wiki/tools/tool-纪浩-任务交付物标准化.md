# 技能：任务交付物标准化

- src_unknown

## 原始表述

任务交付物标准化是纪浩在AI协作方法论分享中提出的具体方法，用于任务交付物标准化。

## 操作步骤

1. 每个任务定义明确的交付物形式（文档/代码/数据/报告等）
2. 制定交付标准（验收条件）
3. 交付物独立存放，不混入系统文档或项目代码
4. 任务完成后按标准验收，未达标不结束

## Constraints & Boundaries

### 适用边界

| 边界 | 说明 |
|:-----|:-----|
| ✅ 适合 | 复杂任务拆解执行时，需要明确每个子任务的交付物 |
| ✅ 适合 | 多人或多AI协作时，需要统一输出格式和验收标准 |
| ✅ 适合 | 需要明确进度和完成状态时，用交付物作为完成标志 |
| ✅ 适合 | AI原地打转输出大量无效内容，需要收敛到具体交付物 |
| ❌ 不适合 | 开放式探索、无明确目标时 → 过早标准化扼杀探索 |
| ❌ 不适合 | 创意发散阶段 → 标准化会限制创意空间 |
| ❌ 不适合 | 紧急任务时间不足 → 先完成再标准化 |
| ❌ 不适合 | 个人独立快速任务 → 标准化成本超过收益 |

#| 模式 | 症状 | 修复 |
|:-----|:-----|:-----|
| **交付模糊** | AI任务完成后输出混乱，无法判断是否真的完成 | 每个任务定义明确的交付物形式（文档/代码/数据/报告）。无交付标准=无完成标准 |
| **存放混乱** | 交付物混入系统文档或项目代码，难以查找和复用 | 交付物独立存放，不混入系统文档。建立独立的交付物目录结构 |
| **验收随意** | 任务验收时标准不一，有时严格有时宽松 | 制定交付标准（验收条件），任务完成后按标准验收。未达标不结束 |
| **格式混乱** | 多人协作时各自输出格式不一致，难以整合 | 统一交付物模板和格式规范。复杂任务拆解后，每个子任务交付物格式一致 |
| **无效输出** | AI原地打转，输出大量内容但没有实际交付物 | 任务开始前明确交付物定义。AI输出不是交付物，符合验收标准的输出才是 |
| **标准僵化** | 交付标准过于 rigid，无法适应任务变化 | 标准分核心项（必须）和可选项（灵活）。核心项不变，可选项根据任务调整 |
| **验收缺失** | 有标准但不验收，流于形式 | 验收必须执行，未达标不结束。验收结果记录到日志，作为迭代依据 |
| **过度标准化** | 所有任务都追求标准化，小任务也走完整流程 | 区分核心任务（标准化）和辅助任务（快速交付）。不是所有任务都需要完整标准 |

## 为什么有效

有交付标准和交付物才能证明任务真正完成，防止AI原地打转或输出无效结果。标准化交付物降低协作摩擦，提升复用性。

## 质疑

- **具体假设**：该工具假设结构化方法论能提升效果，但方法论的有效性取决于执行者的判断力和场景适配——没有判断力的执行只是'走流程'，不等于'做好事'。
- **边界**：在全新领域或快速变化的环境中，已有数据和经验可能完全失效——工具的有效性高度依赖场景的稳定性。
- **前提**：该工具的前提是使用者能正确理解和执行工具的规则，但执行者的认知偏差和经验限制会影响工具的实际效果。

**Peter Drucker**（管理学大师）会质疑：工具的价值不在于"有没有"，而在于"用得好不好"。任何工具都是"能力放大器"——如果使用者的判断力不足，工具只会放大错误。真正的风险不是"缺少工具"，而是"有了工具后产生的虚假安全感"——让你以为自己已经覆盖了所有可能性，实际上只是走完了流程。
