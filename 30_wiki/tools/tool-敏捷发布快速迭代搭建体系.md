# 技能：敏捷发布快速迭代搭建体系

## 原始表述
> 多版本快速发布，快速测试反馈，快速迭代。

## 操作步骤
1. 制作最小可用版本
2. 快速发布到实际场景
3. 收集用户/客户反馈
4. 识别问题
5. 快速调整迭代
6. 循环直至稳定

## 目的

从 0 到 1 搭建一个新业务或产品体系时，用"最小可用版本 → 快速发布 → 真实场景反馈 → 迭代"的循环替代完美主义和过度规划。核心价值在于：用真实用户反馈替代会议室争论，缩短假设验证周期。适用于创业初期、新产品线、或进入新市场等不确定性高的场景。

## 不要用的场景

- 产品或服务涉及人身安全（医疗/航空/自动驾驶），快速迭代的试错成本不可接受
- 已进入规模化阶段，频繁变动会破坏用户习惯和品牌一致性
- 团队缺乏快速收集和分析反馈的能力时，迭代只是盲目试错

## 质疑

- **具体假设**：该工具假设结构化方法论本身能产生正确结论，但方法论只是框架——结论质量取决于输入数据的质量和执行者的判断力。
- **边界**：在数据稀缺或快速变化的新兴领域，已有经验框架可能完全失效——工具的有效性高度依赖场景的稳定性。
- **反例**：一个团队完整执行了所有步骤，产出了漂亮的文档，但核心假设从一开始就是错的——流程的完整性掩盖了判断的缺陷。
- **前提**：使用者已具备该领域的基础认知，能正确理解和执行工具规则，且数据来源具有代表性。

**Eric Ries**: 我虽然是 Lean Startup 的倡导者，但必须指出 MVP 的最大风险不是产品太简陋，而是团队把"快速迭代"等价于"不需要思考"。敏捷不是不做计划的借口——你仍然需要对问题空间有足够理解，否则快速迭代只是在更快地撞墙。速度不等于方向正确。

**W. Edwards Deming**: 只依赖用户反馈来驱动迭代是一种被动的质量改进——用户只能反馈他们体验到的，而非你产品中缺失的东西。一个完全依赖反馈迭代的系统会陷入局部最优，永远无法发现用户没说出口的需求。
