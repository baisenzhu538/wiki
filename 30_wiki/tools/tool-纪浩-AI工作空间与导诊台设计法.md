# 技能：AI工作空间与导诊台设计法

## 不要用的场景


- 数据严重不足时暂停使用——AI工作空间与导诊台设计法的输出质量高度依赖输入数据的代表性和完整性。宁可先补数据。
- 刚接触AI工作空间与导诊台设计法的新手不要直接用——先通过3-5个真实案例建立体感，否则执行只是走流程。
- 资源极度受限时不要追求AI工作空间与导诊台设计法的完整流程——做20%的核心步骤比做100%的敷衍步骤更有价值。

## 目的


帮助团队在AI工作空间与导诊台设计法任务中减少盲目试错——提供清晰的执行路径和验证节点，降低返工率。

## 原始表述

纪浩在AI协作方法论中提出：AI是模式匹配系统，不会自己搞结构设计。让AI做事的第一步不是写prompt，而是先搭建一个结构化的工作空间。工作空间包含五大模块：系统自述、领域知识、Agent服务文档（导诊台+工作手册+工具集+经验模式库）、任务管理、日志。信息按场景聚合，不按分类聚合。

## 操作步骤

1. **创建项目目录**——为AI创建一个独立的工作目录，不要和你自己的文件混在一起
2. **写系统自述**——用一个Markdown文件记录系统的架构、组件、技术栈。检验标准：如果一个新同事看了这个文档能理解系统大致结构，就算合格
3. **收集领域知识**——把与项目相关的纯业务知识单独放一个目录或文件。**关键原则：领域知识和项目本身无关**。例如：直播间运营知识和一堂代码库是两件事
4. **设计导诊台**——如果AI需要处理多种不同类型的任务（开发、调试、运维、需求讨论等），创建一个"导诊台"文档。导诊台的作用是：当AI收到一个复杂任务时，先通过导诊台路由到正确的工作手册
5. **编写工作手册**——为每种任务类型写一份执行规范（SOP）。工作手册和领域知识是独立的，但可以互相引用
6. **准备工具集**——收集和编写AI执行任务时需要的脚本、命令、系统访问方式。**原则：AI更喜欢用工具，而不是自己动脑子分析**
7. **建立经验模式库**——AI犯错后，把纠正方法和避免方案记录下来，形成可复用的经验。下次执行相似任务时注入这些经验
8. **设计任务管理规范**——定义任务的输入标准、交付标准和交付物。使用成熟的任务管理工具（如飞书多维、GitHub Issues），没必要自己搭建
9. **验证渐进式披露**——检查信息组织是否符合"导诊台→工作手册→经验库→领域知识"的递进顺序。AI每次对话只绕一个任务展开

## Constraints & Boundaries

### 适用边界

| 边界 | 说明 |
|:-----|:-----|
| ✅ 适合 | 准备让AI执行一个新项目或新任务时，需要稳定上下文 |
| ✅ 适合 | AI产出质量忽高忽低，需要稳定化上下文环境 |
| ✅ 适合 | 多个AI任务需要分类和路由（开发/调试/运维等） |
| ✅ 适合 | 团队内部复用AI工作流配置，需要标准化 |
| ❌ 不适合 | 一次性、单轮的简单任务 → 直接写prompt更快 |
| ❌ 不适合 | 只有一种类型的单一任务 → 不需要导诊台路由 |
| ❌ 不适合 | 已有成熟的自动化平台覆盖 → 重复搭建 |
| ❌ 不适合 | 创意发散阶段 → 结构化过早钉死思维 |

#| 模式 | 症状 | 修复 |
|:-----|:-----|:-----|
| **知识混同** | 领域知识和项目文档混在一起，AI把业务逻辑和技术实现混淆 | 检查领域知识目录和系统自述文件是否分开，领域知识和项目本身无关 |
| **导诊台失效** | 导诊台缺失或过于复杂，任务被错误分配或AI在导诊台上浪费太多时间 | 导诊台只做'任务分类'不做'任务执行'，保持简洁，复杂路由用工作手册处理 |
| **经验沉睡** | 经验库只记录不注入，AI反复犯同样的错误 | 每次任务开始时把相关经验注入上下文，经验库的价值在'用'不在'存' |
| **信息过载** | 一次性把全部上下文扔给AI，信息过载注意力分散 | 遵守渐进式披露原则，每次对话只绕一个任务展开，按'导诊台→工作手册→经验库→领域知识'递进 |
| **结构膨胀** | AI接手任务变多后出现混乱，目录结构只能延缓膨胀不能解决膨胀 | 定期Review工作空间结构，合并重复模块，删除过时经验，保持结构精简 |
| **自动化悖论** | 系统高度自动化，人的技能系统性退化 | 专门留出AI不能碰的区域，不是因为它做不好，而是因为它做了你就会退化 |
| **情境过时** | 导诊台路由规则三个月后变成紧身衣 | 设计机制检测路由规则是否过时，定期Review任务类型变化 |
| **无源之水** | 还在探索'我要做什么'，连系统自述都写不出来 | 先明确需求和边界，再搭建工作空间。需求不明时先用自由文本发散 |

## 为什么有效

AI是模式匹配系统，不会自己创造结构。当上下文环境稳定、结构清晰时，AI的产出质量从"抽奖模式"变为"稳定模式"。工作空间的作用是把隐性标准显性化——让AI知道"这里有什么、该怎么用、不能踩哪些坑"。

### 外部攻击

#### Don Norman 的"自动化悖论"批评

**Don Norman**（《设计心理学》作者，认知科学家，UX之父）的研究揭示了自动化的深层矛盾：**当系统高度自动化时，操作者的技能会系统性退化**。这不是因为他们偷懒，而是因为系统替他们做了所有的微决策。纪浩让AI执行80%的工作，自己只做20%的验证——Norman 会说，验证比执行的认知要求更低，你的编码能力不会因为review得多而变强。

> **Norman 的敛命敲响**："你设计的Agent Workspace让AI工作得越来越顺。但你在设计的时候，有没有专门留出一些AI不能碰的区域——不是因为它做不好，而是因为它做了你就会退化？如果没有留，你的系统就是一个完美的退化加速器。"

#### Lucy Suchman 的"情境行动"批评

**Lucy Suchman**（《Plans and Situated Actions》作者，人类学家）会质问：**五层结构假设了完美的自上而下传递**——人在顶层定义项目，AI在底层执行日志。但真实的协作是 messy 的，层与层之间有大量灰色地带。Suchman 会说：你的导诊台设计了一套完美的路由规则，但当情境发生变化时，这些规则会迅速过时。

> **Suchman 的敛命敲响**："你的导诊台是为了当下的任务设计的。但任务会变，人会变，场景会变。你今天设计的导诊台路由规则，三个月后可能就是一套紧身衣。你有没有设计一个机制来检测路由规则是否已经过时？如果没有，你的AI就在按照过时的地图走路。"

## Action Triggers

| 触发条件 | 行动 | 预期结果 |
|---|---|---|
| 当你准备让AI执行一个新项目时 | 先花30分钟搭建工作空间，不要直接写prompt | 按此行动执行 |
| 当AI产出质量不稳定时 | 检查工作空间的五大模块是否完整，尤其是约束文档和经验库 | 按此行动执行 |
| 当需要在团队内部复用AI配置时 | 把工作空间当作标准交付物，让其他人能按图索骥 | 按此行动执行 |

## Synthesis

### 不要用的场景

| 场景 | 为什么失效 | 替代方案 |
|---|---|---|
| 创意发散阶段 | 结构化工作空间会把思维过早钉死在框架上 | 先用自由文本或脑图发散，待方向明确后再搭建结构 |
| 个人探索性学习 | 工作空间需要明确的"系统"和"任务"，学习还没有这些边界 | 用清单体笔记或思维导图记录，不急于结构化 |
| 需要严格保密的敏感任务 | 工作空间中的上下文可能被AI泄露或误用 | 在本地私有环境中执行，限制上下文范围 |
