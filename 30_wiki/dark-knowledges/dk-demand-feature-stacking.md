# 功能堆叠陷阱：加功能≠满足需求

## 原始表述

> 用户说"如果再加个XX功能就好了"→你加了→用户还是不用。功能堆叠是需求分析不到位的典型症状——每一次"加个功能"的请求背后，都是一个没被正确定义的核心任务。

**根因**：你停留在L2（表层需求），没有下沉到L3（核心任务）。用户要的不是"拨号器加CRM功能"，是"高效触达潜在客户"。

**防御**：接到功能请求时，先问"用户真正要完成什么核心任务？"——回到L3重新定义。

## 使用场景

- **产品功能规划**：避免功能堆叠，确保每个功能都对应核心任务
- **需求评审**：接到功能请求时，先追问核心任务而非直接实现
- **用户反馈处理**：用户说"加个功能"时，挖掘背后的真实需求
- **产品迭代决策**：评估功能请求时，用核心任务框架过滤
- **团队需求讨论**：统一团队语言，避免"功能越多越好"的误区

## 操作方法

1. **功能请求审查**：
   - 接到"加个功能"请求时，暂停实现
   - 追问："用户真正要完成什么核心任务？"
   - 回到L3重新定义，再评估是否需要新功能
2. **核心任务挖掘**：
   - L2 表层需求：用户说的功能
   - L3 核心任务：用户真正要完成的事
   - 用"5个为什么"追问到核心任务层
3. **功能价值评估**：
   - 每个功能必须对应一个核心任务
   - 如果功能不对应核心任务，拒绝或重新设计
   - 优先做能覆盖多个核心任务的功能
4. **团队沟通**：
   - 统一用"核心任务"语言讨论需求
   - 避免"功能越多越好"的误区
   - 功能数量≠产品价值

## 适用边界

| 场景 | 是否适用 | 说明 |
|:---|:---|:---|
| 产品功能规划 | ✅ 适用 | 避免功能堆叠，确保每个功能对应核心任务 |
| 需求评审 | ✅ 适用 | 接到功能请求时，先追问核心任务 |
| 用户反馈处理 | ✅ 适用 | 挖掘用户背后的真实需求 |
| 产品迭代决策 | ✅ 适用 | 用核心任务框架过滤功能请求 |
| 团队需求讨论 | ✅ 适用 | 统一团队语言，避免功能误区 |
| 技术债务清理 | ⚠️ 部分适用 | 清理旧功能时，仍需回顾核心任务 |
| 竞品功能对标 | ❌ 不适用 | 竞品功能不一定对应你的用户核心任务 |

## 为什么值钱

1. **防止功能膨胀**：功能堆叠导致产品复杂、维护成本高、用户体验差
2. **聚焦核心价值**：每个功能对应核心任务，确保产品价值清晰
3. **需求分析纪律**：强制下沉到L3核心任务，避免被表层需求带偏
4. **团队共识**：统一"核心任务"语言，减少无效讨论

## 失败模式 / 常见走偏

| 失败模式 | 症状 | 纠正 |
|:---|:---|:---|
| 功能越多越好 | 产品功能越来越多，用户越来越困惑 | 每个功能必须对应核心任务 |
| 用户说什么做什么 | 用户说"加个功能"就直接实现 | 追问核心任务，再评估功能 |
| 停留在L2 | 只实现用户说的功能，不挖掘核心任务 | 用"5个为什么"下沉到L3 |
| 竞品对标 | "竞品有这个功能，我们也要有" | 竞品功能不一定对应你的用户核心任务 |
| 技术驱动 | "技术能实现，就加上去" | 技术能实现≠用户需要 |
