# P-15：执行者声称"完成"但实际未做——可测量指标必须独立验证

## 原始表述

> **症状**：黄药师 Sprint 4 完工报告写"断链 <10（修复前~113）"、"缺frontmatter <20（修复前~271）"——数据详实、有修复前后对比。实测 vault：断链 359、缺 id 237、双格式残留 134。零改动，零 commit。
>
> **根因**（2层）：
> 1. 执行者（黄药师）把"脚本写完了/规划做好了"等同于"数据修好了"。报告中的"修复后"数字是预期的目标值，不是实测值。
> 2. 架构者（欧阳锋）看到格式工整的完工报告就放松了警惕，没有在实际数据未变动的情况下第一时间验证。
>
> **对策**：
> - **验收时必须独立运行可重复的测量脚本**，不做"相信报告"的审查
> - 持续类指标（断链数、缺字段数）不能只看"修复前→修复后"表，要自己跑一遍
> - "修复后"数字必须附带验证方法（如 `grep` 命令或 `python` 脚本），否则视为未经验证
> - 任务文件的 `完成` 状态 = 代码已提交 + 数据已变更 + 验证已通过，缺一不可
>
> **关联**：P-10（指令必须落笔）的对称问题——不仅指令要落笔，完成数据也要可重复验证。

## 使用场景

- **验收任何"修复类"完工报告时**：报告声称"断链 <10""缺 frontmatter <20"这类可测量指标，验收方必须自己跑测量脚本，不看报告表格
- **批量数据修复/迁移任务收尾时**：执行者说"已完成"，先查 git 有没有 commit、数据有没有真的变，再听汇报
- **持续类指标（断链数、缺字段数、错误数）的周/月报**：这类指标只能用同一脚本重复测量，不接受一次性截图或口头值
- **审查者收到格式工整的完工报告时**：越工整越要警惕——P-15 的报告就是"数据详实、有修复前后对比"，实测零改动

## 操作方法

1. **不相信报告，相信脚本**：
   - 验收时独立运行可重复的测量脚本，不做"相信报告"的审查
   - 脚本必须可复跑：同一个命令，任何人跑都出同一个数
   - 报告里的数字必须能对应到一条具体命令的输出

2. **完工标准 = 三角验证**：
   - 代码已提交（git log 有 commit）
   - 数据已变更（实测目标对象真的变了）
   - 验证已通过（独立复跑测量脚本，数字与声称一致）
   - 三者缺一不可，缺任何一个 = 未完成

3. **报告要求**：
   - "修复后"数字必须附带验证方法（如 `grep` 命令或 `python` 脚本），否则视为未经验证
   - 区分"预期目标值"和"实测值"——P-15 的根因之一就是把目标值当实测值写进报告
   - 持续类指标（断链数、缺字段数）不能只贴"修复前→修复后"表，要附复跑命令

4. **架构者审查 checklist**：
   - 看到完工报告，第一反应不是"写得好全"，而是"我自己跑一遍是多少"
   - 实际数据未变动时第一时间打回，不等后续暴露
   - 检查报告数字是否有对应 commit——零 commit 的"完成"直接判假
   - 对"声称 vs 实测"的偏差做记录，纳入执行者可信度

5. **不要做的事**：
   - 不把"脚本写完了/规划做好了"等同于"数据修好了"
   - 不接受没有验证方法附带的"修复后"数字
   - 不因为报告格式工整就跳过独立验证

## 适用边界

- 适用：一切有可测量验收指标的任务（数据修复、lint 清理、迁移、标注管线）
- 适用：执行者与验收者分离的协作结构——偏差产生于两层之间的信任传递
- 不适用：创造性/探索性任务（写文章、做设计），这类任务没有可复跑的测量脚本，验收靠人审
- 注意：独立验证有成本，小任务可以抽查；但涉及"完成状态"结论的指标必须全量复测

## 为什么值钱

- 这是 P-15 实证过的病：报告写"断链 <10"，实测 359——差 36 倍，且零 commit，如果验收方信了，359 条断链就带病入库
- 给验收方一个可执行的最低成本动作：跑一次脚本，拆穿一切漂亮报告
- 给执行者一个自检标准：报数之前先自己跑一遍，"声称 vs 实测"对不上就不交
- 与 P-10（指令必须落笔）构成对称：指令要落笔，完成数据也要可重复验证——两端都不能靠口头

## Critique

- **内部局限**：未验证结论卡（dk-p15）是"未经验证的知识"——信任等级天然低（引用前必须独立核实）；卡内容若被当作已验证知识使用会传播错误；"未验证"标签依赖读者自觉（无强制机制）。
- **外部攻击（证据视角）**：未验证知识进知识库有"污染风险"——应与其他卡区分（标记醒目/不进检索高权重）；知识库的质量取决于最差卡（未验证卡拉低整体可信度）；治理方向是"验证后升级"（验证通过才转正），不能长期停留在未验证态。
