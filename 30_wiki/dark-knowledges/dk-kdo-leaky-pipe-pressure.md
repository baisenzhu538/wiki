---# 暗知识：在漏水的管子上加压

> 基础链路没跑通时，硬门禁不是质量控制，而是流程卡死。更多控制 ≠ 更高质量。

## 原始表述

> EC 的 F001-F014 全部来自真实事故。KDO 的失败模式也必须从事故沉淀，提前编的清单无法落地为 lint 规则。基础链路（ingest → enrich → produce）没跑通时，上硬门禁——不是质量控制，是在漏水的管子上加压。

——黄药师，`kdo-ec-industrialization-migration-proposal` 讨论，2026-06-17

## 核心洞察

这是一个在 KDO 管线建设中反复出现的反模式：**当基础链路还有漏水点时，团队的第一反应往往是"加一道门禁堵住"，而不是"先把漏水点修好"。**

这个直觉是错的。原因有三：

1. **门禁依赖数据质量。** lint 规则、自动检查、质量门——它们的输出取决于输入数据的完整性。如果 source_refs 已大量缺失、frontmatter 残缺、卡片 status 漂移，那么基于这些数据的门禁只会产生更多噪音，不会提高质量。

2. **漏水 + 加压 = 更大的灾难。** 在管线不稳定时加硬阻断，后果不是"筛选出好卡片"，而是"所有人绕过门禁"。因为完成一个基本动作的成本已经高于绕过的成本，理性用户会选择绕过。

3. **门禁的成本不是零。** 每加一道检查，就多一个维护负担、一个误报来源、一个可以绕过的接口。在基础链路稳定之前，大多数门禁的"发现真实问题的概率"远低于"产生误报或被人绕过的概率"。

**正确的顺序**：先让基础链路（source 追踪、enrich 不跳过、broken links 归零）稳定运行，再逐步上锁。就像先修好漏水的管道，再加压测试。

## 使用场景

- 你在设计或优化一个知识管理/内容管线的质量门禁体系。
- 团队争论"要不要加硬门禁"时，基础链路的健康度尚未被评估。
- 你发现团队成员在系统性绕过某道流程，而不是遵守它。
- 你在做 KDO/类似管线的迁移或工业化升级。
- 你想区分"需要修的基础设施问题"和"需要加的门禁规则"。

## 操作方法

1. **先跑健康检查，再做任何门禁决策。**
   运行 `kcard-quality-gate.py`，拿到 broken links、source 缺失、status 漂移的基准数字。

2. **修复顺序 = 数据完整性 → 自动化 → 门禁。**
   - 第一周：归零 broken links，修复 source_refs 缺失。
   - 第二周：确保 ingest → enrich → produce 三步自动化稳定运行。
   - 第三周：基于修复后的洁净数据，评估需要哪些门禁。

3. **每加一道门禁，必须回答三个问题：**
   - 这道门禁在过去一个月能拦截多少次真实问题？（要数据，不要直觉）
   - 它的误报率是多少？误报的处置成本谁承担？
   - 绕过它的成本是否高于遵守它的成本？

4. **失败模式必须从事故生长。**
   不要坐在房间里设计"可能会出什么问题"——去看日志、去读 feedback 记录、去问被门禁卡过的人。EC 的 F001-F014 全部来自真实事故，KDO 的门禁也应该这样生长。

## 适用边界

| 边界 | 说明 |
|:-----|:-----|
| **适用于质量门禁 / 管线建设** | 不适用于产品功能设计或组织管理。 |
| **前提是管线已有雏形** | 如果管线还没搭起来，先搭管线，再谈加压。 |
| **不反对门禁本身** | 反对的是"在基础链路坏掉时加门禁"。基础稳定后，门禁极其重要。 |
| **需要执行者有暂停的权限** | 如果上级强制要求"本周上线三道门禁"，这条暗知识无法生效。 |

## 常见失败模式

| 失败模式 | 典型症状 | 修复方法 |
|---|---|---|
| 漏水 + 加压 | lint 报错越来越多，没人修，门禁变成"已知可忽略"的噪音 | 暂停新增规则，先修数据源 |
| 跳过根因硬加审批 | 审批节点被加在"常被跳过的环节"前面，结果审批的人也跳过 | 降低该环节的执行成本，或改为事后审计 |
| 门禁标准讨论前置 | 花大量时间争论"conf≥0.85 还是 0.9"，但 30% 的 source 是空值 | 先修数据，再定标准 |
| 理论门禁无法落地 | 坐在房间里设计 F001-F014，上线后发现一半规则对不上真实场景 | 每条规则从真实事故中提取，编号对应具体案例 |
| 加门禁却不减旧规则 | 管线越来越重，但旧的 lint 规则、旧的检查清单从未退役 | 每加一条新规则，评估是否可以退役一条旧规则 |

## 为什么值钱

- **反直觉**：多数人的第一反应是"有问题就加检查"，但这个直觉在管线建设中是错的。
- **有惨痛教训支撑**：EC 工业化过程中真实踩过坑，14 条失败模式编号（F001-F014）全部是从事故中提取的。
- **通用可迁移**：不仅适用于 KDO，任何涉及质量门禁、CI/CD、内容审校的管线都会遇到同样的陷阱。
- **区分了"基础设施问题"和"门禁问题"**：这是两个完全不同的问题类型，但常常被混为一谈。混在一起的结果是两者都搞不好。
