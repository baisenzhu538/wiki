# 过度管理 vs 裸跑的平衡暗知识

> **一句话**：过度管理（给A级项目上甘特图）和裸跑（D级项目不用任何工具）都是要命的。真正的功夫不在"管"或"不管"，而在"匹配"——让工具的复杂度恰好等于项目的复杂度。

---

## 原始表述

> "我发现市场上有非常多的课都在讲公司级别的战略管理……但是初创公司，五十人一百人以内，究竟怎么做项目，怎么去具体地把项目做成？……很多公司一直在裸跑，就是一点机制都没有，就是硬上硬上，就逮着个项目就硬上。"
>
> "复杂的项目，大项目用大工具，小项目用小工具，就这么一句话。你要是做一个贼复杂的、九死一生的、价值几百万几千万的项目，就把整个的工具全用上。但是如果你就是解决一个特小的问题……你就上一点点就好了。"
>
> —— 老顽童，一堂项目管理系列课·入门篇口述

核心洞察：**"拿大炮打蚊子"和"拿小锤造航母"都是错的。** 大多数团队的项目管理问题，根源不是"不会管"，而是"不会匹配"——不知道该用多重的管理去管多复杂的项目。这个匹配能力，才是项目管理的真功夫。

---

## 使用场景

- 团队刚开始建立项目管理体系，不知道该从哪下手、用多重的工具。
- 团队已经"管伤了"——之前流程太重导致全员抵触，现在一提管理就反感。
- 项目频繁延期、质量失控，但每次复盘都归因于"管得不够"，于是每次加流程、每次更糟。
- 老板看到大公司用甘特图就要求全公司所有项目都用甘特图。
- 新接手一个团队，发现要么文档堆成山但项目不动，要么什么都没有全凭口头。
- 你想说服团队/老板：不是所有项目都需要完整方案和甘特图。

---

## 操作方法

### 一、识别两条死亡螺旋

**死亡螺旋1：过度管理死亡螺旋**

```
重流程（A级项目被迫写完整方案）
  → 团队觉得流程是负担，效率下降
  → 管理者看到效率下降→加更多检查节点
  → 团队更厌恶，开始绕过流程（私下做事）
  → 管理者发现失控→再加管控
  → 流程彻底崩坏，团队集体"裸跑"
```

典型症状：方案文档写得越来越厚但实际推进越来越慢；团队表面遵守流程，私下有"影子项目"；启动会变成了走过场。

**死亡螺旋2：裸跑死亡螺旋**

```
无流程（D级项目凭感觉硬上）
  → 依赖/冲突/遗漏集中爆发
  → 紧急救火，高层干预
  → 老板恐慌，一刀切："以后所有项目都必须用全套流程"
  → A/B/C/D级全部被套上D级重流程
  → 团队怨声载道，产出暴跌
  → 管理者左右为难，不知道该裁哪个流程
```

典型症状：项目启动时"信心满满"，第二周开始各种"意外"；每次复盘都说"下次早点沟通"，但下次依然重复；跨部门冲突在项目后期才暴露。

### 二、找到 Goldilocks 区（匹配区）

核心原则：**工具的复杂度 = 项目的复杂度。**

| 级别 | 复杂度 | 合适的管理工具 | 过度管理信号 | 欠管理信号 |
|:---|:---|:---|:---|:---|
| **A**（单人） | 极低 | 口头确认目标即可 | 要求写方案文档、填排期表 | 目标说不清、老板不知道你在做什么 |
| **B**（2-5人） | 低 | 一页纸方案+简单排期 | 要求甘特图+RASCI完整版+启动会 | 没人认领负责人、交付时间模糊 |
| **C**（跨部门） | 中 | 三段论方案+里程碑+周报+变更管理 | 要求背景分析8维度+深度复盘 | 没开启动会、跨部门没签字、没有变更流程 |
| **D**（战略级） | 高 | 完整方案+甘特图+健康度雷达+复盘画布 | —（D级本该重，不存在过度管理） | 没有签字画押、没有Plan B、没人敢说可能失败 |

### 三、实操三步法

**第一步：先分级，再选工具。** 任何新项目启动前，花1分钟跑ABCD分级：
- 几个人做？（1人→A，2-5人→B，5-15→C，全公司→D）
- 跨部门吗？（否→A/B，是→至少C）
- 失败代价多大？（低→A/B，中→C，不能失败→D）

**第二步：默认向低级别启动。** 不确定选B还是C时，先按B管，跑两周看实际情况。比一开始就按C级管更务实——升容易，降难。

**第三步：设置"重新分级"检查点。** 每周检查：范围还在原始设定的20%以内吗？新增了跨部门依赖吗？老板突然说"很重要"吗？任一触发→重新分级。

### 四、修复已陷入螺旋的团队

**从过度管理螺旋拉出：**
1. 立刻对所有项目跑一次ABCD分级
2. 把A/B级项目从重流程中解放（宣布"这些项目不需要甘特图/启动会"）
3. 保留C/D级的重流程，但明确告知团队：这不是一刀切，是分级匹配
4. 用数据对比：分级前vs分级后，项目交付速度

**从裸跑螺旋拉出：**
1. 先在一个最小项目上试点轻量工具（如：一个B级项目只加一页纸方案）
2. 让团队体验"匹配的工具不重"
3. 用这个成功案例，逐步推广到其他项目
4. 绝不一刀切上重流程

## 适用边界

| 场景 | 是否适用 | 说明 |
|:---|:---|:---|
| 初创公司/50-200人规模 | ✅ 最适用 | 这是ABCD框架的原生场景 |
| 大公司成熟PMO体系 | ⚠️ 部分适用 | 大公司已有分级体系，核心问题不同——不是"没有分级"而是"分级后僵化" |
| 纯敏捷/Scrum团队 | ⚠️ 部分适用 | 敏捷环境下的分级维度不同，但"匹配"原则依然成立 |
| 只有一个项目的小团队 | ⚠️ 部分适用 | 没有多项目对比，分级价值有限——重点是对这一个项目不断调整工具 |
| 紧急危机项目 | ✅ 适用 | 危机中更需匹配：能活下来就行，别上全套流程 |

### 外部攻击

**攻击者1：PMP/PMBOK正统派**
> "ABCD分级太粗糙了。PMBOK有10大知识领域49个过程，每个都应该根据项目裁剪——不是简单分四级就能解决的。你们的框架可能漏掉关键管理动作。"

回应：ABCD不是取代PMBOK，而是给"不知道该用哪个过程"的团队一个最低启动框架。成熟团队可以在ABCD基础上做精细裁剪。对大多数50人以下的公司，ABCD已足够。

**攻击者2：敏捷/Lean派**
> "所有流程都是浪费。最好的管理是不管理——自组织团队、持续交付、面对面沟通。你搞ABCD分级本身就是过度管理。"

回应：自组织的前提是团队成熟度高。当团队成员来自不同部门、有不同的KPI时，没有基础的结构会导致比过度管理更大的浪费。ABCD的本质是"最小必要管理"。

---

## 为什么值钱

1. **揭示两个对称的失败模式**：大多数管理培训只讲"怎么做"，不讲"做过头"和"做不够"的对称伤害。过度管理和裸跑看起来相反，但会互相转化——过度管理导致流程废弃变成裸跑，裸跑导致恐慌变成过度管理。看到这个来回摆荡的结构，才是真正理解了平衡。

2. **给出匹配原则而非工具清单**：市面上有大量"项目管理必用10大工具"的清单，但没人教"什么时候不该用这些工具"。ABCD的本质不是给工具，是给匹配逻辑。

3. **面向真实的人性阻力**：裸跑和过度管理都不是因为"不懂"，而是因为上一次管理体验太差。修复团队的管理创伤，需要让团队先体验"匹配的管理不重"——这是一个信任重建过程，不是工具选择问题。

4. **死亡螺旋的预警价值**：每个螺旋都有可识别的早期信号。在螺旋刚开始时就识别并干预，成本远低于螺旋走完后的修复。

## 失败模式 / 常见走偏

| 失败模式 | 典型症状 | 纠正 |
|:---|:---|:---|
| 一刀切加流程 | 出了一个问题→给所有项目加一个流程→问题更严重→再加流程 | 先分级，再针对特定级别调整流程 |
| 一刀切裁流程 | 一次管理失败→宣布"以后都不搞流程了"→全员裸跑 | 裁的是不匹配的流程，不是所有流程 |
| 分级后僵化 | ABCD定了一次就不再改，项目范围翻了3倍还在用B级工具 | 每周检查触发条件，强制重新分级 |
| 把"重要性"当"复杂度" | 老板说"这事很重要"→立刻上全套D级流程（即使只有1人1天） | 分级依据是客观复杂度（人数/跨部门/失败代价），不是老板的主观重要性 |
| 不敢降级 | 项目简化后还在用C级流程，因为"降级显得项目不重要" | 降级是务实，每两周问：现在的复杂度配得上这套流程吗？ |
| 忽略团队成熟度 | 死套ABCD，老手团队被流程拖慢，新手团队被轻流程坑惨 | ABCD是默认值，根据团队成熟度上下调整一级 |
