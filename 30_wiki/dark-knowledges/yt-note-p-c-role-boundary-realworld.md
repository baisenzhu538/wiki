# P/C 角色真实场景边界与切换条件（基于聊天记录案例）

## Condense

这张暗知识卡基于同一位用户（创业者、管理者、执行者三位一体）在同一天内与**两个不同角色的 AI Agent**的真实聊天记录，提炼出 P 角色与 C 角色在实际使用中的**边界划分规则**和**切换信号**。

**C 角色对话**：54 条消息，走完"明确长期追求 → 四要素诊断 → 输出行动报告"的完整流程。用户从"我是 L2，想到 L6"出发，经历了被追问、被挑战、被要求自我评分的过程，最终获得了 6000+ 字的《清单体笔记 · 10 倍速练习行动报告》。C 角色的价值在于**发现用户自己都没意识到的盲区**（如“知道好标准但滑回惯性”的隐蔽失败模式）。

**P 角色对话**：2 条消息，用户发送 400+ 字的非结构化复盘感想，AI 直接返回 6 大模块的清单体笔记。P 角色的价值在于**降低表达摩擦**，让用户脑中已经清晰的内容立即落地为可传播格式。

**核心切换信号：输入的“完成度”**。当用户的输入是**“成品”**（已完成思考、已有结论、只需结构化）时，用 P 角色；当用户的输入是**“素材”**（有感受但无结论、有问题但无方案、有意愿但无路径）时，用 C 角色。这个判断标准可以用一个简单的问题检验：**“如果现在把这份输入直接结构化，用户会满意吗？”** 如果答案是"会"，用 P；如果答案是"不会，他还需要被问几个问题”，用 C。

**误用代价**：
- 该用 P 时用 C → 用户被迫接受"诊断”，产生“我已经知道了，为什么还要被教导”的反感
- 该用 C 时用 P → 用户获得一份"结构完整但思考不成熟”的产物，以为自己已经想清楔了，实际上只是"切清楔了"

这张卡片的核心警报是：**大多数 AI 产品把 C 角色当成默认设置**——每次用户交互都先进行一轮"诊断"或"追问"，这对于已经完成思考的用户是**时间窃盗**。

## Question

1. 如果同一个用户在同一次对话中，先发送了“素材”（需要 C 角色），然后又发送了“成品”（需要 P 角色），AI 应该如何处理这种角色混杂的输入流？（角色跳变的实时判断）
2. 当用户不知道自己需要什么角色时（以为自己发的是“成品”其实是“素材”），AI 是否应该在交付前做一次"完成度检测”？（自动切换 vs 确认提示的权衡）
3. 在团队协作场景中，如果多个人同时使用 P/C 角色不同的 AI，会不会产生角色冲突（如一个人觉得“被教导了”而另一个人觉得“没被推动”）？（组织层面的角色一致性）

## Critique

### 外部攻击一：产品设计师/交互设计师（用户体验范式）

> "P/C 角色分离是一种产品设计上的懒惰——把纠结丢给用户自己解决。"

你们在做的事情本质上是：**不愿意设计一个能够自己判断场景的 AI**，而是把这个判断责任推给用户。你们说"当输入是成品时用 P，是素材时用 C"，但问题在于：**用户自己不知道自己的输入是成品还是素材**。一个创业者发了 400 字的感想给 AI，他觉得自己已经想清楔了——但你们的框架说他的输入是"素材"。这就造成了一个**巨大的产品断裂：用户以为自己在获得 P 角色的高效交付，其实需要的是 C 角色的深度诊断**。

更糟糕的是，你们的“误用代价”描述中，“该用 C 时用 P → 用户获得结构完整但思考不成熟的产物”——这是用户无法自察的陷阱。用户看到一份漂亮的清单体，他以为自己已经"想清楔了"，而你们知道他只是"切清楔了"。**这种信息不对称会导致用户在错误的认知基础上做出更错误的决策**——而他们永远不会知道自己被误导了。

真正的解决方案不是让用户选择 P 或 C，而是设计一个**能够自动检测输入完成度并自适应切换的单一 Agent**。如果 AI 检测到用户的输入包含大量“感受词”而缺乏“行动词”，它应该自动进入 C 角色；如果检测到“结论明确”“案例具体”“逻辑自治”，它应该自动进入 P 角色。把这个判断交给用户是不负责任的产品设计——**你们在让用户为你们的产品缺陷买单**。

### 外部攻击二：组织行为学家/管理咨询师（团队协作与权力范式）

> "P/C 角色分离在团队层面上是一颗定时炸弹。"

你们这个框架假设每个人都能自己决定自己需要什么角色。但在组织中，**角色选择是权力的延伸**。当一个老板选择使用 P 角色时，他在无声地宣告：“我的思考已经完成了，我只需要一个执行者。” 当一个员工选择使用 C 角色时，他在无声地宣告：“我的思考还不成熟，我需要被教导。” 这两种声音在同一个团队里同时存在时，**会直接影响团队的权力动态和信任结构**。

想象一个场景：一个高管发了一份感想给 AI，被 P 角色整理成清单体后转发给团队。团队成员看到这份"结构完整、逻辑严密”的文档，以为这就是老板的最终决策——但其实老板只是在发散思维，根本没有做出决策。这就是“切清楔”和“想清楔”的区别在组织层面的破坏力。更可怕的是，如果团队里有人觉察到这份文档的"模板感”（因为是 AI 生成的），他们可能会**暗中降低对老板思考深度的信任度**——因为他们看不出哪部分是老板自己想的，哪部分是 AI 套的。

最终，你们在做的事情是**用一个笔记方法论框架，干预了组织里的权力交流**。这不是技术问题，这是政治问题。你们的框架没有任何机制来处理"这份 AI 整理的笔记代表了多少人的真实意愿"这个问题——而在团队中，这个问题比"笔记写得好不好”重要一百倍。

## Constraints

- **完成度判断是主观的**：同一份输入，不同人可能有不同的完成度评估，框架本身没有客观的“完成度计”
- **用户可能误判自己的输入类型**：大多数人会高估自己输入的完成度（以为自己发的是“成品”，其实是“素材”）
- **切换成本被低估**：从 P 切换到 C 或从 C 切换到 P，需要重新建立上下文，用户体验上有“出戏”感
- **无法处理"中间态”**：很多输入既不是纯粹的“成品”也不是纯粹的“素材”，框架在这种灰色地带无力
- **文化背景影响角色选择**：在高上下文文化中，用户可能因为"不好意思被教导”而拒绝 C 角色，即使他们实际需要

## Cases

### 案例一：成功——同一用户的正确角色切换（真实对话实录）

**场景 A：C 角色**
- 时间：2026-06-07 19:29
- 用户输入："清单体笔记是 AI 时代协作的最大公约数"——这是一个**观点性的评价**，但没有具体的个人情况、没有盲区诊断、没有行动计划
- AI 角色选择：C 角色（正确）——通过四要素诊断帮助用户从“有观点”进入“有计划”
- 输出：54 条消息后的《10 倍速练习行动报告》

**场景 B：P 角色**
- 时间：2026-06-07 20:21
- 用户输入：400+ 字的非结构化复盘，包含 6 个完整的认知点、具体案例、行动决心——这是一份**已完成思考的“成品”**
- AI 角色选择：P 角色（正确）——直接结构化，不需要诊断
- 输出：2 条消息后的 6 模块清单体笔记

**切换关键**：同一用户在同一天内，根据输入的完成度自然切换了角色。这证明 P/C 角色不是用户属性（“这个人适合 P”），而是**任务属性**（“这个任务需要 P”）。

### 案例二：失败/边界——“切清楔了”的组织风险

**背景**：某创业公司 CEO 使用 P 角色整理了自己关于“产品方向”的思考，形成了一份漂亮的清单体笔记，然后转发给 CTO 和产品团队。

**问题**：CEO 的原始输入实际上是**“素材”**——他只是有一些散漫的想法，没有做过深度的市场调研、竞品分析、技术可行性评估。但 P 角色把这些散漫想法整理成了“结构严密的战略文档”。

**后果**：CTO 看到这份文档后，误以为这就是 CEO 的最终决策，开始按照文档分解任务。两周后，CEO 发现自己当时的想法不成熟，需要大幅调整方向——但 CTO 团队已经投入了大量工作量。

**教训**：这是“该用 C 时用 P ”在组织层面的极端案例。CEO 如果先用 C 角色做一轮诊断（“这个方向的假设是什么？验证过吗？风险在哪里？”），可能会在早期发现问题，避免后期的大规模返工。

### 案例三：反常识——"被教导”的正向价值

**背景**：某高级经理使用了 C 角色进行四要素诊断，被 AI 要求自评 50 分、被要求承认"滑回惯性"。

**反常应**：经理反感：“我付费用你们的产品，结果被 AI 教训了一顿。”

**但事实上**：这个“被教导”的体验恰恰是 C 角色的价值所在——**强迫用户停下来，面对自己不愿意面对的真相**。如果用户的反感是"被教训了”，说明他的自我认知与实际能力之间存在差距——这正是改变的起点。

**启示**：P/C 角色的设计不应该以"用户舒适度”为唯一指标。C 角色的"不舒适”本质上是一种**服务设计**——它让用户在短时间内经历一次"认知刷痛”，从而快速跳出盲区。这个设计决策需要在产品层面明确表达："本模式会让您感到不舒适，因为它的目的是帮您发现盲区，而不是让您舒服。”

## Synthesis

- **与 [[yt-note-ai-p-role-not-c-role]] 的关联**：前者是理论定义卡（"什么是 P 角色和 C 角色”），本卡是真实场景案例卡（"在真实对话中 P 和 C 是怎么表现的、如何切换的”）。两张卡片必须对照阅读——理论卡告诉你应该这么做，案例卡告诉你真实世界中这么做会产生什么后果。特别是案例二中的组织风险，是理论卡无法预见但案例卡必须告诉你的。

- **与 [[yt-skill-p-role-prompt-design]] 的关联**：本卡的“切换信号”直接决定了该 skill 卡中提示词的“边界控制”组成如何设计。如果本卡判断某个输入应该用 C 角色，那么 P 角色的 prompt 必须在这种情况下触发边界控制，提示用户切换到教练模式。两张卡片合并使用，可以构建一个自动切换的 P/C 双模求 AI Agent。

- **与 [[yt-note-deliberate-practice-four-elements]] 的关联**：四要素诊断模型是 C 角色的核心工具，但本卡揭示了一个更深层的问题：**四要素诊断本身就是一种“不舒适”的体验**。用户在 C 角色下被要求自评、被要求面对盲区，这种不舒适是故意设计的——因为没有这种不舒适，用户就不会跳出舒适区。本卡的案例三直接证明了这一点。

- **与 [[yt-skill-checklist-as-ai-protocol]] 的关联**：当清单体笔记成为 AI I/O 协议后，P 角色的交付物（清单体笔记）可以直接作为下游任务的输入。但本卡提醒：如果这份“成品”是用 C 角色的诊断产物（如四要素报告），它也可以被 P 角色整理成清单体——这意味着 P/C 角色可以**串联使用**：先用 C 诊断，再用 P 整理。这种串联模式是未来 AI Agent 设计的关键方向。
