## 对比框架

| 关注点 | 记录什么内容 | 增长速度 | 缺失时的影响 | 一堂（be） | SQL-Helper |
|:---|:---|:---|:---|:---|:---|
| **系统自述** | 记录系统的架构、组件、技术栈 | 缓慢 | 系统架构随演化发生漂移 | 项目架构文档 | 项目架构文档 |
| **领域知识** | 系统所服务的领域的相关知识 | 缓慢 | 业务逻辑冲突/混乱/不可验证/不可解释 | 业务知识：课程运营知识、复盘营知识、马拉松知识、直播间知识、MBA 知识、快递知识、… | 类似，但更简单，主要描述名词与表结构/查询的映射关系 |
| **ForAgent** | 服务于 Agent 日常工作的约束信息 | — | Agent 行为模式混乱，反复犯同样的错误，效率低下… | — | — |
| **导诊台** | 当用户给出新任务时，应该先通过导诊台进行路由，用正确的知识和流程解决问题 | 慢 | （同上，共享影响） | 开发任务、debug 任务、运维任务、运营 SOP 任务、新需求讨论、面向前端的文档撰写、… | 封闭任务：把用户问题翻译成合适的 SQL。**不需要导诊台** |
| **Agent 工作手册** | AGENTS.md + 各类任务的执行规范 | 慢 | — | 每类任务有独自的规范 | 数据分析任务的执行步骤 |
| **工具箱** | 系统命令、脚本 | 慢 | — | 飞书 CLI、分析库、线上服务器访问 | 从 Metabase 更新 SQL 信息脚本、从 TiDB 更新表结构脚本 |
| **经验与模式库** | Agent 工作过程中积累的经验（最好能通过 hook + RAG 进行注入） | 中等 | — | 运营 SOP、case 排查记录 | 慢查询积累、业务知识积累 |
| **任务管理** | 长周期任务/复杂任务的状态/上下文管理。可以接入成熟的 issue 管理平台，没必要自己搞 | 快 | 复杂任务难以跟踪、推进和交付，多任务之间存在冲突 | 用 git 和 Codex 对话简单管理 | 每次用户查询任务，独立生成一个物理目录。记录查询的上下文。保存 AI 生成的文档和 SQL 文件 |
| **日志** | Agents 日志、系统日志 | 非常快 | 系统性问题难以追踪、定位和排查，没有指标和优化方向 | — | — |

## 子项拆解：任务管理

任务管理在"一堂"案例中有三个子维度：

| 子维度 | 一堂（be） |
|:---|:---|
| 任务定义与状态管理与归档 | 用 git 和 Codex 对话简单管理。可以接入成熟的 issue 管理平台，没必要自己搞 |
| 交付物 | — |
| 上下文 | — |

SQL-Helper 的任务管理则围绕每次查询独立生成物理目录，保存上下文和产物。

## 关键对比洞察

### 1. 复杂度差异
- **一堂**：业务复杂度高，需要完整的导诊台路由（开发/debug/运维/运营/新需求等多种任务类型）
- **SQL-Helper**：封闭任务，目标单一（翻译 SQL），**不需要导诊台**

### 2. 领域知识广度
- **一堂**：跨多个业务领域（课程运营、复盘营、马拉松、直播间、MBA、快递等）
- **SQL-Helper**：聚焦数据层，仅需名词与表结构/查询的映射关系

### 3. 增长速度规律
- 架构层知识（系统自述、领域知识）→ **缓慢**
- 工作规范（导诊台、工作手册、工具箱）→ **慢**
- 经验积累 → **中等**
- 任务状态 → **快**
- 日志 → **非常快**

### 4. 缺失影响层级
- 架构层缺失 → **系统漂移、业务混乱**
- Agent 约束缺失 → **行为模式混乱、反复犯错**
- 任务管理缺失 → **难以跟踪、推进困难**
- 日志缺失 → **无法追踪、无优化方向**

---

## 实践启示

> **简单系统（SQL-Helper）可以跳过导诊台，直接封闭执行；复杂系统（一堂）必须通过导诊台进行任务路由，才能避免 Agent 行为混乱。**

> **日志增长速度最快，是排查问题的核心资产；架构知识增长最慢，却决定了系统的长期演化方向。**
