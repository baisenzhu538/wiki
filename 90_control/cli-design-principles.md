# KDO CLI 输出设计原则

> 基于 讲香十指模型（李頔 260731），从"编译器风格"升级为"教练风格"。
> 面向所有 CLI 命令开发者（黄药师）+ 所有 CLI 使用者（老顽童/欧阳锋/王语嫣/外部 Agent）。

## 核心原则：讲香六律

| # | 原则 | 一句话 | 反模式 |
|:--|:--|:--|:--|
| 1 | **场景化** | 每条输出说清楚"你什么时刻会需要这条信息" | "missing required field 'title'" |
| 2 | **口语化** | 用"你"，像人在说话，不像编译器 | "the user must provide..." |
| 3 | **数字化+锚点** | 数字必须配参照基准，不然用户不知道好坏 | "8254 errors" |
| 4 | **情绪化** | 失败给路径感（"修这个→省一轮往返"），通过给成就感（"门禁全绿=欧阳锋可以专注审内容"） | "PASS"/"FAIL" 两个字 |
| 5 | **比喻化** | 复杂概念给锚点——MCP=万能插座，Graph RAG=知识地图，lint=门禁安检 | "Graph RAG index" |
| 6 | **升华化** | 关联更大价值——"你不在修 YAML，你在训练未来 AI 的商业判断力" | "status updated" |

## 错误消息模板

```
[级别] 路径: 问题描述
       场景化提示——这个错误意味着什么、不修会怎样、怎么修。
```

### 示例

**Before（编译器风格）**：
```
[ERROR] 30_wiki/dk/dk-xxx.md: DK_SECTION MISSING: ## Critique
```

**After（教练风格）**：
```
[ERROR] 30_wiki/dk/dk-xxx.md: DK_SECTION MISSING: ## Critique
       缺 Critique = 只讲了观点没接受质疑。补上后提交，欧阳锋不会再为这个退回你。
```

## 成功消息模板

```
✅ 结果描述
   这意味着什么——用户现在可以做什么、省了什么、快了多久。
```

| 命令 | 当前讲香水平 | 目标 | 优先改进点 |
|:--|:--|:--|:--|

| `health-check` | 50 → 75 | 数字→叙事 | 场景化解释 (已实现) |

## 何时用哪根手指（速查）

| 用户反馈/场景 | 问题本质 | 用哪根手指 |
|:--|:--|:--|
| "这个错误什么意思？" | 缺场景化 | 场景化 |
| "看起来像编译器报错" | 缺口语化 | 口语化 |
| "这个数字是好还是坏？" | 缺数字化+参照 | 数字化 |
| "通过了然后呢？" | 缺情绪化（成就感） | 情绪化 |
| "失败了怎么办？" | 缺情绪化（路径感） | 情绪化 |
| "Graph RAG 是什么？" | 缺比喻化 | 比喻化 |
| "我在干什么？修格式？" | 缺升华化 | 升华化 |

## 迭代原则

- **只改输出，不改行为**：参数、返回值、协议不变
- **先改高频触点**：lint/pre-submit 每次提交必经 > health-check 周期性查看
- **狗粮测试**：改完自己跑一遍，确认输出比之前好读
- **渐进**：不用一次把所有命令升级到 90 分，70 分就是巨大的用户体验飞跃
