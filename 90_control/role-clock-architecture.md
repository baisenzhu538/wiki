# 角色级时钟与探针架构设计 v1（#525）

> 黄药师 2026-08-25。老朱直令：「时钟和探针机制严格意义上应该是每个角色都有，不是和工具挂钩」
> 「工具可能用 kimi/claude/codex/hermes/CodeBuddy 等，可能会换，但自动化工作流不能变」。
> 核心命题：**工具是变量，角色是恒量**（命名铁律同哲学）。本稿只设计不施工，拍板后拆实施单。

## 0. 现状判词（问题定义）

| 层 | 现状 | 缺口 |
|:--|:--|:--|
| 探针层 | ✅ 已达标：conveyor_probe 工厂级单例 + `todos/<role>.md` 收件箱 + 飞书按角色推送；失败可见已覆盖（#519 空转根治+state 年龄报警，#523 拒删上报） | 无（维持单例） |
| 时钟层 | ❌ 绑在工具上：CLI 实例靠老朱手动开会话才醒（时钟=人手——#514 口径卡半天实证：风清扬无时钟无人报，任务书前置无人触发）；hermes 实例靠平台 profile cron（工具给的时钟，换工具就丢）；黄药师时钟=Kimi CLI 会话内 cron（会话活时钟活，会话死时钟死） | 角色级时钟不存在 |
| 注册层 | ❌ 不存在：「角色当前活在哪个工具实例上」无任何机器可读记录 | 活性注册表缺失 |
| 语义层 | 🟡 半统一：叫醒文案各写各的（🔔/⚖️/📥 各自硬编码） | 唤醒语义未统一 |

## 1. 角色→活跃实例注册表（`90_control/role-registry.json`）

```json
{
  "huangyaoshi": {
    "instances": [
      {"tool": "kimi-cli", "kind": "cli", "session_scope": "C:/Users/Administrator/Desktop/wiki",
       "heartbeat_ts": 1787654400.0, "channels": ["todos", "feishu"]},
      {"tool": "hermes", "kind": "platform", "profile": "huangyaoshi",
       "heartbeat_ts": 1787654000.0, "channels": ["feishu"]}
    ],
    "active": "kimi-cli"
  }
}
```

- **写侧**：实例上线/心跳写注册表——CLI 会话启动钩子写一次+会话内时钟每拍顺手写（零成本蹭拍）；hermes 平台由 profile 侧心跳脚本写。心跳写=单行 JSON 更新，无锁竞争（单角色单活跃实例写自己键）
- **读侧**：调度器/探针路由前读注册表——`active` 指向当前活跃实例
- **活性判定**：heartbeat 年龄 >2×该角色节奏 = 疑似死亡（复用 #519 state 年龄口径），调度器降级到次活实例；全死 → gate-blocked.log 机器自报（复用 #471 通道，不新造报警器）
- **多实例并存口径**：同角色 CLI+飞书双活（欧阳锋在家/在外模式）→ 唤醒**双发**（两通道都推，消费幂等靠各自去重）；`active` 仅用于「哪个实例该执行动作」（单执行者防双写）
- 从轻实现：单 JSON 文件，不落数据库（边界纪律）

## 2. 角色心跳调度器（`kdo-tools/role_clock.py`，新）

- 每角色唤醒节奏可配置（注册表内 `wake_cron` 字段）：王语嫣定时对账（如每 30min）、欧阳锋有提审即醒（事件驱动，探针信号触发）、风清扬审计节奏（如每日 2 拍+事件触发）
- 调度循环：schtasks 每 5min 跑 `role_clock.py` → 对每角色查注册表 → 到点/有信号 → 路由唤醒到 active 实例通道 → 写心跳日志
- **工具切换=注册表改一行，工作流零改动**（核心验收点）：角色的 wake_cron、唤醒语义、收件箱路径全部不变，只有 `active` 指向的工具实例变
- 与 conveyor_probe 分工：探针=信号检出（看世界变化），调度器=节奏唤醒（催人干活）——两单例不合并（探针 10min 扫描节奏 ≠ 角色各异唤醒节奏）

## 3. 唤醒语义统一层

底层不管是 hermes cron / schtasks / CLI 会话内 cron / 会话启动钩子，角色收到的唤醒语义统一为一个payload：

```
【叫醒】<role>：读 90_control/todos/<role>.md 未读段 + 70_product/tasks/production-queue.md 你名下状态
（有任务按队列序施工；无任务报告待命；会话纪律照 AGENTS.md）
```

- 传输层适配器（薄）：feishu=webhook 推送 / cli=todos 落盘+下次会话启动读 / hermes=profile 消息
- #520 提审叫醒作为第一个用例纳入：现有「🔔 新提审」通知改为经统一层路由（文案不变，路径换轨）
- 语义层不含业务判断——「该干什么」的判读在角色侧（唤醒只负责叫醒+指路，红线：调度器不做裁决）

## 4. 工具接入契约（新工具最小实现清单）

任何新工具（CodeBuddy/未来 CLI/平台）接入须满足：

1. **能收唤醒**：实现至少一个传输适配器（feishu webhook / 文件落盘读 / 平台消息）
2. **能读收件箱**：`90_control/todos/<role>.md` 可读（文件系统可达）
3. **能跑流转**：`queue_transition.py` 可执行（Python 3.12+ 环境）
4. **能写心跳**：注册表单行 JSON 更新（启动+节奏拍）
5. **MCP 可挂**（检索面）：kdo_search/kdo_read 可用（kdo MCP server 或等价物）

接入动作=实现契约+注册表登记一行。**不碰工作流、不碰探针、不碰门禁**。

## 6. 探针层确认

维持工厂级单例（不多头扫描——多头=重复通知/状态竞争）。失败可见已由 #519（空转根治+state 年龄报警入 health-check）/#523（拒删接 gate-blocked 通道）覆盖，本设计只引用不改动。

## 7. 工具切换演练剧本（核心验收推演）

场景：黄药师生产主力从 Kimi CLI 切到 Claude Code（或任意两款互换）。

| 步骤 | 动作 | 断点检查 |
|:--|:--|:--|
| 1 | Claude Code 装 MCP（kdo server 挂载）+ 启动钩子指向 `20_memory/huangyaoshi-amnesia-recovery.md` | 契约第 2/5 条 |
| 2 | `role-registry.json` 改一行：huangyaoshi.active = "claude-code"，新实例登记心跳 | **工作流零改动**——queue/探针/门禁/收件箱路径全不变 |
| 3 | role_clock 下一拍读注册表 → 唤醒路由到 claude 实例通道 | 语义层 payload 原样 |
| 4 | Claude 会话启动：读锚点→读 todos/huangyaoshi.md→巡查看板 | 与 Kimi 侧启动 SOP 逐字相同 |
| 5 | 施工流转：claim→施工→complete 全走 queue_transition.py | 契约第 3 条 |
| 6 | Kimi 实例下线：注册表删除该实例条目（或心跳自然超龄降级） | 活性判定自动失效 |

推演结论：无断点。唯一前提=新工具实现 §4 契约五条。

## 8. 红线符合性自检（供风清扬审计）

- **熔断自动化**：调度器只做唤醒路由，无裁决/无流转能力；活性判定失败→降级报警，不自动切换执行权
- **误判成本不对称**：唤醒误发=低成本（角色多看一眼）；唤醒漏发=高成本（#514 实证卡半天）——设计偏向「宁可多发」
- **L1 全量留痕**：心跳/唤醒/降级全留日志（心跳日志+gate-blocked 复用）
- **抽检永不归零**：本设计不碰审查层，终审权责不动（欧阳锋终审、降档老朱拍板 F-055）

## 9. 实施拆分建议（拍板后立项，不在本单）

1. 注册表+心跳写钩（CLI 会话启动写+时钟蹭拍）——小单
2. role_clock 调度器+schtasks 挂载——中单
3. #520 叫醒换轨统一层——小单
4. 风清扬/王语嫣/欧阳锋时钟开通（按角色节奏配置）——中单
