# 诊断版固件套路

> 路径：`90_control/electronics-practice/diagnostic-firmware-skills.md`

## 核心思路

一段复杂的信号链路出问题了，你不可能同时调试所有环节。

正确的做法是：**短路掉中间环节，看两端是否正常。**
- 如果两端正常 → 问题在中间环节的时序/配置上
- 如果两端不正常 → 问题在硬件/电源/焊接上

---

## 来自实战的三阶段诊断法

案例：广冷电子 HX-SMJ 红外光栅板 V2.2
- 链路：MCU → 电平转换(SN74LVC2G07) → 595 → MOSFET → LED → 接收管 → MUX → 运放 → MCU
- 故障：绿灯常亮，16 通道全部检测失败

### 第一阶段：确认"两端"是否正常

**做法**：写一个诊断版固件，跳过所有中间逻辑，直接控制输出端。

```c
void Diagnostic_ForceTx(void)
{
    GPIO_SetBits(GPIOC, GPIO_Pin_6);  // QD1 强制高
    GPIO_SetBits(GPIOC, GPIO_Pin_15); // QD3 强制高
}
```

**结果判断**：
- LED 亮了 → **发射管和接收管硬件是好的，问题在中间的控制逻辑上**
- LED 不亮 → 查硬件（电源、焊接、元件损坏）

### 第二阶段：分区逼近设计意图

硬件确认后用增量修改反推设计者的意图。**每次只改一个变量**，有效就留下，无效就回退换一个改。

```
第一轮：调延时参数
  Ir_Delay: 15→30→100→200→300→500
  → 200 开始有效果 → 锁定在 RCLK 时序上

第二轮：调接收判断逻辑
  原来：IN1&&IN2&&IN3&&IN4 全通才判有
  改为：只判一路 → 发现 IN2/IN3/IN4 其实没信号
  改为：分段检测 → no<8 判 IN1&&IN3，no>=8 判 IN2&&IN4
  → 全通道正常工作 ✅
```

**关键判断**：参数调不通时不要继续调参数——**换一个变量。**

### 第三阶段：反推设计思路

修好之后回头想清楚"为什么这个参数能修好"，这比修好本身更有价值。

**反推出来的设计思路**：
1. V2.2 硬件加了 SN74LVC2G07 电平转换器——这是为了抗干扰，改对了
2. 但开漏输出只能拉低不能拉高，拉高靠上拉电阻充电
3. RCLK 拉高后如果不等电平稳定就锁存 → 595 读到错误数据
4. RCLK 后加 Ir_Delay(200) = 等电平稳定再锁存 → 问题了

**所以真正的问题不是硬件坏了，而是软件没跟上硬件的特性。**

## 当没有原理图时：故障树 + 逆向推理

现实情况往往是：资料不全、原理图不可靠、没有人可以问。这时候不能从"看懂设计"入手，而要从**测试反推设计**入手。

### 核心理念

> 把被测物当成黑盒，通过设计诊断实验来逐步勾勒出它内部的逻辑结构。

每一次诊断实验就像在故障树上剪掉一个分支——不指望一次找到根因，只指望排除一个错误答案。

### 操作流程

```
Step 1：定义顶事件（故障现象明确、可观测）
  └── 绿灯常亮、通道错位、无输出……

Step 2：建立下一层假设（至少 2-3 个互斥的可能原因）
  ├── 可能是发射链路坏了
  ├── 可能是接收链路坏了  
  └── 可能是电源/时序问题

Step 3：为每个假设设计一个诊断实验（最小的可执行测试）
  ├── "强制拉高 QD" → 验证发射链路硬件是否正常
  ├── "手动短接接收管" → 验证接收链路是否正常
  └── "加长 RCLK 后延时" → 验证时序是否关键

Step 4：执行实验 → 根据结果排除分支 → 进入下一层
  ├── LED 亮了 → 排除发射链路硬件故障 → 进入时序分支
  ├── Ir_Delay(200) 有效 → 锁定在 RCLK 上升沿
  └── …

Step 5：根因锁定后，修复 → 验证 → 沉淀
```

### 实战案例：广冷红外板

```
顶事件：绿灯常亮（16 通道全失败）
  │
  ├─ 假设 A：发射链路硬件损坏
  │   └─ 诊断实验：强制拉高 QD1/QD3 → LED 亮了 ✅ → 排除 A
  │
  ├─ 假设 B：接收链路硬件损坏
  │   └─ 诊断实验：手动挡光看 IN 引脚电平变化 → 能检测到变化 ✅ → 排除 B
  │
  ├─ 假设 C：595 控制时序异常（剩下唯一可能）
  │   ├─ 子假设 C1：SRCLK 时序问题
  │   │   └─ 实验：加长 SRCLK 后延时 → 无效 ❌ → 排除 C1
  │   ├─ 子假设 C2：RCLK 时序问题
  │   │   └─ 实验：加长 RCLK 后延时 Ir_Delay(200) → 开始有效 ✅ → 锁定 C2
  │   └─ 子假设 C3：QD1/QD3 数据线时序
  │       └─ 实验：调整数据线时序 → 无效 ❌ → 排除 C3
  │
  └─ 根因：SN74LVC2G07 开漏输出 → RCLK 上升沿变缓 → 595 锁存不可靠
      修复：RCLK 拉高后加 Ir_Delay(200)
```

这个过程的关键不在于每一步都猜对，而在于**每个实验都能排除一个分支**。哪怕三个假设全错，排除法也会让你靠近真相。

### 和"有原理图"的根本区别

| | 有原理图 | 没有可靠原理图 |
|:----|:---------|:--------------|
| 分析方法 | 看懂设计 → 推测故障点 → 验证 | 设计实验 → 排除分支 → 逼近根因 |
| 依赖 | 文件准确性 | 实验设计能力 |
| 速度 | 如果原理图正确则快 | 初期慢，但不受资料质量影响 |
| 适用 | 资料完整的新项目 | 二手资料、离职交接项目 |

### 故障树分析法的关键原则

1. **每个节点必须可测试**——如果一个分支你没法设计实验来验证，那这个分支就没用。不如把它拆成更细的子分支，直到每个都"可测"
2. **优先排除最简单的假设**——先怀疑电源、焊接、接触不良，再怀疑芯片损坏，最后才怀疑设计本身
3. **诊断实验越简单越好**——强制拉高一个 GPIO 比写一段复杂的扫描逻辑快得多，也可靠得多
4. **参数调不通时，换变量，不要继续调参数**——如果在同一个参数上试了 3 个值都无效，说明假设错了，不是值没找对

## 常用诊断手法速查

| 手法 | 做法 | 适用场景 |
|:----|:-----|:--------|
| 强制拉高 | GPIO 直接输出 1，不经过任何外设控制 | 确认驱动管/MOSFET 本身正常 |
| 单步扫描 | 每步加长延时到秒级，肉眼观察灯变化 | 定位哪一步开始出错 |
| 分半测试 | 先只测前半通道，再只测后半 | 缩小范围到具体几个通道 |
| 参数扫描 | 一个参数从最小值步进到最大值，记效果 | 找最佳时序参数 |
| 诊断主循环 | main 里只留被测功能，关掉所有其他任务 | 排除多任务干扰 |
