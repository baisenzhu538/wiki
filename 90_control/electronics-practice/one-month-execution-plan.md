# 电子工程域：一个月实操路线图

> 目标：利用现有电子资料和电路板，一个月后能独立做设计改动和功能新增。
> 原则：每周一个闭环——做了、学到了、沉淀了。不写空中楼阁的架构。

---

## 先统一一个认知

**"能改能加"需要什么？**

```
能看懂现有设计 → 知道每个模块干什么、为什么这样设计
能动手改        → 改原理图/PCB/固件，知道改了会影响到什么
能验证          → 改完能自己测，知道测什么、怎么算通过
改了不忘        → 踩过的坑记录下来，下次不踩
```

这四个能力不是靠"归档完文件"获得的——是靠**实际改一次、实际加一次**获得的。所以这个路线图不是"先把文件整好再动手"，而是**边动手边整文件边沉淀**。

---

## 第 1 周：能看懂一块板

### 目标

拿一块现有的电路板（广冷红外板），能说清：每个 IC 干什么、信号怎么流的、固件怎么控制的。

### 具体动作

| 天 | 做什么 | 产出 | 验收 |
|:--:|:------|:-----|:-----|
| 1-2 | 画出信号链路图（从 MCU 管脚到最终输出/输入，经过的每一颗 IC） | 一张手绘/白板图 → 拍下来放 `_archive/06_photos/` | 能对着图说清"信号从哪来、经过谁、到哪去" |
| 3 | 列出每个 IC 的型号 + 关键参数（电压/电流/速度等级/输出类型） | 一张 IC 清单表，放 README 或单独 md | 每颗 IC 的 datasheet 至少翻过第一页 |
| 4 | 读懂固件主循环——初始化了什么外设、主循环干了什么、中断干了什么 | 固件注释版（不修改代码，只加注释） | 能说清 main() 的执行流程 |
| 5 | 收网：文件三分类清理 + 版本锁表 | `_archive/` 结构完整 + README 版本锁表 | 广冷项目归档 ≤ 500MB，基准线文件全部有版本号 |

### 本周不做的

- 不改任何设计
- 不写新的架构文档
- 不纠结"这个文件该放哪个目录"——先按欧阳锋的模板放，不对再调

---

## 第 2 周：改一个东西

### 目标

在广冷红外板上做**一个真实的改动**——最好是用户想改的、有实际用途的。走完"改→测→记"的完整闭环。

### 具体动作

| 天 | 做什么 | 产出 | 验收 |
|:--:|:------|:-----|:-----|
| 1 | 选定改动（例如：改指示灯行为、加一路检测、调响应速度）。写下来：改什么、为什么、预期效果 | 改动说明（3 句话，写 README 里） | 说清了"改什么"和"为什么" |
| 2 | 改固件（不改硬件的情况下改固件是最安全的起点） | 新固件版本 Vx.x | 烧进去能跑，改动生效 |
| 3 | 验证：测原来的功能没坏 + 新功能正常 | 测试记录（简单：测了什么、结果） | 至少测了 3 个场景 |
| 4 | 如果出问题了——走诊断流程（先做诊断版固件、分段隔离）。修好。 | 问题记录（症状→诊断→修复） | 修好了 |
| 5 | 沉淀：这次改了什么？踩了什么坑？有什么下次能复用的？ | 更新 README + 如果踩了新坑→写一条失败模式 | 版本锁表更新 + 至少一条知识沉淀 |

### 关键原则

- **先改固件，不动硬件**。固件改错了重烧，硬件改错了重做板。
- **每次只改一个变量**。不要"顺便把那个也调了"。
- **改之前先备份**。固件 hex + 源码整个目录 copy 一份。

### 本周不做的

- 不改原理图/PCB（那是第三周的事）
- 不追求"完美的测试覆盖率"
- 不建新的工具或脚本——用现有的

---

## 第 3 周：加一个功能

### 目标

在第 2 周的基础上，**新增一个需要改硬件设计的功能**。这是最难的一步——它要求你真正理解了设计意图。

### 具体动作

| 天 | 做什么 | 产出 | 验收 |
|:--:|:------|:-----|:-----|
| 1 | 选功能 + 做方案。例如：加一个光敏电阻自动调亮度、加蜂鸣器报警、改用更便宜的替代器件。写方案时回答：加什么元件？接哪个管脚？改多少代码？ | 方案（半页纸，画个草稿） | 方案没有明显矛盾（管脚没被占用、电平匹配、电流够） |
| 2 | 改原理图（在现有设计上增加） + 改 BOM | 新版本原理图 PDF + BOM 更新 | 新增部分有版本号 |
| 3 | 改 PCB（如果需要） + 改固件 | 新版本 PCB + 固件 | 能编译 |
| 4 | 验证：焊接→上电→测功能→测原有功能没被破坏 | 测试记录 | 两项都通过 |
| 5 | 沉淀：原理图为什么这样接？选这个器件的原因？踩了什么坑？ | 新版 README + 更新失败模式库 + 更新器件选型对照表 | 下次做类似功能能直接查 |

### 关键原则

- **新功能从最简单版本开始**。"加蜂鸣器"第一个版本只让它响/不响就行，不要一上来就 PWM 调音调。
- **新增元件优先用已有的**——如果广冷板上已经用了某颗运放，新功能尽量复用同型号。
- **改完之后跑一遍"原功能没坏"的回归测试**。

---

## 第 4 周：闭环 + 下一个项目启动

### 目标

把前三周踩的坑、学到的方法、积累的知识**结构化入库**，然后用这套东西启动下一个项目。

### 具体动作

| 天 | 做什么 | 产出 |
|:--:|:------|:-----|
| 1-2 | 广冷项目最终收网：版本锁表更新到最新状态、README 完整、失败模式整理、知识卡片入库 | 广冷项目 = "样板项目"——以后每个项目都按这个标准收网 |
| 3 | 提炼复用资产：哪些是"下个项目也能用的"？至少产出 3 样 | ① 器件选型速查表 ② 调试 checklist（从两次动手经历中提炼）③ 至少 2 张 dk-ef 卡 |
| 4 | 启动下一个项目：用广冷的模板建目录、写 README、标版本号。**花 1 小时搜 KDO**——"这个项目类似的坑以前踩过没有？" | 新项目骨架立好 |
| 5 | 回顾：这一个月达到了"能改能加"吗？差在哪？下个月重点是什么？ | 月度回顾（半页） |

---

## 每周检查（给自己看的）

每周末问自己三个问题：

1. **这周有没有实际动手碰硬件/烧固件？**——如果没有，说明在纸上谈兵
2. **有没有新踩的坑没记下来？**——如果有，现在就写，不要等到"项目结束"
3. **能不能在 5 分钟内找到上周改的那个文件的正确版本？**——如果找不到，说明版本管理没做到位

## 不建议做的事（在本月内）

- **不建"完美的归档体系"再动手**——一边改一边归档。完美的归档体系不存在。
- **不追求全自动化**——先手动跑通"改→测→记"的闭环，再谈哪些步骤能自动化。
- **不照搬 KDO 的卡片体系到硬件**——硬件知识的核心载体不是卡片，是"改过一次记住了"的肌肉记忆 + 检索时能找到的版本锁表。
- **不花时间学新工具**——Altium/KiCad/立创EDA 选一个你已经会的，不改。学工具的时间不算在"能改能加"的进度里。

---

## 一个月后的验收标准

- [ ] 能拿出一个"样板项目"（广冷），里面有：版本锁表、信号链路图、README、失败模式记录
- [ ] 能独立完成一个固件级改动（改代码→烧录→验证→记录）
- [ ] 能独立完成一个硬件级改动（改原理图→改 BOM→验证→记录）
- [ ] 遇到问题时第一反应不是"调参数"，而是"做诊断版固件先定位问题"
- [ ] KDO 能检索到至少 3 条电子工程的失败模式或调试方法
