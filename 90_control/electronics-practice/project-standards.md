# 电子工程基线规则

> 路径：`90_control/electronics-practice/project-standards.md`
> 
> 所有电子工程项目必须遵守的三条规则。

---

## 规则一：文件三分类

项目中的每一份文件必须归入以下三类之一：

| 类别 | 色标 | 定义 | 管理方式 |
|:----|:----:|:------|:---------|
| **基准线** | 🔴 | 描述"产品是什么"的不可替代文件 | 只增不改，新版本=新文件，不覆盖旧文件 |
| **佐证** | 🟡 | 有存档价值但不是产品本身的文件 | 按项目归档，可批量压缩 |
| **过程** | ⚪ | 用完即弃的中间产物 | 项目结束时删除 |

### 典型归属

| 文件 | 类别 | 说明 |
|:----|:----:|:------|
| 原理图（PDF/源文件） | 🔴 | 唯一的设计意图记录 |
| PCB 设计文件（JSON/Gerber） | 🔴 | 不可替代 |
| BOM（CSV/XLSX，标注版本号） | 🔴 | 不可替代 |
| 坐标文件（PickAndPlace CSV） | 🔴 | 不可替代 |
| 固件源码 + 最终烧录 hex | 🔴 | 不可替代 |
| 项目 README（版本对照表） | 🔴 | 不可替代 |
| 调试日志、实物照片 | 🟡 | 有存档价值 |
| 示波器截图、采购清单 | 🟡 | 备份即可 |
| 芯片数据手册 PDF | 🟡 | 可归档 |
| 编译中间产物（.o/.crf/.d） | ⚪ | 随时可删 |
| 重复备份、微信传图副本 | ⚪ | 随时可删 |
| 未解压的 .rar（内容已在外） | ⚪ | 可删 |
| KEIL 临时文件 | ⚪ | 可删 |

---

## 规则二：基准线文件的版本管理

1. **每份基准线文件必须标注版本号和日期**——文件名含 `Vx.x_YYYY-MM-DD`，否则视为草稿不投产
2. **原理图+PCB+BOM+坐标 四者锁定为同一个设计基线**——动了其中任何一个，其他三者必须重新确认匹配
3. **固件可以独立迭代**——不改硬件时可以单独改固件版本
4. **每一个基线变更必须记录原因**——在 README 版本对照表中注明

### 版本锁表示例

| 基线 | 原理图 | PCB | BOM | 坐标 | 固件 | 说明 |
|:----|:------|:---:|:---:|:----|:----|:-----|
| B1.0 | V1.0 | V1.0 | V1.0 | V1.0 | V1.0 | 初始设计 |
| B2.0 | V2.0 | V2.0 | V2.0 | V2.0 | V2.0 | PCB 改版 |
| B2.1 | V2.0 | V2.0 | V2.0 | V2.0 | **V2.1** 🔧 | 仅固件修复，硬件不变 |

## 规则三：项目收网清理

项目结束时（批量投产或结项），必须执行以下收网步骤：

1. **删除所有 ⚪ 类文件**（OBJ 目录、重复副本、未使用的压缩包）
2. **🟡 类佐证文件压缩归档**（照片、日志、截图等可打包）
3. **🔴 类基准线文件锁入 `_archive/`**，确保版本对照表完整
4. **确认"收网后存储 < 收网前存储的 50%"**——如果删掉的不到一半，说明有该删没删的

---

## 四、快速清查清单

| 文件类型 | 处理方式 |
|:--------|:---------|
| .o / .crf / .d / .htm / .dep | 直接删除 |
| .rar / .zip（已解压的内容已使用） | 确认后可删除 |
| 微信传图 `微信图片_*` 的重复副本 | 每张只留一个 |
| `广冷001` 与 `广冷002` 的完全重复 | 删 002 |
| JLinkLog.txt / .bak / .iex | 直接删除 |

## 规则五：固件发布管理

固件是项目中迭代最频繁的组件，也是最容易丢失版本记录的部分。

### 每一次烧录必须有记录

不管是谁、在哪台电脑上烧录的，必须记录：

```
日期：YYYY-MM-DD
烧录人：XXX
固件版本：Vx.x（对应源码的 git tag 或 commit）
硬件基线：Bx.x（对应哪一版 PCB/BOM）
hex 文件路径：05_firmware/production/
烧录用途：原型测试 / 小批量 / 量产
变更摘要：改了什么东西，为什么改
```

### 固件文件命名规则

```
{项目名}_{硬件版本}_{固件版本}_{YYYY-MM-DD}.hex
```

示例：`HX-SMJ-03B-A_V2.2_V2.3_2026-06-04.hex`

### 烧录记录存放位置

每次烧录的记录写入项目的 `07_logs/flash_log.csv`，格式：

```csv
date,person,fw_version,hw_baseline,hex_path,purpose,summary
2026-06-04,Codex,V2.3,B2.1,05_firmware/production/HX-SMJ-03B-A_V2.2_V2.3_2026-06-04.hex,debug,加了Ir_Delay(200)和分段检测逻辑
```

### 禁止行为

- ❌ 在 hex 文件名不写版本号就烧录
- ❌ 烧录了不记日志（过两周就忘了烧了哪个版本）
- ❌ 用覆盖的方式保存 hex（每次烧录的 hex 应该保留，不是替换）

## 规则七：项目目录结构（物理落地）

> 每条板卡按五类归档。外援在广冷项目中验证了这个结构能直接把文件给工厂生产。

```
项目名/
├── README.md                  ← 版本锁表（规则二）
├── 01_主控板/
│   ├── 01_BOM/                ← BOM 含版本号+日期
│   ├── 02_Gerber/             ← 制板文件
│   ├── 03_坐标/               ← PickAndPlace 文件
│   ├── 04_原理图/             ← PDF/源文件，与实物一致
│   └── 05_固件/               ← diagnostics/ + production/
├── 02_子板A/
├── ...
├── _archive/                  ← 收网后锁入（规则三）
└── 07_logs/                   ← flash_log.csv + 调试日志（规则五）
```

## 规则八：交叉验证检查单

> 拿到全套原文件后，必须执行五层交叉验证。不只对比"哪里不一样"——要判断"哪个是对的、为什么、物理后果是什么"。

验证模板：`kdo checklist hardware-cross-validation`

核心原则：
- L1 文件完整性（10 分钟）→ L2 跨文档一致性（30 分钟/板）→ L3 根因推断（不一致时必做）→ L4 问题分级 → L5 dk 卡对照
- L3 不能跳过：发现不一致≠问题定位了。必须回答**物理后果、已知模式对照、验证方法**
- L5 复用 KDO 知识库：查 `dk-ef-*` 卡判断是否已知模式复现

## 规则六：交接清单

> 本规则针对最脆弱的环节——**资料整理好之后，下一个人怎么快速接手？**

### 接手人需要在什么时候看到什么

| 接手步骤 | 看什么文件 | 目的 |
|:--------|:----------|:-----|
| 第 1 步（5 分钟） | `_archive/README.md` | 搞懂这板子是干什么的、哪个版本是对的 |
| 第 2 步（30 分钟） | `_archive/07_logs/` 调试日志 | 知道踩过什么坑、修了什么东西 |
| 第 3 步（2 小时） | `02_schematics/` + `04_bom/` | 理解设计细节 |
| 第 4 步（动手前） | `05_firmware/diagnostics/` | 烧诊断版固件确认硬件状态 |
| 第 5 步（收尾） | `05_firmware/production/` | 确认要烧录的 hex 版本 |

### 交接前的自查清单

项目交接前，上一任必须确认以下事项全部完成：

- [ ] `_archive/README.md` 存在且版本锁表填写完整
- [ ] 所有 🔴 基准线文件有版本号
- [ ] 07_logs/ 包含完整的调试日志（至少记录关键决策点）
- [ ] 05_firmware/diagnostics/ 有诊断版固件
- [ ] 05_firmware/production/ 有最终烧录的 hex
- [ ] ⚪ 过程文件已清除
- [ ] 版本锁表中的硬件版本与实物一致
