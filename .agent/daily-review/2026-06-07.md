## 一、今天最大的认知升级

### 1. 调试的误区：先分析，后动手，不如先动手，后分析

广冷红外板的案例给了我一个深刻的教训——我把大把时间花在分析 PCB JSON、BOM diff、原理图 OCR 上，但这些分析没有一个指向真正的根因。Codex 和用户的做法是：**做一个诊断版固件，制造一个可观测的信号，然后根据信号反推。** 这是"动手驱动分析"而不是"分析驱动动手"。

以后遇到类似问题，第一反应应该是"我能不能做一个实验？"而不是"我能不能看懂这个文档？"

### 2. 技能卡是被系统性地遗漏的，不是漏了几张

四篇口述稿，老顽童第一次只产出 5 个技能点，黄药师的扫描器跑出 100 个候选。这不是人不努力，是**管线默认优先萃取概念，技能被当作"太小了不值得记"而忽略。** 建立明确的分工（黄药师扫描→老顽童筛选写卡）后，一下午产出了 343 张 skill 卡。

### 3. 四卡体系覆盖了 KDO 的全部知识形态

concept（是什么）+ skill（怎么做）+ case（谁做过）+ dk（别踩坑）——这四个类型覆盖了所有知识形态。黄药师的提案是对的，不需要再新增类型。

## 二、今天犯的错 / 可以更好的地方

### 1. Edit 命令反复遗漏 file_path 参数

**今天至少犯了 15 次以上这个错。** 每次写 Edit 都忘了加 `file_path`，被拒绝后才补上。这个问题太低级了，浪费大量往返时间。

**防错机制**：写 Edit 命令前，先把文件路径打在草稿里：
```
Edit -file_path X -old_string Y -new_string Z
```

### 2. 混淆了"褚勉"和"Truman"

用户纠正我才发现——一堂课的口述老师是 Truman，不是褚勉。根本原因是我对一堂的课程体系和人物不熟，又没花时间去确认。

**防错机制**：遇到不确定的人名/地名，先确认再输出。

### 3. 分析广冷资料时用了过时的 PDF 作为基准

我把 V1.0 的设计分析 PDF 当成"矛盾证据"来分析，实际上那只是旧版草案。用户的交叉验证报告比我做得好——他按版本演进时间线梳理，而不是把所有文件平铺对比。

## 三、明天可以尝试的新方法

### 1. 遇到硬件问题先问"能不能用软件绕过"

这次广冷电动是典型案例——最终修的就是一行延时和一段判断逻辑，不需要动 PCB。以后任何硬件相关问题，第一反应先想"能不能用诊断版固件定位？"

### 2. 接受"不完美但够用"的模板

今天建了很多模板和规则文件。有些我反复调整细节——但其实只要框架对、能跑通，细节可以后续迭代。不要追求一次到位。
