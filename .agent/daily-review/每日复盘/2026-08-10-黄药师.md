## 思维盲点

"改了文件 = agent 会读"的幻觉——SOUL.md 第一版（TCPR=Teach/Consult/Practice/Research）正确写入了磁盘，gateway 也重启了，但 agent 三次回复都是老版 TCPR（Thinker/Coach/Practitioner/Reviewer + Assistant 默认身份）。反复检查文件内容、清缓存、重启，都没怀疑到"模型训练先验覆盖系统指令"这个层面。直到用"小海测试员"做 AB 测试才定位。

教训：当 agent 的行为精确匹配某个已知的旧版本内容，而磁盘上是新版本时，优先怀疑模型先验覆盖，而不是文件系统问题。验证方法：写一个极端简化的 SOUL（2 句话），如果生效了就是先验问题，如果不生效才是加载问题。

## 顿悟

1. SOUL.md 的措辞是 prompt engineering，不是文档——代码围栏、措辞的软硬程度（"默认以 Assistant 身份" vs "你永远是 X，禁止使用 Y"）直接影响模型是否服从。SOUL 不是给人读的说明书，是给模型下的指令。
2. 飞书 App 不能跨 gateway 共享——复制 profile 时顺手复制了 .env，导致两个 gateway 抢同一个飞书 WebSocket。Hermes 的报错很明确，但第一次部署时容易漏。
3. 时间胶囊的本质是"降低 agent 启动的认知负荷"——不是存更多信息，而是让 agent 用最短路径找到"我是谁、我在哪、别人在干嘛"。CAPSULE_STARTUP.md 的设计原则：每个 agent 只读 2 个段落（自己 + Shared State），1 分钟读完。

## 过程资产

- SOUL.md 反先验覆盖模板：绝对化用语（永远/禁止/不存在）+ 去代码围栏 + 内嵌关键定义（五阶梯表/冰山画布）
- "小海测试员"AB 测试法：2 句话 SOUL → 验证加载机制 → 排除文件系统问题
- 时间胶囊架构：time-capsule.db (SQLite) → capsule_sync.py (定时生成) → CAPSULE_STARTUP.md (agent 读取)
- systemd timer 模板：hermes-capsule-sync.timer（每 30 分钟），可直接复用

## 元反思

下次部署新 agent 时：
1. 新建飞书 App（不复制现有 .env）
2. SOUL.md 第一版就用绝对化用语（不要等出了问题再改）
3. 部署完立刻用"你是什么角色"冒烟——这是最快的 TCPR 一致性检查
4. 在 cap_hub 注册 + 飞书冒烟通过后，再加到时间胶囊 seed 数据里
5. 跑 capsule_sync.py 手动同步一次，确认 CAPSULE_STARTUP.md 更新
