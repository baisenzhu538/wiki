## 一、本阶段最大的认知升级（收获）

### 1. 九层深挖可以通过 skill 固化，且必须显式触发

药柜案例分析中，我通过多轮自我纠错把认知补到较深水平。事后把它写成 `40_outputs/capabilities/skills/nine-layer-business-dig/SKILL.md`，明确了触发条件（用户说"需要深挖"）、九层流程、停止条件和输出格式。

**关键洞察**：深挖不是默认行为。默认状态下我会给出适度深度的结构化回答；只有在用户明确触发后，才启动九层迭代。这样既避免过度分析简单问题，又能在复杂问题上复用药柜经验。

### 2. 垂直行业"决策工具卡簇"是产生高质量分析的核心资产

药柜案例之所以能支撑深度分析，不是因为我的能力强，而是因为知识库里有一簇专门卡片：
- `smart-medicine-cabinet-financial-model`（财务模型）
- `case-smart-medicine-cabinet-failure-patterns-library`（失败模式库）
- `smart-medicine-cabinet-national-policy-redlines`（政策红线）
- `smart-medicine-cabinet-o2o-cost-structure`（O2O 成本）
- `tool-smart-medicine-cabinet-site-selection-guide`（选址指南）

**关键洞察**：泛泛的概念卡价值有限。未来知识库建设的重点应该是把这种"财务模型 + 失败模式库 + 政策红线 + 成本结构"的卡片簇复制到 SaaS、餐饮、教育、内容平台等垂直领域。

### 3. 域间自检三问是防止"为凑数精修"的有效质量门

第二十节、第二十一节要求老顽童每完成一个域回答：案例够了吗？暗知识在哪里？共同模式是什么？

这三个问题迫使老顽童从"完成 30 张卡"转向"反思这 30 张卡构成的知识网络"。实际效果：
- 提炼出"因果防错四问"
- 提炼出"KDO 静默失败防御四步"
- 提炼出"工具投资决策五段式"
- 发现多个框架卡需要补案例、多个 case 卡需要互链

**关键洞察**：自检问题越具体，产出越不敷衍。"案例够了吗"不能回答"够"，必须说"还缺哪类案例、为什么"。

### 4. case 卡是框架卡的锚，没有 case 支撑的框架卡容易空转

本轮精修中，很多框架卡（如 `yt-panproduct-execution-roi-analysis`、`yt-management-basic-skills`）在补充了 case 互链后，可用性明显提升。反过来，一些只有概念描述的框架卡即使 DS 扩到 3 条，仍然感觉"飘"。

**关键洞察**：未来应该优先为核心框架卡配置 1-2 个独立 case 卡，而不是继续扩大框架卡数量。

### 5. Agent 高速产出必须匹配明确的验收标准和抽查机制

老顽童可以在 10 分钟内完成 30 张卡精修，但质量并不稳定：
- 有时会漏改 `status`（如 `yt-lean-daily-chemical-mvp` 还是 draft）
- 有时会漏填 `related`（如 2 张药柜 case 卡 related=[]）
- 有时会按自己的理解替换目标卡 ID（如第二十节批次 5）

**关键洞察**：速度不是风险，缺乏验收才是风险。王语嫣/欧阳锋必须在每批完成后跑门禁 + 抽样 + 核查元数据。

## 二、本阶段犯的错 / 可以更好的地方

### 1. 早期把老顽童按人类节奏理解

第十八节安排任务时，我按"几天完成"的人类节奏写执行计划。后来老朱纠正：老顽童是 agent，可以高速执行。这导致早期任务文件的时间预估失真。

**防错机制**：
- 对 agent 任务不写具体天数，写"批次"和"验收标准"
- 在任务文件中注明"用户已允许 agent 高速执行"
- 把时间节奏交给用户定，而不是我预设

### 2. 验收时过于机械地检查 case 卡结构

第二十一节验收时，我最初用脚本检查"case 卡正文是否有'诊断信号'和'失败模式'字样的 section"，结果把一些"业务公式错误示范"型 case 卡误判为不达标。这些卡的结构是"错误拆解 → 正确拆解 → 关键教训 → 可迁移校验方法"，内容上已经等价于诊断信号和失败模式。

**防错机制**：
- 验收时区分"结构模板"和"内容等价"
- 对非标准结构卡，检查是否有等价的触发信号、边界、教训
- 建立"结构偏离说明"字段，允许卡片声明自己采用的结构类型

### 3. 对 `kdo_lint.py` 误报问题推进不够坚决

多轮验收都提到 `kdo_lint.py` 对 wikilink 和中文 card ID 存在 regex 误报，但一直没有推动黄药师修复。长期以质量门禁为唯一依据是权宜之计，不是长久之计。

**防错机制**：
- 把修复 `kdo_lint.py` 列入黄药师的 P0 任务
- 明确修复标准：能正确处理 `[[id]]`、`[[id|别名]]`、中文 card ID
- 修复后以 30 张目标卡为测试集跑通

### 4. 对 reviewed_by 字段把关不严

为了满足门禁，多张卡把 `reviewed_by` 设为"王语嫣"或"欧阳锋"，但实际并没有独立走审流程。这会造成"形式上 reviewed，实质上未审"的风险。

**防错机制**：
- 王语嫣代欧阳锋评估的卡，`reviewed_by` 统一写"王语嫣（代欧阳锋）"，不要写"欧阳锋"
- 欧阳锋正式返回后，对 enriched/reviewed 卡进行抽检
- 建立"review 记录"，说明审了什么、没审什么

### 5. 没有及时识别同素材双卡风险

`case-personal-map-modeling` 和 `case-truman-personal-growth-map-creation` 是同素材双卡，直到第二十一节小结才明确提出。如果早些识别，可以在精修前就明确边界。

**防错机制**：
- 每批 case 卡精修前，先扫描是否有同素材/同主题双卡
- 对双卡明确分工：一张讲方法论，一张讲心路历程
- 必要时合并

## 三、下阶段可以尝试的新方法（行动）

### 1. 验收时增加"反向 checklist"

除了告诉老顽童"要做什么"，还要明确"不能做什么"：
- 不能替换目标卡 ID
- 不能把 case 卡写成概念描述
- 不能把 dk 卡写成普通概念卡
- 不能批量改完再跑 lint
- 不能把 `reviewed_by` 写成未实际审查的人

### 2. 建立"垂直行业卡片簇"模板

把药柜模式抽象为可复制模板：
```
<行业X>-financial-model.md
<行业X>-failure-patterns-library.md
<行业X>-policy-redlines.md
<行业X>-o2o-cost-structure.md
<行业X>-site-selection-guide.md
```

下阶段优先选择 1-2 个行业（如 SaaS、餐饮）试点复制。

### 3. 对 draft 卡按"价值密度"排序，而非随机挑选

674 张 draft 卡不能平均用力。下阶段挑选标准：
- 是否被多张 enriched 卡引用（入边多）
- 是否属于当前重点域（ToB、建模、决策）
- 是否有真实案例/数据支撑
- 是否影响用户高频咨询场景

### 4. 建立"深挖"使用反馈闭环

每次使用 nine-layer-business-dig skill 后记录：
- 用户问题是什么
- 实际挖了几层
- 哪层最有价值
- 哪层是多余的
- 知识库缺什么素材

这些反馈用来迭代 skill 和知识库。

### 5. 增加"同素材双卡/多卡"扫描步骤

每批精修前用脚本扫描相似标题/同 source 的卡片，提前处理边界问题。
