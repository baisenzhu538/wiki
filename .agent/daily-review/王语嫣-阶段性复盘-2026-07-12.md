## 一、本阶段最大的认知升级（收获）

### 1. 长素材分层读取协议实战验证成功——子代理是外存，行号索引是可回溯指针

C 域素材体量：5 篇口述逐字稿约 96 万字 + 5 份笔记 + 101 张 VLM 图 + 7 张方法论大图 + 洪七公三件套。全量亲读必然爆上下文。执行方案：5 篇逐字稿派 5 个 explore 子代理全量精读、回传带行号的结构/案例/勘误索引；101 张 VLM 派 1 个子代理建图号索引；7 张大图和 5 份笔记（短而密）我亲读；6 个冲突点我按行号 `sed -n` 定点复核后下裁定。结果：王语嫣上下文零爆炸，所有裁定有一等证据锚点，生产零返工风险。协议已落 dk 卡（#154 reviewed）。

**关键洞察**：协议的价值不在"省上下文"，在"可回溯"——回传的不是结论而是指针（`source_refs: ...L104-L360`），任何结论都能回到原文验证。这是子代理协作与纯摘要外包的本质区别。

### 2. 「口述稿一等证据」不是口号，是纠错引擎

6 项冲突裁定全部靠一等压二等救出错误：PEAHD（笔记 TEAHD、转写 PAHD 均误）、C=宏观效率（整合笔记写成微观×效率，口径置换）、复盘营 100→3000-4000 人/期（ASR「34000」误识）。实测笔记的错误率不低，二等证据只能用于交叉定位疑点，不能用于定案。老朱 07-12 再次强调此纪律，已确认落盘三处（诊断证据等级表 / personal-os 协议 / zhu-feedback-patterns）。

**关键洞察**：证据等级的真正用途是**冲突发生时的裁判规则**，不是阅读顺序的建议。没有冲突时一二等看起来差不多；冲突一来，等级就是生死线。

### 3. 建域规模由素材粒度决定：一次分享→几张卡，一部大课→完整域

之前（07-09/07-10）我判断 C 域"够了"，依据是孔源一次分享的素材已产 15 张卡。本次全量处理后发现 C 域是一部五篇教学闭环的完整大课（导入→实操→进阶→参数→逻辑→管理），对应规模是 ~47 张卡 + agent-spec + digest。素材粒度决定建域粒度：分享级素材出补丁卡，大课级素材建完整域，代码库级素材（EC 线）走分库。

**关键洞察**：建域立项的第一个问题应该是"这批素材是什么粒度"，而不是"这个域有没有卡"。

### 4. 域完整度的衡量标准是 agent 检索命中率，不是「有没有卡」

KDO 本质是给 agent 用的。底稿 15 张卡覆盖了"是什么"（ABC/冰山/范式名词），但 agent 接到"帮我挖参数"任务时，给不出 L1-L6 逐层动作——工作流层（三段工作流/降龙十八掌/格式打分/攻坚会/假设池）和案例证据层（旗舰 8 案+学员 7 案+合集 4 组）整个缺失。名词成卡≠域建成。

**关键洞察**：验收一个域时，模拟 agent 拿三个真实任务坐标来检索，命中不了的动作层和证据层就是缺口清单。

### 5. 建议书审计的第一步是识别建议者的目标函数

洪七公建议 20 张、黄药师建议 20 张+三批，两人都在压缩体量——他们优化"可交付性"，老朱的铁律是"不遗漏"（优化知识完整性）。目标函数不同，建议自然系统性偏低。另：黄药师建议独立域目录，与他自家 #151 的 digest+cap_hub 架构自相矛盾——建议书内部一致性也是审计点。最终裁定：体量维持 ~47 张，目录维持通用目录+digest，采纳其防呆清单和桥接卡实物，其 agent-spec draft 因 source_refs 全引笔记（踩口述一等线）裁定有条件采纳。

**关键洞察**：建议书审计三问——建议者的目标函数是什么？与老朱的一致吗？建议与建议者自家架构一致吗？

## 二、本阶段犯的错 / 可以更好的地方

### 1. 早期误判「C 域够了」——用二等证据判断一等域的完整度

07-09/07-10 对齐时，我凭孔源单次分享素材+笔记判断 C 域 15 卡"够了"。老朱当时说"孔源分享只是冰山一角"，我口头同意但判断上没真信。全量素材进来后被体量差直接打脸（96 万字口述 vs 2 万字卡库）。

**防错机制**：
- 建域规模评估前先做数量级对比：口述稿体量 vs 卡库体量，差两个数量级就是"冰山一角"信号
- 素材粒度三档（分享/大课/代码库）先定档再定规模
- 老朱说"不够"时默认他对，举证责任在我

### 2. 漏读黄药师补充建议书——收尾前没做输入目录终扫

黄药师补充建议书 03:18 落盘，比我的诊断（03:13）晚 5 分钟。我收尾时没回头扫素材目录，老朱问"黄药师的建议你看了没"才补读。幸好裁定来得及补进诊断 §八和 spec，没造成编排缺陷。

**防错机制**：
- 诊断/spec 收尾前固定一步：`ls -lt` 输入目录，凡 mtime 晚于诊断落盘的文件必须纳入裁定
- 此条追加为长素材协议的第四道防线（原三道：提取清单/定点复核/欧阳锋终审）

### 3. 看板状态列滞后于队列真实状态

泳道 1 状态列仍写 #150/#151「生产中」，实际早已 reviewed（队列显示已完成 152）。直到老朱问"能领 #156 吗"核对队列时才修正。状态列和下一步列不同步，看板会误导领取决策。

**防错机制**：
- dashboard 数字是队列唯一真相源；每次重跑 dashboard 后核对泳道状态列
- 看板更新=状态列+下一步列成对更新，不允许只改一列

### 4. 跨角色资产的 assignee 边界没在第一版 spec 写死

#158 spec 2.5 初版只说黄药师预写件"如何处置"，没说"谁修、何时修、走什么门禁"。老朱追问"黄药师直接修对吧"时才补全（黄药师修自己的 draft/正文卡归老顽童/诊断书只读）。

**防错机制**：
- spec 中凡涉及他人预写资产，当场写明四要素：assignee + 时机 + 修改范围 + 门禁路径
- 角色边界条款与处置条款同段出现，不分离
