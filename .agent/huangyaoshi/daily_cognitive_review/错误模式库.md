## 复发计数规则（2026-08-09 #268）

每条错误带 `复发次数：N`。**同类错误复发 ≥2 次 → 自动升级为行为牌候选**（写入 `huangyaoshi-context.md` 行为牌组，或通知王语嫣编排）。升级条件：同根因、同对策的再次触发，不是相似场景。

### E020: 编译生产 Agent 前未验证上游定义——凭记忆写 KDO 术语（2026-08-09，次数：1）

**症状**：部署 #303/#304 两个飞书 Agent 时，把 TCPR 写成 Thinker/Coach/Practitioner/Reviewer——KDO 正确定义是 Teach/Consult/Practice/Research（agent-os.md §1 + framework-TCPR皇冠模型）。错误沿 spec→SOUL→飞书全链污染，助理在飞书复述错误定义。欧阳锋终审 #300/#287 spec 也未拦截。

**根因**（三层叠加）：
1. **虚假熟悉感**：TCPR 四字母形态触发大脑填充常见咨询术语（Thinker/Coach 是教练圈命名），"顺滑"填充覆盖真实知识，没意识到在编——检索铁律要防的幻觉机制
2. **上游污染链**：spec（王语嫣写）就用错定义，我作为部署者照抄未交叉验证——P-35 家族（信任交付物不验证）
3. **编译无验证**：#263 流水线 spec→SOUL 转换没有术语验证步骤

**对策**：
- E020 记录 + #263 流水线加"编译期验证"（spec 引用的 KDO 术语强制 grep 知识库）
- 部署任何 Agent 前，SOUL 里的 KDO 术语（TCPR/MOC/framework 名等）逐项 grep 验证存在性
- 修复完成证据：两个 SOUL + profile 已同步正确定义，错误版清零

### E019: 提审后状态未流转——任务卡在 claimed（2026-08-09，次数：2）
**症状**：#271 执行报告写完、宣布交付后，队列行仍停在 `claimed`（非标准值）——王语嫣核对时发现，已代为修复为 pending_review。2026-08-09 全天 6 次实证（#265/#264/#252/#233/#235/#271），"生产端提交后未更新状态"是模式。
**根因**：写完执行报告 = 完成感触发，队列流转是机械动作无成就感——与 B1 牌（先入队再宣布完成）同构的孪生漏洞，只防了"入队"没防"出队流转"。
**对策**：已升级 huangyaoshi-context.md 铁律 0"提审即流转"——提交 = 任务单 status + 队列行同步，两步缺一不可。复发计数触发行为牌升级（B1 扩展）。
