# 知识挖掘飞轮的发现

> 今晚我们不小心开启了一个自迭代的知识体系。这篇文章记录它是怎么发生的、为什么有效、以及如何把它变成 KDO 的基础设施。

---

## 一、飞轮是怎么转起来的

```
用户说"老顽童的文章不够深刻"
    ↓
黄药师诊断：不是老顽童的问题，是三步编译法的结构性盲区
    ↓ 产出：四步编译法 + D1-D4 深度门禁 + 深度合成文章模板
    ↓
欧阳锋审查通过 → 黄药师执行基础设施 5 项改动
    ↓
老顽童用新产线重写 AI 数据文章
    ↓
黄药师读老顽童的文章 → 写了一篇从 Builder 视角的深度复盘
    ↓ 产出：四个死刑诊断 + ADUCIT 五层映射表 + 技术提案附录
    ↓
文章 Feedback 段留了三个更深的问题
    ↓
用户说"这三个问题值得你再深度思考推理一遍"
    ↓ 产出：U 建模三路径 / D↔U 共生关系 / Pilot 阶段插入方案
    ↓
用户说"跑 Pilot，拿数据回来继续转飞轮"
    ↓ 产出：20 张卡 320 chunk 的 9 维标签数据
    ↓
数据发现了 chunk_type bug + confidence 聚集问题
    ↓
修 bug → 重跑 → 新数据 → 下一轮分析 → ...
```

**六个循环，每一轮都产出了上一轮无法预见的深度。**

## 二、为什么这个飞轮有效

### 2.1 它不是"思考飞轮"，是"建造→使用→反思"三拍节奏

| 拍 | 动作 | 本轮示例 |
|:--:|------|------|
| **建造** | 建一个工具/框架/产线 | 四步编译法 + D1-D4 门禁 |
| **使用** | 用自己建的工具做真实的产出 | 黄药师写深度复盘文章 |
| **反思** | 在使用中发现问题 → 挖深一层 | Feedback 三个问题 → 新文章 |

**关键**：建造和反思之间必须插入"使用"。如果建了不用，飞轮转不起来——你没有真实的摩擦来暴露下一层问题。

### 2.2 它不是"单人飞轮"，是多角色接力

```
用户（决策者）：提出问题 → 判断深度 → 逼下一轮
欧阳锋（架构者）：审查方案 → 对齐标准 → 写工单
黄药师（建造者）：诊断→建工具→自用→发现新问题
老顽童（生产者）：用新工具产出 → 触发建造者的反思
```

**每个人的产出是下一个人的输入。** 用户的一声"不够深刻"触发了链条，但链条能转六圈是因为每个角色都在自己的位置上推了一把。

### 2.3 它不是"计划好的"，是"被反馈驱动的"

这六个循环里没有一个是在 Sprint 计划里的。它们是被**质量反馈**驱动的：

- "不够深刻" → 诊断根因
- "你报的 88.3% 和我测的 79.3% 不一致" → 双轨标准
- "这三个问题值得你再深度思考" → 新文章
- "跑 Pilot 拿数据" → 发现 chunk_type bug

**计划告诉你做什么，反馈告诉你做错了什么、还漏了什么。**

## 三、如何把这个飞轮变成 KDO 基础设施

### 3.1 飞轮需要三个条件才能持续转动

| 条件 | 当前状态 | 差距 |
|------|:--:|------|
| **质量反馈通道**：产出后有人告诉你哪里不够好 | ✅ 用户+欧阳锋双审查 | — |
| **建造→使用→反思节奏**：建完必须自己用 | ⚠️ 依赖个人习惯 | 没有流程强制 |
| **快速实验能力**：发现问题→跑实验→拿数据 | 🔨 Pilot 刚跑通 | 需要泛化为 `kdo pilot` |

### 3.2 建议：把飞轮固化到 KDO 的 Feedback 回路里

当前 KDO 的 feedback 回路是断裂的（死刑三）。飞轮提供了修复它的具体路径：

```
kdo produce（产出文章/卡片）
    ↓
kdo validate --article（质量门 + D1-D4）
    ↓
kdo ship（发布）
    ↓
kdo feedback --auto-enrich（收集反馈 → 触发重新加工）★ Sprint 6 断裂点 3
    ↓
kdo label --card（重新标注）★ Sprint 6 断裂点 1
    ↓
回到 produce（用更新后的卡产出更好的文章）
```

**这个回路修好后，飞轮就从"人的习惯"变成了"系统的机制"。**

### 3.3 飞轮的停止条件

飞轮不会永远转。停止信号：

1. **下一轮需要实验数据而不是纯推理** → 转实验模式（如 Pilot）
2. **连续两轮产出的新问题全部是"已知的未解决问题"** → 进入稳态
3. **ROI 递减** → 下一轮的深度增量 < 投入时间

## 四、方法论总结：知识挖掘飞轮操作手册

### 触发条件

- 有人对产出说"不够好"或"不够深"
- 不是直接修改产出，而是问"为什么不够好？"

### 操作步骤

```
1. 诊断（不是修复）：这个"不够好"是执行问题还是系统问题？
   - 执行问题 → 直接修复
   - 系统问题 → 进入飞轮

2. 建造：建一个工具/框架/门禁来解决系统根因

3. 使用：自己先用这个工具做一次真实产出
   - 关键——不跳过这步。建造者和使用者必须是一个人。

4. 反思：在这次使用中发现了什么新问题？
   - 写在 Feedback 段
   - 挑最深层的问题进入下一轮

5. 实验：当推理碰壁时，跑实验拿数据
   - Pilot、A/B、Gold Standard 比对

6. 循环：回到步骤 2，用新发现驱动下一轮建造
```

### 红线

- **不能跳过"使用"**：建了不用 = 飞轮空转
- **不能跳过"反思"**：发现问题不挖 = 飞轮卡住
- **不能一个人转**：需要用户/架构者/建造者/生产者的反馈接力
