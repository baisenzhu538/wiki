不同的项目设定不同的负责Agent？这个就是我在协作平台上项目空间板块的思路来源了。 

再插一句：使用AI确实是很费注意力和判断力的，AI有时候确实会出现夸大（AI老师是这个风格） 

前后矛盾逻辑有问题的，我们需要有自己的判断力，即使我们不懂这个事情。 

我们也能从产品使用者的视角找出漏洞，或者要求AI按照我们尽可能详细的模版来提供信息 

这是我的龙虾版飞书现在可实现的功能：

提炼建模专家算是目前最难建的Agent。

【互动🙋🏻‍♀️】大家觉得提炼和建模的最佳实践在哪里？ 

没错，就是在一堂的《知识萃取系列》和《高阶建模》系列的课程~ 

所以我把这两个系列课程给到建模专家，让建模专家自己建立一套提炼规则和流程： 

好用是好用，但是建模专家总是不按照已经定好的规则和流程来提炼，每次都要提醒。 

这时候我又遇到了一个很典型的问题：如果每次都靠我提醒 AI 遵守规则，那这个规则其实没有真正变成系统能力。 

那怎么办？ 

大家记得我上面有出现过dify不，dify就是类似coze一样的可以用视觉化的方式构建工作流 

区别在于dify可以做本地化部署。 

我当时就想是不是可以让建模专家在dify上构建工作流，让它每次的执行都按照我们的要求来做呢？ 

于是我就让建模专家在dify上构建工作流，因为dify本身的限制无法实现我们想要的工作流。 

结果最意外的地方出现：提炼专家自己创建了一个平台！ 

它们可以在里面使用代码、脚本等形式制作出工作流，后来我才知道这个东西叫做MCP。 

MCP 的全称是模型上下文协议（Model Context Protocol），简单来说，它就是 AI 世界里的“万能插头”或“USB 标准接口”。它的核心作用是让各种大语言模型能够安全、便捷地连接并调用外部的数据库、API 和工具，打破了过去 AI 系统之间封闭的“数据孤岛”。 

自从它们做出来这个东西，我已经陆陆续续将他们的标准任务迁移到MCP。 

- •
OpenClaw本身有一个类似服务器的东西叫做gateway 
- •
这个gateway的内存容量是有限的，同时运行太多东西就会卡死。 
- •
但是gateway是负责API调用、上下文加载、会话处理等工作 
- •
一般超过1GB就会出现堵塞情况，严重的话会把整个OpenClaw卡死 
- •
如果需要做复杂的任务gateway基本都会卡死的，比如建模专家去做一堂课程的提炼和复刻 
- •
快的话十几分钟，长的话三四十分钟都会有的，如果在gateway上跑 
- •
gateway就会直接卡死、任务也进行不下去。 
所以我后续就会把能剥离到MCP的功能都放到MCP，让gateway真的就充当一个服务器就行了。 

这样A2A功能也不用再看gateway的脸色了。 

这个MCP功能我正在尝试做成我可以访问的链接，加入到“龙虾版飞书”的工具列表中。 

#### 十指讲香 

现在我单独立项了一个十指讲香的优化项目，里面会包含问诊和优化功能： 

- •
问诊环节主要看看内容素材是否足够，不足够的话会提醒补充对应场景素材，最多5轮 
- •
优化后会显示优化前后的对比 
- •
在优化后LLM会对优化后的内容再做一次评分和提供建议，这样就可以结合AI提供的优化和评判建议，再来做我们内容的优化。

- •

评判AI内容是我可以避免被AI忽悠、产出好结果的能力了。

#### 5. AI 人效：让 Agent 尽可能复用 

不知道大家有没有听说过管理半径和人效，一个管理能力比较强的管理者可以管理5-10个人。

### 收尾：不是所有问题都值得训练一个 Agent 

讲到这里，我想用几个小 Tips 收一下尾。 

【Tips🔧】很多人以为AI能创造新事物，其实它真正擅长的是降低现有工作的门槛和成本。 

AI擅长的不是造“飞船“，而是把做“工具”、做“应用”这类成熟事情的门槛和成本降下来，大家看我现在在做的事情也有体感 

【Tips🔧】AI确实能给你一种"能力变强、效率起飞"的错觉，但问题是——你是在用对的方法解决问题吗？这一步，得你自己把关。 

就好像我在部署ComfyUI的环节，我不需要自己去学习模型、节点怎么搭配使用做出工作流。 

但是我太心急了，对ComfyUI本地部署这个事情都还没做好充分调研和建立审美。 

导致我们在不必要的地方耗费了很多时间和精力。所以AI确实会给到一种能提高“能力”、提高“效率”的错觉 

但是是不是在合适的方法来解决问题呢，这个是需要我们把关的。 

【Tips🔧】不是所有事情都值得像我这样去做训练Agent，去做本地部署。 

一次性、成熟的、有解决方案的可以直接问豆包，比如只是想要问一个excel公式怎么做。 

查一下文档有没有错别字，豆包都很方便的，还是免费的。复杂的、长期有价值的问题，我才建议使用Agent的。 

根上就是：根据问题复杂度去选择对应的Feature和工具。

AI并不是特别高大上很高深的事情，我们可以带着实际想要解决的问题去使用AI，只要时间和耐心，一周、二周、一个月总能够用AI解决我们的问题。

## 8. 技术配置

### 8.1 上下文管理

| 参数 | 推荐值 | 原因 |
|------|--------|------|
| `compaction.keepRecentTokens` | `8000` | 压缩保留最近 tokens 数 |
| `compaction.notifyUser` | `true` | 压缩时通知用户 |
| `compaction.memoryFlush.enabled` | `true` | 压缩前保存重要信息到 memory |
| `contextPruning.mode` | `cache-ttl` | 工具输出自动裁剪 |
| `contextPruning.ttl` | `5m` | 每 5 分钟清理一次 |
| `exec.timeoutSec` | `{按任务需要调整，例 120 / 300}` | 命令执行超时 |

> **Dashboard 分析**（基于 2026-06-13 架构文档 + 实际使用）：
> - 项目空间使用 **sub session** 隔离，每个项目独立上下文，**不污染 main session**
> - Sub session 的能力和 main session **完全一致**（工具、记忆、上下文传参都一样）
> - Compaction 行为 per-session，不影响其他项目
> - 当前参数（8000 tokens / 5min pruning）在 Dashboard 下**暂时不需要改**——工具的调用频率和复杂度并没因为 UI 变化而改变
> - **需要关注的**：如果 Dashboard 项目空间的消息频率显著高于 WebChat（比如持续几个小时高强度迭代），pruning ttl 可以考虑降到 3m

### 8.2 记忆系统

| 配置 | 推荐值 | 原因 |
|------|--------|------|
| `memorySearch.provider` | `ollama` | 本地轻量化 |
| `memorySearch.model` | `bge-m3` | 多语种中文+英文最佳 |
| 嵌入模型验证 | SQLite > 1MB, Embeddings: available | 确保索引可用 |
| 索引重建 | cron 每天 5:00 | 避免索引过期 |

> **Dashboard 分析**（基于 2026-06-13 架构文档 + 实际使用）：
> - Dashboard 项目空间的记忆检索行为 **和 DM 完全一致**——用同一套 memorySearch 配置，都走 SQLite + embedding
> - 索引是 per-agent 的，不是 per-session，所以项目空间的对话也会沉淀到 Agent 的全局 memory 中
> - 当前配置 **不需要改**
> - **值得关注的点**：每天 5:00 的索引重建 cron 是否覆盖了所有 Agent？如果新建 Agent 但没配 cron，记忆索引会过期

### 8.3 Session 管理

| 配置 | 推荐值 | 原因 |
|------|--------|------|
| `session.maintenance.mode` | `enforce` | 自动清理旧 Session |
| `session.maintenance.pruneAfter` | `30d` | 项目周期通常跨周，14d 可能过早清理 |
| `session.maintenance.maxEntries` | `500` | 每个项目独立 session + DM + A2A，200 可能不够 |

> **Dashboard 分析**（基于 2026-06-13 架构文档 + 实际使用）：
> - Dashboard 下的 session 模型已经明确：**每个项目一个独立 sub session** + **DM session** + **A2A session**
> - 和之前 WebChat 只有 DM + A2A 的场景比，session 数量多了**一个数量级**
> - Session 管理的变化：
>
> | 维度 | WebChat 时代 | Dashboard 时代（当前） |
> |------|-------------|---------------------|
> | session 类型 | DM + A2A | DM + A2A + **项目 session × N** |
> | 隔离方式 | 命名 session（手动） | Dashboard 项目空间自带隔离 |
> | 保留策略 | 14d 全局统一 | **建议调为 30d**（项目跨周运行） |
> | 最大条目 | 200 | **建议调为 500**（项目越多 session 越多） |
> | 碎片清理 | 自动 | 需要关注：项目结束后 session 自然过期，不需手动清理 |
>
> **已基于以上分析确认采用 30d / 500**（2026-06-13 kinda 决策）

### 8.4 权限方案（基于白皮书职责）

| 维度 | 设计 | 依据 |
|------|------|------|
| **exec 命令** | `{允许执行哪些命令}` | {职责依据} |
| **文件系统** | `{workspaceOnly: true / false}` | {读写范围} |

**审批水位三层模型：**

| 层级 | 操作类型 | 示例 |
|------|---------|------|
| 🔵 **自动跑** | 低风险、频繁使用 | read、web_search、memory 操作 |

### 8.5 子 Agent 策略（如果适用）

| 需要多 Agent 协作 | 查 `company/registry.yaml` 自行对接，**不经过 kin 中转** |

**Sub-Agent 规则**:

- 每次 spawn 是独立 session，做完即销毁

### B. 配置文件修改流程

`openclaw.json` 的修改遵循以下分工和生效规则：

**分工**

1. 🦞 **大虾出方案** — 明确要改哪个字段、改成什么值、为什么改
2. 💻 **Mat 动手改** — 由 Mat 直接编辑 openclaw.json，因为大虾有多次写坏记录
3. 🦞 **大虾验证** — 检查修改后的文件没有 JSON 语法错误，功能符合预期

**生效规则**

| 改动类型 | 是否需要重启 Gateway | 说明 |
|---------|---------------------|------|
| `agents.list` / `bindings` | ❌ 不需要 | Dashboard 热加载 |
| `session.maintenance` | ✅ **必须重启** | `pruneAfter` / `maxEntries` 等 |
| `models.providers`（新增模型源） | ✅ **必须重启** | — |
| `agents.defaults.*`（如 imageModel） | ⚠️ 待验证 | 先试 `config.apply`，不行再重启 |
| 文件级（AGENTS.md / SOUL.md / TOOLS.md） | ❌ 不需要 | 直接写入，即时读取 |
| `company/registry.yaml` | ❌ 不需要 | 文件级，即时读取 |
| Cron 任务（`cron add/update`） | ❌ 不需要 | API 级，即时生效 |

**安全规则**

## 8. 技术配置 
 
### 8.1 上下文管理 
 
| 参数 | 推荐值 | 原因 | 
|------|--------|------| 
| `compaction.keepRecentTokens` | `8000` | 压缩保留最近 tokens 数 | 
| `compaction.notifyUser` | `true` | 压缩时通知用户 | 
| `compaction.memoryFlush.enabled` | `true` | 压缩前保存重要信息到 memory | 
| `contextPruning.mode` | `cache-ttl` | 工具输出自动裁剪 | 
| `contextPruning.ttl` | `5m` | 每 5 分钟清理一次 | 
| `exec.timeoutSec` | `{按任务需要调整，例 120 / 300}` | 命令执行超时 | 
 
> **Dashboard 分析**（基于 2026-06-13 架构文档 + 实际使用）： 
> - 项目空间使用 **sub session** 隔离，每个项目独立上下文，**不污染 main session** 
> - Sub session 的能力和 main session **完全一致**（工具、记忆、上下文传参都一样） 
> - Compaction 行为 per-session，不影响其他项目 
> - 当前参数（8000 tokens / 5min pruning）在 Dashboard 下**暂时不需要改**——工具的调用频率和复杂度并没因为 UI 变化而改变 
> - **需要关注的**：如果 Dashboard 项目空间的消息频率显著高于 WebChat（比如持续几个小时高强度迭代），pruning ttl 可以考虑降到 3m 
 
### 8.2 记忆系统 
 
| 配置 | 推荐值 | 原因 | 
|------|--------|------| 
| `memorySearch.provider` | `ollama` | 本地轻量化 | 
| `memorySearch.model` | `bge-m3` | 多语种中文+英文最佳 | 
| 嵌入模型验证 | SQLite > 1MB, Embeddings: available | 确保索引可用 | 
| 索引重建 | cron 每天 5:00 | 避免索引过期 | 
 
> **Dashboard 分析**（基于 2026-06-13 架构文档 + 实际使用）： 
> - Dashboard 项目空间的记忆检索行为 **和 DM 完全一致**——用同一套 memorySearch 配置，都走 SQLite + embedding 
> - 索引是 per-agent 的，不是 per-session，所以项目空间的对话也会沉淀到 Agent 的全局 memory 中 
> - 当前配置 **不需要改** 
> - **值得关注的点**：每天 5:00 的索引重建 cron 是否覆盖了所有 Agent？如果新建 Agent 但没配 cron，记忆索引会过期 
 
### 8.3 Session 管理 
 
| 配置 | 推荐值 | 原因 | 
|------|--------|------| 
| `session.maintenance.mode` | `enforce` | 自动清理旧 Session | 
| `session.maintenance.pruneAfter` | `30d` | 项目周期通常跨周，14d 可能过早清理 | 
| `session.maintenance.maxEntries` | `500` | 每个项目独立 session + DM + A2A，200 可能不够 | 
 
> **Dashboard 分析**（基于 2026-06-13 架构文档 + 实际使用）： 
> - Dashboard 下的 session 模型已经明确：**每个项目一个独立 sub session** + **DM session** + **A2A session** 
> - 和之前 WebChat 只有 DM + A2A 的场景比，session 数量多了**一个数量级** 
> - Session 管理的变化： 
> 
> | 维度 | WebChat 时代 | Dashboard 时代（当前） | 
> |------|-------------|---------------------| 
> | session 类型 | DM + A2A | DM + A2A + **项目 session × N** | 
> | 隔离方式 | 命名 session（手动） | Dashboard 项目空间自带隔离 | 
> | 保留策略 | 14d 全局统一 | **建议调为 30d**（项目跨周运行） | 
> | 最大条目 | 200 | **建议调为 500**（项目越多 session 越多） | 
> | 碎片清理 | 自动 | 需要关注：项目结束后 session 自然过期，不需手动清理 | 
> 
> **已基于以上分析确认采用 30d / 500**（2026-06-13 kinda 决策）

## 8. 技术配置

### 8.1 上下文管理

| 参数 | 推荐值 | 原因 |
|------|--------|------|
| `compaction.keepRecentTokens` | `8000` | 压缩保留最近 tokens 数 |
| `compaction.notifyUser` | `true` | 压缩时通知用户 |
| `compaction.memoryFlush.enabled` | `true` | 压缩前保存重要信息到 memory |
| `contextPruning.mode` | `cache-ttl` | 工具输出自动裁剪 |
| `contextPruning.ttl` | `5m` | 每 5 分钟清理一次 |
| `exec.timeoutSec` | `{按任务需要调整，例 120 / 300}` | 命令执行超时 |

> **Dashboard 分析**（基于 2026-06-13 架构文档 + 实际使用）：
> - 项目空间使用 **sub session** 隔离，每个项目独立上下文，**不污染 main session**
> - Sub session 的能力和 main session **完全一致**（工具、记忆、上下文传参都一样）
> - Compaction 行为 per-session，不影响其他项目
> - 当前参数（8000 tokens / 5min pruning）在 Dashboard 下**暂时不需要改**——工具的调用频率和复杂度并没因为 UI 变化而改变
> - **需要关注的**：如果 Dashboard 项目空间的消息频率显著高于 WebChat（比如持续几个小时高强度迭代），pruning ttl 可以考虑降到 3m

### 8.2 记忆系统

| 配置 | 推荐值 | 原因 |
|------|--------|------|
| `memorySearch.provider` | `ollama` | 本地轻量化 |
| `memorySearch.model` | `bge-m3` | 多语种中文+英文最佳 |
| 嵌入模型验证 | SQLite > 1MB, Embeddings: available | 确保索引可用 |
| 索引重建 | cron 每天 5:00 | 避免索引过期 |

> **Dashboard 分析**（基于 2026-06-13 架构文档 + 实际使用）：
> - Dashboard 项目空间的记忆检索行为 **和 DM 完全一致**——用同一套 memorySearch 配置，都走 SQLite + embedding
> - 索引是 per-agent 的，不是 per-session，所以项目空间的对话也会沉淀到 Agent 的全局 memory 中
> - 当前配置 **不需要改**
> - **值得关注的点**：每天 5:00 的索引重建 cron 是否覆盖了所有 Agent？如果新建 Agent 但没配 cron，记忆索引会过期

### 8.3 Session 管理

| 配置 | 推荐值 | 原因 |
|------|--------|------|
| `session.maintenance.mode` | `enforce` | 自动清理旧 Session |
| `session.maintenance.pruneAfter` | `30d` | 项目周期通常跨周，14d 可能过早清理 |
| `session.maintenance.maxEntries` | `500` | 每个项目独立 session + DM + A2A，200 可能不够 |

> **Dashboard 分析**（基于 2026-06-13 架构文档 + 实际使用）：
> - Dashboard 下的 session 模型已经明确：**每个项目一个独立 sub session** + **DM session** + **A2A session**
> - 和之前 WebChat 只有 DM + A2A 的场景比，session 数量多了**一个数量级**
> - Session 管理的变化：
>
> | 维度 | WebChat 时代 | Dashboard 时代（当前） |
> |------|-------------|---------------------|
> | session 类型 | DM + A2A | DM + A2A + **项目 session × N** |
> | 隔离方式 | 命名 session（手动） | Dashboard 项目空间自带隔离 |
> | 保留策略 | 14d 全局统一 | **建议调为 30d**（项目跨周运行） |
> | 最大条目 | 200 | **建议调为 500**（项目越多 session 越多） |
> | 碎片清理 | 自动 | 需要关注：项目结束后 session 自然过期，不需手动清理 |
>
> **已基于以上分析确认采用 30d / 500**（2026-06-13 kinda 决策）

## 8. 技术配置 
 
### 8.1 上下文管理 
 
| 参数 | 推荐值 | 原因 | 
|------|--------|------| 
| `compaction.keepRecentTokens` | `8000` | 压缩保留最近 tokens 数 | 
| `compaction.notifyUser` | `true` | 压缩时通知用户 | 
| `compaction.memoryFlush.enabled` | `true` | 压缩前保存重要信息到 memory | 
| `contextPruning.mode` | `cache-ttl` | 工具输出自动裁剪 | 
| `contextPruning.ttl` | `5m` | 每 5 分钟清理一次 | 
| `exec.timeoutSec` | `{按任务需要调整，例 120 / 300}` | 命令执行超时 | 
 
> **Dashboard 分析**（基于 2026-06-13 架构文档 + 实际使用）： 
> - 项目空间使用 **sub session** 隔离，每个项目独立上下文，**不污染 main session** 
> - Sub session 的能力和 main session **完全一致**（工具、记忆、上下文传参都一样） 
> - Compaction 行为 per-session，不影响其他项目 
> - 当前参数（8000 tokens / 5min pruning）在 Dashboard 下**暂时不需要改**——工具的调用频率和复杂度并没因为 UI 变化而改变 
> - **需要关注的**：如果 Dashboard 项目空间的消息频率显著高于 WebChat（比如持续几个小时高强度迭代），pruning ttl 可以考虑降到 3m 
 
### 8.2 记忆系统 
 
| 配置 | 推荐值 | 原因 | 
|------|--------|------| 
| `memorySearch.provider` | `ollama` | 本地轻量化 | 
| `memorySearch.model` | `bge-m3` | 多语种中文+英文最佳 | 
| 嵌入模型验证 | SQLite > 1MB, Embeddings: available | 确保索引可用 | 
| 索引重建 | cron 每天 5:00 | 避免索引过期 | 
 
> **Dashboard 分析**（基于 2026-06-13 架构文档 + 实际使用）： 
> - Dashboard 项目空间的记忆检索行为 **和 DM 完全一致**——用同一套 memorySearch 配置，都走 SQLite + embedding 
> - 索引是 per-agent 的，不是 per-session，所以项目空间的对话也会沉淀到 Agent 的全局 memory 中 
> - 当前配置 **不需要改** 
> - **值得关注的点**：每天 5:00 的索引重建 cron 是否覆盖了所有 Agent？如果新建 Agent 但没配 cron，记忆索引会过期 
 
### 8.3 Session 管理 
 
| 配置 | 推荐值 | 原因 | 
|------|--------|------| 
| `session.maintenance.mode` | `enforce` | 自动清理旧 Session | 
| `session.maintenance.pruneAfter` | `30d` | 项目周期通常跨周，14d 可能过早清理 | 
| `session.maintenance.maxEntries` | `500` | 每个项目独立 session + DM + A2A，200 可能不够 | 
 
> **Dashboard 分析**（基于 2026-06-13 架构文档 + 实际使用）： 
> - Dashboard 下的 session 模型已经明确：**每个项目一个独立 sub session** + **DM session** + **A2A session** 
> - 和之前 WebChat 只有 DM + A2A 的场景比，session 数量多了**一个数量级** 
> - Session 管理的变化： 
> 
> | 维度 | WebChat 时代 | Dashboard 时代（当前） | 
> |------|-------------|---------------------| 
> | session 类型 | DM + A2A | DM + A2A + **项目 session × N** | 
> | 隔离方式 | 命名 session（手动） | Dashboard 项目空间自带隔离 | 
> | 保留策略 | 14d 全局统一 | **建议调为 30d**（项目跨周运行） | 
> | 最大条目 | 200 | **建议调为 500**（项目越多 session 越多） | 
> | 碎片清理 | 自动 | 需要关注：项目结束后 session 自然过期，不需手动清理 | 
> 
> **已基于以上分析确认采用 30d / 500**（2026-06-13 kinda 决策） 
 
### 8.4 权限方案（基于白皮书职责） 
 
| 维度 | 设计 | 依据 | 
|------|------|------| 
| **exec 命令** | `{允许执行哪些命令}` | {职责依据} |

**审批水位三层模型：**

### 8.5 子 Agent 策略（如果适用） 
 
| 场景 | 做法 | 
|------|------| 
| 短期简单任务 | Agent 自己处理 | 
| 需要多 Agent 协作 | 查 `company/registry.yaml` 自行对接，**不经过 kin 中转** | 
| 需要一个专门助手 | 生成 Sub-Agent（一次性，做完销毁） |

**Sub-Agent 规则**: 
- 基于已有 Agent 能力的镜像，不做全新角色 
- 每次 spawn 是独立 session，做完即销毁

#### 9.4.2 流水线谁来做

**kinda 的角色：** 定标准 + 验收定稿 
**Agent 的角色：** 出草稿（写成 R1-R5 格式） 
 
#### 9.4.3 流水线的执行保障 
 
**短期保障（BOOT.md 强制预处理）：** 各 Agent 的 BOOT.md 已写入启动预处理流程——每次收到消息先走关键词提取→知识库预检→流水线匹配，匹配成功则按 R1-R5 执行。

### B. 配置文件修改流程

**分工** 
 
1. 🦞 **大虾出方案** — 明确要改哪个字段、改成什么值、为什么改

**生效规则** 
 
| 改动类型 | 是否需要重启 Gateway | 说明 | 
|---------|---------------------|------| 
| `agents.list` / `bindings` | ❌ 不需要 | Dashboard 热加载 | 
| `session.maintenance` | ✅ **必须重启** | `pruneAfter` / `maxEntries` 等 | 
| `models.providers`（新增模型源） | ✅ **必须重启** | — |

| `company/registry.yaml` | ❌ 不需要 | 文件级，即时读取 | 
| Cron 任务（`cron add/update`） | ❌ 不需要 | API 级，即时生效 | 
 
**安全规则** 
 
- 改 JSON 前先备份：`cp ~/.openclaw/openclaw.json ~/.openclaw/openclaw.json.bak` 
- 改完后验证：`node -e "JSON.parse(fs.readFileSync('$env:USERPROFILE/.openclaw/openclaw.json'))"` 
- 大虾不得直接编辑 openclaw.json（历史记录：写坏 4-5 次）
