## 一、今天最大的认知升级

### 1. 元数据缺失是比内容缺陷更隐蔽的系统性风险

今天扫描 30_wiki 全库时，发现 1,216/1,320 张卡片没有 `author`，972 张没有 `trust_level`，978 张没有 `reviewed_by`。这比 "内容写得不好" 更危险——**没有作者就无法追责，没有 reviewer 就不知道谁确认过，没有 trust_level 就无法做分层审查。** 在治理内容之前，必须先让元数据可被信任。

### 2. 自动化治理 + 人工抽样审查是处理 1320 张卡片的唯一可行路径

今天手动修复了 20 个 YAML 中文引号错误、废弃了 2 个空文件、补全了 1,228 张卡片的 `id/author/reviewed_by/created_at`。如果靠人工逐张检查，一个阶段就要几天。写脚本批量治理 + Agent 抽样验证，可以把一周工作量压到半天，同时保证每阶段都有可审计结果。

### 3. "高置信低信任" 是一个此前未被显式标记的高危类别

抽样审查 30 张 `confidence ≥ 0.85` 但 `trust_level` 为空/偏低的卡片，发现 40% 存在 confidence 虚高问题。典型模式：draft 未审稿却标 0.85、课件截图无法验证、source 引用只有作者名或口头来源。这类卡片最容易误导用户，应该优先治理。

## 二、今天犯的错 / 可以更好的地方

### 1. 派 Agent 前对文件清单记忆错误，导致第一次派工方向偏了

最初启动阶段 2 时，我把"王语嫣第二批卡"误记为"老顽童 review 的卡"，派出去的 Agent 审查对象错误。虽然及时发现并 stop，但浪费了约 10 分钟和一个 Agent 资源。

**防错机制**：派 Agent 前，先用脚本或 `Glob` 重新确认样本集合，不要凭对话记忆中的文件名直接派工。

### 2. Bash `grep -P` 在 Windows Git Bash 下因 locale 问题失败

扫描 YAML 引号问题时，第一反应是用 `grep -P` 正则匹配中文引号，结果报 "PCRE 不支持 locale" 类错误。后来改用 Python 脚本才跑通。

**防错机制**：Windows 环境下文本/编码相关扫描统一用 Python，不再用 Bash 做复杂正则。

### 3. 阶段 1 批量修改 1,228 个文件前没有显式创建恢复快照

虽然 git 工作区干净、且项目有自动备份机制，但这次修改量太大（全库 93% 文件），理应在执行前手动打一个 git tag 或副本快照。这次侥幸没出错，但不能依赖侥幸。

**防错机制**：任何影响超过 50 个文件的操作前，先执行 `git tag pre-<阶段名>-<日期>` 或复制目标目录到 `60_feedback/audit/snapshots/`。

## 三、明天可以尝试的新方法

### 1. 阶段 2 结果出来后，先用脚本批量处理"无争议"问题，再人工复核边界案例

Agent 抽样已给出明确的批量处理规则（draft+pending review 的 confidence 上限 0.75、PNG-only source 下调、空 source 下调等）。明天可以直接脚本化执行这些规则，再对机器无法判断的案例单独审查。

### 2. 建立"阶段出口报告"机制

每个阶段结束后生成一份独立 Markdown 报告（如 `kcard-stage2-report-YYYYMMDD.md`），记录：本阶段目标、抽样结论、批量操作、剩余风险、下阶段建议。这样用户随时叫停都能看到完整上下文。

### 3. 对老顽童的卡片采用"Domain 专项审查"而非抽样

老顽童的非药柜专项域审计显示：业务公式、AI 短剧、建模能力三个域流于形式、案例库缺失。这类问题抽样会漏掉系统性缺陷，应该按 domain 逐块审查，而不是按卡片随机抽样。
