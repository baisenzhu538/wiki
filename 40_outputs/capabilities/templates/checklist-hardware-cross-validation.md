# 硬件项目交叉验证检查单

> 使用方式：拿到一个硬件项目的全套文件后，逐项核对。不只对比"哪里不一样"——要判断"哪个是对的、为什么、物理后果是什么"。

## L1：文件完整性（10分钟）

- [ ] 每块板卡有 BOM / Gerber / 坐标 / 原理图 / 固件 五个目录
- [ ] 每个文件命名含版本号+日期（E-FM-002 防呆）
- [ ] README.md 含关键文件版本对照表

## L2：跨文档一致性（30分钟/板）

- [ ] 原理图上的元件位号 → BOM 中存在对应行
- [ ] BOM 中的元件型号 → 原理图上标注一致
- [ ] BOM 中的封装 → PCB Gerber 实际占用空间匹配
- [ ] 固件 pin define → 原理图引脚号一致

## L3：根因推断（不一致时必做，不跳过）

发现不一致后，回答三个问题：

- [ ] **物理后果**：这个不一致会导致什么？信号问题？电源问题？功能缺失？不工作还是概率性故障？
- [ ] **对已有知识库的引用**：这个不一致是否匹配已知失败模式？查 `dk-ef-*` 卡对照
- [ ] **验证方法**：怎么确认哪个是对的？示波器？读芯片 ID？换一块板子对比？

## L4：问题分级

| 级别 | 标准 | 处理 |
|:---|:---|:---|
| 🔴 高 | 不一致会导致功能性故障或安全隐患 | 必须修正后再生产 |
| 🟡 中 | 不一致影响可维护性但不影响当前功能 | 建议修正 |
| 🟢 低 | 命名不统一、注释缺失等 | 可选修正 |

- [ ] 每个不一致都有分级 + 分级理由

## L5：dk 卡对照（KDO 知识复用）

- [ ] 查 `kdo case list --query "硬件"` → 看广冷案例
- [ ] 每个不一致对照 dk-ef-001~004 判断是否已知模式复现
- [ ] 新发现的模式 → 记录为新的 dk-ef 候选

---

## 自检通过标准

L1-L4 全部 ✅ → 项目文件进入基线。任何 L3 回答不完整 → 不进入基线。
