# 深度调试技能 (Deep Debug)

## 核心理念

**你观察系统的次数越多，修改系统的次数就越少。**

本技能强制使用科学的调试方法：

```
❌ 直觉驱动：问题 → 快速猜测 → 修改代码 → 希望
✅ 科学驱动：问题 → 提出假设 → 交叉验证 → 确认根因 → 最小化修复
```

## 何时激活

**始终使用本技能当：**
- 问题无法用明显原因解释
- 第一次修复尝试无效
- 问题是间歇性或非确定性的
- 多个症状表明相互关联的问题
- 问题涉及复杂数据流或并发
- 之前的修复引入了新问题

**不要用于：**
- 简单的拼写或语法错误
- 有已知解决方案的文档化问题
- 明显的配置问题

## 为什么直觉式调试会失败

### 认知偏差

| 偏差 | 影响 | 对策 |
|------|------|------|
| **首因效应** | 第一个合理假设占据全部注意力 | 判断前列出 5+ 个假设 |
| **确认偏差** | 只看到支持证据 | 主动寻找反驳证据 |
| **沉没成本** | 投入越多越难放弃 | 提前设定验证标准 |
| **修改偏见** | 把代码修改当作主要验证手段 | 先用日志、历史、静态分析 |
| **局部最优** | 治标不治本 | 连问 5 次"为什么" |

### 系统作为可观测的黑盒

```
输入 → [黑盒] → 输出
         ↓
    观测点：
    - 日志文件
    - 指标数据
    - 数据库状态
    - Git 历史
    - 堆栈追踪
```

**核心原则**：最大化观测，最小化干预。

## 六步验证法

```
① 定义问题 → ② 生成假设 → ③ 优先级排序
      ↑                              │
      │         ④ 交叉验证 ← ⑤ 确认根因
      │                   ↓
      └───────────────── ⑥ 最小化修复
```

---

## 第一步：定义问题

### 五 W 框架

| W | 问题 | 示例 |
|---|----------|---------|
| What | 什么现象？ | "API 返回 500" |
| When | 何时发生？ | "工作日上午 9-10 点" |
| Where | 在哪里发生？ | "生产环境 US-East" |
| Who | 谁受影响？ | "iOS 应用用户" |
| How | 如何触发？ | "空闲后点击刷新" |

### 量化问题

```
"很慢" → "响应时间 3.2s，预期 <100ms"
"经常崩溃" → "每小时崩溃 2-3 次"
"数据不对" → "字段 X 是 null，预期是字符串"
"有时失败" → "30% 失败率"
```

### 复现路径

```
最小复现步骤：
1. 清空缓存
2. 以用户 A 登录
3. 导航到页面 X
4. 点击按钮 Y
5. 观察错误 Z
```

---

## 第二步：生成假设

### 假设分类树

```
问题现象
    │
    ├─ 数据流（输入、传输、存储）
    ├─ 控制流（分支、循环、异常）
    ├─ 时序问题（异步顺序、竞态条件）
    ├─ 依赖问题（库版本、API 变更）
    ├─ 资源问题（内存、连接、磁盘）
    └─ 环境问题（OS、网络、配置）
```

### 生成技巧

#### 5 Why 分析法
```
症状：页面加载失败

Why 1? → API 超时
Why 2? → 数据库查询慢
Why 3? → 没有索引
Why 4? → 索引被删除
Why 5? → 迁移脚本有 bug
```

#### 逆向思考
"什么条件下问题不会发生？"

```
正常：开发环境 OK，生产失败 → 配置差异
正常：旧数据 OK，新数据失败 → 数据格式变化
正常：单用户 OK，多用户失败 → 并发问题
```

#### 模式匹配
"这像什么已知模式？"

```
重复数据 → 重复提交模式
间歇性失败 → 竞态条件模式
内存增长 → 资源泄漏模式
```

## 第三步：假设优先级排序

### 优先级矩阵

```
高影响 ┃  H1  ┃  H2  ┃
       ┃ 立即 ┃ 紧急 ┃
━━━━━━━━━━━━╋━━━━━━╋━━━━━━╋━━━━━━━━
低影响 ┃  H4  ┃  H3  ┃
       ┃ 计划 ┃ 暂缓 ┃
━━━━━━━━━━━━┻━━━━━━┻━━━━━━┻━━━━━━━━
       低可验证性      高可验证性
```

### 评估维度

| 维度 | 高优先级 | 低优先级 |
|------|----------|----------|
| 可验证性 | 可通过日志/历史验证 | 需要修改代码 |
| 解释力 | 解释所有现象 | 只能解释部分 |
| 修复成本 | 配置、单行修改 | 架构变更 |

## 第四步：交叉验证

### 核心原则

**单一证据可能误导。多个独立来源 = 高置信度。**

```
只有日志 → 可能日志本身有问题
只有代码 → 可能代码有误导性
日志 + 代码 + 历史 → 高置信度
```

### 验证方法

#### 1. 时间线分析
```bash
git log --since="date" --until="date" --oneline
git log -p -S "suspicious code" --all
git blame file
```

#### 2. 日志模式识别
```bash
grep "HH:MM:" /path/to/log
grep "ERROR" log | awk '{print $5}' | sort | uniq -c
```

| 模式 | 含义 | 原因 |
|------|------|------|
| A → B → B → C | 重复执行 | 循环/重复调用 |
| A → C → B | 乱序 | 并发 |
| A → B → D | 分支异常 | 条件错误 |

#### 3. 静态代码分析
- 绘制调用链：A → B → C
- 检查每个节点的输入/输出
- 查找重复、缺失检查

#### 4. 数据状态验证
```sql
-- 检查完整性
SELECT * FROM messages WHERE content IS NULL;

-- 检查一致性
SELECT m.* FROM messages m
LEFT JOIN conversations c ON m.conversation_id = c.id
WHERE c.id IS NULL;
```

### 交叉验证检查表

```
假设 H：[描述]

方法 1：日志分析
- [ ] 证据 1 ✓
- [ ] 证据 2 ✓
- [ ] 证据 3 ✗

方法 2：代码分析
- [ ] 找到调用点
- [ ] 验证路径

方法 3：Git 历史
- [ ] 变更时间与问题出现时间吻合
```

## 第五步：确认根因

### 根因层次

```
症状：API 超时
  ↓
直接原因：数据库查询慢
  ↓
根本原因：缺少索引
  ↓
深层原因：没有性能测试
```

| 修复层次 | 效果 |
|----------|------|
| 症状 | 问题被隐藏，可能复发 |
| 直接 | 问题解决 |
| 根本 | 同类问题不再出现 |

### 确认方法

#### 预测验证
"如果假设正确，还应该观察到什么？"

#### 对抗性证据
主动寻找能够**推翻**假设的证据。

#### 独立复现
在隔离环境中稳定复现。

---

## 第六步：最小化修复

### 决策树

```
问题范围
    ├─ 单个函数 → 局部修复
    ├─ 多个调用点 → 统一抽象
    ├─ 接口受影响 → 重构 + 适配
    └─ 架构受影响 → 渐进式重构
```

### 原则

| 原则 | 描述 |
|------|------|
| 精确匹配 | 修复范围 = 问题范围 |
| 可逆性 | 保留回滚方案 |
| 添加防护 | 添加日志/断言 |
| 测试覆盖 | 先写测试 |

### 验证检查表

```
代码层面
- [ ] 范围最小化
- [ ] 无新依赖
- [ ] 风格一致

测试层面
- [ ] 单元测试通过
- [ ] 集成测试通过
- [ ] 手动验证

影响层面
- [ ] 检查调用方
- [ ] 检查配置
- [ ] 检查文档
```

## 工具箱

### Git 命令
```bash
git log -p -S "string" --all           # 查找字符串变更
git log --since="date" --until="date"  # 按时间查找
git blame file                         # 逐行历史
git bisect start                       # 二分查找
```

### 日志分析
```bash
grep "pattern" log | tail -100
grep "HH:MM:" log
awk '{print $X}' log | sort | uniq -c  # 频率统计
```

### 进程调试
```bash
lsof -i :port                          # 端口占用
ps aux | grep name                     # 查找进程
strace -p PID                          # 系统调用追踪
```

## 常见陷阱

| 陷阱 | 对策 |
|------|------|
| 过早排除假设 | 先列出 5+ 个假设 |
| 单一证据下结论 | 用 2-3 种方法交叉验证 |
| 确认偏差 | 寻找反驳证据 |
| 治标不治本 | 连问 5 次"为什么" |
| 过度修复 | 修复范围匹配问题范围 |

|----|------------|------|--------|
| H1 | [描述] | [类型] | 待验证 |

| 假设 | 方法 1 | 方法 2 | 方法 3 | 结论 |
|-----------|----------|----------|----------|------------|

症状 → 直接原因 → 根本原因

## 与 KDO 体系的关联

- **假设驱动 ↔ 关键假设**：六步法的"生成假设→交叉验证"与 KDO 关键假设方法（拆解→验证→迭代）同构，本技能是其在系统工程域的特化
- **多源交叉验证 ↔ 六层交叉验证 skill**：调试域的"多个独立来源=高置信度"与调研域的六层交叉验证共享同一证据纪律
- **最小化修复 ↔ KDO 批量纪律**："修复范围=问题范围"与 KDO"改动范围声明+非空不覆盖"同构——都是防止修复本身成为新事故源

## 判断标准（何时算用对了本技能）

1. 修改任何代码之前，你能说出当前在验证哪个假设、用什么证据
2. 根因确认前有 ≥2 个独立证据来源支持
3. 修复后能回答"为什么这个修复不会引入新问题"
4. 调试报告能被另一个工程师独立复核

---

## 总结

**核心原则：**

1. **先观测后修改** - 修改前充分理解
2. **假设驱动** - 每个假设都有验证方法
3. **基于证据** - 多个独立来源
4. **根因修复** - 不是症状
5. **最小化修复** - 范围匹配问题

**记住**：你观察系统的次数越多，修改系统的次数就越少。
