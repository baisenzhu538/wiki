# 三层开发架构

基于王欢方法论。AI 时代的软件工程——不是"AI 替我写代码"，而是"我定义架构，AI 执行，我验收"。

## 三层架构

| 层 | 做什么 | 人的角色 | AI 的角色 |
|:--|:--|:--|:--|
| **L1: 需求拆解** | 把模糊需求变成精确的任务规格 | 架构师——定义要什么 | 辅助——帮拆解、帮补全 |
| **L2: AI 开发** | AI 按规格写代码 | 监督者——检查方向 | 执行者——写代码 |
| **L3: 哨兵质检** | 自动检查+人工验收 | 验收者——最终拍板 | 哨兵——自动检查 |

## L1: 需求拆解

### 输入 → 输出
- 输入：模糊需求（"我要一个能自动发周报的系统"）
- 输出：精确任务规格（功能列表 + 接口定义 + 数据格式 + 验收标准）

### 拆解原则
1. 每个任务必须可独立验证
2. 任务粒度：一个人+AI 在 2 小时内能完成
3. 任务之间依赖关系明确

## L2: AI 开发

### 工作流
```
任务规格 → AI 生成代码 → 人工review方向 → AI 修改 → 通过
```

### 关键原则
- 不要微管理 AI 的代码细节——管方向，不管实现
- 如果 AI 卡住超过 3 轮，拆成更小的子任务
- 每次只让 AI 做一件事

## L3: 哨兵质检

### 哨兵检查项
- [ ] 代码能跑通（自动化测试）
- [ ] 输入输出格式符合 L1 规格
- [ ] 边界情况处理（空输入/超大数据/格式错误）
- [ ] 安全扫描（SQL注入/XSS/密钥泄露）
- [ ] 性能基准（响应时间/内存占用）

### 哨兵配置
```yaml
哨兵:
  - 自动测试: pytest / jest
  - 格式检查: ruff / prettier
  - 安全检查: bandit / npm audit
  - AI哨兵: 用另一个AI检查主AI的产出
```

## 常见失败

| 症状 | 根因 | 修复 |
|:--|:--|:--|
| AI 写的代码跑不通 | L1 需求不精确 | 回 L1：加接口定义和验收标准 |
| 代码能跑但方向错了 | L2 没做人工 review | 每轮 AI 产出后先 review |
| 上线后出 bug | L3 哨兵覆盖不全 | 从 bug 反推补检查项 |
