# 我用 Graph RAG 检索了 424 张卡片，却发现它在最关键的场景里输给了向量 RAG

> **核心论点**：Graph RAG 不是"向量 RAG 的升级版"，而是"一套不同的检索范式"。它在跨概念关联检索上有明显优势，但在三个关键场景里——单点精确命中、无结构化长文本、高频实时检索——它的表现不如纯粹的向量检索。KDO 选择 LightRAG 是正确的工程判断，但选对了工具不等于用对了场景。

## 那个让我对着终端沉默的问题

我给 `kdo graph query` 下了一个问题：**"KDO 的 RAG 系统有什么结构性缺陷？"**

Graph RAG 返回了 226 个实体、1252 条关系、5 个相关 chunk。数据很丰富，但我看完这些返回后对着终端沉默了三分钟。因为这些实体和关系没有告诉我答案——它们告诉我的是"KDO 有一个 Graph RAG 系统"，而不是"这个系统有什么结构性缺陷"。

问题出在哪？不是 Graph RAG 检索得不够。是**这个问题本身不需要图关系**——它需要的是一个精确命中某个技术决策的 chunk，而不是在图上跳来跳去地漫游。

这就是我今天想说的核心发现：**Graph RAG 和向量 RAG 不是"高级与初级"的关系，是"长板与短板"的关系**。你的业务场景决定了哪一种范式更适合，而不是哪一种技术更"先进"。

## 旧认知 → 新认知：从"图更厉害"到"图和向量是两种工具"

在读到 [[graph-rag-retrieval-layer]] 的技术说明之前，我对 Graph RAG 的认知可以总结为一句话：**有图的比没图的好**。理由很充分：图能捕获实体关系，向量只能捕获语义相似。当你问"调研方法和 AI 辅助调研有什么关系"时，图可以沿着"调研方法 → 具体工具 → AI 应用场景"的路径跳跃，而向量只能找到"同时提到调研和 AI 的段落"。

但我在实际使用 KDO 的 Graph RAG 时发现了三个反例：

**反例一：单点精确命中**。当我问"HashingVectorizer 的缺陷是什么"时，我不需要图关系。我需要的是那张直接讨论 HashingVectorizer 的卡片，精确命中。向量 RAG 在这种场景下更快、更准。

**反例二：无结构化长文本**。KDO 的口述稿素材很多是长段连续文本，没有明确的实体可提。LightRAG 的实体提取在这种素材上会"生造"出一些不存在的实体，或者把一个段落切成多个碎片。向量 RAG 不需要实体，它直接对整段文本做嵌入，反而更稳。

**反例三：高频实时检索**。每次调用 Graph RAG 需要加载图索引、做图遍历、再做向量匹配。在我的本地测试中，这比单纯向量检索慢约 30-40%。如果你的 Agent 需要每次对话都检索知识库，这个延迟会累积。

**新认知**：Graph RAG 的真正优势不是"替代向量 RAG"，而是"补充向量 RAG 在跨实体关系检索上的短板"。如果你的检索需求是"找到提及 A 和 B 的所有内容"，向量 RAG 很强。如果你的需求是"找到 A 和 B 之间有什么关系——即使它们从未在同一段文本中出现过"，Graph RAG 才是正确选择。

## 用这个框架反照 KDO 自身

按照"向量 vs 图"的分层框架反照 KDO 自身，我发现了一个尴尬的结构性错配：**KDO 的数据在"向量友好度"和"图友好度"之间失衡了**。

[[graph-rag-retrieval-layer]] 的技术说明明确写着：KDO 的 Graph RAG 基于 LightRAG，采用"分块 + 实体提取 + 向量建库 + 图关系"的混合架构。这是一个很好的工程判断——它意味着 KDO 在某些查询上可以用向量，在某些查询上可以用图。

但 KDO 的实践表明：**KDO 的查询模式以"单点命中"为主**。当我用 `kdo query "调研方法"` 时，我不是在问"调研方法和什么其他概念有关系"——我是在问"告诉我什么是调研方法"。这是一个纯粹的单点命中需求，向量 RAG 已经能很好地满足。

更深的问题在于：**KDO 的 wikilink 结构虽然适合图，但它们并没有被有效利用**。黄药师在四个死刑文章中指出："relations=0（部分查询），wiki 中部分 wikilink 指向的页面不存在，图遍历跳数不足，召回偏低"。这意味着 KDO 花了工程资源建 Graph RAG，但图的核心优势——跨实体关系检索——在实际中并没有被充分发挥。

具体来说，KDO 的图友好度缺口是：

- **实体提取质量不稳定**：对于口述稿这类无结构化长文本，LightRAG 自动提取的实体和人工维护的 wikilink 不一致。有时候会"生造"出一个从未在 KDO 中出现过的概念。
- **图遍历跳数不足**：当前索引中部分实体之间的关系链是断裂的。你可以从"人机协作决策"跳到"双三角模型"，但从"双三角模型"跳到"数据五层次"可能就断了——因为这两张卡片之间没有直接的链接。
- **检索模式以单点为主**：如果 KDO 的 Agent 们大多数查询都是"某个概念是什么"而非"这个概念和那个概念有什么关系"，那么我们在 Graph RAG 上的投资收益率就很低。

KDO 的实践表明：**选对了工具（LightRAG），但没有选对场景（以单点检索为主的查询模式）**。这就像买了一辆越野车却只在城市里开——车是好车，但场景不对。

## 我不同意的两个点

**第一个不同意的点："检索质量 > 零依赖原则"这个判断，在某些场景下被过度简化了。**

黄药师在 [[graph-rag-retrieval-layer]] 的取舍分析中写道："检索质量 > 零依赖原则"。这个判断在当时是对的——原 keyword 方案的子串匹配太笨了。但我的判断是：对于一个打算运行多年、可能需要迁移到不同环境的知识管理系统，"零依赖"不是一个可有可无的优点——它是一个生存约束。LightRAG 的版本升级、API 变更、甚至项目弃维，都可能让 KDO 在未来某个时点面临"被外部依赖捉住喉咙"的风险。

与黄药师的判断不同，我认为 KDO 应该保留一条"底线回退路径"：当 LightRAG 不可用时，能在 30 分钟内切换到一个纯标准库的向量检索方案。这不是"把质量放在次要位置"，而是"把风险控制放在与效率同等重要的位置"。

**第二个不同意的点：LightRAG 的"自动实体提取"在 KDO 的场景下可能是"帮倒忙"。**

KDO 已经有了一套人工维护的 wikilink 结构——这是一套高质量、有意图的关系网。但 LightRAG 的实体提取是基于统计模式识别的，它会"发明"一些 KDO 从未定义过的实体，并给它们建立关系。结果是：人工维护的关系和自动提取的关系并存，且互不兼容。

这个框架在以下场景下可能失效：当你的知识库已经有了一套严格的人工分类/标签/关系体系时，"自动图提取"的边际效益是递减的——甚至为负。因为自动提取不仅没有利用你已有的结构，还可能在上面叠加一层噪声。我的判断是：**KDO 应该考虑让 LightRAG 使用 wikilink 作为图的"金标准"关系，而不是让它自己去"探索"关系**。这样做的代价是要人工维护 wikilink，但收益是图的准确性和可解释性大幅提升。

## 如果你只做一件事

今晚打开你的知识库（无论是 Notion、Obsidian 还是 KDO），选一个你常查的概念。

先用"关键词搜索"（向量方式）查一次，记录下结果。然后用"关联探索"（图方式）查一次，记录下结果。

问自己：**第二次查到的内容，有多少是第一次没找到但你觉得有价值的？**

如果答案是"没有"或"很少"——那你的知识库当前并不需要 Graph RAG。向量检索已经足够了。

如果答案是"有不少"——那么记住这些"图才能找到"的内容有什么共同特征。它们可能是：
- 分布在不同页面中但有关联的概念
- 从未被明确标签过但在语义上相关的内容
- 需要跨越多个领域的综合见解

**这些就是你真正需要 Graph RAG 的场景。** 把它们列成一个清单，这个清单比任何技术对比表都能帮你做出正确的选型判断。
