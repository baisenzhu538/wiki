# 三个不该被留在 Feedback 段的问题

> 前一篇文章的 Feedback 段留了三个问题。欧阳锋说"值得你再深度思考推理一遍"。这篇文章就是对这三个问题的逐层解剖。每个问题都不是"对/错"判断题——它们暴露的是 ADUCIT 框架在工程落地时的结构性张力。

## 问题一：U 的"给谁用"维度如何建模？

### 问题的起源

同一段月白口述稿。老顽童看到暗知识卡素材，洪七公看到设计工作流，段王爷看到渠道分发素材。如果 U 要做升仓决策——"这段素材值得从湖升到仓吗？"——答案取决于你问的是哪个角色。

**这不是一个技术问题。这是一个"谁有权力定义价值"的架构问题。**

### 三种建模路径，三种权力结构

#### 路径 A：单角色 Owner 制

每段素材在 capture 时就指定一个 Owner。Owner 说了算——Owner 觉得值得升仓就升，其他角色只能消费 Owner 加工后的产物。

```
月白口述稿 Owner = 老顽童
    → 老顽童判断：值得升仓（含暗知识）
    → 老顽童加工：产出 10 张 dk-yb 暗知识卡
    → 洪七公消费：从暗知识卡里提取设计工作流？
    → 问题：暗知识卡已经丢失了月白的操作细节——洪七公拿到的不是原矿，是尾矿
```

**适用**：Owner 是全职负责该领域的人。
**失效**：当一段素材同时服务多个领域时，Owner 制是单点瓶颈。Owner 的判断盲区 = 其他角色的信息黑洞。

#### 路径 B：多角色标签制

不对素材做升仓决策。而是给素材打上"可能对谁有用"的标签。升仓决策推迟到消费时——由消费者自己判断。

```
月白口述稿
    → 自动标签：#useful_for/producer #useful_for/design_va #useful_for/publisher
    → 老顽童打开 inbox，筛选 #useful_for/producer → 看到月白口述稿
    → 洪七公打开 inbox，筛选 #useful_for/design_va → 看到同一篇稿
    → 各自决定是否升仓
```

**适用**：多角色交叉消费的场景。
**失效**：标签由谁打？自动打需要 LLM（回到 D 的问题），人工打需要有人读过所有素材——这个人的存在本身就是一个 bottleneck。

#### 路径 C：工作类型路由制（我的选择）

不问"谁需要这个"，问"这个素材能支撑什么类型的工作"。

```
工作类型 ≠ 角色
工作类型 = {卡片生产, 视觉分析, 渠道分发, 代码开发, 架构审查}

月白口述稿 → 自动检测：含工具用法(适合卡片生产) + 含设计流程(适合视觉分析)
    → 路由到"卡片生产"队列 → 老顽童取用
    → 路由到"视觉分析"队列 → 洪七公取用
```

**为什么选 C 而不是 B**：

B 的问题是标签的维护成本——`#useful_for/producer` 这个标签需要有人持续判断。而 C 的路由键是**素材的内在属性**——"含工具用法"是素材本身的特征，不依赖于"谁来消费"。标签随角色变，路由键随素材不变。

**但 C 也有盲区**：路由键的粒度。如果只设 5 种工作类型，月白的"图层管理标准"会被路由到"卡片生产"——但它可能对洪七公的 VA 也有用。路由键是粗粒度的，消费者在队列里看到的仍然是"可能相关"的素材集合，不是精准匹配。

**结论**：短期选 C（工作类型路由，5 个队列）。中期在队列基础上加订阅——每个 Agent 声明自己的消费偏好，素材入队时自动通知相关 Agent。长期才考虑自动标签（需要 D 先跑通）。

## 问题二：D 应该在 U 之前还是之后？

### 问题的起源

ADUCIT 是 A→D→U→C→I→T 的线性顺序。但逻辑上有矛盾：

- D（识别隐藏高价值数据）需要翻看素材才能发现价值
- U（升仓决策）需要判断哪些素材值得翻看
- 你不翻看怎么知道值不值得？不判断值不值得怎么决定翻看哪些？

**这是一个鸡生蛋蛋生鸡的问题。Truman 的线性框架在这里遇到了现实中的循环依赖。**

### D 和 U 不是先后关系，是共生关系

我之前在文章里画 ADUCIT 的线性流程图，现在意识到那个图是错的。D 和 U 的真实关系不是 A→D→U，而是：

```
D ────→ U
↑        │
│        ↓
└── C ←──┘

D 在湖里发现线索 → U 决定升仓 → C 加工 → 加工过程中发现新线索 → 回到 D
```

**D 和 U 是同一个飞轮的两半，不是流水线的两个工位。**

### 这对 KDO 的架构意味着什么

线性模型下，我们试图先做完 D 再做 U——这意味着 D 要一次性扫描整个 inbox，找出所有隐藏的高价值数据。这在工程上是不可行的：424 张卡 + 162 个源文件 + inbox 里的大量原始素材，全量扫描的成本太高。

飞轮模型下，D 和 U 可以同时启动，互相加速：

| 阶段 | 动作 | D 的输入 | U 的输出 |
|:--:|------|------|------|
| 冷启动 | 手动挑选 5-10 个明显高价值的素材先升仓 | 欧阳锋的人工判断 | 第一批卡片 |
| 第一圈 | C 加工这 5-10 个素材 → 在加工过程中发现"类似的素材还有哪些" | C 过程中的发现 | 第二批升仓清单 |
| 第二圈 | U 升仓第二批 → C 加工 → D 发现更多模式 | 模式识别："含工具名的口述段通常是暗知识" | 第三批升仓清单 |
| 稳态 | D 和 U 交替驱动，不需要全量扫描 | 增量发现 | 增量升仓 |

**结论**：D 和 U 应该同时启动，不是先后。Sprint 6 的 `kdo inbox --audit` 是冷启动的第一步（让 D 有东西可看），第一批手动升仓是 U 的第一步。之后的飞轮靠 C 过程中的发现自动推进。

## 问题三：四个死刑的修复顺序是否应该调整？

### 问题的起源

Sprint 6 的当前顺序是：

```
1. enrich+label 串联 (L2)
2. ingest 预判 (A)
3. feedback 回流
4. ship → Agent 消费
```

问题是：**如果 A（预判）没修好，先修 L2（精加工）是否本末倒置？** A 决定"什么值得加工"，L2 是"怎么加工"。先修怎么加工，却不先修什么值得加工——那我们会不会在给一堆不值得加工的卡片做精加工？

### 正反论证

#### 正方：应该先修 A

- A 是 ADUCIT 的起点——Truman 说"从预判价值开始，以终为始"
- 424 张卡已经在库里了，如果 A 判断出其中 200 张不值得加工，我们省了一半工作量
- 先修 A 可以在 ingest 新卡片时立刻生效——新卡从第一天起就有价值标签
- A 的工程成本最低（2h），ROI 最高

#### 反方：应该先修 L2

- A 的判断依据是什么？"这张卡 AI 未来会怎么用"——**如果你不知道 AI 能怎么用你的数据，你没法做预判**
- 修 L2（给卡片打 9 维标签）能让你第一次看到：哪些类型的 chunk AI 能准确分类？哪些卡片的内容结构适合精加工？
- **先用 L2 在小范围跑出数据，再用数据反哺 A 的判断标准**
- 否则 A 就是盲猜——"这张卡 AI 未来怎么用？"在没有标注数据的情况下，答案只能是"我觉得"

### 我的立场：不是调整顺序，是插入一个 Pilot 步骤

当前 Sprint 6 顺序的根本问题不是 L2 和 A 谁先谁后——是**没有 Pilot 阶段**。

改为：

```
Phase 1: L2 Pilot（20 张卡）→ 产出标注数据
    ↓
Phase 2: A 设计（基于 Pilot 数据）→ 定义"什么值得加工"的判断标准
    ↓
Phase 3: L2 全量（基于 A 的优先级排序）→ 高价值卡先标，低价值卡后标
    ↓
Phase 4: feedback 回流
    ↓
Phase 5: ship → Agent 消费
```

**Pilot 的价值不在"验证 L2 能跑通"（已经验证了），在"给 A 提供判断依据"。**

具体来说：Pilot 20 张卡跑完后，我们会知道：
- 哪些 chunk_type 的标注准确率最高/最低？
- 哪些 domain 的卡片 chunk 密度最大（标注 ROI 最高）？
- 哪些卡片跑完 label 后 value_tier 应该被标记为 macro（护城河级）？

这三个问题的答案就是 A 的判断标准。

**结论**：不调整 L2 和 A 的先后顺序——在两者之间插入一个 Pilot 阶段。L2 Pilot → 数据 → A 设计 → L2 全量。Pilot 是 L2 和 A 之间的桥梁，解决"不知道判断标准就开始判断"的盲猜问题。

## 三个问题的交汇点

回头看这三个问题，它们指向同一个根因：

**ADUCIT 被设计为线性框架，但数据工作的现实是飞轮。** U 的"给谁用"依赖角色间反馈（不是单向路由）。D 和 U 是共生关系（不是先后关系）。L2 和 A 互相依赖（L2 产出数据 → A 产出判断标准 → L2 按优先级执行）。

Truman 画了一条漂亮的线：A→D→U→C→I→T。但这只是**教学简化**。真实系统中的 A 和 D 互相纠缠、D 和 U 交替推进、U 和 C 互为前提。

线性图适合教给别人，飞轮图适合自己建。两个都要有。但**建系统的人如果只按线性图施工，会建出一个每层都对但层与层之间断裂的管线**——这正是 KDO 的现状。
