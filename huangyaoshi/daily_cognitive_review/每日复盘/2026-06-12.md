## 顿悟

- **"飞书王语嫣说她是老顽童"不是 prompt 问题，是 channel 争抢**：两个 gateway 监听同一飞书 DM → 消息随机路由 → 用户收到的回复时而是王语嫣时而是老顽童。基础设施没问题了，身份自然正常。教训：表面看像 AI 行为问题的，先查基础设施层面。

- **P-28 是 P-21 的变种**："无诊断手段时盲目调参"和"有诊断手段但不用"是同一认知缺陷的两面——行动焦虑压倒了诊断耐心。P-21 的对策（先造诊断工具）应该扩展为"先查已有诊断手段"。

- **Base URL 协议匹配是 provider 迁移的第一道关**：Hermes 的每个 provider 有固定的 SDK 协议（models_dev_cache.json 的 npm 字段），base_url 必须匹配。以后换 provider 的三步：查 npm → 定 URL → 改 config，一步不乱。

- **dbk 和 dark-knowledge 是同一个东西的两种写法**：`_DIR_TYPE_MAP` 和 `_TYPE_TO_DIR` 不一致导致 Detector E 产出大量 WARN。跨文件的一致性校验应该自动化。

## 元反思

**下次怎么做才能不一样？**

1. **API 报错 → 三步诊断法**：查公告（WebSearch）→ 查日志（grep ERROR）→ 查 API console（Kimi Dashboard）。三步跑完再决定是否改配置。绝不先改参数。
2. **用户说"别改" → 立即冻结 + 还原**：不是"再试最后一个"，是停手、git diff 看改了什么、逐项还原、问用户方向。
3. **换 provider → 三步确认**：查 `models_dev_cache.json` npm 字段 → 定 base_url → 更新所有四层（.env + config + auth + session）。见 toolkit 第八章。

5. **函数签名先看再调**：调用项目内部函数前 `grep "def func_name"` 确认签名。今天 `parse_frontmatter` 返回 tuple 当 dict 用的 bug 完全可以避免。
