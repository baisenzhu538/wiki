`--extract-skills` 从设计到验证只用了 2 小时。半肥猫的 15 个技能提取验证了 prompt 有效性，月白深挖时用分段策略突破了 Kimi 的字数限制。330 个技能素材池一次跑通。

### 4. 复盘文档化
每次踩坑立刻写入 pitfalls（P-22 跨域边界、P-23 插件依赖链、P-24 Win10 沙箱）。每阶段产出写入 `huangyaoshi/` 文件夹。任何后来者（包括换电脑后的自己）都能通过读文件夹重建上下文。

## 三、做得差的

### 1. Codex 安装——在同一条路上撞了 6 个小时
Max 的错。Win10 sandbox 阻断 localhost——这个根因在前 30 分钟就应该锁定。但我换了端口、换了协议栈、换了代理语言、换了 WSL、换了安装方式……就是不接受"沙箱是根本原因"这个结论。

**教训**：当同一个症状（Codex 请求不到代理）在换端口/换协议/换语言后依然出现 → 问题不在代理，在操作系统层。排除法应该往上走，不是在同一层换变量。

### 2. WebSocket 盲区
那边的代理用 Node.js + ws 库处理 WebSocket，我用 Python + aiohttp 只处理 HTTP。Codex 默认走 WebSocket——我的代理根本接不住。如果一开始就看 Codex 的网络请求类型（WebSocket vs HTTP），半小时就能定位。

**教训**：接入新工具的第一件事不是写代理，是看它往哪发请求、用什么协议。

### 3. 在 GUI 工具上浪费了时间
CC Switch 装了两次、CCX 试了 4 种启动方式——这些都是 GUI/二进制工具，不适合命令行自动化的场景。应该更早接受"自研代理"这条路。

## 五、P-24 反思：为什么 6 小时 vs 10 分钟

那边的 Claude 10 分钟装好 Codex + Kimi，理由：
1. **没有 Win10 sandbox 问题**（Win11）
2. **直接用了 WebSocket**——看了 Codex 的协议就写 ws 代理
3. **Kimi Chat Completions API**——不需要 Anthropic 协议转换
4. **一次写对**——因为看了 Codex 的实际请求格式再动工

我 6 小时才装好，因为：
1. **Win10 sandbox 是独有的坑**——那边没遇到
2. **先写了 Anthropic 协议转换**——绕了远路（Kimi Chat Completions 更简单）
3. **没先看 Codex 的请求格式**——WebSocket 优先这件事折腾了 3 小时
4. **试图绕沙箱而不是关沙箱**——在端口/协议层浪费了 2 小时

## 六、改进措施

1. **接入新工具的标准流程**：先抓包看请求格式 → 选最简协议 → 再写代理
2. **操作系统的坑优先排查**：3 次尝试后若问题依旧 → 往上走一层（OS/沙箱/防火墙）
3. **接受沙箱关闭**：Win10 + Codex + localhost 代理 = 必须关沙箱。不要试图绕过
4. **GUI 工具不碰**：不适合命令行自动化，浪费时间
