# 纪浩 AI 协作体系的完整解读

> 之前老顽童产出了 25 张 skill 卡，黄药师做了 Skills Market 的分析。但两者都只抓了局部，没看到 纪浩 构建的完整体系。
> 
> 他的体系不是几个孤立的方法论，而是一个从"判断该不该做"到"组织 AI 工作环境"到"执行复杂任务"到"规模复用"的完整闭环。

---

## 一、四要素验证法——入口把关

这是体系的入口。不是方法论的全部。

纪浩说大部分人在 AI 协作中犯的错，是把 Question 当成了 Problem。他用四个问题来验证：

| # | 要素 | 判断标准 | 伪需求的信号 |
|:-:|:----|:---------|:------------|
| 1 | **Before/After** | 解决前和解决后的状态有明确可对比的变化 | "有了会更好"但说不清好在哪里 |
| 2 | **真实锚点** | 在真实世界中有一个具体的场景 | "如果我有……"式的幻想 |
| 3 | **受益人** | 解决了之后一定有人切实受益 | "这个做出来应该有人用" |
| 4 | **可解有支撑** | 有因果链，有能力去解决 | 没有就想用技术硬上 |

**四个要素不够，不要下场动手。** 但他马上反问：我们是新手，看不出来怎么办？

然后他给出了工具——假设、调研、访谈、问 AI、做实验。他不是在说"要有深度思考"，而是在说**新手也可以验证，关键是有验证的方法。** 这一点之前的分析都漏了。

---

## 二、Agent Workspace（五大类）——AI 的工作环境设计

四要素验证通过后，第二件事：**先搭工作空间，再让 AI 动手。**

AI 是一个模式匹配系统——它不会自己搞结构设计。你给它一个乱的工作空间，它就会在错误的道路上越走越远。你让它自己去修，它在错误的基础上继续错。

纪浩总结的五大类：

| 类别 | 内容 | 为什么需要 |
|:----|:-----|:-----------|
| **① 系统自述** | 架构、组件、技术栈、项目结构 | 没有这个，需求越多架构越漂移（"架构会长在代码里"） |
| **② 领域知识** | 业务逻辑、概念定义、规则 | AI 没有这些就会自己猜，导致不可验证、不可解释 |
| **③ 服务文档** | 导诊台、工作手册、工具集、经验模式库 | 复杂任务需要分类+分流+标准作业程序 |
| **④ 任务管理** | 任务上下文、执行记录 | AI 接手多个任务后会混乱——"他让你干A他干了B" |
| **⑤ 日志** | 执行日志、反馈记录 | 复盘和迭代的基础 |

这五个东西不是理论框架，是他踩了无数次坑之后总结出来的。他原话：**AI 接手任务变多后会出现混乱行为，目录乱七八糟，最后只能放弃让 AI 重新投胎。**

这个描述和我们之前的广冷调试不一样——广冷是硬件问题，这里是 AI agent 的工程化管理问题。

---

## 三、复杂任务执行流程——从 Do 开始的 PDCA

第三层是他做复杂任务的执行流程。关键洞察是：**PDCA 不是从 Plan 开始的，是从 Do 开始的。**

他举了一个 UI 设计的例子（1100 行约束文档），执行了 5-6 个阶段：

```
阶段 1：冻结任务定义 → 这个页面是干什么的
阶段 2：定义约束 → 必须怎么怎么样
阶段 3：用户旅程 → 进入页面之后干什么
阶段 4：定义代码模型
阶段 5：校验 → 方案是否正确
阶段 6：编码 → 真实的系统上实现
```

然后他做 PDCA 迭代。注意他的顺序：**Plan → Do → Check → Act，但你第一次是从 Do 开始的。** 先动手去做，遇到具体问题，针对具体问题想办法解决，循环才能搭起来。

> "所有的 PDCA 流程，它不是从一个 Plan 开始的，它一定是从 Do 开始的。一定要去解决具体的问题，才有可能把这个 PDCA 去搞好。"

这句话背后的逻辑：**如果你没有真实的 Problem，你做不出 Plan，你只能在原地空转。** 四要素帮你验证 Problem，Problem 确认后用 Do 启动循环，循环跑起来后自然越滚越大。

## 四、Skills Market——规模复用的基础设施

这是体系的出口，不是全部。

| | 没有 Skills Market | 有 Skills Market |
|:---|:-----------------|:----------------|
| 分发 | 微信传 zip | 集中管理、集中分发 |
| 版本 | 文件名标记 | 平台版本号 |
| 反馈 | "模糊的口述" | 带上下文的结构化上报 |
| 安装 | 人手动搞 | AI 自己去下载安装 |

但最值钱的一点是之前没人提的：**Skills Market 不是给人用的，是给 agent 用的。**

- 人不需要知道市场长什么样
- agent 按分类 + capability 匹配 → 自己下载 → 自己安装 → 自己上报上下文
- 写描述不要人写——人跟 AI 说清楚，AI 去补全

这个模式和 KDO 的 `kdo encapsulate` 是同一件事——把技能打包成 agent 可以直接加载的格式。区别在于他做了一个网页平台，而我们可以用 git + 命令行实现同样的闭环，甚至更轻。

---

## 五、贯穿始终的底层哲学

**五层体系不是孤立的，是一条链：**

```
人机协同的完整链路

新手心态启动             ← 心态层（"不要用高手标准抽打自己"）
  →
四要素验证               ← 判断层（"四个要素不够不下场"）
  →
Agent Workspace 设计      ← 环境层（"AI 不会自己搞结构设计"）
  →
Do-first PDCA 执行        ← 执行层（"从 Do 开始，不是从 Plan 开始"）
  →
Skills Market 规模复用    ← 扩展层（"让人和 agent 都能复用"）
```





每一层解决一个具体问题，每一层同时是下一层的前提。五件东西的胜率加起来远高于五件东西各自独立使用。

---

## 六、对 KDO 的直接启示

1. **技能卡有了，但"工作空间设计"的知识还没建。** 我们的知识库主要面向人，但 纪浩 的分享揭示了另一个需求：**知识库也需要面向 agent 的结构化设计。**
2. **question vs problem 的四要素验证也可以写成一张 skill 卡。** 这是我们每个人每天都在用的判断工具。
