# 知识库进化的冷热混合模型（Systematic + Dialogue KB Evolution）

> 回答核心问题：知识库进化能不能系统化？还是只能依赖高质量对话？
> 结论：**系统性进化负责发现机会、降低摩擦；对话驱动进化负责创造高价值桥接和方向校准。两者必须混合。**

---

## 1. 核心论断

| 维度 | 系统性进化（冷进化） | 对话驱动进化（热进化） |
|:---|:---|:---|
| **能做什么** | 发现缺口、检测腐烂、建议候选链接、量化结构健康度 | 创造跨域洞察、重新定义角色、把真实问题映射到知识结构 |
| **不能做什么** | 判断哪个桥接最有价值、理解用户真实目标、创造新框架 | 持续大规模扫描、自动修复机械错误、保持图谱整洁 |
| **产出** | 进化候选清单（backlog） | 高优先级桥接卡/方法论模型 |
| **成本** | 低（可脚本化） | 高（需要高质量对话） |
| **错误成本** | 低（建议可被忽略） | 高（错误方向会污染知识库） |

**一句话**：系统告诉我们「哪里可能有问题」，对话告诉我们「这里值不值得深挖、要挖成什么」。

---

## 2. 冷进化：可以系统化的 6 类工作

### 2.1 机械健康度扫描

| 检查项 | 工具/脚本 | 处置 |
|:---|:---|:---|
| 死链 | `check_dead_links.py` | 自动报告，人工确认后修复 |
| YAML 解析失败 | `check_p0a_yaml.py` 扩展版 | 自动标记 blocker |
| 缺 id/title/type | `kdo lint` | 自动报告 |
| domain typo | 字典匹配脚本 | 自动建议修正 |
| source_refs 缺失 | `kdo lint` / 自定义扫描 | 标记为 `src_unknown` 或 `pending_archive` |

### 2.2 结构缺口扫描

| 检查项 | 方法 | 输出 |
|:---|:---|:---|
| related 数量过少 | 统计 `< 5` 或 `< 8` 的卡片 | 低连接卡片清单 |
| 跨域链接缺失 | 图分析：不同 domain 的高相似度节点无连接 | 候选桥接对 |
| 孤儿卡片 | 入度为 0 的卡片 | 需要补充被引用的清单 |
| 域摘要缺失 | 检查 `domains/` 下 digest 覆盖 | 待建 domain digest 清单 |
| 旧版卡片未链新版 | 检查 deprecated/旧模型卡片的 related | 需要双向链接的清单 |

### 2.3 内容质量衰减扫描

| 检查项 | 信号 | 输出 |
|:---|:---|:---|
| 薄卡 | 行数 < 100、段落缺失 | 需要 enrich 的卡片 |
| 长期未 review | `review_date` 超过 90 天 | 待复审卡片 |
| confidence 与 trust_level 不一致 | 高 conf + low trust 或反之 | 可信度校准清单 |
| 概念卡缺少边界 | 无 When NOT to Use / Constraints | 结构补全清单 |

### 2.4 跨域桥接候选发现

| 方法 | 原理 | 输出 |
|:---|:---|:---|
| 共现词分析 | 不同 domain 卡片共享大量关键词 | 候选桥接对 |
| 图最短路径 | 两个域核心卡之间的路径长度 | 需要更短桥接的域对 |
| 向量相似度 | 用 embedding 找语义相近但无链接的卡片 | 高语义相似候选 |
| 案例迁移 | A 域案例的方法论可迁移到 B 域 | 跨域案例卡候选 |

### 2.5 用户对话资产化

| 资产 | 来源 | 处置 |
|:---|:---|:---|
| 用户追问模式 | 历史对话中反复出现的问题类型 | 提取为 query_trigger |
| 用户纠正记录 | 用户指出卡片错误/不完整的记录 | 写入 `60_feedback/corrections/` |
| 用户高兴趣点 | 「这几个我尤其感兴趣」类信号 | 提升相关卡片优先级 |

### 2.6 进化 backlog 生成

把以上所有扫描结果汇总成一个优先级队列：

```
evolution-backlog.md
├── P0：机械错误（死链/YAML/缺 id）
├── P1：结构缺口（低 related/孤儿卡/缺 digest）
├── P2：质量衰减（薄卡/旧 review）
├── P3：跨域桥接候选（系统发现）
└── P4：对话驱动高价值桥接（需用户确认）
```

## 3. 热进化：只能由对话完成的 5 类工作

### 3.1 真实问题映射

系统无法知道用户当前真正困惑的是什么。例如：
- 用户说「渠道增长×单元模型」不够深；
- 系统可以发现这两个域没链接，但不知道用户关心的是 **CAC payback by channel** 还是 **渠道投资组合**。

### 3.2 跨域框架设计

两个域的接口需要创造性设计。例如：
- `framework-yitang-channel-unit-economics` 的核心公式是什么？
- `framework-ai-deliberate-practice-loop` 的闭环图如何画？
- 这些需要对话中的反复校准。

### 3.3 角色与目标重定义

当用户说「你不是做知识库，你是给我做咨询」时，这是对话层面的方向校正，系统无法替代。

### 3.4 价值判断与优先级

系统可以列出 100 个跨域候选，但只有对话能决定哪 2-3 个最值得立刻生产。

### 3.5 外部证据解读

系统可以抓取文献，但无法判断哪条证据与一堂素材最契合、哪些需要降级为「待验证」。

## 4. 冷热如何连接：三层漏斗

```
┌─────────────────────────────────────────┐
│  Layer 1：系统扫描（冷进化）              │
│  每天/每周自动跑，产生 evolution backlog  │
└──────────────────┬──────────────────────┘
                   ↓ 过滤：机械错误自动修，候选进下一层
┌─────────────────────────────────────────┐
│  Layer 2：对话筛选（热进化入口）           │
│  王语嫣把 backlog 中 Top N 候选呈现给用户 │
│  用户用一句话决定：深挖 / 跳过 / 降级      │
└──────────────────┬──────────────────────┘
                   ↓ 触发：method-dialogue-driven-kb-evolution
┌─────────────────────────────────────────┐
│  Layer 3：对话深挖 + 生产（热进化执行）    │
│  九层深挖 → 跨域桥接 → 更新任务单 → 生产  │
└─────────────────────────────────────────┘
```

**关键规则**：
- 冷进化负责「广度覆盖」；
- 热进化负责「深度创造」；
- 热进化的输入来自冷进化的 backlog，而非每次从零开始问用户「你觉得知识库缺什么」。

## 5. 可落地的第一步：建立「进化信号面板」

不需要一次性做完整套系统，可以先做一个轻量面板：

### 5.1 每周自动生成的信号报告

`60_feedback/auto/kb-evolution-signals-weekly.md`

| 信号类型 | 数量 | Top 3 候选 | 建议动作 |
|:---|---:|:---|:---|
| 跨域无链接高相似卡片 | 23 对 | A-B, C-D, E-F | 王语嫣挑选后对话确认 |
| related < 5 的卡片 | 47 张 | X, Y, Z | 自动分配给老顽童补 related |
| 90 天未 review | 31 张 | P, Q, R | 安排复审 |
| 薄卡（<100 行） | 12 张 | M, N, O |  enrich 或降级 |
| 死链 | 0 | - | 无需动作 |

### 5.2 每月对话校准会

王语嫣把信号报告中的 Top 10 候选呈现给用户，用 10-15 分钟确认：
- 哪 2-3 个桥接点最值得深挖？
- 哪些卡片应该优先 enrich？
- 有没有新域要启动？

### 5.3 把用户对话中的元反馈自动归档

每次用户给出类似「跨域不够深」「这个有意思」「我疑惑的是…」的信号，王语嫣写入：
`60_feedback/methods/method-dialogue-driven-kb-evolution.md#关键触发语料库`

形成组织记忆，减少重复摸索。

## 6. 失败模式

| 模式 | 症状 | 修复 |
|:---|:---|:---|
| **过度系统化** | 每天跑 100 个扫描，但没人看 backlog | 把系统输出限制在「可行动的 Top N」 |
| **过度依赖对话** | 每次进化都从零讨论，效率低 | 用系统 backlog 作为对话起点 |
| **系统建议质量低** | 推荐的桥接对都是表面相关 | 引入多信号加权（共现 + 向量 + 图距离） |
| **对话资产不沉淀** | 用户纠正只在当次对话生效 | 必须写入 `60_feedback/corrections/` 或更新方法论卡 |

## 7. 与已有机制的关系

| 已有机制 | 在混合模型中的位置 |
|:---|:---|
| `kdo lint` / `kdo pre-submit` | 冷进化的机械健康度层 |
| `check_dead_links.py` | 冷进化的死链扫描器 |
| `framework-yitang-nine-layer-deep-dig` | 热进化的深度工具 |
| `method-dialogue-driven-kb-evolution` | 热进化的五环流程 |
| 本模型 | 把冷热两层连接成完整系统 |

---

## 8. 王语嫣的承诺

以后我不会再问你「知识库要不要进化」这种空泛问题，而是会：

1. **定期**（每周/每月）给你一个 `evolution-signals` 简报；
2. 从简报中挑出 **Top 3-5 高价值候选**；
3. 用一句话说明每个候选的「如果深挖，可能产生什么桥接卡」；
4. 你用一句话回：「挖这个」「跳过」「换个方向」。

这样，对话的质量会被系统性扫描放大，而不是被大量低价值选择稀释。
