# 概念卡：智能药柜医疗信息系统（HIS/SaaS）架构与合规

## 一句话定义

智能药柜的医疗信息系统是一套连接诊疗、处方、药房、医保、药监、支付、设备控制的软件系统，必须在云端部署效率与医保专网/数据安全合规之间找到可行架构。

---

## 系统功能模块

根据项目录音和医疗信息系统通用架构，药柜项目至少需要以下模块：

| 模块 | 功能 | 合规/技术要点 | 项目状态（基于录音） |
|------|------|--------------|---------------------|
| **诊疗模块** | 患者建档、问诊、开方 | 需由具备执业资质的医生操作；处方需符合《处方管理办法》 | 8032774 称已具备基础诊疗、开方功能，内测两周 |
| **处方管理** | 处方开具、审核、留存、追溯 | 需执业药师真实审方；处方留存不少于规定年限 | "数字人分身"审方存在合规风险 |
| **药房管理** | 库存、进销存、效期、拆零控制 | 需符合 GSP；处方药不可拆零销售 | 基础药房管理功能已具备 |
| **药柜控制** | 上下位机通信、出货控制、库存同步 | 安卓版已开发；Windows/医保版仍在开发 | 安卓版完成，Windows/医保版待成熟 |
| **医保对接** | 医保个账/统筹结算、医保电子凭证 | 需 Windows 工控机 + 医保前置服务器 + 医保专网 | 4528361/7296034 显示仍在开发/部署复杂 |
| **药监上传** | 药品追溯码、进销存数据上传 | 需对接省级药监平台 | 录音中提到需"无 T 上传"，具体状态不明 |
| **O2O/线上商城** | 按设备选药、就近取药、统一收款 | 需药品网络销售备案；避免二清 | 7898987 称初期不做 B2C/O2O，只做设备选药 |
| **健康数据管理** | 检验检测、家庭设备数据、大院处方存档 | 涉及个人隐私和医疗数据，需符合《个人信息保护法》《数据安全法》 | 7683984 称家庭设备数据仅做展示，核心分析由慢病系统承担 |
| **ERP/财务** | 分账、结算、报表 | 需与药店/诊所 ERP 对接；税务合规 | ERP 对接为共性痛点 |

## 核心架构张力：云端 SaaS vs 医保专网本地化

### 两种部署方式对比

| 维度 | 云端 SaaS 部署 | 医保专网本地化部署 |
|------|---------------|-------------------|
| **适用场景** | 普通诊所、民营药店、线上商城 | 医保定点医院/药店、公立医院、社康中心 |
| **优点** | 部署快、成本低、迭代快、易扩展 | 符合医保/医院网络安全要求、数据不出院 |
| **缺点** | 医保专网无法访问外网，不能直接刷医保 | 部署周期长、成本高、运维复杂 |
| **对药柜的影响** | 可支撑乙类 OTC 自助售药、自费药品 | 支撑医保个账/统筹支付、医院 HIS 对接 |
| **项目现状** | 8032774 称 SaaS 云端部署 | 7151864 称医保专网无法访问外网，必须本地化 |

### 项目当前矛盾

同一项目若同时服务：
- **诊所端**：倾向于 SaaS 云端部署（成本低、上线快）
- **医保定点医院/药店端**：必须本地化部署（医保专网要求）

**结论**：项目可能需要同时维护两套部署方案，或在云端与本地之间建立安全的数据交换机制，这显著增加了技术复杂度和合规成本。

## 数据合规与安全

### 1. 医疗数据分级

| 数据类型 | 敏感度 | 合规要求 |
|---------|--------|---------|
| 患者基本信息 | 高 | 需知情同意，最小必要原则收集 |
| 处方信息 | 极高 | 严格授权访问，完整留存，可追溯 |
| 诊疗记录 | 极高 | 属于电子病历/健康医疗大数据，需符合相关规范 |
| 健康设备数据 | 高 | 7683984 称仅做展示，若用于诊断需升级合规 |
| 医保结算数据 | 极高 | 需在医保专网内处理，不得外泄 |
| 药品追溯码/进销存 | 高 | 需按药监要求上传 |

### 2. 数据安全法与个人信息保护法要求

- **数据分类分级**：识别重要数据和核心数据
- **数据出境**：若使用境外云服务或向境外传输数据需评估
- **最小必要**：只收集业务必需的数据
- **知情同意**：患者数据收集需明确告知用途
- **安全事件响应**：建立数据泄露应急预案

### 3. 项目中的具体风险

| 风险点 | 说明 | 来源 |
|--------|------|------|
| 云端部署与医保数据本地化冲突 | 医保结算数据若走云端，违反医保专网要求 | 7151864、8032774 |
| 多设备/多投放商数据隔离 | 通过员工账号+门店编码隔离，技术可行但需审计 | 7898987 |
| 家庭健康设备数据 | 仅做展示可降低风险，若用于慢病干预需符合医疗数据规范 | 7683984 |
| 处方照片/复制处方存档 | 拍照上传处方存在真实性和完整性风险 | 7683984、8032774 |

## 项目当前系统能力边界

### 已确认的能力

- 安卓版药柜控制程序已开发完成
- 基础诊疗、开方、药房管理功能已具备（8032774 内测两周）
- 服务器程序已部署
- 家庭设备数据可接入并展示

### 未成熟/待验证的能力

| 能力 | 状态 | 风险 |
|------|------|------|
| Windows 版上位机 | 仍在开发 | 医保/HIS 对接依赖此版本 |
| 医保前置服务器 | 部署复杂 | 各地医保要求不同 |
| 医院 HIS 对接 | 7983893 称已可对接，但 4528361 称 Windows 仍在开发 | 销售承诺与研发进度不一致 |
| 电子处方流转平台 | 6362082 称已对接，7683984 称实际只能拍照上传 | 合规路径未打通 |
| 药监数据上传 | 提到"无 T 上传"，具体状态不明 | GSP 合规风险 |
| ERP 对接 | 药店 ERP 五花八门，对接成本高 | 运营效率受限 |

## 对项目的技术建议

### 短期（1–3 个月）

1. **明确两套部署方案**：分别设计 SaaS 云端版（诊所/自费场景）和本地化版（医保/医院场景），避免一套方案硬套所有场景。
2. **优先保障 Windows/医保版本稳定**：这是医保支付和医院 HIS 对接的前提。
3. **解决断电状态持久化**：药店 24 小时运营要求设备具备高可靠性。
4. **完成药监上传对接**：这是药品经营合规的基础。

### 中期（3–6 个月）

5. **建立统一数据中台**：在云端和本地之间建立合规的数据交换机制，避免数据孤岛。
6. **完善处方合规流程**：从拍照续方过渡到真实的电子处方流转或规范复诊开方。
7. **ERP 对接标准化**：以"网页内嵌 + 中台系统"方式降低逐店对接成本。

### 长期（6 个月以上）

8. **通过等保/密评**：医疗系统通常需通过网络安全等级保护。
9. **建立数据治理体系**：明确数据分类分级、访问控制、审计日志、应急响应。
10. **考虑互联网医院资质**：若持续做线上诊疗/处方，需申请互联网医院牌照。

## 局限与使用边界

1. **录音中关于 3424604 云聚米私有化的直接信息有限**，本卡结合了项目其他录音和医疗信息系统通用知识。
2. **具体系统架构需以实际技术文档为准**，本卡仅为概念框架。
3. **法规要求因地而异**，不同省份对医保专网、药监上传、数据本地化要求不同。
4. **本卡不是技术实施指南**，具体部署需由医疗信息化专业团队评估。
