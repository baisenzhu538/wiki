# #525 角色级时钟与探针架构设计（工具可换，自动化工作流不变）

- **任务号**：#525
- **状态**：queued
- **assignee**：huangyaoshi（架构设计稿；风清扬审计；欧阳锋终审；老朱拍板）
- **优先级**：P1（全自动路线的地基——工具随订阅额度轮换是常态，工作流不能跟着工具漂）
- **立项**：2026-08-25 王语嫣（老朱直令：「时钟和探针机制严格意义上应该是每个角色都有，不是和工具挂钩」+「工具可能用 kimi/claude/codex/hermes/CodeBuddy 等，可能会换，但自动化工作流不能变」）

## 背景

命名铁律同哲学：工具是变量，角色是恒量。现状拆分：**探针层已达标**（conveyor_probe 工厂级单例 + `todos/<role>.md` 角色收件箱 + 飞书按角色推送，#519/#523 已补失败可见）；**时钟层绑在工具上**——CLI 实例靠老朱手动开会话才醒（时钟=人手），hermes 实例靠平台 profile cron（工具给的时钟，换工具就丢）。角色级时钟不存在。缺的三块：活性注册表、角色心跳调度、唤醒语义统一。

## 任务（出设计稿，不施工）

设计稿落 `90_control/role-clock-architecture.md`，覆盖：

1. **角色→活跃实例注册表**：实例上线/下线登记+活性心跳（角色当前活在哪个工具实例上）；从轻实现（JSON/文件，不落数据库）；含多实例并存口径（同角色 CLI+飞书双实例都算活跃时的路由规则）
2. **角色心跳调度器**：每角色唤醒节奏可配置（如王语嫣定时对账/欧阳锋有提审即醒）；调度器查注册表把唤醒路由到该角色当前活跃实例；**工具切换=注册表改一行，工作流零改动**（设计稿的核心验收点）
3. **唤醒语义统一层**：底层不管是 hermes cron / schtasks / 会话启动钩子，角色收到的唤醒语义统一（「读你收件箱+该干什么」）；#520 提审叫醒作为第一个用例纳入统一层设计
4. **工具接入契约**：新工具（CodeBuddy/未来任何 CLI 或平台）接入要满足的最小契约清单——能收唤醒/能读 todos 收件箱/能跑 queue_transition/MCP 可挂；接入=实现契约+注册，不碰工作流
5. **现状资产统图**：#501 收件箱 / F-036 双通道 / #520 叫醒 / #509 飞书实例 / F-048 codex-homes 切换，画进同一张架构图，标注各归哪层、缺口在哪
6. **探针层确认**：维持工厂级单例（不多头扫描），设计稿只需引用 #519（空转根治）/#523（拒删上报）说明失败可见已覆盖

## 边界

- **只出设计稿不施工**——拍板后分批立项实施（防止与在跑的 #514/#515/#520 叠加改造）
- 探针单例架构不改；注册表从轻（文件/JSON）；不引入新平台依赖（能跑在现有 Windows+Python+hermes 栈上）
