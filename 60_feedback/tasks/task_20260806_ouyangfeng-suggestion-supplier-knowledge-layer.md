# 任务编排建议书：客户/供应商/员工内容的知识分层（情报层 vs 知识层）

> **提交人**：欧阳锋（Architect）
> **提交给**：王语嫣（编排）
> **日期**：2026-08-06
> **触发**：用户审阅 `00_inbox/供应商/千惠-廖总.md` 后提出担忧——"怕一些似是而非的概念污染 agents"

---

## 一、背景

`00_inbox/供应商/千惠-廖总.md` 是基于听脑录音整理的第一手供应商档案。用户审阅后指出三类问题：

| # | 问题 | 案例 |
|:--|:--|:--|
| 1 | **事实矛盾未标可信度** | "廖总花了七八千万" vs "木工欠一屁股债"——两条转述并存，无证据等级 |
| 2 | **实体名混用未澄清** | 通望 / 风网 / 通旺——同一公司三种写法 |
| 3 | **情绪化判断混入事实** | "明摆着廖总就不靠谱"——单方判断与事实并列 |

**核心担忧**：这类内容若以卡片形式进 `30_wiki/`，agents 检索时会把"单方转述/情绪判断"当事实使用——**知识层被污染，判断失真**。

---

## 二、建议原则：三层分层

```
┌──────────────────────────────────────────────────────────────┐
│ 第一层 情报层（00_inbox/ + 10_raw/sources/）                  │
│   ← 客户/供应商/员工的一手档案、录音转写、关系记录             │
│   特点：单方来源 · 口语噪音 · 时效性强 · 含隐私/敏感信息        │
│   规则：留在这里，补"证据等级"标注，不直接进知识层             │
├──────────────────────────────────────────────────────────────┤
│ 第二层 项目档案（personal-os / 项目域，如 zhu-* 系列）         │
│   ← 与老朱具体项目绑定的结构化档案（供应商关系/合作时间线）     │
│   规则：结构化 + 证据等级标注 + 更新机制（状态变化时更新）       │
├──────────────────────────────────────────────────────────────┤
│ 第三层 知识卡（30_wiki/）                                     │
│   ← 只放方法论/可复用模式：                                 │
│     "供应商尽调检查清单"（怎么验证）                         │
│     "单方情报可信度分级"（怎么判断来源）                     │
│   规则：判断不进知识卡，方法进知识卡                          │
└──────────────────────────────────────────────────────────────┘
```

**一句话**：**判断进项目档案，方法进知识卡，情报留在情报层。**

---

## 三、建议编排的任务（3 项）

### 任务 A：证据等级标注模板（流程规则落盘，P1）

**内容**：定义"情报层文件"的证据等级标注规范，写进 `90_control/AGENTS.md` 或工业化手册：

| 等级 | 标记 | 含义 | 示例 |
|:--|:--|:--|:--|
| ✅ 事实 | `[事实]` | 多方确认/可复核 | 合作开始时间（有合同/录音多方确认）|
| ⚠️ 转述 | `[转述]` | 单方声称，未核实 | "廖总花了七八千万" |
| 🎯 判断 | `[判断]` | 情绪化/主观评价 | "廖总不靠谱" |

**验收**：`00_inbox/供应商/千惠-廖总.md` 按模板标注完毕（示例档案落地）。

### 任务 B：供应商尽调检查清单（方法论卡，P1）

**内容**：从千惠档案提炼"如何验证供应商"的可复用维度，产出 1 张 tool 卡：

```
tool-supplier-due-diligence-checklist
- 研发交付可验证性：要求样机+时间节点，不只听口头（"一年多没做完"教训）
- 成本透明协议：报价单/明细，拒绝"能做但成本没说"
- 人员归属：社保/工资/责任主体书面化（"人挂在这里"教训）
- 转包链长度：一级供应商 vs 层层转包（"廖总→王总→张总"教训）
- 单一来源依赖：备选供应商预案（"明摆着不靠谱"后的退路教训）
- 实地验证：看产线/样机/设备（"只有千惠有了"的稀缺性核实）
```

**验收**：tool 卡五段齐全（操作步骤/适用边界/失败模式/When NOT to Use/Critique），related≥5 跨域（供应链/决策/OPC）。

### 任务 C：情报层入口规范（流程规则，P2）

**内容**：`00_inbox/` 下客户/供应商/员工目录的规范：
- 目录：`00_inbox/供应商/`、`00_inbox/客户/`、`00_inbox/员工/`（或统一 `00_inbox/关系档案/`）
- 每份档案 frontmatter 含：`evidence_level`（事实/转述/判断占比）、`last_updated`、`privacy`（是否含敏感信息）
- **边界**：此类档案不自动升级为 30_wiki 卡；只有提炼出的方法/模式由王语嫣评估后入卡

**验收**：目录规范落盘 + 千惠档案迁移符合规范。

---

## 四、为什么现在做

1. **污染已现**：千惠档案已存在，同类档案（客户/员工）会持续产生——规则不立，污染累积
2. **成本低**：模板 + 1 张方法论卡 + 目录规范，工作量小（1-2 天）
3. **风险真实**：agents 检索"廖总"类判断当事实用 → 商业判断失真（用户原话："怕似是而非的概念无敌你们"）

---

## 五、边界

- **不建"千惠-廖总"知识卡**（单方来源+隐私+时效，不够格进 30_wiki）
- 千惠档案留在 `00_inbox/供应商/`（情报层），只补标注不迁移
- 隐私红线：电话/人名/财务数字不进 30_wiki（同 #225 case-2 教训）
