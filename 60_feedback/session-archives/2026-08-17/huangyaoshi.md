## 思维盲点

1. **死代码没在第一次审查时清掉**——download_via_scribe（缺 import shutil 会 NameError）和 build_knowledge_note（TODO 占位、main 不调用）在 00:10 修改时已存在，我第一遍读代码（记忆恢复时）没标记为问题，直到"做成工作流"修链路时才清。为什么漏掉？读代码是"理解意图"导向不是"执行路径"导向——**修链路要按执行路径读（main → 每个分支 → 实际调用），死代码是干扰**。
2. **processed.log 正反斜杠不匹配是第一遍没抓到的根因**——我最初归因为"limit 逻辑/多次运行"，实际是路径规范化问题（glob 正斜杠 vs Path 反斜杠）。为什么漏掉？凭"字符串应该一样"的直觉，没实测比较。**路径比较必须规范化（normcase），字符串相等不可信**（与 08-16 的"路径语义按运行时平台实测"同族）。
3. **LLM 失败静默降级覆盖**——wechat_knowledge.py --all 对已有好 case 直接覆盖成骨架，我是知识化后抽查 d9742461 才发现。为什么漏掉？LLM 总结是"成功预期"，失败路径没被设计为"保护旧资产"。**批处理脚本的失败分支 = 数据保护分支，必须先想好**。

## 顿悟

1. **"调研结论→工程实现"的落差是断链之源**——R 型报告说"MITM 嗅探下载最稳"，代码里对应函数是死代码；报告说"链接可解析下载"，实际公共 Worker 已失效。**案头调研给出的是"决策矩阵"，工程落地要选"用户可执行的那条"**——res-downloader 播放即下载是用户零操作的，元宝扫码要用户建登录态，TikHub 要 token——按用户操作成本排序选型。
2. **楚门"偶遇自动采集"的 KDO 版本质 = 把"用户动作"降到最低**——楚门：点收藏/扔给超级入口→两分钟出逐字稿；KDO 版：手机转发链接→PC 打开播放→res-downloader 嗅探→管线转写→知识化。**每个用户动作都是断链点，设计时数一下用户要动几次手**。
3. **恢复会话的产出可以是"修用户卡点"而不只是"校准记忆"**——08-15 先例是零基建纯校准，本次把恢复直接续上了用户重启前的工作（用户说"你继续把顶层文档搞清楚"），恢复和干活无缝衔接。
