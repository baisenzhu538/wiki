## 差异栏

与上次复盘（08-30 战略笃定篇三单连续生产）的差异：
1. **任务性质变了**：上次是纯生产（按任务书产卡提审），本次是**运维诊断 + 基建修复 + 调研生产**三混合——老朱直令从"产卡"扩展到"查 bot 为什么慢/为什么还去 WSL/检查工作流/提取命名规则做全网调研"，运维类任务占比首次超过生产类。
2. **复发模式被实证**：上次复盘的"队列数字要紧邻重跑"（E013）在本次升级为"**文档声称的架构也要实证**"——管线文档说"WSL GPU 转写"且 02:08 还成功过，实际 wsl.exe 已间歇僵死，差点把整个采集管线判为"正常"。
3. **被打破的假设**：我以为"bot 变慢"的根因只有 skill 里记的"会话膨胀+压缩卡死"一种模式，本次实证出第二种——**全新会话（history=0）也会因工具挂死导致 turn 悬死**，且诊断签名完全不同（end_reason=NULL + last_activity 冻结 vs 压缩日志刷屏）。
4. **新视角**：老朱问"WSL 都废除了为什么还去 WSL"——这不是新问题，是**环境迁移后的残留依赖审计缺失**。迁移只迁了 bot 进程，没迁 bot 依赖的工具链。这类"迁移盲区"以后每个迁移动作都要配 grep 全量扫描。

## 思维盲点

1. **环境迁移残留依赖盲区**：五绝迁 Windows 时没人扫"还有谁在调 wsl.exe"——管线脚本、sync 脚本里的 wsl 调用全成了定时炸弹。为什么漏掉：迁移被框定为"bot 进程搬家"，工具链依赖不在任务边界内；且 02:08 转写还成功过一次，"最近成功过"掩盖了"间歇性僵死"的真相——**间歇性故障比持续性故障更难被发现**。
2. **诊断模式单一化**：skill 里只记了一种慢的模式（会话膨胀），我一开始也顺着老模式查，直到发现 history=0 才切换思路。为什么漏掉：skill 是按"最常见根因"组织的，缺一个"模式不匹配时的排除清单"；单模式记忆导致确认偏误——先入为主找膨胀证据。
3. **月白卡片信任度分层没提前做**：一开始把 7 张卡等同看待，读到第 5 张才发现有 draft 卡 definition_of_done 全是 src_unknown。为什么漏掉：没有先扫一遍 status 字段再决定证据权重，提取类任务应先做"证据分层"（reviewed>draft，一手口述>卡片转述）再开工。

## 顿悟

**"迁移"不是搬进程，是搬整套依赖闭包——这推翻了我过去一直以为的"迁移=把服务跑起来就完事"。** 以前认为迁移的验收标准是"新环境能跑"，本次实证：五绝 bot 迁 Windows 只迁了 gateway 进程和配置，但 bot 干活时调用的 kdo-tools 里还有 wsl.exe 硬编码调用（转写、MCP 同步）。进程迁了、依赖没迁，等于人搬了家但钥匙还留在旧房子里——平时没事，某天要开门时才发现开不了。迁移的真正验收标准应是：grep 全量扫描旧环境依赖 + 逐个改写 + 真实验证，三步缺一不可——旧认知"能跑=迁完"是误区。

## 元反思

下次不同的三件事：
1. **诊断先对模式再动手**：遇到 bot 慢/卡，第一步不是套已知模式，而是先采集三种签名（history 大小、压缩日志有无、last_activity 是否冻结）分型，再走对应修复路径——分型错，修复全错。
2. **迁移类任务自带审计动作**：凡涉及"XX 已迁移/废除"的语境，主动 grep 旧环境关键字（如 wsl），把残留清单报给老朱，不等出事。
3. **提取类任务先做证据分层**：先扫所有候选来源的 status/来源等级（reviewed/draft/一手/二手），排好序再逐字读，避免读到一半才发现权重错。

### 对照实验

- **无人（无老朱）**：王语嫣卡死会触发重启，但"WSL 废除为什么还去 WSL"这个定性不会出现——大概率修好 WSL 通道继续用，废墟上加固，下次再挂再修。老朱的"方向性问题"（废除 WSL）是把技术修复升级为架构治理的关键输入。
- **无老顽童（无 AI）**：gateway 日志几万行、state.db 无文档、管线脚本散在 kdo-tools——人工定位 turn 悬死签名需要小时级；本次从下令到修复完成约 40 分钟。
- **合在一起**：老朱给方向和优先级（废除 WSL/检查工作流/报告放桌面），老顽童给执行和验证——双向闭环，单边都不成立。
