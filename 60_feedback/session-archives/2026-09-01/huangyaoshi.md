## 思维盲点

1. **一开始低估了 event.db 的信息量**：第一棒只看了日志文件，把「本地云端删除记录镜像」理解成日志 grep；实际上坚果云的 SQLite event.db 才是结构化全史（每条含 opType/编辑者/删除标记/base64 路径）。为什么漏掉：惯性思维把「日志排查」等同于「文本日志文件 grep」，没有先探 DB schema 就下「本地能查的都查了」的结论。修正：查证据源先 list 表结构再定查法。
2. **假设「计划任务全量排除」=「调度器全排除」**：第一棒排除了 Windows 计划任务就收了，但本机还有 Hermes profile cron 这一独立调度层（11 个 profile），直到本棒才补扫。为什么漏掉：调度面在脑内默认= schtasks，忘了本厂自己就运营着另一套 cron 基础设施。修正：排查清单按「调度器家族」穷举（schtasks/Hermes cron/KDO 时钟/CLI 内 cron），不按「最常见」。
3. **bat 脚本 first-run 就该在无 TTY 场景测**：for /f 引号吞噬问题在交互 cmd 里测不出来，第一次实跑直接 FAIL。为什么漏掉：写了脚本就跑，没有先想「计划任务运行环境=非交互」。修正：给计划任务写的脚本，交付前一律用 schtasks /run 链路验证，不只前台跑。

## 顿悟

1. **「静默」本身是证据**：坚果云主日志在事故窗口两小时空档、event.db 零事件——阴性证据排除了嫌疑人，比阳性证据更有收敛力。排查报告应该明确给「阴性证据」留章节（本报告三节排除清单就是这么组织的），而不是只堆找到的东西。
2. **git 仓的 .git 目录结构本身就是防篡改指纹**：objects/info mtime 新建+commit-graph 老文件=「目录级重建但未重扫」的操作痕迹；只有 objects 幸存=操作者懂 plumbing。以后所有事故排查都应该第一步看 .git 内部 mtime 分布，这是比 USN 更持久的物证（USN 会被覆盖，mtime 不会）。
