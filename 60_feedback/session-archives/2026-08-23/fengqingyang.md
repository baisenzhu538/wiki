## 思维盲点
> ≥1条：什么被漏掉了？每条追问「为什么漏掉」。

1. **「建设好了」第一眼差点停手**——看到 A/B 库存在 + verify PASS 时，表面证据已足够下「可恢复」结论，但我继续挖 schtasks/#434 才发现「没在用了」。**为什么漏**：完成类声明的表面证据（库在+verify 过）容易让人停手；真正判断「能不能用」要查数据流（谁在写）+ 自动化（谁在跑）。固化为「完成声明拆三问：壳在/数据流/自动化」。
2. **编码坑**——PowerShell 管道喂 Python 写中文被吞成 `?`，导致执行报告第一次被 F-034 拦。**为什么漏**：默认「管道传输不改内容」，没意识到 $OutputEncoding 默认 ASCII。固化为「写中文文件用 .NET File IO UTF-8，禁管道喂 Python」。

## 顿悟
> ≥1条：什么基础认知被推翻了？

1. 负向判词天然易错（判「有」找一处、判「没有」穷尽），所以解法不是「更小心」，是「把负向断言从结论降级成需举证的过程」——这也是门禁必须「只验锚点存在、不判质量」的原因。
2. 「建设好了 ≠ 在用了」：审计基建要区分「壳存在」和「数据流在跑」，二者之间隔着 #434 和计划任务。
3. 「被门禁拦不是丢脸，是系统在替我兜底」——F-034 实拦我一次，正面实证「想犯错也犯不了」不是口号。

## 元反思
> 下次怎么做才能不一样？

1. 审计「完成」类声明必拆三问：壳在不在（文件/库存在）、数据在不在流（谁在写）、自动化在不在跑（计划任务/挂钩），不停在①。
2. Windows 写中文文件用 .NET File IO UTF-8 no-BOM，禁管道喂 Python（$OutputEncoding 坑）。
3. 负向判词用三段式（存在性核查 + 未发现/确认缺失分级 + 反向清单）——#433 落地后，我审计也用它。
4. 建议书/审计报告写完即 conveyor_probe 自登，不欠登记债。
