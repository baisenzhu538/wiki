## 思维盲点
1. **写了「幂等：先清空」注释却没写实现**——为什么漏掉：我把「意图写清楚了」当成了「行为正确」，probe→full 两步走时重复入库。狗粮测试的最大讽刺：测别人工具的坑，先踩了自己的坑。教训：**注释不是代码，带破坏性语义（清库）的注释必须立即兑现为断言或实现**。

3. **域知识检索审视（10.4.1 A 级要求）**：本次对 wiki 的检索很充分（kdo query 即对照组、30_wiki 抽样、production-queue 查惯例、agent-os.md 查复盘格式），并发现了训练记忆里没有的事实：kdo query 对「frontmatter id 直查」这个动作基本失能（前 30 名都捞不到目标卡），纠正了「kdo query 是万能检索入口」的错误认知。

## 顿悟
1. **「省 token」的杠杆点不在检索引擎，在注入策略**——以前以为「用带压缩层的记忆引擎」是省 token 的抓手，实测推翻：同一查询，k=5 全文注入 25,637 tok vs 标题路由 146 tok，差 175 倍；而 compress_text 这种「文本压缩」只省 5.4%。此前（包括王语嫣初测）都在问「这个工具能压多少」，正确的问题是「LLM 真正需要读多少」。检索器的价值=排序能力，不是摘要能力。
2. **「80% 压缩」的适用边界**：论文数字在「对话轮次语料」（大量语气词/客套话）上成立，到「知识卡片语料」（信息密度极高、零废话）就失效——**任何压缩率数字都必须绑定语料类型，跨语料外推=自欺**。
3. **CLI 冷启动也是延迟**：kdo 查询 1253ms 里 235ms 是 Python CLI 启动，占净检索延迟的 24%——对比进程内引擎（mnemo 102ms）时，「检索算法快慢」和「调用方式成本」必须分开归因。
