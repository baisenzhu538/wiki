## 思维盲点

1. **交付物未 commit 就提审（最大盲点，吃了 FAIL）**：我心里的"完成"=代码改完+测试过；但 #362 的规则是"修复未提交=不存在"。为什么漏：我把 commit 当成"需用户授权的附加动作"（git 纪律），但代码类任务的交付标准已是"commit 才算存在"——授权应该批在任务级，不是 commit 级。**教训：代码类交付物的完成定义含 commit；提审前双仓 git status 自查，应该自查先发现，而不是等门禁拦。**
2. **我自己写的 U+FFFD 字面量被自己的输出通道吞掉（两次）**：Write 和 Edit 内容里的 U+FFFD 字符在传输中丢失，`"" in title` 恒真差点上线。为什么漏：相信"我写的就是落盘的"，没有读回验证。**教训：涉及不可见字符的检测代码必须用转义写法（`"\ufffd"`），且写后用 od/字节级读回验证。**
3. **正则字符类凭直觉写**：`[À-ÿ]{2,}` 不匹配真实 mojibake（µ‹ 等 continuation-byte 字符在 À 之下），反向测试夹具才逼出来。**教训：检测规则要由真实失败样本驱动——先拿样本测规则，不是拿规则想象样本。**
4. **`except: pass` 是 bug 温床**：`import os` 缺失潜伏多月无人知，因为 NameError 被"include on parse error"静默吞掉——过滤器从未生效却看起来正常。**教训：防御性 except 至少要有计数/日志，否则失效完全不可见；对"门禁/过滤"类代码，静默通过 = 事故。**

## 顿悟

1. **门禁的有效性 = 声明的完整性**：#363 门禁只查 code_files 声明范围——声明不全就漏检；`KDO仓:` 前缀形态还会路由错仓 fail-open 假通过。门禁不是写了就有效，**输入格式本身就是攻击面**。
2. **"修复未提交=不存在"**：工作区的代码只是意图，仓库里的代码才是现实。三问①的本质是以版本控制为唯一真相源。
3. **修 bug 要过整条数据路径**：import os 是根因，但修完根因立刻暴露下游语义缺陷（无 frontmatter 误杀素材层）。真正的修复 = 根因 + 整条路径在真实数据形态下正确。
4. **裁定可以改判，实证不会浪费**：B→A 改判推翻的是方案，但 B 方案期做的实证（75% 污染率、draft 同权检索）全部成为 A 方案的设计输入。
