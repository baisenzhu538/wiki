## 思维盲点

1. **bash 变量拼 Windows 路径混读错文件**——`r'$P\config.yaml'`（bash 风格 + 反斜杠拼接）读到了错误文件，一度以为 duanwangye config 仍是 launcher 形态、与 sync 幂等声明矛盾；用硬编码 Windows 路径 grep 原文后真相大白（模板形态无误）。**为什么漏**：Unix 路径拼接惯性直接套进 Windows Python——O-11"验证方法决定结论"的又一次实证，且是我第一次在验证路径构造上栽。

3. **报告结构整齐时验证惯性下降**——#350 报告写"3 文件同款修复"，我验了前两个文件与报告一致后，对第三个文件（openmontage）的验证靠 git diff 才逮到 stdout reconfigure；#351 报告"beikai 同批收口已完成"先入为主，直到 grep beikai config 才发现未收口。**为什么漏**：报告的结构化表格和"同款/已收口"措辞制造了完整性假象——"同款"是概括，逐文件验证才是事实。

## 顿悟

1. **部署类报告的"全量/同款/已收口"声明是最新高危验证点**——今天 4 单每单都逮到一个不实/不精确声明：243 vs 244（口径）、openmontage stdout（代码与报告不符）、beikai 未收口（覆盖遗漏）、review_date 偏一天（脚本元数据）——部署类报告的断言密度高、验证成本低（grep/config 原文/进程），**每一句"已完成 X"都值得一次 grep**。
