## 思维盲点
> ≥1条：什么被漏掉了？每条追问"为什么漏掉"。

1. **盲点：先入为主地认为 kdo query 可用。**
   - 为什么漏掉：角色 context 和 README 都推荐使用 `kdo query`，我没有先验证工具状态就直接用，结果返回乱码和空结果，浪费一次查询。
   - 应改为：先跑一个简单查询验证输出是否正常，异常时立即切换为 `Glob`/`Grep` 手工核查，并把工具异常记录到任务单或诊断报告中。

2. **盲点：诊断初期对「利润/定价」域与 KDO 现有方法论的同构关系挖得不够深。**
   - 为什么漏掉：一开始只想到与「单元模型」「需求冰山」桥接，后来才补全到「客户分层」「促销策略」「风控」等域。说明跨域扫描时仍依赖线性联想，没有系统过一遍域索引。
   - 应改为：诊断前先 Read `30_wiki/personal-os/zhu-domain-index.md` 与 `.agent/kb-evolution-direction.md`，按域清单逐一对照，而不是凭记忆。

3. **盲点：口述稿只读了前 1000 行。**
   - 为什么漏掉：Read 工具有 1000 行限制，1606 行与 2898 行的两份口述稿都被截断。虽然拆书逐字稿和笔记已覆盖核心论点，但口述稿后半段可能有更多案例细节与暗知识。
   - 应改为：长口述稿先跑 `python kdo-tools/transcript-index.py build` 建索引，再按需精读；或分两次 Read 后半段，确保暗知识不遗漏。

## 顿悟
> ≥1条：什么基础认知被推翻了？

1. **wiki 查询工具在当前环境下并不可靠。** 角色 context 中把 `kdo query` 放在启动必做步骤里，但今天实际运行出现编码损坏与空结果。这说明「流程规定」不等于「当前可用」，Agent 必须对工具输出做真实性校验，不能盲目信任。

2. **「利润为王」不是简单的概念搬运，而是一个跨域桥接枢纽。** 它向上承接商业战略、向下连接定价/销售/产品/财务，与 KDO 已有的大量方法论（单元模型、需求冰山、客户分层、促销策略）都能产生真实链接。这意味着建好这张 framework 卡后，会反向激活多个已有域的 related 补全需求。

### 飞轮效应
> 本轮加速了哪个回路？

本轮主要加速的是**体系↔数据**回路：通过外部调研验证素材主张、通过 9 层深挖把零散观点压缩为可执行的决策框架，再把结论结构化进诊断报告与任务单。这会让后续老顽童生产时少返工、欧阳锋审查时有据可依。

同时，发现 `kdo query` 不可靠也激活了**审美↔场景**回路——以后启动诊断时会先校验工具状态，这个判断会沉淀进王语嫣的工作方法。

- 合在一起：约 30-40 分钟完成素材读取、调研、诊断、入队，质量达到可提交老顽童生产的标准。
