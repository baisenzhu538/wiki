# 负向判词证据层门禁建议书

> 触发：老朱 2026-08-23 追问——「为什么都是不核对就下判断？有办法解决吗？」并拍板「写建议书」。
> 定位：观察者建议书（B2-2① 只交王语嫣）。**我只出方案与口径，不写门禁代码、不动生产队列、不产卡**——代码归黄药师、编排归王语嫣、终审归欧阳锋。

## 0. 一句话结论

「不核对就下判断」不是态度问题，是**「负向判词（说某物缺失/不足）天然比正向判词更容易错、且系统只治了交付端没治审查端」**的结构性问题。解法两层：**治本**把负向判词从「结论」降级成「需举证的过程」；**治标**在 F-035 上追加一个机读锚点，把 F-034 的门禁思路从交付端复制到审查端。两层配套，缺一复发。

## 1. 三个实证（不是孤例，是全厂同族）

| 编号 | 当事人 | 判词 | 实际 | 错在哪 |
|:--|:--|:--|:--|:--|
| #430 | 欧阳锋 | 「无远程备份（本地单点容灾缺口）」 | agent复盘 已在坚果云同步范围（进程 + 配置 + 用户确认） | 断言「缺失」前未查云同步形态 |
| FQ-E04 | 风清扬 | 「欧阳锋卡住」 | 老朱说「恢复了」 | 只查文件层就下实时状态判词，未标注证据层 |
| FQ-E01 | 风清扬 | 「#427 待终审」 | 已 reviewed（快照 23:20 vs 终审 23:41） | 未拉最新 git/队列就汇报状态 |

三例同族：**「我没看到」被说成了「没有」**。其中 #430 与 FQ-E04 是完全同型（判词前未标注证据层），FQ-E01 是相邻型（状态未拉最新）。

## 2. 根因（四条，决定了解法方向）

1. **负向判断的成本不对称**：判「有」只要找到一处就成立；判「没有」必须穷尽所有来源才成立。大脑默认偷懒，用「我没看到」替代「不存在」。
2. **判词没拆证据层**：一句「无远程备份」实际打包两个命题——「在我查过的范围内没看到」（可验证的事实）+「因此全系统不存在」（不可证的推断）。我们习惯把推断当事实说。
3. **终审的角色压力**：终审职责是「找缺口」，漏报恐惧 > 误报恐惧，于是「疑点」加速变成「缺陷」。
4. **事实是分布式的**：git（本地）、坚果云（云端）、进程、配置、多设备——审查者的观察窗口永远小于负向断言要覆盖的范围。

推论：**光靠「以后小心」治不好**，因为 1/3/4 是结构性压力，不是态度。必须用机制把「没证据的缺失断言」变成「过不去的那道门」。

## 3. 方案

### 3.1 治本（语言层，当天生效，零基建）：负向判词三段式 + 结论分级 + 反向清单

终审意见书（及一切审计判词）凡要说「无 / 缺 / 未 / 不存在 / 没有」，必须走三段式：

```
**存在性核查**：
- 我查过的形态：[本地 git / 云同步 / 进程 / 配置 / 目录 / 多设备 / bundle / 归档] 逐项 ✓✗
- 结论等级：未发现（默认，弱）/ 确认缺失（强，需清单全查过且全 ✗）
- 反向提问：它还可能以哪些我没查的形式存在？
```

两条硬规则：
- **默认只许说「未发现」，不许说「确认缺失」**。「确认缺失」必须清单全查过且全 ✗，否则只能落「未发现」。
- **下判词前先做「反向存在性提问」**：把可能的存在形态先列全，再对照我查了哪些。没列的维度 = 不许下「确认缺失」。

> 关键：#430 欧阳锋只要查「坚果云」这一个维度就会翻案。所以更值钱的动作不是「查得更认真」，而是**先把存在形态清单列全**——它逼出「坚果云同步」这个没被想到的维度。

### 3.2 治标（机械层，黄药师小改）：F-035 追加一个机读锚点

- 位置：`90_control/scripts/queue_transition.py` 的 review 门禁（F-035 现有 `_check_review_record` 旁）。
- 规则：终审意见书正文若含负向断言词（`无` / `缺` / `不存在` / `没有` / `未备份` / `未同步` 等，词表实现时定），必须同时含 `**存在性核查**` 标记，否则 review 不闭环。
- 原则：与 F-034 完全同款——**只验标记存在性，不判核查质量**（拦机械项，不碰判断）。
- 成本：几十行内，复用 F-034 的「锚点存在性」函数。

### 3.3 诚实的边界（必须写进验收，否则门禁给人假安全感）

门禁只能拦「**没标证据**」，拦不住「**标错证据 / 漏了维度**」——欧阳锋这次恰恰是根本没意识到「坚果云同步」这个维度。所以：
- 3.1 的「反向存在性清单」才是治漏维度的主力；
- 3.2 的门禁是兜底，保证「至少写了核查」；
- **两条缺一不可**：只有 3.1 靠自觉会复发（已复发三例）；只有 3.2 会变成「走过场写个空核查节」。

## 4. 存在性核查六查（口径，供 3.1 复用）

负向判词前默认要过一遍的形态清单（审计者定口径，实现时可按场景裁剪）：

| 序 | 形态 | 查法示例 |
|:--|:--|:--|
| 1 | 本地 git 仓 | `git -C <path> rev-parse --show-toplevel`（含独立/嵌套仓） |
| 2 | 云端同步 | 坚果云/OneDrive/飞书云盘 的进程 + 配置 + 同步范围 |
| 3 | 运行进程 | `Get-Process` / tasklist（守护/同步/备份进程） |
| 4 | 配置/注册 | schtasks / 服务 / 开机项 / registry |
| 5 | 目录/文件实存 | `Test-Path` / ls（区分「逻辑登记」与「物理存在」） |
| 6 | 其他介质/多设备 | D 盘镜像 / bundle / 归档 / 历史提交 |
