# 外部基础设施审计洞察与治理建议

## 0. 一句话结论

**KDO 是一台真实运转的活工厂**（2026-09-02 当天 #613 仍在终审流转、通知矩阵 24 类事件 × 10min 探针覆盖扎实），骨架层（目录拓扑 / metadata / 门禁 / 失败模式库）已工业级；但压着**两颗定时炸弹**——C 盘 95% 满（剩 18G）与检索索引膨胀 ~200 倍——**两件事都已诊断、都有现成方案（F-010 等），都躺在停车场等拍板**。缺的不是方案，是决策。

## 2. 六大洞察与对应建议

### 洞察 1｜容量是"一次挂全部"级风险（P0）
C 盘 **95% 已用、仅剩 ~18G**，且无全盘容量监控项。三面夹击：Win11 升级 + 知识库持续增长 + search_index 膨胀。
→ **建议 A**：立即立项容量治理专项。第一动作只做**只读扫描出清单**（大文件/临时目录/旧日志按大小排序），清单给老板过目后再动手，不直接清理。

### 洞察 2｜检索索引膨胀失控，是 MCP 300s 卡死元凶（P0）
`.kdo/search_index.json` 实测 **570MB**（6 月末仅 ~2.8MB，膨胀 ~200 倍）。已记录为 F-010 的瘦身方案（只存行号不嵌原文）**躺停车场约 3 个月**。
→ **建议 B**：F-010 出停车场立项。**修这一个同时解 MCP 卡死 + 释放容量两题**，性价比最高。

### 洞察 3｜治理复杂度逼近人脑极限（P1）
E/F/P/O/R/# 六套编号并存，**撞号事故已发生 3 起**；摩擦日志 60+ 条中占比最大的不是逻辑错，而是"门禁 vs 书写习惯"不匹配（E040 反复出现、误拦 5 次）。
→ **建议 C**：编号体系收敛 + 门禁误拦清单复盘。建议由王语嫣牵头做一次"摩擦根因分层"，把「真违规」与「门禁误伤」分开处理。

### 洞察 4｜双单点：黄药师 + 欧阳锋缺席即全厂停摆（P1）
黄药师 = 基建唯一维护人、欧阳锋 = 审查唯一节点。F-055 降档机制已拍板红线但**未实施**。
→ **建议 D**：F-055 从"已拍板"落地为"已实施"，先做最小可行降档路径（缺人时降档不停线）。

### 洞察 5｜自动化在加、成本在涨（P1）
门铃机制实测约 **264M tokens/日、99% 缓存读、峰值 ~50 元/小时**。F-062 降本杠杆（夜间降频 + 省读文案）待拍板。
→ **建议 E**：F-062 执行夜间降频 + 省读文案，一周后对比 token 用量曲线出效果报告。

### 洞察 6｜基建对外不可及（P2，外部视角自证）
本次审计中，外部 agent 只能靠 grep 文件名碰运气定位资产，无结构化入口。F-052/053 早记录过同一实证。
→ **建议 F**：把 `kdo query` 对受信外部 agent 开放为只读通道（配套"外部协同"定位的基建），消除外部接入摩擦。
