# KDO agent 体系·5 吸收点改进路线图

> 排除：吸收点2（部门化组织，老朱暂不需要）。
> 性质：建议书（王语嫣产，老朱拍板后立项，D4 自改/agent spec 改动走任务制）。
> 与前轮"产物级 DAG 升级 F-047"9层方案同源（都是 result_id 机制）——本件是其在 agent 层的扩展，可合并统一落地。


## 第一批·打底（改进1 + 改进2）

### 改进1：公共参数契约（吸收点4）
- **现状**：业务 agent SOUL 各自定义，无统一接口；新 agent 生成靠模仿旧 SOUL。
- **改进**：定义 KDO 应用层 agent 公共参数契约（4 字段）：
  - `user_context`（用户上下文：身份/目标/已知信息）
  - `scenario_override`（场景维度：行业/规模/角色，按 agent 定轴）
  - `upstream_result_ids`（上游产物 id 列表，软依赖，可选）
  - `output_format`（结构化模板 / 对话文本，按产出类型定）
- **落点**：`agent-os.md` 新增「§应用层 agent 公共契约」节（与 §13 双实例分层并列），charter §2.6 引用。**改 agent-os/spec 走任务制 + 老朱拍板**。
- **谁做**：王语嫣起草契约 → 老朱拍板字段集 → 黄药师落 spec + #263 流水线加"公共契约校验"Step
- **拍板项**：公共参数 4 字段是否够（是否加 `space_id` 做 agent 隔离）
- **难度**：中（契约设计 + 流水线加 Step，黄药师 1 单）

### 改进2：结构化产出（吸收点5）
- **现状**：业务 agent 产出=飞书对话文本，下游 agent 无法机读消费。
- **改进**：业务 agent **关键产出**落结构化交付物模板（复用 #307 6 模板机制），不只对话文本。
  - 关键产出定义：用户画像 / 团队诊断 / 调研结果 / 能力评估（4 类，不全做）
  - 每类产结构化模板（frontmatter + 字段集），落 vault 文件，带 `result_id`
  - result_id 落 vault frontmatter（**不引入独立 DB**——前轮9层 L8 边界2 已定）
- **落点**：`40_outputs/capabilities/agents/<agent>/deliverables/` 加结构化模板；复用 #307 交付物模板机制
- **谁做**：王语嫣定义"哪些产出需结构化"+ 老顽童产模板 + 黄药师加 result_id 索引（state.sqlite/search_index 按 result_id 查）
- **拍板项**：4 类关键产出是否对（是否增减）；result_id 命名规范（建议 `<output_kind>_<YYYYMMDD>_<short>`）
- **难度**：中（4 模板 + 索引验证，黄药师+老顽童 1-2 单）

> **第一批产出 = result_id 机制打底**（公共契约 + 结构化产出）。这同时也是前轮9层方案 F-047 任务级升级的 agent 层对应——**第一批可与 F-047 任务级 result_id 合并一个统一单**（任务单 + 业务 agent 产出都用同一 result_id 机制）。

## 第二批·核心（改进3）

### 改进3：agent 间产物复用链（吸收点1）——最有价值
- **现状**：业务 agent 各干各的，产出不复用（教练助理画像开会助理不知；调研Partner 结果销售参谋不消费）。
- **改进**：业务 agent 间 result_id 串联，下游 SOUL 加"取上游 result_id → kdo_search 按 result_id 查 → 消费"检索指令。
- **复用场景定义**（试点 2 个验证）：
  - 场景A：用户画像复用——调研Partner/教练助理产出"用户画像 result_id" → 喂开会助理（参会人分析）/ 销售参谋（客户画像）
  - 场景B：能力诊断复用——AI基本功教练产出"能力诊断 result_id" → 喂调研Partner（调研方向参考能力缺口）
- **落点**：下游 agent SOUL 加 upstream_result_ids 检索指令；kdo_search 支持 result_id 查询（黄药师加）
- **谁做**：王语嫣定义复用场景 + 老朱拍板复用边界（隐私/跨 agent 共享）+ 黄药师改下游 SOUL + 真机冒烟
- **拍板项**：哪些 agent 产出可跨 agent 共享（用户隐私边界）；试点 2 场景是否对
- **难度**：高（SOUL 改 + kdo_search 扩 + 真机冒烟，黄药师 2-3 单）
- **依赖**：第一批（公共契约+结构化产出）必须先完成

## 第三批·增强（改进4 + 改进5，独立可并行）

### 改进4：场景自适应（吸收点3）
- **现状**：业务 agent 通用（开会助理不区分创业团队 vs 大厂；销售参谋不分 2B/2C）。
- **改进**：业务 agent SOUL 加 override 机制——对话启动识别场景维度（行业/规模/角色），按维度调知识卡子集。
  - 每 agent 定场景维度轴：开会助理（团队规模/会议类型/行业）；销售参谋（2B/2C/行业）；教练助理（管理者层级）
  - SOUL 加"启动识别 scenario_override → 按维度调卡子集"
- **落点**：各业务 agent SOUL 加 override 节；scenario_override 维度轴落 agent spec
- **谁做**：王语嫣定义每 agent 维度轴 + 黄药师改 SOUL
- **拍板项**：每 agent 的场景维度轴（4-6 个 agent 各定轴）
- **难度**：中（每 agent 1 维度轴节，可分批改 SOUL）
- **独立**：不依赖第一批（可并行先做，但要与公共契约 scenario_override 字段对齐）

### 改进5：MANIFEST 门禁链（吸收点6）
- **现状**：业务 agent 产出无强制审查链（产出直接飞书对话，不走欧阳锋审）。
- **改进**：业务 agent **对外正式交付物**加"审查→发布"强制链。
  - 仅对"对外正式交付物"加门禁（日常对话不拦，避免过度门禁）
  - 复用欧阳锋终审 + #421 探针通知 + REVIEW-PENDING 登记
  - 强制链：业务 agent 产出 → 提审（自动登记 REVIEW-PENDING + 探针通知欧阳锋）→ 终审 → 可对外
- **落点**：charter §3 门禁节加"应用层 agent 对外交付门禁"；复用 #421/#429 既有门禁基建
- **谁做**：王语嫣定义"哪些是对外正式交付物"+ 欧阳锋审 + 黄药师接探针
- **拍板项**：哪些业务 agent 产出算"对外正式交付物"（边界——日常对话不拦，正式报告/方案拦）
- **难度**：低（复用既有 #421/#429 基建，主要是定义边界）
- **独立**：不依赖第一批（可并行）

## 落地建议

**合并统一 result_id 落地方案**：第一批（改进1+2）= 前轮9层 F-047 任务级 result_id 的 agent 层扩展。建议合并成一个统一单「KDO result_id 机制（任务级 + agent 级统一）」——一份契约、一套索引、两层应用（任务单 frontmatter + 业务 agent 产出）。

**执行顺序**（若老朱拍板）：
1. **先立统一 result_id 机制单**（合并第一批 + 前轮9层）→ 黄药师（排队，当前 3 单在队）
2. **第二批改进3**（产物复用链）→ 依赖 1 完成，试点 2 场景
3. **第三批改进4+5**（并行，独立）→ 可与 1/2 并行起步

**估算**：第一批 1-2 单（黄药师）+ 第二批 2-3 单（黄药师）+ 第三批 2-3 单 = 共 5-8 单，跨 2-3 轮会话。不抢当前基建线（#479 #426 线优先）。

**风险（前轮9层已识别）**：
- F4 result_id 持久化——用"落 vault + 复用现有索引"绕开独立 DB，需验证 state.sqlite/search_index 按 result_id 查命中率
- F7 产物 vs 任务混淆——result_id 绑产物文件不绑任务状态（已解）
- agent SOUL 改动=D4 自改——需老朱批准（禁止清单第15条）
