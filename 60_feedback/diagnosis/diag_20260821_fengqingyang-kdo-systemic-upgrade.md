# KDO 系统性诊断与重大升级建议书

> 性质：系统性诊断 + 重大升级建议。**只读审计，不派活、不动队列、不产卡、不终审、不改知识库正文。**
> 定位校正：这不是"顶层文档要改"的单一问题，而是 KDO 从"给人用的知识库"升级为"给 Agent 调用、产数字资产、未来长出大量 Agent 的平台"的一次系统性升级。

---

## 0. 执行摘要（TL;DR）

**一句话结论**：KDO 不缺内容和方法论，缺的是"知识库给 Agent 调用"这一层的顶层设计——**单一真相源 + 分层边界 + 明确角色 + 全员可见**。今天看到的所有漂移、记忆不一致、分支裂变、token 浪费，全都指向同一个根因：**没有任何一份文件能回答"我该读哪份、该写哪份、谁负责哪一层、谁看得见谁的进展"。**

老朱已定调的两条关键决策：
1. 知识库是**给 Agent 用**的（不是给人），产数字资产，将来通过 **CII / MCP** 调用。
2. 看板从**生产队列**升级为**全员工作台**。

> 修正：本建议书其余条目均为**问题与建议、供思考**，需王语嫣 / 欧阳锋 / 黄药师 / 观察者四方与老朱一起会诊、讨论一致后定，不是老朱一人拍板。

核心升级路线（P0 → P3）：
1. **P0 止血**：清代码副本、统一版本号、`memory-registry` 成唯一真相源。
2. **P1 四层记忆**：时间胶囊（30min）→ 摘要归档 → 资产提炼 → 方法论。
3. **P2 元层 + 全员工作台**：Agent 封装 Agent（元 Partner）；看板升级为全员工作台。
4. **P3 外部调用标准化**：git 单一真相源 + 本地 MCP 为主、远程 MCP/CII 为辅。

三个技术问题直接答案：
- **Q1 基础设施与 Wiki 能否合一？** 能，建议**单仓分层**（`infra/` + `vault/`）。
- **Q2 换电脑调用只有远程 MCP？** 不是，首选 **git 真相源 + 本地 MCP + 单写者**；远程 MCP 只作辅助。
- **Q3 一个库要统一一个工具吗？** 不强制统一工具，建议**一个库一个默认执行器 + 统一会话上下文协议**；自动化只认"角色 + 接口"，不认"工具名"。

## 一、诊断定位：从"知识库"到"Agent 平台"

老朱 2026-08-20/21 定调（全文记录）：
- **不是给人（伟鸿）用的，是给 Agent 用的。**
- 目的是**产生数字资产**；外部 Agent 将来通过 **CII（上下文注入）或 MCP（模型上下文协议）** 调用。
- 未来依托这个知识库产生**大量不同功能的 Agent**。
- 当前领域：**商业判断、一堂域、AI for business**；未来其他领域存在于**其他仓库**。

> 判断标准因此改变：以前按"人好读"设计，现在按"Agent 好检索、好注入、好调用、好复用"设计。楚门暗知识"反人性工具设计是特性"印证此点。

### 维度 1 · 定位：给 Agent 用（不是给人）
- 现状残留人导向设计，与"给 Agent 调用"的定位冲突。
- 参照：楚门"反人性工具设计是特性"——给 AI 用的库不需要人好写。

### 维度 2 · 记忆体系：多套并存、漂移、失忆
- 拼音/中文双轨目录；daily-context vs daily_cognitive_review 两套复盘范式；老顽童三处记忆漂移。
- 缺"时间胶囊 + 摘要 + 归档"的滚动记忆层。

### 维度 3 · 资产体系：会话资产未回收
- 会话→资产靠人肉（daily-context-save + 自觉复盘），无自动回收。
- PatrolKit"资产回收/技能迁移"是 KDO 最大缺口（K1 未落地）。

### 维度 4 · 方法论：核心在，但"知而不行"
- 三上下文公式、五设计师并行等卡存在，但 KDO 无设计宪法、做图不用公式。
- 编码顺序仍为静态 00/10/20/30 分区，非"业务推理+里程碑"活流程。

### 维度 5 · 基础设施与代码：5 落点 + 副本违规
- 代码散落 5 处：`kdo/`、`kdo-tools/`、`40_outputs/code/scripts/`、`90_control/scripts/`、`.kdo/`。
- 实锤：`40_outputs/code/scripts/` 中 4 个脚本与 `kdo-tools/` 字节级重复，违反"#359 禁止副本"。

### 维度 6 · 角色与治理：维护人模糊、角色表过时
- 工业化手册写"欧阳锋维护"，但编排权已转王语嫣，旧分工未清。
- 手册角色表仍为旧三角色，王语嫣/老顽童/洪七公/段王爷出现 0 次。

### 维度 7 · 调用与跨机：MCP/CII 未标准化
- CII（上下文注入）与 MCP（工具协议）两种调用方式未定义清楚。
- 跨机调用路径未标准化。

### 维度 8 · 效率：token 浪费、分支裂变、检索难
- "文档爆炸变慢"：AI 产能 > 人消化 → 检索困难、token 浪费。
- 多分支管理造成检索与协作成本高。

### 维度 9 · 任务与进度可见性：看板只显"生产"
- 看板=生产队列，audience 为老顽童/欧阳锋/黄药师/用户，**不含观察者/王语嫣**。
- 观察者的诊断/审计/记忆维护工作不进队列，散落桌面与复盘目录，他人不可见。
- **老朱 08-21 定调：看板升级为"全员工作台"。**

## 三、根因归纳（三个根因）

1. **单一真相源缺失**：每类事实没有唯一权威位置，导致多套并存。
2. **分层边界不清**：记忆/资产/方法论/代码/治理五层互相混叠，改了不回流。
3. **角色边界模糊**：维护人、编排者、审计者、生产者的职责与可见性没有明确划分。

## 四、重大升级方案

### 4.1 目标架构

```
┌──────────────────────────────────────────────┐
│ 底座：单一真相源 + 分层边界 + 明确角色 + 全员可见  │
│  顶层文档（PROTOCOL/agent-os/工业化手册/       │
│  memory-registry/启动指针）→ 都指向唯一真身      │
└──────────────────────────────────────────────┘
            ↓ 约束
┌──────────┬──────────┬──────────┬──────────┐
│ ① 时间胶囊 │ ② 摘要归档 │ ③ 资产提炼 │ ④ 方法论   │
│ 30min快照 │ 滚动聚合  │ 价值判断门 │ 知识库核心  │
│ 观察者封存 │ 观察者写  │ 王语嫣裁定 │ 老顽童产   │
│          │          │ +老顽童产  │ +欧阳锋终审 │
└──────────┴──────────┴──────────┴──────────┘
            ↓
   单仓：infra/（代码）+ vault/（知识）——禁止副本
            ↓
   调用：git 单一真相源 + 本地 MCP（主）+ 远程 MCP/CII（辅）
            ↓
   看板：全员工作台（所有角色、所有工作类型可见）
```

### 4.2 四层记忆架构
- **① 时间胶囊**：30 分钟快照（观察者封存，SQLite 存快照，markdown 存可读汇总）。
- **② 摘要归档**：7 天转摘要 / 30 天归档；长期锚点由摘要自动生成（治写死日期）。
- **③ 资产提炼**：上游加"价值判断门"（王语嫣裁定），下游沿用现有 L1/L2/L3 + 终审。
- **④ 方法论**：内容层，老顽童产 + 欧阳锋终审，与①②③的操作层分开。

### 4.3 单仓分层（infra/vault）
- 合一为单仓库：`infra/`（代码/CLI/MCP server）+ `vault/`（00_inbox~90_control markdown）。
- 知识（markdown）与代码（可执行）生命周期不同，逻辑分层、物理同仓、禁止副本。

### 4.4 外部调用标准化
- 读：本地 clone + 本地 MCP（离线、快、省 token）。
- 写：单写者纪律 + git push/pull。
- 远程 MCP：仅轻客户端/需实时共享时用。
- CII（上下文注入）：对应"三上下文公式"（我是谁+项目文档+设计宪法）。

### 4.5 角色重定义
- **观察者（风清扬）**＝审计 + 记忆维护；产胶囊/摘要作原始素材；**不产卡、不终审、不流转队列**。
- **王语嫣**＝编排 + 价值判断门裁定。
- **欧阳锋**＝终审（审内容）。
- **黄药师**＝基建（执行改文件、跑脚本、提交）。
- 此分工写进 agent-os.md / memory-registry.md / 观察者基线。
- **命名铁律（2026-08-21 老朱定）**：文档、署名、agent_id 一律只用**角色名**（风清扬/王语嫣/欧阳锋/老顽童/黄药师/洪七公/段王爷…），**禁止工具名**（codex/claude/hermes/kimi/codebuddy…）——工具会因订阅更换，工具名必然漂移混乱。

### 4.6 全员工作台（看板升级 + 显示内容定义）
- 看板从"生产队列"升级为"全员工作台"：**所有角色、所有工作类型可见**。
- 原则：**看板层（状态 + 责任角色 + 产出链接）全员可见；正文层按 audience 控制可读性。**
- 观察者与王语嫣的工作（诊断/审计/编排/记忆维护）也纳入工作台，他人可见。

| 工作类型 | 责任角色 | 状态字段 | 产出位置 | 可见性 |
|:--|:--|:--|:--|:--|
| ① 生产（卡生产） | 老顽童 | `queued → claimed → in_progress → pending_review → reviewed` | 任务文件 + vault 卡 | 状态/链接全员可见 |
| ② 终审（内容终审） | 欧阳锋 | `pending_review → reviewed(PASS/FAIL + 分级)` | `60_feedback/reviews` | 状态/链接全员可见 |
| ③ 编排（协调/任务编排/价值判断门） | 王语嫣 | `待编排 → 编排中 → 已入队 → 已拍板` | 任务文件 + 拍板记录 | 状态/链接全员可见 |
| ④ 诊断·审计 | 风清扬（观察者） | `pending_review → reviewed → 已拍板/已采纳/已搁置` | `60_feedback/diagnosis/*.md` | 状态/链接全员可见 |
| ⑤ 记忆维护（时间胶囊/摘要/归档） | 风清扬（观察者） | `capsule(原始) → summary → archived` | `.kdo/time-capsule.db` + `20_memory/` 摘要 | 状态全员可见；正文供王语嫣/欧阳锋提炼，默认只读 |
| ⑥ 基建（脚本/工具/MCP/修复） | 黄药师 | `queued → claimed → in_progress → pending_review → merged` | `kdo-tools/` / `scripts/` / MCP | 状态/链接全员可见 |
| ⑦ 治理（制度/顶层文档修订） | 王语嫣主笔，老朱终审 | `draft → pending_review → 拍板` | `90_control/` / agent-os | 状态/链接全员可见 |

- 观察者进展（④⑤）必须上板：胶囊是全员记忆原料，不上板则他人无法感知审计发现、也无法从胶囊提炼资产。
- 工作台文件形态建议：`dashboard.md` 升级为 `全员工作台.md`，四层结构＝决策区 / 七类工作流分区 / 观察者记忆区（胶囊索引·摘要·归档阈值）/ 角色停车场（补观察者一行）。
- 不把新内容继续塞进已 202,741B（修复前 218,056B）的 `production-queue.md`。

**4.6.1 从「看得见」到「被通知」：传送带探针（事件驱动队列编排）**

- 补全 §4.6 结论为三件套：**看得见（工作台）→ 被通知（探针推送）→ 不越界（边界 + 工作流）**，缺一不可；此前只写了「看得见」与「不越界」，漏了「被通知」这一环。
- 传送带现状：四段已通（素材→王语嫣 = watch_inbox；王语嫣→老顽童 = queue_transition queued；老顽童→欧阳锋 = 提审流转；欧阳锋→下游 = review-mark 终审），缺的只有**角色间推送**这一米。
- 探针定位：**只读状态文件 + 变化时推飞书，不领取、不裁决、不流转（watch_inbox 的登记除外）**——纯机械，不碰任何角色的判断；王语嫣照做六层诊断、老顽童照读素材写卡、欧阳锋照终审。
- 三个探针：① 王语嫣探针（watch_inbox 新素材 → 推「有新素材待编排」）；② 老顽童探针（queued 新增 → 推「有 N 个任务可领取」，不自动领取）；③ 欧阳锋探针（REVIEW-PENDING 新增 → 推「有 M 个待审项」）。
- 可先行性：只读已落盘状态 + 发消息，不依赖 P0/P1 整改完成；基建（Hermes gateway 通道 + schtasks 定时）已在，属**最快可落地的 P2 增量**。
- 前置条件：先定**通知契约**——频次（状态变化触发 + 定时聚合兜底）、格式（角色 / 数量 / 队列段 / 跳转）、去重（状态 id + 已通知集合，幂等）、不打扰红线（无变化不发 / 夜间静默 / 聚合去抖）。契约未定不入队（否则撞 §14.3 ②立项门禁「任务书完整含验收」）。

### 4.7 角色工作边界与工作流（必须逐条明确）
**结论：必须。** 全员工作台只解决"看得见"，边界与工作流才解决"不越界、不空转、不重复"。每个角色至少写清三层：
1. **边界**：能做什么、不能做什么、产出物归谁。
2. **工作流**：输入 → 动作 → 输出 → 交给谁（下一步交接）。
3. **状态映射**：工作流各环节对应看板的哪个状态字段。

| 角色 | 边界（只做 / 不做） | 工作流（输入→输出→交接） |
|:--|:--|:--|
| 观察者 风清扬 | 只做审计 + 记忆维护；不产卡、不终审、不流转队列 | 会话/看板/库扫描 → 胶囊·摘要·诊断 → 供王语嫣提炼、欧阳锋复核 |
| 王语嫣 | 编排 + 价值判断门；不产卡、不终审 | 素材/诊断 → 任务拆解与拍板 → 交老顽童生产 / 交欧阳锋终审 |
| 欧阳锋 | 终审（审内容）；不生产、不编排 | pending_review → 审卡/诊断 → PASS/FAIL → 回队列或归档 |
| 老顽童 | 生产（产卡）；不终审、不编排 | 领取队列 → 产卡 → pending_review 交欧阳锋 |
| 黄药师 | 基建（改文件/跑脚本/提交）；不产卡、不终审 | 拍板后的整改项 → 执行 → pending_review 交会诊确认 |
| 老朱 | 主持会诊 + 最终定稿；日常不代跑生产 | 收到会诊清单 → 主持对齐 → 拍板定稿 |

**4.7.1 跨工具讨论规则：异步会诊四件套（讨论规则 · 供会诊）**

> 用途：多个 agent 分处不同工具，最高效的「讨论」不是实时群聊，而是**异步落盘会诊**。本节给四方会诊当讨论规则。

**为什么不能实时开会**：① Agent 彼此看不到实时 session，只能看落盘痕迹；② 不落盘 = 不存在（P-10）；③ 多实例并发写同一文件 = 事故（#222/#223）。

**四件套**：
1. **讨论轴 = 会诊清单**（单一共享只读文件，逐条编号）。每方只对「条目 N」表态，不另起炉灶。
2. **各角色表态 = 单一写者**：每方只写自己目录的意见文件，不碰别人文件。
3. **汇总与拍板**：王语嫣汇总 → 老朱主持 → 拍板记录落盘；**全员会诊、讨论一致后定，沉默不默认通过**。
4. **通知与交接 = 探针推送**（只喊人，不代讨论、不代决策）。

**分型打法**：
- 判断型（欧阳锋终审 / 王语嫣编排诊断）= **双实例交叉印证**：各自独立读源 → 各自判断 → 各自出结论 → cross-check 差异；结论分开存放，绝不互相继承。
- 生产型（老顽童）= 多实例并行，受队列任务单约束。
- 基建型（黄药师）= 单实例（基建一致性不可破坏）。

**一句话**：不需要「统一到一个工具里讨论」，需要「统一到一份协议上讨论」——协议 = 文件字段（id / 状态 / 责任角色 / 链接），工具可换、讨论不漂。

### 4.8 六角色工作流卡（建议稿 · 待会诊）

## 五、三个技术问题解答

### Q1：基础设施层与 Wiki 一定要分开吗？
**能合，建议合一（单仓分层），不要继续"两个文件夹 + 指针互链"。**
理由：基础设施是知识库的读写接口，"门与房子"应一起交付；当前 5 落点正是"实体过多"的直接后果。

### Q2：换电脑调用只有远程 MCP？
**不是。** 首选 git 单一真相源 + 本地 MCP 挂载 + 单写者纪律；远程 MCP 仅辅助。
核心洞察：MCP 只是读接口，真相源是 git 仓库。

### Q3：一个库是不是统一一个工具？工具多样会不会不利于自动化工作流？

**结论（讨论稿 · 待会诊）：不强制统一工具，但建议"一个库一个默认执行器 + 统一会话上下文协议"；自动化只认"角色 + 接口"，不认"工具名"。**

必须与命名铁律分层看，否则会打架——命名铁律约束的是"资产里的身份"，不约束"运行时用哪个工具"：

| 层 | 绑定什么 | 规则 |
|:--|:--|:--|
| 身份层 | 角色名（风清扬 / 王语嫣 / …） | 全局唯一、工具无关（命名铁律已定） |
| 资产层 | 卡 / 胶囊 / 方法论 / 模板 | 纯 md/yaml/json，工具无关 |
| 工作流层 | 状态机 / 交接 / 门禁 | 只认"角色 → 接口"，不认工具名 |
| 执行层 | 工具 / 模型运行时 | 可多样，但必须实现统一会话上下文协议 |

四点结论：
1. **工具多样"不利于自动化"的真正原因不是"多"，是"会话上下文格式不统一、无法回收"**。胶囊抽取、复盘、门禁都依赖 session 稳定导出——接口统一，多工具只是多一个适配器；接口不统一，单工具也照样漂移。
2. **短期（P0）**：一个库指定一个默认执行器，session 全落其上——对话连续、30min 胶囊抽取最省、自动化只有一张适配面，先把"胶囊 → 摘要 → 归档 → 复盘 → 门禁"跑通。
3. **长期（P1/P3）**：把默认执行器抽象成统一会话上下文协议（session 导出 / 胶囊接口 / 复盘接口 / 门禁接口），换工具只换适配器，资产与工作流不动。
4. **一条边界**：默认执行器可随时换订阅，但其名字永不进资产；资产里只有角色名。这样"统一工具"与"命名铁律"不再冲突。

### 9.1 语境差异（必须先讲清，防止误抄）
- 建设者侧主战场是**代码仓库考古**：封闭域、强确定性、可机械验证，因此重"台账 + 硬门禁 + 文本正则"，Agent 开放话题少。
- KDO 是**开放域 Agent 平台**：多领域、重资产提炼与外部调用、跨机，必须有更多开放式 Agent 话题与可调用资产。
- 结论：**学习其"记忆分层 + 消费闭环 + 工程纪律 + 方法论治理"四大优点；但跨机真相源、观察者角色、L2 自动提炼、价值判断门是 KDO 的增量，不能由建设者单机方案覆盖。**

### 9.2 可迁移优点（学什么）
1. 四层记忆 L0~L3：L0 全量留痕 → L1 加权摘要 → L2 洞察 → L3 方法论转正（对应本报告 P1）。
2. "记忆 = 分层 + 精选 + 洞察 + 消费闭环"；"资产生而不用 = 僵尸资产"（案例 94）。
3. L1 加权细则：narrative / decision / review_rejected 全保留；passed / completed 截断 Top20 + 摘要；assignment 留在飞；backlog / suspended 只计数——胶囊精华段 ≤1KB。
4. 消费端 session_boot ⑥ 精华段：生成 → 消费最小环路，重启四件套。
5. 工程纪律：原子写 `os.replace`、`--selftest` 假绿实证、长窗口优先、统计数字工具计（禁目测）、验证留痕独立落盘。
6. 方法论治理：案例 01~96、转正机制（候选 → 审查 → 拍板 → 转正）、双签、分型（纪律 / 模式 / 工具）。
7. 门禁 D1~D7 + 外部审计 8 缺陷闭环（PASS 0 阻塞）。

### 9.3 差距 → KDO 增量清单
| # | 建设者缺口 | KDO 增量动作 |
|:--|:--|:--|
| 1 | L2 洞察提炼"待建（缓议）" | P1 必须补：胶囊 → 资产自动提炼，不靠人肉转正 |
| 2 | 单机单库，无跨机真相源 | P3：git 单一真相源 + 本地 MCP + 单写者 |
| 3 | 无"常驻观察者"角色（审计为一次性外部审计） | 明确观察者胶囊 vs 建设者胶囊的生成 / 消费关系 |
| 4 | 门禁靠文本正则打补丁 | 结构化单一真相源（SQLite/JSON）+ 门禁读字段 |
| 5 | 价值判断门散在审查者 / 用户 | 价值判断门独立归王语嫣 |
| 6 | 方法论一夜 14 版、缺版本语义 / changelog 强制 | 方法论版本治理纳入 P0（防版本漂移） |
| 7 | 只有胶囊段 561B，缺端到端 token 账 | 补"生成成本 vs 消费收益"账 |
| 8 | 阈值 / 命名易漂移（30m 采集 vs 2h 摘要；14 天 vs 7/30 天） | 会诊时统一"采集频率 vs 摘要频率"与滚动阈值 |

### 9.4 一句结论
建设者方案是"封闭域考古"跑通的四层记忆 + 门禁样本；KDO 要做的不是复刻它，而是**取其记忆 / 纪律之长，叠加"开放 Agent 平台"所需的跨机真相源、观察者、L2 自动提炼与价值判断门**。

## 十、复盘体系实证：消费闭环与质量门禁

> 触发：老朱问"为什么只有欧阳锋每次都自动更新上下文 + 复盘"，实测 `review-check.py` 全量审计后补入本节。
> 性质：维度 2（记忆体系）与维度 9（可见性）的实证案例，同时暴露 P0 格式漂移与 P1 消费闭环两个整改项。

### 10.1 实证现象（2026-08-21 全量审计）
- 欧阳锋：🟢 A级（52KB，11/11 章，含多场"追加"）；王语嫣：🟢 A级（8.9KB，11/11 章）。
- 黄药师 / 老顽童 / 洪七公 / 段王爷 / 销售对话参谋：❌ 未复盘（5/7）。
- 关键反差：四份 context 文件都有"⛔ 复盘强制动作（不执行=会话未完成）"，规则相同、命令相同，行为却 2/7 vs 5/7 分化。

### 10.2 根因：规则 ≠ 行为，消费闭环 + 即时反馈才产生行为
- 欧阳锋稳定复盘的三因：① 终审产出天然是"判定+证据"，复盘与交付同动作；② 他的 daily-context 有消费者（协调节点视角，他人必读）；③ 经历 8/10-8/16 断档被审计补齐，把复盘内化为"对己审查（O3 对己）"。
- 其余角色缺的不是"要求"，是"消费 + 反馈"——复盘没人读 → 僵尸资产 → 能省则省。
- 结论：**复盘可持续的第一因是消费闭环，不是纪律条文**（同建设者案例 94"资产生而不用=僵尸资产"）。

### 10.3 质量拦路虎一：格式漂移（"规定格式"没有唯一权威）
| 出处 | 说法 |
|:--|:--|
| `templates/daily-context-template.md` 标题 | Truman **10 章**（正文却含差异栏） |
| `review-check.py` TEN_CHAPTERS | 判 **11 章**（差异栏…下次改进） |
| 欧阳锋 context L533 | Truman **10 章**缺一不可 |
| 王语嫣 context L573 | Truman **10 章**缺一不可 |
| 黄药师 context L78 | Truman **11 章**缺一不可 |
| 老顽童 context L385 | Truman **11 章**缺一不可 |

另：模板文件"概要在前"，`daily-context-save.py`"差异栏在前"——章节顺序双标。

### 10.4 质量拦路虎二：门禁只查形式、不查深度
- `review-check.py` 现只查：11 章是否齐 / 字数 ≥3000B / 盲点 ≥2 且有"为什么" / 检索关键词。
- 结果：**写满 11 章 + 两句套话也能拿 🟢 A级**——"形式完整度"≠"洞察深度"。
- 缺硬指标：盲点必须"追问为什么漏"、顿悟必须"推翻某认知"、过程资产必须"真实路径"、差异栏必须"具体差异而非套话"。

### 10.5 升级动作（并入 P0/P1）
1. 格式收口唯一：定死"差异栏=第1章、共11章 + 域知识检索审视"，同步模板/save 脚本/四份 context 的"10/11 章"与章节顺序（P0）。
2. 门禁双查：形式门禁（现有）+ 深度门禁（新增 10.4 四条硬指标）（P1）。
3. 复盘配消费者：每份 daily-context 写前明确"谁读、读完做什么"；观察者（风清扬）为常驻消费者，定期提炼成胶囊/资产喂价值判断门（P1）。

### 10.6 口径漂移第三例：批次收口声明（#406 汇报 · 2026-08-21）
> 触发：老顽童 #406 完成汇报，出现两处计数口径问题，与 §10.3 格式漂移、#399 归零纪律同族。

1. **"累计闭环 13 任务（#373…#406 共 21 件）"——13 vs 21 自相矛盾**：括号内实列 21 个 ID，句首却写 13。要么 13 是旧数未更新，要么"任务/件"两个口径混用，句子本身未讲清。
2. **#406 状态 pending_review（待审）却列入"闭环"清单**：生产者"交卷"≠"终审通过=闭环"；若按"闭环=已终审"，#406 应排除；若按"闭环=交卷"，应统一用词。

**意义与建议**：#399 工具只封住了"全库归零声明必须附脚本输出"，尚未封住"批次/会话收口声明"的口径一致。建议并入 P0：**收口声明同样必须附口径一致的计数——计数按状态分组（已终审 / 待审 / 在制），且"闭环"一词全厂只允许一种定义（建议＝已终审）**。

## 十一、多工厂架构：元层单份 · 执行层随库 · 代码先合并定版

> 触发：老朱问"再建几个不同域的 KDO 工厂，Agent 能否直接复制迁移复活？基础设施一个够还是随库走？KDO 代码仓先合并还是直接随库走？"

### 11.1 四个"怎么走"（一表定）
| 东西 | 怎么走 |
|:--|:--|
| 元层（角色卡/方法论/门禁规范/复盘格式） | 全局一份，能力中枢（cap_hub 上位扩展） |
| 执行态数据（胶囊/台账/索引） | 随库走，每库一套 |
| KDO 代码（CLI/门禁/脚本） | 先合并定版，再各库安装 + 锁版本，不复制 |
| Agent 身份（三件套 + spec） | 随库复制，重挂新库真相源 |

### 11.2 Agent 复活 = 复制身份 + 重挂真相源
- 可复制：SOUL/config/skills/agent-spec/cap_hub 注册（域无关）。
- 不可复制：daily-context/胶囊/台账/队列/失忆锚点（域相关记忆）。
- 三步：复制三件套 → cap_hub 注册 → 对齐新库 git HEAD/队列尾/memory-registry，胶囊台账从零起。

### 11.3 KDO 代码：先合并定版，再安装式随库走
- 现状两套真相源：CLI 源码仓 `github.com/baisenzhu538/kdo.git`（HEAD 419bd92）+ wiki 内 `kdo-tools/`；另有 `40_outputs/code/scripts/` 4 个字节级副本。
- 直接随库走 = 把"两套真相源 + 副本"的漂移扩散到每个厂 → 分支裂变放大器。
- 正确顺序：P0 归位唯一源码仓 + 删副本 + 版本化（`kdo==x.y.z`）→ P3 各厂安装锁版本，不复制代码。

### 11.4 与单仓结论自洽
- 单工厂内部：`infra/` + `vault/` 单仓分层。
- 多工厂之间：元层全局一份 + 执行层随库 + 代码安装式分发。
- 调用：git 单一真相源 + 本地 MCP 为主，远程 MCP/CII 为辅。
