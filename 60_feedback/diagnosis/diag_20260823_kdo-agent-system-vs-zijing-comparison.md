# KDO agent 体系 vs 紫鲸·详细比对调研

> 触发：老朱洞察"KDO 知识卡也能生成一系列 agent 服务不同目的，我们现在不就在做吗（AI基本功教练/开会助理都在飞书）"——要求详细比对，吸收有用点。
> 范围：KDO 主线（agent 体系反思）。紫鲸仅作参考，不入 KDO 知识库。

## 一、KDO agent 体系全貌（双层）

### A 层·工厂治理（charter §2.6 六角色，已入宪 v1.0）
| 角色 | 职责 | 接口 |
|:--|:--|:--|
| 老顽童 | Producer 生产（卡/内容）| claude/hermes |
| 欧阳锋 | Reviewer 审查+唯一协调 | claude |
| 王语嫣 | Orchestrator 编排+诊断（双实例）| kimi/feishu |
| 黄药师 | Builder 基建+部署（单一实例）| claude/codex |
| 风清扬 | Observer 审计+记忆 | feishu |
| 老朱 | Boss 定方向 | 直接对话 |

### B 层·应用层业务 agent（飞书，#263 流水线生成）
| agent | 目的 | 边界 |
|:--|:--|:--|
| AI基本功教练 | Feature 点菜/AI 能力咨询 | 不管人/不管会议 |
| 教练式领导力助理 | 管人（1v1 倾听/提问/反馈）| 不管 AI 能力/不管会议 |
| 科学开会助理 | 管一群人（该不该开/会议设计）| 不管 1v1 |
| R型爆炸式调研Partner | 调研（默认 R）| — |
| 销售对话参谋 | 销售话术 | — |

**生成模式**：#263 流水线——素材→spec→SOUL.md（system prompt）→config.yaml→agents目录→cap_hub注册→飞书链接→自举→真机冒烟。每个 agent"SOUL 内置检索指令驱动，gateway 常驻"（CAPSULE_STARTUP §3）。

**共享基建**：知识库 2500+卡（kdo_search 检索）+ 飞书文档 MCP（#306，操作型）+ 交付物模板（#307，6 模板）+ 记忆胶囊 L1-L4。

## 二、紫鲸模式回顾（对照基准）
- 18 数字员工 × 5 部门（战略/内容/制作/运营/销售）
- 13 工具 DAG（result_id 串联 + 强类型 output_kind + 邻接表）
- **画像（ag103）是超级枢纽**——8 个下游消费画像；运营规划（ag-cao）第二枢纽驱动 6 下游
- 公共参数契约（13 工具共享）+ pack_only 双形态返回 + override 场景自适应
- MANIFEST 门禁（compliance→publish 强制）+ 积分计费
- 定位：内容营销工厂（产出即弃）

## 三、详细比对

### 同构点（两者都是"知识/方法论→agent→服务不同目的"）
1. 都从沉淀的方法论/知识卡生成 agent（KDO=2500卡，紫鲸=COMPLIANCE/PUBLISH-xxx + 24铁律）
2. 都有应用层 agent 服务不同目的（KDO=5 业务 agent，紫鲸=18 数字员工）
3. 都共享知识底座（KDO=kdo_search，紫鲸=内置方法论）
4. 都有生成流水线（KDO=#263，紫鲸=远程 MCP + 工作台）

### KDO 比紫鲸更扎实的地方（不必学）
| 维度 | KDO | 紫鲸 |
|:--|:--|:--|
| agent 生成可溯源性 | O0 抽查零编造（spec→SOUL→卡链可溯）| 远程黑盒，方法论不对外 |
| 治理层 | 双层（工厂六角色 + 应用业务 agent）| 单层（18员工无治理层）|
| 任务流转 | queue_transition 状态机 + #390 原子 commit | 无状态（result_id 链无流转）|
| 通知机制 | 探针 #421 自动通知 + REVIEW-PENDING 登记 | 无 |
| 记忆 | 记忆胶囊 L1-L4 全量保存 + WAL | "共享记忆"黑盒 |
| 门禁深度 | 三层（L1结构/L2内容/L3管线）+ KF-001~022 + pre-submit | 两层（L2合规/L3发布）|
| 产出哲学 | 产出即资产（进 vault 可溯源复用）| 产出即弃（一次性内容）|

### 紫鲸比 KDO 强的地方（可吸收，核心）
| 维度 | 紫鲸 | KDO 现状 |
|:--|:--|:--|
| **agent 间产物复用** | DAG result_id 串联（画像喂 8 下游）| **业务 agent 各干各的，产出不复用** |
| agent 组织化 | 5 部门归类 | 业务 agent 零散无归类 |
| 公共参数契约 | 13 工具共享参数 | SOUL 各自为政 |
| 场景自适应 | override 行业/商业模式/买家角色 | 通用，无场景自适应 |
| 产出结构化形态 | pack_only（小包 vs 结构化封装）| 产出=飞书对话文本（非结构化）|
| 门禁强制链 | MANIFEST（compliance→publish 不可跳）| 审查是欧阳锋人工，非强制链 |

## 四、KDO 可吸收的有用点（按价值排序）

### ★★★ 吸收点1：agent 间产物复用链（result_id 串联）——最有价值
**紫鲸机制**：画像（ag103）→ 喂选题/脚本/销售/内容形态 8 个下游；同一脚本喂小红书+公众号+图文。

**KDO 现状缺口**：业务 agent 各自服务，产出不复用——
- 教练助理画的用户/团队画像，开会助理不知道
- 调研Partner 的调研结果，销售参谋不消费
- AI基本功教练的能力诊断，调研Partner 不参考

**吸收价值**：KDO 业务 agent 从"各自服务"升级到"协同服务"——共享中间产物，多 agent 围绕同一用户/场景协同。这是 KDO agent 体系从"5 个独立 agent"到"agent 协同网络"的关键跃迁。

**落地（适配 KDO 资产化哲学，非照搬）**：
- KDO 业务 agent 产出加 `result_id`（落 vault 文件，不引入独立 DB——见紫鲸9层方案 L8 边界2）
- 定义跨 agent 复用场景：如"用户画像 result_id"由调研Partner/教练助理产出 → 喂开会助理/销售参谋
- 下游 agent SOUL 加"取上游 result_id"检索指令（kdo_search 按 result_id 查）

### ★★ 吸收点2：业务 agent 部门化组织
**紫鲸机制**：5 部门（战略/内容/制作/运营/销售）归类 18 员工。

**KDO 现状缺口**：5 业务 agent 零散，无目的域归类。

**吸收价值**：按目的域组织，用户/编排者一眼看清 agent 全景，且为产物复用链提供"同域优先复用"框架。

**落地**：KDO 业务 agent 按目的域归类——
- 认知域：AI基本功教练（AI 能力）/ 调研Partner（调研）
- 协作域：教练式领导力助理（1v1）/ 科学开会助理（一群人）
- 业务域：销售对话参谋（销售）
（这是示例，老朱可重组）

### ★★ 吸收点3：场景自适应（override）
**紫鲸机制**：override 覆盖 industry/business_model/buyer_role，同 agent 适配多场景。

**KDO 现状缺口**：业务 agent 通用（如开会助理不区分行业/团队规模）。

**吸收价值**：同一 agent 按用户场景自适应——开会助理按"创业团队 vs 大厂会议"给不同话术；销售参谋按"2B vs 2C"不同。

**落地**：业务 agent SOUL 加 override 机制——对话启动时识别场景维度（行业/规模/角色），按维度调知识卡子集。

### ★ 吸收点4：公共参数契约
**紫鲸机制**：13 工具共享 13 公共参数（input/space_id/override/upstream_result_id...）。

**KDO 现状缺口**：业务 agent SOUL 各自定义，无统一契约。

**吸收价值**：统一 agent 接口契约，降低新 agent 生成成本 + 为产物复用链提供统一 upstream_result_id 入口。

**落地**：定义 KDO 业务 agent 公共参数（user_context/scenario_override/upstream_result_ids），新 agent 生成时 #263 流水线强制含此契约。

### ★ 吸收点5：产出结构化形态（pack_only）
**紫鲸机制**：产出可"小包 result_id+runtime_object"或"结构化封装"。

**KDO 现状缺口**：业务 agent 产出=飞书对话文本，agent 间不可机读消费。

**吸收价值**：业务 agent 产出加结构化形态（如画像产出=结构化 JSON，不只对话文本），下游 agent 可机读消费。

**落地**：业务 agent 关键产出（画像/诊断/调研结果）落结构化交付物模板（复用 #307 交付物模板机制），不只对话文本。

### ★ 吸收点6：MANIFEST 门禁强制链
**紫鲸机制**：compliance→publish 强制顺序（合规过才发布）。

**KDO 现状缺口**：业务 agent 产出无强制审查链（产出直接飞书对话，不走欧阳锋审查）。

**吸收价值**：业务 agent 对外交付物加"审查→发布"强制链，防未审产出。

**落地**：仅对"对外正式交付物"加门禁（日常对话不拦），复用欧阳锋终审 + #421 探针通知。

## 五、不该吸收的（场景不匹配）
- **远程黑盒 MCP 模式**：KDO agent 是可溯源本地生成（#263），不是远程黑盒——供应链信任不同
- **积分计费**：KDO 内部工厂无计费需求（对外产品化再说）
- **AG4-OPS gateway 自动路由**：KDO 是王语嫣人编排，不是系统自动编排（人 vs 系统编排哲学不同）
- **限时试用/套餐**：紫鲸的获客钩子，KDO 内部不需要
- **数字人制作部**：KDO 洪七公多模态已覆盖（OCR/VLM/视觉资产），不重复

## 六、核心判断 + 落地建议

**判断**：KDO 的"知识卡生成 agent"模式已比紫鲸更扎实（可溯源+双层治理+状态机+记忆+门禁深度），**但缺紫鲸的"agent 间产物复用 DAG"**——这是 KDO agent 体系从"各自服务"升级到"协同服务"的关键缺口。

**落地优先级**：
1. **吸收点1（产物复用链）是核心**——但它依赖吸收点4（公共参数契约）+ 吸收点5（结构化产出）做基础。三者一体，不能单做1。
2. 先做 4+5（公共契约+结构化产出）打底，再做 1（产物复用链）+ 2（部门化组织提供框架）。
3. 吸收点3（场景自适应）+ 6（门禁链）是增强，后置。
4. 与前轮"产物级 DAG 升级 F-047"9层方案一致——那次是任务级升级，这次是 agent 级升级，**两者同源**（都是产物 result_id 机制），可合并一个落地方案。

**建议下一步**：把"产物级 DAG"落地方案（前轮9层）扩到"业务 agent 间产物复用"——一个统一的 result_id 机制，同时服务任务级（F-047）和 agent 级（业务 agent 协同）。是否要我出合并版落地方案？
