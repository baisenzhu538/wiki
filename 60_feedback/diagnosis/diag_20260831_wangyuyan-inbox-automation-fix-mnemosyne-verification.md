## 1. 根因诊断：为什么素材进 inbox 没人管

### 1.1 断点链还原

```
偶遇工作流（watch_inbox 探针）
  → 自动登记 INBOX-PENDING 段 ✅（这步是自动的）
  → 等王语嫣「维护看板时处理」 ❌（这步等人）
```

- **08-29 架构切换遗留盲区**：各角色独立时钟停用、王语嫣时钟成为全厂唯一节拍器。08-30 重建时钟 v4 时，值守范围写了：建议书裁定（第0步）/结构地图（第1步）/终审落点（第2步）/headless拉起（第3步）/心跳（第4步）——**唯独漏了 INBOX-PENDING 消费**。
- 探针只管「登记」，时钟只管「产线事件」，中间的「素材诊断消费」成了双盲区。素材进 inbox 后只能等老朱人工会话撞见提点。
- 讽刺的是：08-28 我人工处置过 12 条积压行（战略卡/微信 OCR 污染件等），处置动作本身有先例，但没把它固化进时钟 prompt——**人工做过的事没有变成机制**，这是本次根因的根因。

### 1.2 修复方案（已生效）

时钟 prompt 升级 v4.1，插入**第 0.5 步：INBOX-PENDING 自动消费**：

| 素材类型 | 自动动作 | 边界 |
|---|---|---|
| 索引/元数据副产物（_sogou_index.json、0B 空文件、OCR 中间产物） | 直接划销+注明理由 | 原文不动（00_inbox 只增不删） |
| 真实内容素材 | 入口诊断（盘点/域归属/初判/建议）→ 收件箱落账 → 划销看板行 | 🔴 **禁自动立项**：不写任务单/不加队列行/不拉起生产，立项必须老朱明示（08-30 #581 越权红线不变） |
| 撞车/劣质素材 | 划销+理由（同 08-28 音译污染先例） | |
| 拿不准的 | 不划销，收件箱标「待老朱」 | |

- 划销 = 「已诊断」，不等于「已立项」——两阶段处理铁律完整保留。
- 01:30 下一拍起生效，之后每 30 分钟巡一次。

### 1.3 为什么不直接全自动立项

#581 私董会素材被自动立项生产的教训还在挂起中（老朱 08-30 拍板「私董会素材不入产线」）。本次修复刻意保持「诊断自动、立项人工」的边界——自动化解决「没人看见」的问题，不解决「该不该生产」的判断问题。若老朱认为诊断后的素材也应自动进产线，需要明示修改这条红线（牵动 #581 挂起件的处置逻辑）。

## 2. Mnemosyne 素材交叉验证报告

### 2.1 素材背景

- 来源：今日头条文章，微信偶遇采集（watch_inbox 自动转三层框架卡落 pending-cards）
- 核心声明：「11.78 亿 Token 仅 ¥92.08，Mnemosyne 记忆系统让 DeepSeek-V4-Pro 成本暴降 97.4%」「GitHub 首发」「Hindsight 14 维评分 9.58/10、LongMemEval Session Recall 85%」

### 2.2 六项验证结果

| # | 验证点 | 方法 | 结果 | 判定 |
|---|---|---|---|---|
| 1 | GitHub repo 真实性 | GitHub API | `FrankHu-HK/mnemosyne` 存在，2026-08-10 建，24 star，MIT，v7.0.0，PyPI `mnemosyne-os` 可访问（200） | ✅ 真 |
| 2 | 论文/DOI 真实性 | DataCite API | `10.5281/zenodo.21870436` 注册有效：作者 Hu, Jingkun，标题《Mnemosyne: Pushing Lexical Retrieval to the LongMemEval Ceiling with a Zero-Dependency Architecture》，2026-08-10 发布，CC-BY 4.0 | ✅ 真 |
| 3 | 评测体系真实性 | arXiv/GitHub | LongMemEval = ICLR 2025 论文（arXiv:2410.10813，200）✅；Hindsight = vectorize-io/hindsight 仓库存在（200）✅ | ✅ 真 |
| 4 | DeepSeek-V4-Pro 存在性 | DeepSeek 官网 pricing 页 | `deepseek-v4-pro`（版本 DeepSeek-V4-Pro-0813）官方在售：cache-hit $0.022-0.044/M input、cache-miss $0.66-1.32/M input、output $1.98-3.96/M | ✅ 真 |
| 5 | **核心数字「97.4%/¥92.08/11.78亿token」** | 抓取 repo README/README_CN/verify.py/CHANGELOG 全文关键词扫描 | **0 命中**——论文摘要自报口径是「reduces LLM context token consumption by **80%+**」，与文章 97.4% 差距巨大；92.08 元实测账单无任何第三方可查记录 | ⚠️ **无源头，作者单方宣称** |
| 6 | 文章内部数学自洽 | 复算 | 92.08 ÷ 1178.66M = 0.0781 元/M ✅；0.078 ÷ 3 = 2.6% ✅；100−2.6 = 97.4% ✅ | ✅ 自洽（但自洽≠真实，只说明没算错账，不证明账单存在） |

**关键矛盾**：论文自己说的是 80%+ 压缩，头条文标题却喊 97.4%——同一作者的正式文书与非正式宣传之间数字差了一个量级口径。另注：文章定价表述「输入 3 元/百万、输出 6 元/百万」与官网美元价不完全对应（官网 peak $0.66-1.32/M input），疑为旧价/四舍五入/未计 cache 分层，精确性存疑但非硬伤。

### 2.3 素材判定

- **概念层**（记忆预检索架构、计费 Token ≠ 存储 Token、压缩率梯队：原生 0% / 基础 RAG 30-70% / 高级记忆系统 85-95%）：✅ 成立，有论文背书，**可进知识层**
- **数字层**（97.4%/¥92.08/11.78 亿）：⚠️ 作者单方宣称，**不进事实层**，如引用必须标注「作者自述未复现」
- **编排建议**：概念可留卡（AI 域记忆系统方向），标题党数字降级处理；**编排待老朱触发**（08-30 红线：偶遇素材禁自动立项）

### 2.4 验证方法学备注

- DuckDuckGo 搜索后端本夜持续超时，全程改用**一手信源直查**（GitHub API / DataCite API / DeepSeek 官网 / arXiv）——比搜索引擎二手摘要更硬。
- Zenodo 域名 DNS 解析失败（本机网络限制），经 doi.org 302 跳转 + DataCite 元数据双路确认 DOI 有效。
