# 审查供给卡点诊断：提审→叫醒通道缺失 + 阻塞链无优先级

## 现象

2026-08-25 00:51 #505 提审 → 黄药师 #506-#511 依赖链全线被 can_claim 前方阻塞（这正是 #503/#504 刚修好的锁在正常工作）→ 直到用户发现卡点、手动唤起欧阳锋会话说"必须审"才解封。**审查供给的触发器是"用户想起/发现"——系统自己不会叫人。**

讽刺点：锁修得越好（#503/#504 把静默漏拦全堵死），审查卡点越硬——漏拦时代生产者能偷跑（质量代价），全拦时代生产者合规停摆（产能代价）。**门禁完善的副作用是审查供给成为唯一瓶颈，必须配套供给端机制。**

## 根因

1. **叫醒方向缺失**：conveyor_probe 已有"审查完成→通知生产者"通道（#462 探针），但没有"提审→叫醒审查者"反向通道。审查者（Claude 端欧阳锋）是用户手动唤起型会话，不提审不知道有活
2. **阻塞链无优先级**：REVIEW-PENDING 段内所有单同权，按提审序审。但 #505 这类单后面挂着 6 个依赖单——阻塞权重不同，队列里看不出
3. **降级机制错配**：分级审查协议的降级触发器是"积压 >15 张"（量），对"单点阻塞关键链"（质）无机制
4. **自动领审 cron 存在但方向相反**（每 23 分钟，7 天过期需续）——它解决"任务被领"，不解决"提审被审"

## 实证

| 时点 | 事件 |
|:--|:--|
| 08-25 00:51 | #505 提审（complete 63bebec17） |
| 00:51 起 | 黄药师 #506-#511 链被 can_claim 阻塞（锁正常工作） |
| 用户发现 | 用户追问"505 是否已经审查"→ 答"未审"→"必须审啊，否则是个卡点" |
| 解封 | 欧阳锋终审 PASS A（59ffcac11/e9ebc806d）——从提审到解封的时延=用户发现时延 |

## 建议方向（R1-R4，王语嫣裁定）

- **R1 提审叫醒通道**（核心）：conveyor_probe 增加 REVIEW-PENDING 段新行检测 → 飞书通知审查端（复用 #462 双通道机制，探针已有队列解析能力）——把"用户发现卡点"变成"系统叫醒审查者"。最小实现：探针比对 REVIEW-PENDING 行数/最新行 task_id，变化即推
- **R2 阻塞链标记**：queue 看板生成时，对"后方有同角色 queued 单"的 pending_review 行加 🔴阻塞链 标记——审查者进队列先审阻塞单（今天靠用户人工识别卡点）
- **R3 审查 SLA 观测**：health-check 增"pending_review 最大年龄"指标，超阈值（如 2h）入巡检报告——卡点从"被发现"变"被预测"
- **R4 应急通道**（可选）：阻塞链单超 X 小时未审，生产者 --force 继续+台账留痕（force-exceptions.log 机制已在，#504 落地）——质量风险可见化，不静默

## 边界

- R1 优先，R2/R3 低成本可同批，R4 待老朱拍板（涉及审查权下放边界）
- 不改审查标准本身（分级审查协议不动）；只补供给端叫醒与优先级
- 审查者侧自律同步生效：欧阳锋会话启动即查 REVIEW-PENDING（本 session 已如是）；恢复口令可加"有行就审"触发
