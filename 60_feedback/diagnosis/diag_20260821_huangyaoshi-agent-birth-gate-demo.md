# 出生两问拦截实测（#403 验收标准 2）

> 目的：假想"调度 agent"提案走一遍两问检查，验证能被拦下。

## 提案

> "要不要加个调度 agent 自动分配任务？它读队列，把任务分给各 agent，收集状态回报。"

## 两问走查

### 第 0 问（AI 人效闸）：现有角色 + workflow/skill 组合能否覆盖？

| 提案要的能力 | 现有机制 | 覆盖? |
|:--|:--|:--|
| 任务分配 | 欧阳锋=唯一协调节点（AGENTS.md），王语嫣编排入队 | ✅ |
| 队列读取/领取 | production-queue.md 唯一真相源 + queue_transition.py 硬状态机 + claim 门禁 | ✅ |
| 新任务自动登记 | watch_inbox（每 10 分钟，INBOX-PENDING 看板自动登记） | ✅ |
| 状态回报 | 任务单 status + 队列行流转 + 提审即流转（铁律 0） | ✅ |
| 待审提醒 | REVIEW-PENDING 段（#389）+ 每日 kdo watch --health | ✅ |

**结论：全覆盖。** "调度"是已有机制的复读——调度 agent 只是把队列的读写再包一层。

### 传话反模式检查：是否实质承担传话/转发职责？

- 调度 agent 读任务 → 转告给执行 agent → 收集结果回报 = **A→中间层→B 传话模式**
- 执行 agent 直接读队列（文件即真相源）即可，不需要中间人转述
- 龙虾员工实证：中间层既不能 100% 懂他想法、转述还失真，最终砍掉
- KDO 侧同样：调度 agent 转述任务意图必然失真（它读队列写提示词，丢上下文），且多一个故障点

**结论：是传话反模式 → 拒。**

## 判定

```
第 0 问：能覆盖 → 不新造     🔴 拦截
传话检查：是传话层 → 拒      🔴 拦截
┌──────────────────────────────┐
│  ❌ 提案被拦，不创建调度 agent  │
│  替代：直连队列（现状即是）      │
└──────────────────────────────┘
```

## 拦截后的正确动作（若真实出现该提案）

1. 指出现有机制覆盖点（上表）
2. 若痛点是"没人领任务"→ 查 watch_inbox/欧阳锋协调，不是新建 agent
3. 若痛点是"上下文隔离"→ 用 #402 workspace，不是新建 agent
