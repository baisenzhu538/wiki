# 诊断补遗：跨库映射机制（老朱纠偏触发）

## 一、漏掉的暗知识 №20：跨库/多库的映射处理（口述 L630-654 一等原话）

**场景**（半肥猫实战）：用食谱写小红书文案——
- 专业知识库（一个库）：提供知识的**准确度**
- 营销运营规则库（另一个库）：提供平台表达、流量规则、**敏感词**
- 两个库**独立分库**（防串扰），中间用**映射表桥接联动**
- 需要时再加人设内容库（输出像真人说话）
- 效果：「既专业又合规，还像真人讲的话一样，还不容易被平台违规」

**机制本质**：映射表=跨库协同的**语义层协议**——不是把 A 库内容复制进 B 库（防串扰/防副本漂移），而是定义「A 库对象 ↔ B 库对象」的对应关系，调用时各库各司其职。

## 二、漏因检讨（老朱问「为什么漏掉」）

**已知性偏差**：我逐字读到了 L630-654，但筛选暗知识时把它归为「KDO 已知」（B1-3 多工厂拍板过 MCP 多挂、#465 卡 7 也排了分库映射卡）——**把「原则已拍板」误当「机制已掌握」**。事实上：
- KDO 已有的：MCP 多挂原则（怎么**连**）
- 半肥猫补的：映射表机制（连起来之后内容**怎么协同**——哪个库管哪个维度、跨库对象怎么对齐、为什么不复制）
- 这是 B1-3 开分店模式的**实现方案级**输入，不是已知确认——正是暗知识清单该收的东西

筛选纪律修正：暗知识的判断标准是「对 KDO 有无增量」而不是「KDO 是否提过」——提过原则 ≠ 掌握机制。

## 三、对 KDO 的落点理解（老朱问「你怎么理解这件事」）

1. **B1-3 多工厂的缺失另一半**：开分店模式（主库+推广获客库）拍板了「跨库引用靠 MCP 多挂不复制」——MCP 多挂=接入层（管道）；映射表=语义层（协议）。两者互补，缺语义层则多挂只是一堆管道，内容协同仍靠人肉
2. **KDO 实例推演**：获客库写文案需引主库方法论卡——映射表定义「获客场景 ↔ 方法论卡」对应关系，方法论卡不复制（防 #222/#223 副本漂移家族复发），获客库自带平台规则/敏感词/人设维度（半肥猫三库结构的 KDO 版）
3. **与五维标注的关系**：映射表跨库对齐的前提=各库标注体系兼容（维度轴可对齐）——词表 v0.3 的分域维度轴设计天然为此铺路（每域轴文件里预留跨库对齐字段）
4. **与既有纪律同构**：单一真相源（§3.1）的跨库版——映射表是「引用不复制」的机器化

2. **#465 卡 7（分库与映射表）按本补遗补强**：口述 L630-654 一等锚+三库结构+映射表机制+对 B1-3 的落点——已飞书通知洪七公/老顽童（#465 上板冻结，口径经补遗件传递）
