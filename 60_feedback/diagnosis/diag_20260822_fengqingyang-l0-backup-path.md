## 0. 一句话结论

L0（全量留痕 SQLite）放 git 外，但「git 外」≠「没备份」。方案建议 **A 本机 git 外主库 + B 第二盘镜像 + C 云端冷备**，RPO=30min（B3-1 频次红线）。**老朱已拍板 B（D 盘）**；动工（建库/脚本/cron/备份）归黄药师，我风清扬只审计 + 定口径。

## 1. L0 数据规格（先定口径再谈备份）

| 项 | 口径 | 依据 |
|:--|:--|:--|
| 形态 | 单文件 SQLite `activity_log.db` + WAL | 巨米建设者 activity_log.db |

## 2. 体积估算（红线校验，首周实测校准）

| 假设 | 取值 |
|:--|:--|
| 活跃角色 | 6–8（六角色 + 观察者 + 飞书挂载） |
| 每角色日会话 | 1–2 场 |
| 每场事件 | 50–300 条（参考 08-22 复盘单场 14 轮 + 工具/状态事件） |
| 单事件体积 | 300B–1KB（JSON 含文本节选） |

**推算**：日增量 ≈ 0.5–3 MB；月 ≈ 15–90 MB；年 ≈ 0.2–1 GB。

> 结论：L0 是轻量库，30min 频次不触体积红线；真正的风险是「只存一份、坏了没得恢复」（E034 过时快照同族），不是容量。

## 3. 候选备份位置对比（本机目录 / 外部介质 / 云同步）

| 方案 | 分类 | 位置示例 | 体积 | 优点 | 缺点 |
|:--|:--|:--|:--|:--|:--|
| A | 本机目录 | `C:\Users\Administrator\.kdo-memory\L0\` | 承载 L0 主库本身 | 同机快、零网络、天然隔离 git | 单点：本机盘坏即丢 |
| B | 外部介质/第二盘 | `D:\KDO-memory\L0-backup\` | 日 ~0.5–3 MB 增量 | 跨盘容灾、成本零、恢复最直接 | 仍在本机物理域内 |
| C | 云同步 | 飞书云盘 / OneDrive / 坚果云 指定目录 | 同上 | 异地容灾，抗本机/介质双损 | 依赖网络与云可用性；凭据不进 git |

> **已拍板：B（第二盘镜像 D 盘）**。A 为主库、B 为镜像；C 留第二期。

## 4. 恢复路径清单（谁 / 命令 / 恢复到哪）

> 恢复由 **黄药师（基建）执行**；**风清扬（审计）核验**并出洞察（丢了什么、为什么、怎么防）。只走命令，不凭记忆手改。

**场景 1：本机 L0 库损坏/误删（最常见）**
1. 确认损坏：`python kdo-tools/memory_capsule.py status`（黄药师建）
2. 从 B 镜像恢复：`robocopy D:\KDO-memory\L0-backup\ C:\Users\Administrator\.kdo-memory\L0\ /MIR`
3. 校验：`python kdo-tools/memory_capsule.py verify`（行数 + 最新 ts + WAL 完整性）
4. 补差：若 A↔B 时间差 >30min，回放缺失段（从消费端/会话记录补）

**场景 2：本机全损（含 D 盘）**
1. 换机/重装 → 恢复 wiki 仓（git clone）
2. 因 C 云端未挂（第二期），此场景暂依赖 B 的定期外拷/后续云备补强
3. 校验 + 补差（同场景 1 第 3、4 步）

**场景 3：月检（不通电的备份不算备份）**
1. 每月一次：从 B 拉到临时目录跑 `verify`，确认可恢复

## 5. 推荐方案（老朱已拍板 B）

- A = L0 主库（同机 git 外，跑得最快）
- **B = 第二盘镜像（`D:\KDO-memory\L0-backup\`，30min 后置 `robocopy /MIR`，RPO≈30min）——已拍板**
- C = 云端冷备（每日 zip 上传，RPO≈1 天，抗本机双损）——留第二期
