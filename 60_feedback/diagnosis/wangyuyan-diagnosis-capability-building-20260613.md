# 王语嫣诊断能力建设报告

> 背景：用户指令「诊断能力你也需要去建设下」。本报告整合 `30_wiki/` 中诊断与咨询相关资产、医学临床推理、管理咨询诊断方法论，明确王语嫣的诊断能力边界、工作流和下一步行动。只读知识库 + 写反馈，不改 `30_wiki/`。

---

## 一、为什么王语嫣必须系统建设诊断能力

王语嫣的核心职责是**基于知识库做诊断式咨询**。但当前实践存在三个问题：

1. **诊断即框架匹配**：现有角色文件把诊断描述为「追问 → 匹配框架」，但缺少「如何生成高质量追问」「如何在选择框架前表征问题」的系统方法。
2. **诊断记录依赖灵感**：已有的 18 份诊断记录质量不一，缺少可复用的诊断工作流来保证下限。
3. **与调研能力割裂**：调研解决「信息可不可靠」，诊断解决「问题是什么、该用什么框架看」。二者必须衔接，但 wiki 中没有一张卡明确说明这个衔接。

因此，诊断能力需要从「凭经验追问」升级为「有结构、可验证、可复现的诊断工作流」。

## 三、全网诊断方法论精华

### 3.1 医学临床推理

来自 UNM、Gazi Med J、Clinical Problem Solving 等来源：

| 模型 | 核心步骤 | 对王语嫣的启示 |
|:-----|:---------|:---------------|
| **假设演绎模型** | 线索获取 → 假设生成 → 线索解释 → 假设评估（循环） | 诊断不是先收集全部信息，而是尽早生成假设，再用追问验证 |
| **模式识别** | 将当前问题与已有模式快速匹配 | 王语嫣看到用户描述时应快速匹配知识库中的 framework/case |
| **双过程模型** | System 1（直觉/模式）+ System 2（分析/验证） | 先用 System 1 猜框架，再用 System 2 追问验证 |
| **问题表征（Problem Representation）** | 用一句话抽象定义案例的关键特征 | 王语嫣应在诊断早期生成「用户问题的抽象表征」 |
| **鉴别诊断（Differential Diagnosis）** | 列出最可能、次可能、不可漏诊的假设 | 不要只给用户一个框架，要给一个排序后的框架清单 |

### 3.2 管理咨询诊断

来自 CaseBasix、NMS Consulting、Caselane 等来源：

| 要素 | 核心动作 |
|:-----|:---------|
| **结构化问题框定** | 定义绩效差距、范围边界、成功标准 |
| **Issue Tree + MECE** | 将复杂问题拆解为可测试驱动因素 |
| **假设驱动** | 形成早期解释，用证据验证或拒绝 |
| **事实基础（Fact Base）** | 内部数据 + 访谈 + 外部基准，三角验证 |
| **并行诊断工作流** | 多分支同时测试，定期整合 |
| **洞察合成** | 把证据连接成因果解释，指导决策 |

### 3.3 苏格拉底式提问与教练对话

来自 Colorado State、Philosophy of Coaching 等来源：

| 功能 | 问题示例 |
|:-----|:---------|
| 澄清概念 | "你说的 X 具体指什么？" |
| 探索假设 | "你做出这个判断的前提是什么？" |
| 检验证据 | "这个结论基于什么数据或观察？" |
| 探索视角 | "如果换作你的竞争对手，他会怎么看？" |
| 追问影响 | "如果这个判断错了，最坏结果是什么？" |
| 元认知 | "你为什么这样思考问题？" |

## 四、王语嫣诊断能力模型

### 4.1 定位

> 王语嫣不是给答案的医生，而是帮助用户「看清自己的问题该用什么框架看」的诊断者。

### 4.2 诊断 = 三个核心动作

```
问题表征（Problem Representation）
    ↓
假设生成与框架匹配（Hypothesis Generation & Framework Matching）
    ↓
追问验证与盲区暴露（Interrogation & Gap Exposure）
```

### 4.3 WYY-Diagnosis 工作流

#### Phase 0：准备——诊断前的元问题

在开始追问前，先回答：

| 问题 | 为什么重要 |
|:-----|:-----------|
| 用户要做什么决策？ | 诊断必须服务于决策，否则只是聊天 |
| 用户已经知道什么？ | 避免在已知信息上重复提问 |
| 用户愿意被挑战到什么程度？ | 决定追问的锋利度 |
| 时间窗口有多紧？ | 决定诊断深度 |

#### Phase 1：问题表征

目标：把用户的模糊描述转化为一句抽象的、可匹配框架的问题陈述。

**操作**：
1. 让用户用一句话描述「我现在最卡住的事」。
2. 提取关键特征：谁、在什么场景、想要什么结果、遇到了什么障碍。
3. 用语义限定词抽象：短期/长期、个人/团队/企业、定性/定量、已知/未知。
4. 输出「问题表征句」。

**示例**：
- 用户原话：「我的业务最近不太好。」
- 问题表征：「一个年营收 1000 万左右的 B2B 服务业务，在过去 3 个月出现收入增长停滞，创始人不确定是需求端、供给端还是竞争端出了问题。」

#### Phase 2：生成假设清单

目标：列出 3-5 个可能的解释框架，而不是直接给一个答案。

**来源**：
- `kdo query` 召回的 framework/tool/case
- 王语嫣的内化模式库
- 用户描述中的关键词触发

**示例**（针对上例）：
1. 需求端：目标用户定义过宽（`yt-demand-analysis-hiking-map`）
2. 供给端：产品价值主张衰减（`yt-concept-product-kernel`）
3. 竞争端：替代品出现导致客户流失（`yt-barrier-identification-skill`）
4. 运营端：销售转化率下降（`yt-panproduct-demand-motivation-resistance`）
5. 战略端：终局目标与当前路径错配（`yt-foresight-business-spectrum`）

#### Phase 3：设计诊断性追问

目标：用最少的问题排除最不可能的假设，聚焦最可能的框架。

**追问原则**：
- 每个问题应能区分至少两个假设
- 先问「可观测的事实」，再问「解释和判断」
- 追问用户没问但应该问的问题

**追问类型**：

| 类型 | 目的 | 示例 |
|:-----|:-----|:-----|
| 边界问题 | 缩小范围 | "你说的'最近'是指多久？" |
| 数据问题 | 获取可验证事实 | "过去三个月的收入曲线具体什么样？" |
| 对比问题 | 识别变化 | "和六个月前相比，什么变了？" |
| 反事实问题 | 暴露假设 | "如果这个问题不存在，你的业务会是什么样？" |
| 视角问题 | 打破单一视角 | "你的客户会怎么描述这个问题？" |
| 决策问题 | 连接行动 | "什么证据出现会让你改变方向？" |

#### Phase 4：框架匹配与盲区暴露

目标：根据追问结果，给出最匹配的框架，并指出用户没问但应问的问题。

**输出格式**：

```markdown
## 诊断结论

### 问题表征
<一句话抽象定义>

### 假设清单（按可能性排序）
| 假设 | 匹配框架 | 支持证据 | 反驳证据 | 下一步验证 |
|:-----|:---------|:---------|:---------|:-----------|
| H1 | ... | ... | ... | ... |
| H2 | ... | ... | ... | ... |

### 命中框架
| 框架 | 匹配理由 | 提供的视角 |
|:-----|:---------|:----------|
| ... | ... | ... |

### 盲区 / Gap
<用户应该关注但没问的问题>

### 建议下一步
<调研 / 实验 / 补卡 / 深度研究>
```

## 五、诊断失败模式与防御

| 失败模式 | 症状 | 防御机制 |
|:---------|:-----|:---------|
| **过早收敛** | 用户说第一句话就给出框架 | Phase 1 强制问题表征，Phase 2 强制至少 3 个假设 |
| **框架误配** | 把创业问题用个人成长框架看 | 用 Issue Tree 检查框架覆盖的节点 |
| **确认偏误** | 只追问支持某一框架的问题 | 每个假设必须有「什么证据会推翻它」 |
| **忽视反例** | 用户提到一个反例被忽略 | 在诊断记录中单列「反驳证据」 |
| **过度诊断** | 对简单问题用复杂框架 | Phase 0 的时间窗口和决策重要性评估 |
| **诊断疲劳** | 追问太多让用户厌烦 | 每轮 1-2 个追问，给用户反馈后再继续 |

## 六、与调研能力的衔接

调研和诊断在王语嫣身上是上下游关系：

```
用户问题
  → Phase 0-1：诊断（问题表征 + 假设生成）
    → 如果需要外部信息 → 调用调研能力（WYY-Research）
      → 调研结果回到诊断（假设验证）
        → 框架匹配 + 盲区暴露
          → 诊断记录
```

**规则**：
- 诊断先定方向，调研后补信息。
- 不是所有诊断都需要调研，但所有调研都应服务于某个假设的验证。
- 当用户提供的素材是诊断输入时，先调用置信度评估，再进入诊断。

## 八、关键判断

1. **诊断能力的核心是「问题表征」**，不是「框架匹配」。表征错了，匹配再准也是错。
2. **诊断必须服务于决策**。不为决策的诊断只是聊天。
3. **好诊断的标志是「让用户看到自己没看到的东西」**，而不是「让用户觉得我很聪明」。
4. **医学临床推理对王语嫣高度可迁移**：问题表征 → 鉴别诊断 → 假设验证 → 诊断。
5. **诊断和调研必须衔接**：诊断定方向，调研补信息，诊断再验证。
6. **诊断记录应成为王语嫣最重要的输出资产**——积累 50-100 条后，可训练模式识别能力。
