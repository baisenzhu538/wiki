## 洞察 1：调研的真谛不在“问需求”，而在观察真实行为与替代方案

### 模式描述

yitang 域大量案例反复指出：用户口头回答不可靠，真正高质量的需求洞察来自对真实行为、JTBD 故事、替代方案与现场场景的观察。

直接问“你会用我的产品吗”得到的往往是愿望清单或迎合式回答；只有观察“用户现在怎么解决这个问题”“试过什么但不行”“在什么场景下愿意付费”，才能找到真实需求。

### 支撑案例（≥3）

| 案例 ID | 核心做法 | 关键洞察 |
|:---|:---|:---|
| `case-yitang-pet-fostering-user-research` | 观察现有替代方案 | 真实需求在行为里，不在回答里 |
| `case-yitang-doorstep-nail-service-context` | 在真实场景中访谈 | 同一用户在不同场景下需求可能相反 |
| `case-yitang-jtbd-story-formula` | 用 JTBD 故事公式回溯行为 | 一个完整故事抵得上 100 份问卷 |
| `case-yitang-consumer-offline-channel-decision` | 先访谈一线再算账 | 报告增长率 15%，进场费半年涨 30% |
| `case-yitang-ski-project-user-as-expert` | 把重度用户当专家 | 重度用户对替代方案的认知超过分析师 |
| `case-demand-milkshake-jtbd` | 奶昔 JTBD 经典任务洞察 | 用户“雇佣”产品完成什么任务 |
| `case-demand-silver-parenting` | 银发育儿冰山模型 | 完整行为链才能暴露真实痛点 |

### 框架未覆盖的理由

- `tool-yitang-user-interview-5steps`、`yt-research-user-jtbd`、`framework-demand-iceberg` 已提供基础方法；
- 但现有框架缺少：
  - “行为证据如何系统重于口头证据”的显性规则；
  - 观察法 + JTBD 组合的 SOP；
  - 远程/线上访谈如何还原现场语境的方法。

### 建议沉淀为 dk 卡

`dk-yitang-behavior-over-asking`：调研中让行为证据重于口头证据的操作原则。

## 洞察 2：商业模式/单元模型错误比产品、销售或执行问题更致命

### 模式描述

yitang 域多个失败复盘共同显示：团队把资源投入产品打磨、销售扩张、品牌建设，却未先验证需求存在性、付费意愿、决策链、隐性成本和单销售模型。商业模式不成立时，换销售总监或打磨产品只会加速沉没。

这个模式在 ToB、出海、新赛道中尤其常见——因为这些场景中决策链长、隐性成本高、二手数据容易让人误判。

### 支撑案例（≥3）

| 案例 ID | 投入重点 | 真正未验证的假设 |
|:---|:---|:---|
| `case-yitang-tob-smart-park` | 智慧园区平台开发 | 客户付费意愿、决策链、交付成本 |
| `case-yitang-tob-grinding-machine` | 精密磨床国产化 | 真实市场需求、政策持续性 |
| `case-yitang-tob-career-planning` | 新高考选科产品 | 学校/家长的付费意愿和决策流程 |
| `case-yitang-tob-artificial-bone` | 人工骨医疗产品 | 医院采购路径、临床价值验证 |
| `case-lean-premature-expansion` | 规模化扩张 | 单点模型未跑通 |
| `case-lean-building-in-vacuum` | 产品开发 | 需求存在性未验证 |
| `case-lean-wrong-demand` | 需求/产品 | 真实需求与商业模式未剥离 |
| `case-hr-saas-feature-usage-trap` | 功能堆砌 | 把功能使用率当续费原因 |

### 框架未覆盖的理由

- `yt-entrepreneur-five-step-method`、`yt-tob-unit-model`、`yt-tob-sales-unit-model`、`yt-business-formula-abc-model`、`framework-lean-false-model` 已分别覆盖两端；
- 但缺少“定性调研结论 → 单元模型调整”的自动映射模板：
  - 访谈中发现的哪些信号应该触发单元模型修改？
  - 如何把用户反馈翻译成定价、成本、获客效率假设？
  - 何时从调研切换到单元模型验证？

### 建议沉淀为 dk 卡

`dk-yitang-business-model-risk-over-product-risk`：商业模式/单元模型错误为何比产品错误更致命。

## 洞察 3：组织级模型资产需要主动盘点、定价与迭代，否则会重复发明轮子

### 模式描述

一堂自身案例揭示：模型能力要成为增长引擎，必须建立“周对周交付-复盘-迭代”闭环、用定价飞轮统一质量预期、用 AI 扫描归集范式、用雷达图对象化评选标准。否则个人经验无法沉淀为组织资产。

这个模式区别于个人学习方法论——它关注的是“组织如何把模型变成可复用的基础设施”。

### 支撑案例（≥3）

| 案例 ID | 机制 | 效果 |
|:---|:---|:---|
| `case-yitang-weekly-modeling-engine` | 周对周建模迭代 | 把周五课程逼成公司增长引擎 |
| `case-yitang-model-valuation-flywheel` | 内部模型定价 | 从 5000 元到 10 万美金的价值飞轮 |
| `case-yitang-model-asset-inventory` | AI 扫描内容资产 | 三四百个模型归集到二三十个范式 |
| `case-yitang-radar-chart-selection` | 雷达图对象化评选 | 从 Truman 拍板到“只聊模型不聊结果” |
| `case-yitang-double-triangle-confidence` | 双三角模型底盘化 | AI 难题的通用解题底盘 |
| `case-yitang-education-supply-chain` | 真实实践当教材 | 种菜、摘菜、炒菜的内容供应链 |
| `case-course-milestone-model` | 课程里程碑模型 | 方法论级建模的六步生产流程 |

### 框架未覆盖的理由

- `modeling-weapon-library`、`yt-unit-model-build`、`tool-radar-chart-modeling` 提供概念；
- 但缺少操作细节：
  - AI 辅助盘点的具体 workflow；
  - 模型定价与 OKR/激励如何挂钩；
  - 失败案例如何 48 小时内沉淀为维度补丁；
  - 个人模型如何升级为组织级标准。

### 建议沉淀为 dk 卡

`dk-yitang-model-asset-capitalization`：组织级模型资产的盘点、定价与迭代机制。
