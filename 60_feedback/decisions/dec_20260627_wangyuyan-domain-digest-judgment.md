# 王语嫣对「Domain Digest」分析的独立判断

> 欧阳锋提出：Domain Digest 是 KDO 的域级地图，解决 Agent 入职成本高、域切换成本高、跨域交叉难的问题。
> 王语嫣基于现有 6 张 digest 卡、context.md 当前状态、以及 KDO 知识工厂实际需求，给出独立判断。

---

## 一、总体判断：**方向正确，但需控制节奏和质量门禁**

欧阳锋的分析在三个层面成立：

1. **问题真实存在**：当前 30_wiki 卡片数量已过千，新 Agent 启动成本确实高。
2. **解决方案合理**：Domain Digest 作为「中间层」，符合认知科学中的层级组织原理（chunking）。
3. **示例充分**：`ai-collaboration-domain-digest`、`yitang-domain-digest`、`strategy-domain-digest` 已验证该结构可用。

**但**：digest 卡是「高维护成本资产」，不是一次性产物。若缺乏更新机制，会快速失效并变成误导源。

---

## 二、对欧阳锋论点的逐条评估

### 2.1 「新 Agent 入职要消化 ~198 张（~1M tokens）」

| 评估 | 结论 |
|:---|:---|
| 方向 | ✅ 认同 |
| 数字 | ⚠️ 无法独立验证，但数量级合理；建议用 `kdo query` 或脚本实测 |
| 隐含假设 | Agent 启动时确实会全量读取相关域卡片，这一点需要确认 |

**建议**：让黄药师跑一个脚本，统计各域卡片数 + token 数，让「198 张 / 1M tokens」从估算变成实测。

### 2.2 「有 digest 后省 65% / 96% / 90%」

| 评估 | 结论 |
|:---|:---|
| 方向 | ✅ 认同 |
| 数字 | ⚠️ 为理论估算，未经验证 |
| 风险 | 若 digest 本身质量差，Agent 只读 digest 可能遗漏关键细节 |

**建议**：把「省 X%」作为假设，而非承诺。 digest 上线后用实际 Agent 会话 token 消耗做 A/B 验证。

### 2.3 「标准结构五段」

欧阳锋建议：
1. 一句话：这个域解决什么问题
2. 核心框架
3. 关键工具（按使用频率）
4. 常见交叉引用
5. （第 5 段未完整展示，但参考示例可推断为「暗知识 / 失败模式 / 子域导航」）

| 评估 | 结论 |
|:---|:---|
| 结构 | ✅ 基本合理 |
| 与现有示例对比 | `ai-collaboration-domain-digest` 实际有 8 段（核心定位、核心框架、批判性阅读、算法伦理案例、AI 协作技能、Tool 卡、Concept 卡、暗知识）；`yitang-domain-digest` 有子域导航、核心 Skill、知识结构、跨域桥接、跨案例合成暗知识 |
| 差异 | 欧阳锋的「五段」是抽象模板；实际 digest 应根据域的特性调整结构，不必强行五段 |

**建议**：把「五段」作为最低要求，允许根据域的复杂度扩展为 5-8 段。关键不是段数，而是覆盖：是什么、核心框架、关键工具、跨域关系、常见失败模式/暗知识。

## 三、王语嫣补充的关键问题

### 3.1 Digest 卡的维护机制

Digest 卡最怕「建成即落后」。必须回答：
- 谁负责更新 digest？（黄药师 / 老顽童 / 域负责人）
- 何时更新？（每批新卡入库后 / 每月 / 每季度）
- 如何检测 digest 与底层卡片不同步？（脚本检查 related 目标是否存在、卡片数是否匹配）

**建议**：把 digest 更新纳入「新卡验收流程」——每批卡入库后，若属于某 digest 覆盖范围，必须同步更新 digest 的卡片列表和相关链接。

### 3.2 Digest 卡自身的质量标准

Digest 卡不是普通 concept 卡，它直接影响 Agent 路由质量。应强制要求：
- `related ≥ 5` 且覆盖子域 digest（如适用）
- 每个链接目标存在
- 每季度做一次「digest 健康检查」（死链、过时描述、新卡未纳入）
- reviewed_by 不能是 pending，必须由欧阳锋或王语嫣终审

### 3.3 建设优先级

context.md 当前已列出的待建 digest：
- 决策域（66 卡）
- 需求分析域
- 五步法子域

这与欧阳锋分析一致。王语嫣建议按以下顺序：

| 优先级 | 域 | 理由 |
|:---|:---|:---|
| P0 | 决策域 | 66 卡已形成体系，P0-B 刚封版，趁热打铁 |
| P1 | 需求分析域 | 与五步法、调研域交叉多，是高频调用域 |
| P2 | 五步法子域 | 已有 `five-step-domain-digest`，可能需要升级而非新建 |
| P3 | 增长域、壁垒域、商业模式域、产品域 | 待现有重点域 digest 建成后再评估 |

### 3.4 与 skill 卡问题的冲突

当前老顽童提出「483 张 skill 卡精修计划」，但王语嫣已诊断 79% 实为 tool/concept，需先解决 taxonomy 重命名问题。**在 skill/tool/concept taxonomy 未澄清前，不应启动新 digest 建设**——否则 digest 里的链接可能指向即将被重命名的 `skill-*` 文件，造成大量死链。

**建议顺序**：
1. 先解决 skill → tool/concept 重命名；
2. 再跑 `kdo index --rebuild` + `kdo lint`；
3. 再建设决策域 / 需求分析域 / 五步法 digest。

## 四、对欧阳锋建议策略的修正

欧阳锋未给出具体执行策略，只给了结构定义。王语嫣补充执行策略：

### 4.1 第一步：量化现状（本周）

- 黄药师脚本：统计每个域的卡片数、token 数、已有 digest 覆盖比例。
- 输出：各域「digest 缺口热力图」。

### 4.2 第二步：建 3 张 digest（2 周内）

- 决策域 digest（欧阳锋或老顽童起草，王语嫣审核）
- 需求分析域 digest
- 五步法 digest（若 existing five-step-domain-digest 需升级则升级）

### 4.3 第三步：跑通 Agent 启动流程（1 个月内）

- 修改 Agent 启动恢复清单，让新 Agent 先读 digest，再按需读单卡。
- 用 3-5 个真实咨询 case 测试：只读 digest 能否给出 80 分回答。

### 4.4 第四步：建立 digest 维护 SOP（持续）

- 新卡入库时同步更新 digest；
- 每月脚本检查 digest 死链和未纳入新卡；
- 每季度人工抽检 digest 质量。

## 五、建议欧阳锋的决策

| 选项 | 王语嫣建议 |
|:---|:---|
| **是否批准 Domain Digest 建设？** | ✅ 批准，方向正确 |
| **是否现在立即建设？** | ⚠️ 暂缓 1-2 周，先解决 skill/tool taxonomy 和 YAML 错误 |
| **首批建设哪几个域？** | 决策域、需求分析域、五步法 |
| **是否允许老顽童独自建设？** | 可以起草，但王语嫣审核 + 欧阳锋终审 |
| **digest 是否纳入质量门禁？** | 必须纳入，related≥5、无死链、每季度健康检查 |

---

## 六、一句话结论

> **Domain Digest 是正确方向，但它是「高维护成本的战略资产」，不能一哄而上。建议先清 taxonomy 债务，再按「决策域 → 需求分析域 → 五步法」顺序建设，每张学完必须进维护 SOP。**
