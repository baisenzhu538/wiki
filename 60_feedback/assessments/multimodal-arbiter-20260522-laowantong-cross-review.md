## 二、欧阳锋 4 项交叉验证的洪七公结论

### ✅ Q1：OCR 提取的文本与原图视觉信息差距有多大？

**结论：差距极大，视觉结构信息接近 100% 丢失。**

抽样验证 3 张典型卡片：

| 原图类型 | 卡片 | 丢失的视觉信息 | 影响 |
|---|---|---|---|
| **矩阵分类图** | `ocr-泛产品设计落地篇` | 三列结构（磨设计/磨方案/磨创新）、填充色块含义、难度梯度 | 用户无法从卡片还原原图的分类逻辑 |
| **层级+雷达+Checklist** | `ocr-预判模型` | N 要素的层级嵌套、雷达图 5-7 维度、Checklist 的勾选项 | 三层结构压缩为一段流水账，范式和案例混为一谈 |
| **流程+层级** | `ocr-萃取总结` | 爆炸式研究→MECE 整理的递进关系、最高追求的标注位置 | 过程模型变成无序列表 |

**根因**：PaddleOCR ONNX 轻量版（`X3ZvaWQ/paddleocr.js`）只输出纯文本串，不做版面分析（Layout Analysis）。图中的：
- 表格行列关系 ❌
- 标题/正文层级 ❌
- 色块/边框的分组语义 ❌
- 箭头/连线的流程关系 ❌
- 缩进/对齐的从属关系 ❌

全部丢失。

**定性**：这些卡片不是"浓缩"，是"稀释"——把有结构的视觉知识拍扁成了一维文本流。

---

### ✅ Q2：`deep-image-parser` 的 prompt 模板在这些图片上能比 PaddleOCR 多还原多少结构？

**结论：预计可多还原 60-80% 的视觉结构信息。**

对比两种技术路线：

| 能力维度 | PaddleOCR ONNX（当前） | deep-image-parser / VLM | 差距 |
|---|---|---|---|
| 纯文字识别 | ✅ 85-90% 准确率 | ✅ 90-95% 准确率 | 小 |
| 表格还原 | ❌ 纯文本堆砌 | ✅ Markdown 表格输出 | **大** |
| 层级标题 | ❌ 丢失 | ✅ H1/H2/H3 标注 | **大** |
| 分组/色块语义 | ❌ 丢失 | ✅ "蓝色区域=高优先级"等描述 | **大** |
| 流程/箭头关系 | ❌ 丢失 | ✅ "A → B → C" 流程描述 | **大** |
| 雷达图/矩阵 | ❌ 丢失 | ✅ "5 维度评分：X=3, Y=5..." | **大** |
| 处理速度 | ✅ ~1-2 秒/图 | ❌ ~5-15 秒/图（API） | 慢 5-10x |
| 本地运行 | ✅ 完全离线 | ⚠️ 需 API 或本地 VLM | 依赖重 |

**建议**：
- **高价值图**（知识地图、框架图、矩阵图）→ 用 deep-image-parser 或本地 VLM（如 Qwen-VL、InternVL）重做
- **纯文字截图**（文章段落、简单列表）→ PaddleOCR 够用
- **批量管线应增加"视觉复杂度预检"**：单图颜色数>10 或检测到表格/箭头时，自动路由到 VLM 分支

### ✅ Q3：哪些 `ocr-*` 卡片值得用 deep-image-parser 重做？

按视觉复杂度分级，建议重做清单：

#### 🔴 高优先级（复杂视觉结构，当前卡片几乎不可用）

约 **40-50 张**，典型特征：
- 包含矩阵/网格布局（如泛产品设计落地篇的"磨设计/磨方案/磨创新"三列）
- 包含雷达图/多维度评估（如预判模型的 57 维度+打分）
- 包含流程图/箭头连接（如萃取总结的"爆炸式研究→饱和式建模→MECE"）
- 包含色块分类（如课程地图的不同颜色=不同难度/类型）

代表卡片：
- `ocr-泛产品设计落地篇` — 三列矩阵+色块+难度梯度
- `ocr-预判模型` — 层级+雷达+Checklist 三层
- `ocr-一堂-个人修炼-全景图MUSE模型` — 系统全景图
- `ocr-一堂-个人修炼-科学学习IPO-全景策略` — 策略全景
- `ocr-一堂-个人修炼-表达力火箭模型-执行武器库` — 模型+武器库双层

#### 🟡 中优先级（部分结构可手动还原，但效率低）

约 **50-60 张**，典型特征：
- 列表但有层级缩进
- 简单表格（2-3 列）
- 时间线/阶段划分

#### 🟢 低优先级（纯文本，PaddleOCR 够用）

约 **30-40 张**，典型特征：
- 纯文字段落
- 简单无序列表
- 短句截图

**执行建议**：不要一次性重做 136 张。先选 5 张高优先级用 deep-image-parser 做试点，对比输出质量，确认 ROI 后再批量推进。

### ✅ Q4：源注册表污染的 root cause 是 ingest 逻辑缺陷还是批量脚本的 input parsing bug？

**结论：两者都有，但 root cause 是 ingest 的前置过滤缺失。**

逐层分析：

```
原图 → [OCR] → 原始文本 → [批量脚本] → source 候选 → [kdo ingest] → 注册表
              ↑                    ↑                 ↑
              |                    |                 |
         问题层1：OCR误识      问题层2：无过滤      问题层3：无校验
         `---`被识别为文本    4字符直接提交      语义合理性未检查
         录音碎片被截断        无最小长度门槛     YAML分隔符未拒收
```

**责任归属**：

| 问题 | 责任方 | 修复位置 |
|---|---|---|
| OCR 把图的分隔线识别为 `---` | PaddleOCR 模型局限 | 批量脚本后置过滤 |
| 录音转录碎片（`值班主`/`谢谢。`）被当成标题 | 批量脚本 | 批量脚本：标题最小长度 ≥8 字符 |
| 4 字符标题通过 ingest | kdo ingest | `kdo ingest` 增加 `--min-title-length` 参数 |
| `---` 进入注册表 | kdo ingest | `kdo ingest` 增加 YAML 标记符拒收规则 |
| status=`enriched` 但 body 全 TODO | kdo enrich | 修复 enrich 状态机逻辑 |

**关键发现**：OCR 文本中的 `---` 不是 YAML frontmatter 分隔符被误识——而是**图中真实存在的水平分隔线/虚线被 PaddleOCR 识别成了三个连字符**。这属于 OCR 模型的正常误识范围，应该在 ingest 前做清洗。

## 三、多模态仲裁者专属发现：归属错位

### 🔴 发现 1：OCR 卡片批量创建 = 视觉知识未经视觉理解就入库

136 张 OCR 卡片中，**约 80% 是知识地图、框架图、模型图**——这些本质上是"视觉化知识"。

老顽童作为 Producer，用纯文本 OCR 流水线处理视觉资产，跳过了一个关键步骤：**视觉结构理解**。

正确流程应该是：
```
视觉原图 → [洪七公：视觉解析+结构还原] → 结构化中间件 → [老顽童：三步编译法] → 概念卡
```

当前流程：
```
视觉原图 → [PaddleOCR：纯文本提取] → [老顽童：ingest+enrich] → 概念卡（扁平化）
                    ↑
              洪七公被跳过 = 视觉信息丢失
```

**这是归属错位**：视觉资产的知识提炼，应该由多模态仲裁者主导或至少参与，Producer 负责后续的文本化编译。

### 🔴 发现 2：部分 OCR 卡片主题属于洪七公职责域

抽样发现以下卡片主题明显属于多模态/视觉领域，应由洪七公处理：

| 卡片 | 主题 | 归属 |
|---|---|---|
| `ocr-视觉prompt三层操作系统-srom-visual-os` | 视觉 Prompt 工程 | **洪七公** |
| `ocr-一堂-个人修炼-表达力火箭模型` | 表达力可视化模型 | **洪七公**（信息图产出） |
| `ocr-一堂-个人修炼-讲香十指模型-超级武器库` | 十指模型可视化 | **洪七公** |
| `ocr-一堂-个人修炼-全景图MUSE模型` | 系统全景图 | **洪七公+老顽童联合** |

**建议**：这批 OCR 卡片不应长期以 `ocr-` 前缀存在于 `30_wiki/concepts/`。正确处置：
1. **高价值视觉框架** → 转交洪七公，用 deep-image-parser 重做视觉分析，产出 VA 报告 + Excalidraw 重绘
2. **纯文本类** → 老顽童继续三步编译法处理，完成后去掉 `ocr-` 前缀
3. **低价值/重复** → 归档或删除

## 五、综合判词

> 老顽童造了一条能跑的 OCR 流水线，速度够快，655 张图一夜入库。但这是一条"盲流水线"——PaddleOCR 把视觉知识拍扁成文本流，enrich 把文本流包装成概念卡，质量门全程失明。
>
> 136 张卡，100% 含 TODO，~96% 谎报 enriched，38.5% 的注册表条目是垃圾。
>
> 这不是"产量大但有瑕疵"，这是"产量大但方向错了"——视觉知识应该用视觉理解工具处理，而不是纯文本 OCR。
>
> **修复优先级**：
> 1. 立即停掉盲 OCR 批量入库（P0）
> 2. 加视觉复杂度预检，高价值图路由到 VLM/deep-image-parser（P0）
> 3. 清理 211 条垃圾注册表条目（P0）
> 4. 136 张 ocr-* 卡重新分类：洪七公接管视觉类，老顽童处理纯文本类（P1）
> 5. kdo enrich 修复状态机，只填骨架不改 status（P1）
