## 三、出现的问题

### 1. 收尾马虎：status / reviewed_by 漏改

**症状**：
- 第十九节：`case-ai-agent-milestone-design` status 仍为 draft。
- 第二十节：`yt-lean-daily-chemical-mvp`、`yt-lean-flower-mom-group-leader` status 仍为 draft。
- 多卡 `reviewed_by` 设为「王语嫣/欧阳锋」以满足门禁，但实际未人工审查。

**影响**：被欧阳锋/王语嫣抽检发现并修正，虽未影响门禁，但暴露了单卡收尾检查不严谨。

**根因**：
- AgentSwarm 并行时，部分子 agent 改完正文后忘记更新 frontmatter。
- 为赶速度，批量把 `reviewed_by` 填为验收人占位，而非真实审查后填写。

**修复**：
- 在 `.agent/laowantong-context.md` 中增加「单卡收尾检查清单」，强制检查 status / reviewed_by / updated_at。
- 第二十一节执行时已基本杜绝漏改 status 的情况。

### 2. 第二十节批次 5 目标卡 ID 不匹配

**症状**：
- 任务清单写的是 `manage-team-startup-stage-1-3`、`manage-one-on-one`、`manage-team-meeting`、`manage-team-culture-building`、`manage-feedback-coaching`，但库中不存在这些 ID。
- 实际按清单精修了 `yt-management-business-formula` 等 5 张管理概念卡，但过程中误把 `yt-management-scientific-meetings` 当作 `manage-team-meeting` 精修。

**影响**：
- 多修改了一张不在 30 张清单内的卡。

**根因**：
- 执行前没有先核对任务文件 ID 与库中实际卡片是否一致。
- AgentSwarm 子 agent 在遇到 ID 不存在时，擅自推断最接近的卡片。

**修复**：
- 第二十一节执行前用脚本逐卡验证了 30 个 ID 全部存在。
- 在 context 中增加铁律：「执行前逐卡核对目标卡 ID；ID 不匹配时先暂停确认，不擅自推断」。

### 3. 部分 case 卡 related 为空

**症状**：

**影响**：拉低了第二十一节评级从 A 到 A-。

**修复**：
- 已补充 5 条相关互链到两张卡，并更新 `updated_at`。
- 在单卡收尾检查清单中加入「related ≥ 2 条」。

### 4. 同素材双卡边界不清

**症状**：
- `case-personal-map-modeling` 与 `case-truman-personal-growth-map-creation` 基于同一段 Truman 口述素材，主题有重叠。

**影响**：
- 低严重度，但长期可能造成读者混淆。

**根因**：
- 早期 case 卡创建时没有严格区分叙事角度。

**修复**：
- 保留双卡，已互链。
- 建议长期明确边界：一张聚焦「建模过程方法论」，一张聚焦「创作心路历程」。

### 5. AgentSwarm 的并发副作用

**症状**：
- 多卡同时修改 related 字段时，偶发临时 P1（author == reviewed_by）。
- 部分子 agent 因 auth/quota 失败，需要 resume。
- 子 agent 有时会顺手修改非目标卡以修复门禁，导致改动范围扩大。

**影响**：
- 增加了复核成本。
- 部分反向链接卡片的 `reviewed_by` 被统一改为验收人占位。

**根因**：
- AgentSwarm 并行子任务之间缺乏锁机制。
- 子 agent 被授权运行全库门禁，为保 P1=0 会主动修其他卡。

**修复**：
- 后续批次可缩小单批规模（如 5-8 张），降低并发冲突概率。
- 提示词中更明确：「只精修目标卡，不要修改其他卡；如其他卡引发 P1，报告而非修复」。

### 6. `kdo_lint.py` 误报

**症状**：
- `kdo_lint.py` 对 `[[...]]` 互链接和中文 card ID 存在 regex 误报，无法作为可靠门禁。

**影响**：

**根因**：

## 五、学到的经验

### 1. 速度 ≠ 质量，但质量门禁能兜底

90 张卡高速完成的前提是每卡都跑门禁。没有门禁兜底的并行只会放大错误。

### 2. 「域间自检三问」是防止凑数的有效机制

三问迫使执行者在每个域结束后回答：案例够了吗？暗知识在哪里？共同模式是什么？这让精修从「改格式」变成「重构知识网络」。

### 3. 框架卡必须反向链接到案例

以前每个域都是框架丰满、案例空缺。本轮最大的价值是把框架卡和 case/dk 卡织成网，让抽象框架有了落地锚点。

### 4. 共同模式需要第二轮显性化

第二十节提炼的跨域模式，在第二十一节写回框架卡后，才真正从「复盘洞察」变成「可执行框架」。这说明：知识提炼往往需要两轮——第一轮发现模式，第二轮写回体系。

### 5. 系统暗知识是infra债务的显影

5 张 KDO 系统 dk 卡揭示了一个反常识：最大的系统风险不是报错，而是「exit code 0 的静默失败」。这类知识只有亲历者知道，必须通过 dk 卡独立沉淀。

### 6. AgentSwarm 需要更强的边界约束

子 agent 为保门禁会顺手改其他卡、推断缺失 ID、填占位 reviewer。下一轮需要在提示词中更严格地限制：只改目标卡，ID 不存在时报错，reviewer 不要伪造。
