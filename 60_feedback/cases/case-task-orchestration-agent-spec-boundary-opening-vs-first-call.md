# 任务编排案例：agent-spec 边界不清导致执行范围漂移

## 一、案例背景

本案例来自 #47 / #49 设计之前的一次真实实测。用户（创始人）向 `tool-opc-sales-dialogue-assistant` 提供了一段客户通话录音转写，助手完成了四段式分析（意图判断 → 下一步建议 → 回复选项 → 风险提示）。随后用户追问：

> 「客户有时打电话过来咨询，前面三分钟的话术你觉得我应该怎么说？基于你前面对于我们的了解。」

助手输出了一份 **0:00–3:00 的完整电话攻略**，包括：
- 0:00–0:30 可信开场
- 0:30–2:00 场景诊断 + 两个问题
- 2:00–3:00 给框架 + 推下一步
- 分支处理表
- 整套话术速查卡
- 方法论溯源

用户认为这份输出是高质量的销售话术，可直接使用；而 reviewer（欧阳锋）在终审 #49 时指出：该输出 **超出了 `tool-agent-spec-yitang-opening-3min` 的规格边界**——该 agent 应只输出「首条消息草稿 + 价值钩子 + 第一个开放式问题 + 过渡句」等 7 个固定模块。

双方在「这是否算超范围」上产生了分歧。

---

## 二、客观复盘：双方为什么都觉得自己对？

### 2.1 用户视角：「我要的就是销售话术」

从用户角度看，需求非常自然：
- 他问的是「前面三分钟怎么说」。
- 助手给的就是「前面三分钟怎么说」。
- 内容基于前文分析，紧贴业务场景，可直接用。

所以用户认为：「这没有做错，它就是销售话术建议。」

### 2.2 系统设计视角：「这不是 `tool-agent-spec-yitang-opening-3min` 的职责」

从 agent-spec 设计角度看：
- `tool-agent-spec-yitang-opening-3min` 被定义为 **开场草稿生成器**，只解决「第一句话/首条消息说什么」。
- 它的输出被强制限定为 7 个模块，首条消息控制在 50–80 字。
- 设计意图是：把「拿到提问权」这个动作单独工具化，便于审计、复用、迭代。
- 而用户得到的输出是一份 **首通电话完整剧本**，包含诊断、分支、收尾——这更像一个独立的「首通电话攻略」agent。

所以 reviewer 认为：「内容有用，但执行边界宽了。」

### 2.3 分歧根因：用户的自然语言请求 vs agent 的窄职责定义

| 层面 | 用户的表达 | agent 规格的定义 |
|:---|:---|:---|
| 语义范围 | 「前面三分钟的话术」= 首通电话的前三分钟 | 「opening-3min」= 首次接触的开场草稿 |
| 输出形式 | 一段可执行的通话攻略 | 一份可审核的首条消息草稿 |
| 成功标准 | 内容有用、可直接参考 | 输出严格符合 7 模块模板 |
| 隐含需求 | 用户想要「被辅导怎么打这通电话」 | 规格想解决「第一句话怎么发」 |

**核心问题**：agent 规格把「opening」窄化了，但用户的自然语言提问把「first 3 minutes」宽化了。两者都没有错，只是没对齐。

---

## 三、客观评估：这份输出到底好不好？

### 3.1 作为销售内容：好

- 第一条消息简洁，没有产品倾销。
- 价值钩子基于用户业务场景（医保局接口、医院/药店）。
- 诊断问题和分支处理对 B2B 复杂销售有实际价值。
- 速查卡可直接给销售新人使用。
- 方法论溯源完整。

### 3.2 作为 `tool-agent-spec-yitang-opening-3min` 的标准输出：超范围

- 输出了完整的 3 分钟流程，而不是单一开场草稿。
- 第一个问题「您这边是想放在医院里用，还是药店用？」是二选一问题，不完全符合 spec 对「开放式问题」的要求。
- 没有明确给出 spec 要求的「风险提示与人工复核点」独立模块。
- 没有使用 spec 要求的高/中/低置信度表达。

### 3.3 作为催生 spec 的田野输入：非常有价值

这次实测直接暴露了 #49 设计时必须回答的问题：
- 用户真正想要的是「首条消息」还是「首通电话攻略」？
- 如果两个都要，是做一个 agent 的两个模式，还是两个独立 agent？
- 如何用输入参数让用户的选择显式化？
- reviewer 应该按哪个边界来验收？

## 四、对任务编排的启示

### 4.1 启示一：agent-spec 的「一句话」和「输出格式」必须覆盖用户最常见的宽理解

`tool-agent-spec-yitang-opening-3min` 的「一句话」写的是：

> 把客户来源和已知背景转化为 30 秒自我介绍、价值钩子、开放式问题与过渡句。

这个描述指向的是「首条消息」，但用户问的是「前面三分钟」。

**建议**：在 agent-spec 的 When to Use 或 System Prompt 中明确区分两种模式：
- **模式 A（MVP 开场草稿）**：只输出首条消息/首句话。
- **模式 B（首通电话攻略）**：输出 0–3 分钟完整通话流程，含诊断与分支。

否则用户和 agent 都会默认按自己最自然的理解执行。

### 4.2 启示二：任务单的验收标准要写明「按哪个模式验收」

如果任务单只写「生成开场 3 分钟话术」，执行者可能输出模式 A 或模式 B，reviewer 也可能按不同标准评判。

**建议**：任务单中增加显式参数，例如：

```yaml
output_mode: opening_draft  # 或 first_call_playbook
strict_format: true         # 是否强制使用 7 模块模板
```

验收时按 `output_mode` 对应的检查表核对，而不是凭 reviewer 主观判断。

### 4.3 启示三：reviewer 不能只看「内容有没有用」

这次冲突的本质是 reviewer 从 spec 合规性出发，用户从内容有用性出发。两个视角都重要，但不能混用。

**建议**：未来终审时使用双轨评分：

| 轨道 | 关注点 | 本次结论 |
|:---|:---|:---|
| 内容质量 | 输出是否对用户有价值 | 高 |
| spec 合规 | 输出是否符合 agent-spec 边界 | 不合规 |

任务编排时，如果内容好但 spec 不合规，应该：**修改 spec 或新增模式**，而不是简单打回。

### 4.4 启示四：实测对话本身就是高质量的任务输入素材

这次实测不是失败，而是**一次成功的田野发现**。它告诉我们：
- 用户真正需要的是「可执行的通话攻略」，而不仅仅是「第一句话」。
- 现有 agent-spec 可能过于狭窄，需要扩展或拆分。
- 未来的 agent-spec 卡应该包含「用户可能怎么问」和「 agent 应该按哪个边界回答」的示例。

**建议**：把这类实测对话脱敏后归档为 `case-xxx`，作为后续 agent-spec 迭代的输入源。

## 五、给王语嫣的思考题

1. **边界设计**：我们的 agent-spec 应该「窄而深」还是「宽而全」？窄规格易审计但可能不满足用户真实需求；宽规格灵活但难以验收。
2. **模式化 vs 独立 agent**：「首条消息草稿」和「首通电话攻略」应该是同一个 agent 的两个模式，还是两个独立 agent？
3. **验收口径**：当用户自然语言请求与 agent 规格定义不一致时，终审应该以哪个为准？
4. **任务单模板**：我们是否需要在每个 agent-spec 生产任务中强制填写 `output_mode` 和 `strict_format`？
5. **案例库建设**：是否应该把这类「用户实测 → 发现边界冲突 → 反哺 spec」的过程系统化为 case 卡片，而不是散落在聊天记录中？
