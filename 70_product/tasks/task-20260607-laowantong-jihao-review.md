## 三、本次暴露的一个系统性问题：为什么 Skills 市场没被提炼出来？

纪浩口述中花了大量篇幅（约 2000 字）讲 Skills 市场的完整案例——Before-After 状态变化、四个痛点（存储分散/版本混乱/反馈无上下文/安装靠人）、因果链拆解、Agent 自操作下载安装。这是口述中**最有价值的系统设计洞察**。

但老顽童的 25 张卡里，没有一张是关于 Skills 市场的。

**根因**：老顽童的技能提取模板（`type: skill`）是为"操作方法/技巧"设计的——操作步骤、适用场景、常见失败模式。Skills 市场是一个**系统设计洞察**，不是"怎么做"——它没有标准操作步骤，无法套入"1. 2. 3. 4. 5."的模板。

**这是 P-7 的同构问题**：信息载体不匹配提取工具的格式，就被跳过了。上一次是 Truman 的两张图（视觉轨）被跳过，这次是 Skills 市场（系统设计轨）被跳过。KDO 的提取管线缺少**"非操作性洞察"的收纳格式**——不是所有有价值的东西都是"操作步骤"。

## 四、独立洞察：Skills 市场的真正设计——面向 Agent，不面向人

纪浩的 Skills 市场有一个关键设计细节容易被忽视：

> "Skill 下载安装最好让 Agent 自己操作，不要人去弄，我也搞不对。"

这意味着这个市场**不是给人浏览的**。它的设计逻辑是：

```
人设计的"应用商店"                   纪浩的 Skills 市场
─────────────────────              ─────────────────────
人浏览 → 人搜索 → 人下载 → 人安装    Agent识别任务 → Agent搜索Skill → Agent下载 → Agent安装
前台体验优先                          后台接口优先
分类是为了人好找                      分类是为了Agent按任务类型精准匹配
                                          ↑
                                    "相当于做了一个分类层"
```

关键差异：**分类的目的不同**。给人的分类是"导航"（让浏览体验好），给 Agent 的分类是"路由"（让 Agent 在需要时精确命中，不需要海量盲搜）。

对 KDO 的直接启示：

| 当前 KDO Skill 系统 | 纪浩模式的改进方向 |
|:---|:---|
| `40_outputs/capabilities/skills/` 按名称组织 | 加一个 task→skill 映射层（"这个任务该用哪个 Skill？"） |
| 人手动 `kdo encapsulate` 编译 | Agent 检测到新 manifest → 自动拉取卡片 → 自动编译 → 自动注册 |
| Skill 是静态文件 | Skill 是 Agent 可消费的 API——有 query 接口、有版本号、有兼容性声明 |
| 没有"谁在用"的反馈 | Agent 执行后自动上报使用情况和效果，形成 Skill 的反馈闭环 |

## 五、建议：启动案例库建设

纪浩的 Skills 市场案例本身就是 KDO 案例库的第一条候选：

- **案例名**：一堂内部 Skills 分发平台
- **领域**：Agent 基础设施 / Skill 管理
- **四要素**：Before-After 清晰（微信 zip → 集中平台）、真实锚点（一堂内部）、受益人明确（维护者+用户）、可解性成立
- **可迁移场景**：任何需要"把能力封装为 Agent 可消费的 Skill"的场景——包括 KDO 自己的 `kdo encapsulate` 管线

建议同步建立案例库的**最小结构**（每个案例一页）：

```yaml
案例名 / 来源 / 领域
四要素: Before-After / 真实锚点 / 受益人 / 可解性
可迁移场景: 1-3 个
反例: 什么时候不应该学这个案例
```

案例库不同于概念卡——它是"完整故事的压缩"，带完整的上下文和可迁移判断。
