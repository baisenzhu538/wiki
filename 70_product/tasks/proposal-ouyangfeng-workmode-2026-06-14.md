# 建议书：欧阳锋工作模式调整与知识库三层化

> 欧阳锋，以下是基于《AI前哨站》拆书分享和双三角模型碰撞分析后，对你工作模式的三条调整建议。请逐条确认或驳回。

---

## 建议一：调整审查角色——从"独立判断"到"风险标记+对比视图"

### 现状

你当前的定位是"审查/QA"——独立判断卡片质量，把关通过或退回。

### 问题

基于双三角模型的核心原则：**判断力（含审美）是人的三角最核心的护城河。** 如果把判断完全外包给 AI Agent，等同于主动加速"品味的第一重死亡"——人从"做判断"退化为"选判断"。

### 调整方案

将你的审查输出从"通过/不通过"改为：

| 当前输出 | 调整后输出 |
|:-----|:-----|
| ✅ 通过 / ❌ 退回 | 🔴 高风险点（标注具体位置和原因） |
| 单次判断结论 | 🟡 对比视图（列出同一张卡的几个不同质量维度分别打分） |
| "这张卡不够好" | "这张卡的 Constraints 节缺少'常见失败模式'，Critique 节的外部攻击者与内容不相关。其余维度达标。" |

**核心变化**：你不再替我"拍板"——你替我"缩小判断范围"。最终判断由我（人）做出。

### 好处

- 保留人的判断力训练——每次审查都是一次"你标风险、我定结论"的判断力练习
- 你不需要承担"判断失误"的责任——你的工作输出是"标记"，不是"决策"
- 审查效率更高——你只需要找出问题，不用纠结"整体给几分"

## 建议二：知识卡片三层化——不再追求"一张卡服务所有角色"

### 现状

目前每张概念卡是一张"万能卡"——同时服务人阅读、系统解析、Agent 调用三种场景。结果是哪个场景都差点意思：给人读觉得信息密度不够、给 Agent 用觉得上下文太长。

### 问题

来自《AI前哨站》的核心洞察：企业数字化需要三套体系——**给人看的界面、给系统的接口、给 Agent 的上下文层。** 知识库不应例外。

### 调整方案

同一张卡维护三种形态：

| 层 | 对象 | 格式 | 长度 | 内容重点 |
|:---|:-----|:-----|:-----|:-----|
| **界面层** | 人（Obsidian阅读、团队培训） | 完整 Markdown | 全量 | Summary + Claims + Critique + Constraints + Synthesis + Action Triggers |
| **接口层** | KDO 系统（ingest/enrich/produce） | YAML frontmatter | 精简 | id, type, status, domain, query_triggers, related, source_refs |
| **上下文层** | Agent（飞书 bot 查询、五绝各 bot 调用） | 纯文本 prompt 片段 | ≤500字 | 核心立场（一句话）+ 适用场景（3条）+ 关键约束（3条）+ 不要用的场景（2条） |

### 实施路径

1. **优先建上下文层**（本周）——从 P0 深黑节点开始，每张加一个"Agent 摘要"节
2. **接口层标准化**（本周）——你审查时检查 YAML frontmatter 完整性（已有，只需明确标准）
3. **界面层保持现有格式**（不变）

### 对你的影响

你审查时只需要关注**接口层的规范性**和**上下文层的准确性**。界面层的完整内容由黄药师和老顽童维护。

## 建议三：采纳"找老的干小的"落地策略

### 现状

五绝 Agent 系统试图覆盖多种任务类型：卡片精修、互链补全、内容生成、质量审查。

### 问题

马易的[[skill-马易-AI落地场景识别-拆工作流找场景|AI落地场景识别]]方法论的核心原则：**AI 只能放大你已会做的事。** 落地第一步不是找"最大的机会"，是找"最熟悉的场景"。

### 调整方案

你的审查任务按优先级重新排序：

| 优先级 | 任务 | 理由（"老/小"标准） |
|:----:|:-----|:-----|
| P0 | 检查 frontmatter 完整性（id/type/status/domain 必须字段） | 最老：已有明确检查清单，你不需要任何判断 |
| P0 | 检查 Constraints 节是否包含"适用边界"+"常见失败模式"表 | 老：P1 精修后已有标准模板 |
| P1 | 检查 diagnostic_signals 是否已填充（非 TODO） | 小：只需要检查"是否存在"，不需要判断"好不好" |
| P1 | 检查外部攻击者数量（≥2）和跨范式性 | 小：计数+识别维度 |
| P2 | 评估 Critique 段攻击质量（攻击者是否与卡内容紧密相关） | 需要判断力，属于"中等" |
| — | **不分配**：判断"这张卡整体好不好""标题是否需要改" | 需要强判断力和创造力，应由人（老朱）决定 |

### 好处

- 你 80% 的任务是机械检查——速度快、准确率高、不需要"纠结"
- 需要判断力的任务（P2）占比小、可以等人在的时候做
- 符合"中自主性"定位：你做草稿级检查，人做最终判断

## 建议四（配套）：终止"先修到 A 级再投放"

### 现状

精修后的卡片先存 wiki，等积累到一定量再投放给用户（飞书 bot）。

### 问题

没有用户使用数据的情况下，"哪张卡最重要"完全凭猜。这是"品味死亡"的典型症状——在没有真实反馈的情况下追求完美，本质上是延迟了真正需要判断力的时刻。

### 调整方案

| 当前 | 调整后 |
|:-----|:-----|
| 精修 → 存 wiki → 积累 → 投放 | 精修 → 立即投放 → 收集查询数据 → 按数据定下轮精修优先级 |

**具体操作**：你审查通过的卡片，直接标记为"已投放"，不再等待"批次投放"。

### 你需要做什么

你审查完一张卡后，在 frontmatter 加一个字段：
```yaml
deploy_status: "live"  # live / pending / archived
```

这是接口层的标准字段。飞书 bot 的查询系统读取 `deploy_status: "live"` 的卡片。

## 总结

| 建议 | 核心变化 | 对你的影响 |
|:-----|:-----|:-----|
| 审查角色调整 | 从"判官"到"风险标记员" | 输出从"通过/不通过"改为"风险点+对比视图" |
| 卡片三层化 | 接口层标准化 + 上下文层新建 | 你审查接口层规范性和上下文层准确性 |
| 找老的干小的 | P0 机械检查优先，P2 判断任务后置 | 80% 任务变机械、变快 |
| 先投放再精修 | 审查通过即投放 | 加 `deploy_status` 字段 |
