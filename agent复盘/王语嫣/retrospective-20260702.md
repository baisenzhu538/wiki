## 一、本阶段最大的认知升级（收获）

### 1. "可执行"的深度不能靠压缩卡片数量来换

初版 6 张卡被用户挑战后，我第一反应是"用户要深度"，于是拆分为 10 张（用户分层/卖点独立、新增 case 和 dk）。这个方向对，但还不够——用户真正要的是**拿着具体问题来咨询时，能直接调出一张可执行的卡**。这要求：
- 每张 tool 卡能独立回答一个具体问题；
- 每张 case 卡带数据、可对标；
- framework 卡不仅解释概念，还要给出 OPC 改编路径。

**关键洞察**：卡片数量不是成本，"检索后不能直接调用"才是成本。

### 2. 方法层、操作层、智能体层必须分开判断

黄药师提出 12-15 张时，我最初觉得"很多已有卡可以桥接，不需要重复建"。但他的 critique 让我意识到：我算的是**方法层**，他算的是**操作层 + 智能体层**。

| 层次 | 代表内容 | 是否新建 |
|:---|:---|:---:|
| 方法层 | 用户分层四步法、卖点提炼四步法 | 桥接到已有卡 |
| 操作层 | SABC 具体算法、A/B 测试、带数据案例 | 嵌入现有卡或新建 case |
| 智能体层 | system prompt 规格卡、MVP 对话助手 | 必须新建 |

**关键洞察**：方法可以桥接，但"能直接喂给 AI 的规格"和"带数据的完整案例"必须独立成卡。

### 3. OPC 智能体落地要守"资源少、见效快、能闭环"原则

黄药师建议做 8-10 个智能体，但 OPC 一人公司资源有限。我判断只做一个 MVP：**`tool-opc-sales-dialogue-assistant`**（读对话 → 想策略 → 给话术）。它不改变销售动作，只输出"小抄"，直接解决"同时聊多个客户跟丢/跟乱/跟错节奏"的痛点。

**关键洞察**：智能体层不要一次性铺开，先做一个能跑通的闭环，再按反馈扩展。

### 4. 用户挑战是高质量判断的触发器

用户两次挑战（"深度够不够？""黄药师说 12-15 张，你怎么判断？"）都迫使我跳出原有框架重新评估。没有这两次挑战，我可能停留在 6 张或 10 张的舒适区。

**关键洞察**：王语嫣的价值不是"给用户想要的数量"，而是"在用户压力下做出独立判断并给出可验证的理由"。

## 二、本阶段犯的错 / 可以更好的地方

### 1. 初版 6 张卡过度压缩

为了快速入队，我把用户分层和卖点提炼合并、把案例作为嵌入式证据、没有智能体规格卡。结果用户质疑深度不够。

**防错机制**：
- 做卡片规划时先列"用户可能问的具体问题清单"，每个问题对应一张可调用的卡；
- 当用户要求"直接给可执行方案"时，工具卡和案例卡数量下限要提高，不能为了简洁牺牲独立调用性。

### 2. 对 OPC 智能体层的价值判断偏慢

黄药师在很早的讨论中就提到 OPC 智能体军团映射，但我把它当作"已有 `opc-ai-sales-agent-architecture.md` 的事情"，没有意识到它需要一张**可直接当 system prompt 的规格卡**作为落地入口。

**防错机制**：
- 每次涉及 OPC 的方法论卡片化，都问一句："这个方法论如果要变成 AI 助手，第一张 system prompt 规格卡是什么？"
- 把"智能体规格卡"作为 OPC 改编的默认产出之一。

### 3. 多文件更新时低估了中文/特殊字符的匹配风险

更新 `production-queue.md`、`dashboard.md`、任务单时，Edit 工具多次因中文标点、引号、编码问题匹配失败，最后不得不写 Python 脚本处理。

**防错机制**：
- 涉及中文内容的多文件批量替换，直接用 Python 脚本，不走 Edit；
- 脚本中避免在字符串里混用中英文引号， inner 引号改用中文书名号/单引号或转义；
- 修改后抽查关键行，不依赖"打印成功"就默认生效。

### 4. 收到"复盘，按照模版来"时没有先确认模板

用户没有指定用哪个模板（每日/阶段性/生产复盘），我直接用了王语嫣阶段性复盘模板。如果用户要的是老顽童生产复盘模板或欧阳锋每日模板，这个文件可能不符合预期。

**防错机制**：
- 下次遇到"按模板来"的指令，先列出可选模板并让用户确认；
- 在 AGENTS.md 或角色 context 中明确默认复盘模板。

## 三、下阶段可以尝试的新方法（行动）

### 1. 做卡片数量判断时给出三层清单

以后做"这个专题要产出几张卡"的判断时，同时列出：
- **方法层**：哪些概念可以桥接到已有卡；
- **操作层**：哪些需要销售域实例化/案例/算法；
- **智能体层**：哪张卡是第一个 system prompt 规格卡。

这样用户和黄药师可以针对同一层次 critique，而不是各说各话。

### 2. 强制每张 tool/framework 卡包含"OPC 智能体适配"小节

对 `#44` 的 5 张 Step tool/framework 卡，要求生产时写明：
- 这个方法论映射到哪个智能体；
- 输入/输出/触发条件；
- 一段可直接放进 system prompt 的规则摘要。

这样 `tool-opc-sales-dialogue-assistant` 才能有可靠的底层来源。

### 3. 建立"用户挑战 → 扩展清单"快速响应流程

当用户质疑深度/数量时，按以下顺序响应：
1. 复述当前判断（几张卡、为什么）；
2. 列出被压缩或遗漏的模块；
3. 给出 2-3 个扩展方案（保守/推荐/激进）；
4. 让用户拍板或授权独立判断。

### 4. 批量文件更新走"脚本 + diff 抽查"

以后同时改诊断/任务/队列/看板时：
- 先写一次性 Python 脚本做替换；
- 跑 `git diff --stat` 和关键行抽查；
- 确认无临时脚本残留后再向用户汇报。
