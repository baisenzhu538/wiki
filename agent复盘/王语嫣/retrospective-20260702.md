## 一、今天最大的认知升级（收获）

> 今天有没有一个瞬间让你觉得"原来是这样"？

1. **可执行的深度不能靠压缩卡片数量来换。** 用户要的不是"方法论覆盖"，而是"拿着具体问题来，能直接调出一张可执行的卡"。这要求工具卡能独立调用、case 卡带数据可对标、framework 卡给出 OPC 改编路径。

2. **方法层、操作层、智能体层必须分开判断。** 我最初算的是方法层（已有卡可桥接），黄药师算的是操作层 + 智能体层（必须新建）。方法可以桥接，但能直接喂给 AI 的 system prompt 规格卡和带数据的完整案例必须独立成卡。

3. **OPC 智能体落地要守"资源少、见效快、能闭环"原则。** 不做 8-10 个智能体，只做 1 个 MVP 对话助手（读对话 → 想策略 → 给话术），直接解决一人公司同时聊多客户时跟丢/跟乱/跟错节奏的痛点。

4. **用户挑战是高质量判断的触发器。** 两次挑战（"深度够不够？""黄药师说 12-15 张你怎么判断？"）迫使我跳出 6/10 张的舒适区，最终给出 12 张的独立判断。

## 二、今天犯的错 / 可以更好的地方

> 不是自责，是建立防错机制。同一个坑掉两次才是问题。

1. **初版 6 张卡过度压缩。** 为了快速入队，合并了用户分层和卖点提炼、把案例当嵌入式证据、没有智能体规格卡，结果被用户质疑深度不够。
   - *防错机制*：规划时先列"用户可能问的具体问题清单"，每个问题对应一张可调用的卡；当用户要求"直接给可执行方案"时，不轻易压缩工具卡和案例卡数量。

2. **对 OPC 智能体层的价值判断偏慢。** 早该意识到 `opc-ai-sales-agent-architecture.md` 只是架构图，真正落地需要一张可直接当 system prompt 的规格卡。
   - *防错机制*：每次涉及 OPC 的方法论卡片化，都问"这个方法论变成 AI 助手，第一张 system prompt 规格卡是什么？"

3. **多文件更新时低估了中文/特殊字符的匹配风险。** `production-queue.md`、`dashboard.md`、任务单更新时，Edit 工具多次因中文标点、引号匹配失败，最后不得不写 Python 脚本处理。
   - *防错机制*：涉及中文内容的多文件批量替换直接用 Python 脚本；脚本里避免中英文引号混用；修改后抽查关键行。

4. **收到"复盘，按照模版来"时没有先确认模板。** 先用了王语嫣阶段性复盘模板，现在再按欧阳锋每日复盘模板重写，浪费一次往返。
   - *防错机制*：下次遇到"按模板来"，先列出可选模板让用户确认；在角色 context 中明确默认复盘模板。

## 三、明天可以尝试的新方法（行动）

> 至少一条，明天必须试。不试就永远不知道好不好用。

1. **做卡片数量判断时给出三层清单**：方法层（可桥接）、操作层（需实例化/案例/算法）、智能体层（第一张 system prompt 规格卡）。让用户和黄药师针对同一层次 critique。

2. **强制每张 tool/framework 卡包含"OPC 智能体适配"小节**：映射到哪个智能体、输入/输出/触发条件、一段可放进 system prompt 的规则摘要。

3. **批量文件更新走"脚本 + diff 抽查"**：先写一次性 Python 脚本替换，跑 `git diff --stat` 和关键行抽查，确认无临时脚本残留后再汇报。

4. **建立"用户挑战 → 扩展清单"快速响应流程**：复述当前判断 → 列出被压缩/遗漏模块 → 给出保守/推荐/激进三个方案 → 让用户拍板或授权独立判断。
