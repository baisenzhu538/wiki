**根因**：不是文件编码损坏，而是 Windows Git Bash 终端用 GBK 编码显示 UTF-8 中文，导致文件名和部分内容在控制台显示为乱码。所有文件内容均可正常 UTF-8 解码。

## 检测方法

1. 递归扫描 `30_wiki/`，筛选 frontmatter 中 `domain` 包含 `design` 的 `.md` 文件。
2. 对每个文件检测：BOM、空字节、编码解码测试（utf-8/utf-8-sig/gb18030/big5/latin-1）、chardet 推测。
3. 与 git 历史对比：抽取 `tool-ai-skill-engineering-guide.md`，首次提交和最新提交均可 UTF-8 解码。
4. 抽样验证：3 个样本（含 ASCII 文件名和非 ASCII 文件名）均内容完好。

## 关键决策

1. **只读诊断**：严格遵守任务单禁忌，未修改任何 design domain 文件。
2. **用 Python 脚本绕过显示层**：不依赖 GBK 控制台，直接用 `pathlib` 和 UTF-8 解码读取文件。
3. **保留 JSON 附件**：完整检测数据作为报告附件，便于后续审计。

## 风险与问题

1. **GBK 终端的显示问题**：未来在 Windows Git Bash 中操作中文文件名仍可能遇到乱码，需用 Python 脚本或 UTF-8 终端。
2. **CRLF 行尾**：多数 design 文件使用 CRLF，建议统一为 LF，但这不是编码损坏。
3. **domain 字段不规范**：部分文件 domain 字段有 `design- design` 等重复问题，属于 lint 内容债，不是编码问题。
